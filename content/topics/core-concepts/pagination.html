Pagination means returning a large list in small pieces, called pages, instead of all at once.

Open Instagram and it loads 20 posts, not every post ever made. Scroll near the bottom and it asks for the next 20. Every request says, in some way, “give me the next part of the list, starting from here”.

The pagination types are just different ways of describing that “here”:

  • Offset / page number: “skip the first 40”. A position by counting.
  • Keyset / seek: “give me items after id 9812”. A position by value.
  • Cursor: “continue from this token”. The server hides the position inside it.
  • Time-based: “items created before 10:42”. A position by time.

One-line version: there are only two real methods, counting rows and seeking to a value. Every other name is one of those two in a different wrapper.

Without pagination, GET /orders returns every row. With 5 million orders the database reads millions of rows, your Node server builds one giant JSON in memory, the network carries hundreds of megabytes, and the phone freezes rendering it. The user wanted the top 20.

The method matters as much as having one: a naive one is fine on page 1 and painful on page 50,000, and it shows the same item twice when new data arrives mid-scroll. So the real question is how deep people go, and what happens to a page when the data under it changes.

A long queue at a bank, and you want to talk to people in groups of 10.

  • Offset style: “skip the first 40, send me the next 10”. The guard walks down the queue counting 40 people. For group 1,000 he counts 9,990 first.
  • Worse: 3 people join the front while you talk, so “skip 40” now lands 3 earlier and you meet 3 people twice. If 3 leave instead, you miss 3 you never met.
  • Keyset style: everyone holds a numbered token. “Send me the 10 after token #540.” No counting — tokens are in order, so the guard goes straight there. Group 1,000 costs the same as group 1, and people joining the front change nothing.
  • The catch: you can’t say “jump to group 700”. Nobody knows which token group 700 starts at without counting.

A posts table in PostgreSQL, newest first.

-- offset: GET /posts?limit=20&offset=40
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;

Simple, and it can jump anywhere. But the database still finds and throws away the first 40 rows. At OFFSET 1000000 it walks past a million.

-- keyset: start after the last row we returned
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ($1, $2)    -- last row's values
ORDER BY created_at DESC, id DESC
LIMIT 21;                            -- one extra tells us if more exist

CREATE INDEX posts_created_id_idx ON posts (created_at DESC, id DESC);

Why id too? Two posts can share a timestamp. Without a unique tiebreaker, rows with equal times get skipped or repeated at page edges.

Clients shouldn’t have to know about created_at and id, so pack them into an opaque token, the cursor:

// posts.service.ts
limit = Math.min(Math.max(limit, 1), 100);   // never trust client limits
const hasMore = rows.length > limit;
const items = rows.slice(0, limit);
const encode = (c) => Buffer.from(JSON.stringify(c)).toString('base64url');
return { items, nextCursor: hasMore ? encode(lastOf(items)) : null };

Base64 is not encryption. Anyone can read that cursor. Fine for sort values, but validate it, and sign it if it ever holds something like a tenant id.

Offset: the database walks the index from the start, reads rows 1–40, throws them away, then reads 41–60. There is no shortcut to “the 40th row” — row positions aren’t stored, so it counts.

Keyset: the server decodes the cursor into the last seen (created_at, id), and the index — a B-tree, which keeps values sorted — jumps straight there, like opening a dictionary at the right letter. One jump plus 20 rows, at any depth.

Offset’s other problem is drift:

  1. User loads page 1: posts 1–20, newest first.
  2. 3 new posts are published, and go to the top.
  3. Page 2 asks for OFFSET 20. Everything shifted down by 3, so it starts with the last 3 posts the user already saw. Duplicates. Had 3 posts been deleted, 3 would never be shown. Skips.

“Posts older than this exact post” doesn’t drift, which is why keyset is stable.

Six names, two methods underneath:

  • Offset: ?offset=40&limit=20. Jumps anywhere, works with any sort. Slow deep, and drifts.
  • Page number: offset with maths, offset = (page − 1) × pageSize. Shareable links, but “page 3 of 2,481” needs a COUNT(*), which PostgreSQL answers by scanning.
  • Keyset, also called seek: compare against the last row’s sort values. Flat cost, stable on inserts. No jumping to page N, and it needs an index matching the sort.
  • Cursor: keyset inside an opaque token, so you can change internals without breaking clients. Stripe uses starting_after, Slack next_cursor.
  • Time-based: the value is a timestamp, ?before=2026-11-04T10:42:00Z. Natural for logs, but needs a tiebreaker.
  • Hybrid: numbered pages for the first ten, keyset after. Elasticsearch caps from + size at 10,000 and points you to search_after.

Row counts are exact; time per row depends on your hardware and cache, so measure with EXPLAIN (ANALYZE, BUFFERS). The shape is the point.

“But nobody visits page 10,000.” Humans don’t. Your export job does. Walking 10 million rows in batches of 1,000 with offset means 10,000 queries, the last ones scanning almost everything: about 50 billion rows touched in total (1,000 + 2,000 + … + 10,000,000). The same walk with keyset touches about 10 million.

Page size trades requests for response size: at about 1 KB per post, 20 per page is 20 KB and 1,000 is 1 MB. Most APIs default to 20–50 and cap at 100.

  • Flexibility vs speed. Offset jumps anywhere and works with any sort. Keyset is fast and stable, but only moves forward or backward from where you are.
  • Total counts vs cost. “Page 3 of 2,481” is friendly, but counting a large filtered result can cost more than the page itself.
  • Opaque vs transparent. Cursors let you change internals and stop clients inventing positions, at the price of debuggability and “page 7” links.
  • Stability vs snapshots. No method freezes the list across requests. Offset duplicates and skips; keyset can miss a row whose sort value changes. A real snapshot needs a database snapshot or a temporary table.
  • Speed vs write cost. Keyset is only fast with an index matching the sort, and every extra sort option is another index to maintain.
  • Small list, admin or internal screen: offset or page numbers. Good enough.
  • Numbered pages on a big table: offset for the first pages, then cap depth or switch to keyset.
  • Infinite scroll, mobile, public API: cursor with keyset inside.
  • Exports, backfills, anything walking a whole table: keyset on the primary key, WHERE id > $last ORDER BY id LIMIT 1000. Never offset.
  • Logs and “what changed since my last sync”: time-based with a tiebreaker and a small overlap window, or a sequence number.

When you don’t need any of this: a list that can’t grow past a few hundred rows — saved addresses, countries — just gets returned. Cursor pagination for 12 rows is code with no payoff.

Tip: even on offset, expose a nextCursor field rather than offset, so you can switch the inside later without breaking clients.

  • No stable sort. ORDER BY created_at alone isn’t unique, so equal rows come back in different orders between requests. Always add a unique tiebreaker.
  • Writing the keyset condition by hand, wrong. created_at < $1 AND id < $2 is not (created_at, id) < ($1, $2), and it silently skips rows. Use the row comparison, or the long form: created_at < $1 OR (created_at = $1 AND id < $2).
  • Mixed sort directions with a row comparison. (a, b) < (x, y) only holds when both columns sort the same way. ORDER BY a DESC, b ASC needs the long form.
  • Keyset without a matching index. It still works, it just scans and sorts — the thing you were avoiding.
  • No maximum page size. ?limit=1000000 is a free way to overload your server.
  • Time-based with late commits. A transaction sets updated_at = 10:00:00 but commits at 10:00:05. A sync that already read “up to 10:00:03” misses it forever. Re-read a small overlap, or use a sequence.

Common questions

“How would you paginate a news feed?”
Cursor with keyset inside: sort by (created_at, id) descending, return a nextCursor from the last item, index to match. Offset loses twice: slower with depth, duplicates when new posts arrive.

“Offset vs cursor?”
Offset counts rows to skip, so work grows with depth and inserts shift the results. Cursor remembers where you were by value. The cost is no arbitrary page jumps.

“How do you show ‘page 5 of 300’ on a huge table?”
Offset handles shallow pages; the count is the expensive part. Cache it, estimate it, or show “Next” only.

Follow-ups to expect

  • Why add id to the sort? (Tiebreaker for equal timestamps.)
  • What index? (One matching the ORDER BY columns and directions, equality filters first.)
  • How do you go back a page? (Reverse the comparison and the sort, then reverse the rows.)
  • Across shards? (Each shard returns rows after the cursor; the server merges.)

How it fits a bigger design

Every design question with a list in it — feeds, chat history, notifications — has a pagination decision. A strong answer names the method, the sort key with its tiebreaker, the index, and the API shape: items, nextCursor, a capped limit.

  • Pagination returns a big list in pages, to protect the database, the server and the client.
  • Two methods underneath: counting rows to skip (offset), and seeking to a value (keyset).
  • Page number is offset with maths. Seek is another name for keyset.
  • Cursor is keyset hidden in a token. Time-based is keyset on a timestamp.
  • Offset gets slower with depth, and duplicates or skips when rows are added or removed.
  • Keyset stays flat with a matching index, but can’t jump to page N.
  • Always sort on something unique, cap the page size, and validate cursors.
  • Batch jobs and exports should always use keyset.
