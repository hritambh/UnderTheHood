Pagination means returning a large list in small pieces, called pages, instead of all at once.

When you open Instagram, the app doesn’t download every post ever made. It loads 20, and when you scroll near the bottom, it asks for the next 20. Each request says, in some way, “give me the next part of the list, starting from here.”

The different pagination types are really different ways of describing that “here”:

  • Offset / page number: “skip the first 40 items” or “give me page 3”. A position by counting.
  • Keyset / seek: “give me items after the one with id 9812”. A position by value.
  • Cursor: “continue from this bookmark token”. The server hides the position inside a token.
  • Time-based: “give me items created before 10:42 today”. A position by time.
  • Hybrid: mixing these, for example page numbers for the first few pages and keyset after that.

Important: these seven names are not seven different techniques. There are really two core methods underneath: counting rows (offset) and seeking to a value (keyset). Page-number is a friendly form of offset. Seek is another name for keyset. Cursor is usually keyset wrapped in a token. Time-based is keyset where the value is a time. This topic explains each name, but keep those two core methods in mind.

Without pagination, an endpoint like GET /orders returns every row. With 5 million orders, that means:

  • The database reads and sends millions of rows.
  • Your Node.js server builds one giant JSON response in memory. It can run out of memory or block the event loop while doing it.
  • The network transfers hundreds of megabytes.
  • The phone or browser tries to render all of it, and freezes.
  • The user only wanted to see the top 20.

So we need pagination. But the method matters too. A naive method works fine on page 1 and becomes very slow on page 50,000. It can also show the same item twice, or skip items, when new data is added while someone is scrolling. Those two problems (deep-page slowness and shifting data) are what separate the methods.

Imagine a long queue of people at a bank, and you want to talk to them in groups of 10.

Offset style: you say, “Skip the first 40 people, and send me the next 10.” To do that, the guard must walk down the queue counting 40 people every time. For group 1,000, he counts 9,990 people first. That gets slow.

Worse: if 3 people join at the front while you are talking to a group, “skip 40” now lands 3 people earlier. The next group includes 3 people you already met. If 3 people leave instead, you skip 3 people without ever meeting them.

Keyset style: everyone holds a numbered token. You say, “Send me the 10 people after token #540.” The guard doesn’t count anyone. He goes straight to #540 (because tokens are in order) and takes the next 10. It’s just as fast for the 1,000th group as for the first. And people joining at the front don’t matter; #540 is still #540.

The catch: with keyset, you can’t easily say “jump to group 700”, because you don’t know which token group 700 starts at without counting.

Say you have a posts table in PostgreSQL and an endpoint that returns the newest posts first.

Offset version

-- GET /posts?limit=20&offset=40
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;

Simple, and easy to jump to any page. But PostgreSQL must still find and throw away the first 40 rows before returning 20. With OFFSET 1000000, it walks past a million rows.

Keyset (cursor) version

-- first page
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 21;                       -- ask for one extra to know if there is a next page

-- next page: start after the last row we returned
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ($1, $2)   -- last row's created_at and id
ORDER BY created_at DESC, id DESC
LIMIT 21;

-- index that makes this fast
CREATE INDEX posts_created_id_idx ON posts (created_at DESC, id DESC);

Why id as well as created_at? Two posts can have the same timestamp. Without a unique tiebreaker, rows with equal times could be skipped or repeated at page edges.

Cursor API in NestJS

Clients shouldn’t need to know about created_at and id. So we pack them into an opaque token, the cursor:

// posts.service.ts  (simplified)
type Cursor = { createdAt: string; id: string };

const encode = (c: Cursor) =>
  Buffer.from(JSON.stringify(c)).toString('base64url');
const decode = (s: string): Cursor =>
  JSON.parse(Buffer.from(s, 'base64url').toString('utf8'));

async list(limit = 20, after?: string) {
  limit = Math.min(Math.max(limit, 1), 100);         // never trust client limits
  const params: unknown[] = [limit + 1];
  let where = '';
  if (after) {
    const c = decode(after);                          // validate in real code
    params.push(c.createdAt, c.id);
    where = 'WHERE (created_at, id) < ($2, $3)';
  }
  const { rows } = await this.db.query(
    'SELECT id, title, created_at FROM posts ' + where +
    ' ORDER BY created_at DESC, id DESC LIMIT $1', params);

  const hasMore = rows.length > limit;
  const items = rows.slice(0, limit);
  const last = items[items.length - 1];
  return {
    items,
    nextCursor: hasMore
      ? encode({ createdAt: last.created_at.toISOString(), id: last.id })
      : null,
  };
}

The response looks like { items: [...], nextCursor: "eyJjcmVhdGVkQXQiOi..." }. The client sends ?after=eyJj... for the next page, and stops when nextCursor is null.

Base64 is not encryption. Anyone can decode this cursor. That’s fine if it only holds sort values, but always validate it on the server, and sign or encrypt it if it contains anything you don’t want users to read or change.

Offset flow

  1. Client sends GET /posts?offset=40&limit=20.
  2. Server runs ORDER BY ... LIMIT 20 OFFSET 40.
  3. The database walks the index (or sorts the table) from the start, reads rows 1–40, throws them away, then reads rows 41–60.
  4. Server returns those 20 rows, often with a total count so the UI can show page numbers.

Step 3 is the problem: work grows with the offset. There is no shortcut to “the 40th row”, because the database doesn’t store row positions; it must count.

Keyset flow

  1. Client sends GET /posts?after=<cursor>.
  2. Server decodes the cursor into the last seen (created_at, id).
  3. The database uses the index (a B-tree, which keeps values sorted) to jump directly to that position, like opening a dictionary at the right letter.
  4. It reads the next 21 entries and stops.
  5. Server returns 20 rows and a new cursor built from the last one.

Work stays the same no matter how deep you are: one index jump plus about 20 rows.

Why offset shows duplicates or skips

  1. User loads page 1: posts 1–20 (newest first).
  2. 3 new posts are published. They go to the top of the list.
  3. User loads page 2 with OFFSET 20. Everything has shifted down by 3, so rows 21–40 now start with the last 3 posts the user already saw on page 1. Duplicates.
  4. If 3 posts had been deleted instead, everything shifts up and 3 posts are never shown. Skips.

Keyset doesn’t have this problem in the same way: “posts older than this exact post” means the same thing no matter what was added at the top. (It can still miss a row whose sort value changes while you page, for example if you sort by updated_at and a row gets updated. More on that under time-based.)

1. Offset-based pagination

What: the client sends how many items to skip and how many to return: ?offset=40&limit=20. The database uses LIMIT and OFFSET.

When to use: small or medium tables, admin screens, internal tools, any list where users rarely go deep.

Good: very simple; can jump to any position; works with any sort order and filter.

Bad: slow at large offsets; duplicates and skips when data changes between requests.

2. Page-number pagination

What: the client sends a page number and page size: ?page=3&pageSize=20. The server converts it: offset = (page - 1) × pageSize. It is offset pagination with a friendlier interface.

When to use: UIs with numbered pages (“‹ 1 2 3 … 50 ›”), search results, e-commerce category pages.

Good: people understand it; easy to share a link to page 7.

Bad: same problems as offset. Showing “page 3 of 2,481” also needs a total count, and COUNT(*) on a large PostgreSQL table can be slow, because PostgreSQL has to scan to count. Many apps show an estimate (“about 49,000 results”) or just “Next”.

3. Keyset pagination

What: use the sort values of the last row you returned to fetch the next rows: WHERE (created_at, id) < (last_created_at, last_id).

When to use: big tables, infinite scroll, “load more”, exports, batch jobs that walk through a whole table.

Good: fast at any depth with the right index; stable when new rows are inserted.

Bad: can’t jump to page N; needs a unique tiebreaker column; needs an index that matches the sort; changing the sort order or filters means building a new query shape; going backward needs a reversed query.

4. Seek pagination

What: another name for keyset pagination. The query “seeks” (jumps) to a position in the index instead of counting rows. The name comes from the “seek method”, popularized by Markus Winand’s Use The Index, Luke.

If an interviewer says “seek pagination”, everything in point 3 applies. It’s worth saying out loud that they are the same, since some articles list them as different types.

5. Cursor-based pagination

What: the server gives the client an opaque token (the cursor) with each page. The client sends it back to get the next page. The client doesn’t know or care what is inside.

Inside, the cursor is usually keyset values, sometimes with the sort order and filters too. Some systems store a server-side position instead (database cursors, or search engines like Elasticsearch’s scroll and point-in-time features). Real APIs: Stripe uses starting_after with an object ID; Slack returns next_cursor; GraphQL’s Relay “connections” standard uses cursors on each item.

When to use: public APIs, mobile apps, infinite feeds.

Good: the server can change how pagination works internally without breaking clients; clients can’t make malformed positions as easily; same speed as keyset.

Bad: no page numbers or jumping; cursors can become invalid (for example if the row they point to is deleted, depending on design); harder to debug by eye.

6. Time-based pagination

What: the position is a time: ?before=2026-11-04T10:42:00Z or ?since=...&until=.... Facebook’s Graph API, for example, offers since and until parameters.

When to use: feeds, logs, events, messages, and “give me everything that changed since my last sync”.

Good: natural for time-ordered data; easy to read; works well with time-partitioned tables.

Bad:

  • Same-time rows. Many rows can share a timestamp. Using time alone can skip or repeat them at page edges. Add a tiebreaker (id), which turns it into keyset pagination.
  • Late commits in sync jobs. A transaction can set updated_at = 10:00:00 but commit at 10:00:05. If your sync already read “everything up to 10:00:03”, that row is missed forever. Fixes: re-read a small overlap window, only read up to a little before “now”, or use an ever-increasing sequence or a change log instead of wall-clock time.
  • Clock differences between servers can put times slightly out of order.

7. Hybrid pagination

What: combining methods to get the best parts of each. Common patterns:

  • Offset for shallow, keyset for deep. Show page numbers 1–10 using offset (cheap at small offsets). Beyond that, switch to “Next” using keyset. Search engines do something similar: Elasticsearch limits normal from + size paging to 10,000 results by default and recommends search_after (keyset-style) for going deeper.
  • Keyset + cap. Allow infinite scroll but cap how deep users can go, as many search UIs do.
  • Keyset + page numbers. Walk the table once with keyset in the background and store the starting key of every 100th page, so users can jump close to the page they want.
  • Cursor with an offset inside. Use opaque cursors in the API, but encode an offset internally for small lists. Later you can switch the inside to keyset without changing clients.

Good: matches what users actually do. Bad: more code paths to test and keep consistent.

Does this matter if users never reach page 10,000?

Humans rarely do. But other things do:

  • Scrapers and bots walking every page.
  • Your own export or migration job processing all 10 million rows in batches of 1,000. With offset, that is 10,000 queries where the last ones each scan almost 10 million rows: roughly 50 billion rows touched in total (the sum 1,000 + 2,000 + … + 10,000,000). With keyset, it’s about 10 million rows in total.

Page size

Bigger pages mean fewer requests but bigger, slower responses. If each post in JSON is about 1 KB (assumption), then 20 per page ≈ 20 KB, and 1,000 per page ≈ 1 MB. Most APIs pick a default of 20–50 and enforce a maximum (often 100) so one client can’t ask for 100,000 rows at once.

  • Flexibility vs speed. Offset lets users jump anywhere and works with any sort or filter. Keyset is fast and stable but only goes forward (or backward) from where you are.
  • Total counts vs cost. “Page 3 of 2,481” is friendly, but counting a huge filtered result can cost more than fetching the page itself. Estimates or “Next”-only UIs avoid that.
  • Opaque cursors vs transparency. Cursors let you change internals freely and stop clients from inventing positions. But they are harder to debug, and clients can’t build links like “page 7”.
  • Consistency. No method gives a perfect frozen snapshot across many requests by default. Offset can duplicate or skip; keyset can miss rows whose sort values change. If you truly need a snapshot (for example an export that must match an exact moment), you need something more: a database snapshot, a point-in-time feature in a search engine, or copying results into a temporary table.
  • Indexes. Keyset is only fast with an index matching the sort order and filters. Each new sort option may need its own index, which costs disk space and slows writes.

Quick guide

  • Small list (a few thousand rows), admin or internal UI: offset or page numbers. Simple and good enough.
  • User-facing numbered pages on a large dataset: page numbers for the first pages, and limit or switch to keyset for deep pages (hybrid).
  • Infinite scroll, mobile feeds, public APIs: cursor-based, with keyset inside.
  • Exports, backfills, batch jobs over a whole table: keyset on the primary key (WHERE id > $last ORDER BY id LIMIT 1000). Never offset.
  • Logs, events, “what changed since my last sync”: time-based, with a tiebreaker and an overlap window, or a sequence number.

When you probably don’t need anything fancy

If a list can never grow beyond a few hundred items (a user’s saved addresses, the list of countries), return it all or use simple offset. Building cursor pagination for 12 rows adds code with no benefit.

A practical tip

Even if you start with offset, design the API with an opaque cursor field (nextCursor) instead of exposing offset directly. Then you can switch the inside to keyset later without breaking clients.

  • No stable sort. ORDER BY created_at alone isn’t unique. Rows with equal values can come back in different orders between requests, causing duplicates and skips even with offset. Always add a unique tiebreaker like id.
  • No ORDER BY at all. Without it, SQL doesn’t guarantee any order. Pages can overlap randomly.
  • Keyset without a matching index. The query still works but scans and sorts, losing the whole benefit.
  • Writing keyset conditions by hand wrong. WHERE created_at < $1 AND id < $2 is not the same as (created_at, id) < ($1, $2), and silently skips rows. Use the row comparison, or write it out fully: created_at < $1 OR (created_at = $1 AND id < $2).
  • Mixed sort directions with row comparison. (a, b) < (x, y) only works when both columns sort the same direction. For ORDER BY a DESC, b ASC you must write the long form.
  • Running COUNT(*) on every page request for a large table. Cache it, estimate it, or drop it.
  • No maximum page size. ?limit=1000000 becomes an easy way to overload your server.
  • Trusting the cursor. Clients can send anything. Validate it, and sign it if changing it could expose data (for example if a filter like tenantId were stored inside it).
  • Using offset for batch jobs. The job gets slower and slower as it runs, and misses or repeats rows if data changes meanwhile.
  • Pagination across shards. With data split across shards (see Database Sharding), “page 3 sorted by date” needs the top rows from every shard merged together. Offset becomes very costly here (each shard must return offset + limit rows). Keyset works better: each shard returns rows after the cursor, and the server merges them.

Common questions

“How would you paginate a news feed?”
Cursor-based with keyset inside: sort by (created_at, id) descending, return a nextCursor made from the last item, and use a matching index. Explain that offset gets slower with depth and shows duplicates when new posts arrive.

“What’s the difference between offset and cursor pagination?”
Offset counts rows to skip, so the database does more work the deeper you go, and inserts or deletes shift results. Cursor remembers where you were by value, so it jumps straight there and stays stable. The trade-off: cursor can’t jump to any page you pick.

“How do you show ‘page 5 of 300’ on a huge table?”
Offset works for shallow pages; the total count is the expensive part. Options: cache the count, use an estimate, cap depth, or switch to “Next” beyond some page.

Follow-ups to expect

  • Why add id to the sort? (Unique tiebreaker for equal timestamps.)
  • What index do you need? (One matching the ORDER BY columns and directions, plus any equality filters first, like (user_id, created_at DESC, id DESC).)
  • How do you support “previous page” with cursors? (Reverse the comparison and sort, then reverse the results; or return a prevCursor.)
  • What if an item is deleted or edited while the user is scrolling?
  • How would you paginate across shards or search results?
  • Is seek pagination different from keyset? (No, same thing.)

How it fits a bigger design

Almost every system design question with a list (feeds, chat history, order history, search results, notifications) has a pagination decision inside it. A strong answer names the method, the sort key with tiebreaker, the index, and the API shape (items, nextCursor, limit with a max).

  • Pagination returns large lists in small pages to protect the database, server, network, and client.
  • Two core methods: offset (count rows to skip) and keyset (seek to a value).
  • Page-number is offset with page math. Seek is another name for keyset.
  • Cursor is usually keyset hidden inside an opaque token.
  • Time-based is keyset on a timestamp; add a tiebreaker and watch for late commits.
  • Offset gets slower with depth and shows duplicates or skips when data changes.
  • Keyset stays fast with a matching index, but can’t jump to page N.
  • Always use a stable, unique sort, a maximum page size, and validated cursors.
  • Hybrid designs mix numbered shallow pages with keyset for depth.
