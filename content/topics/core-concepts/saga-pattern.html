Sometimes one user action must change data in more than one database. Example: placing an order must create the order, take payment, and reserve stock, and each of those lives in a different service with its own database.

We want this to behave like one unit: either everything happens, or nothing does. This is called a distributed transaction. There are two main ways to handle it:

  • Two-Phase Commit (2PC): a coordinator first asks every database “Can you commit?” Only if all say yes does it tell them “Commit now.” If anyone says no, everyone cancels. The result is truly all-or-nothing.
  • Saga: do the steps one after another, each as its own small transaction that commits immediately. If a later step fails, run compensating actions to undo the earlier steps (for example, refund a payment).

One-line version: 2PC = “everyone agrees first, then everyone commits together.” Saga = “commit step by step, and clean up if something goes wrong.”

Quick background:
  • A transaction inside one database is all-or-nothing. Its guarantees are called ACID: Atomic (all or nothing), Consistent (rules are kept), Isolated (others don’t see half-done work), Durable (once saved, it stays saved).
  • A local transaction is a normal transaction inside one database.
  • In microservices, each service usually owns its database (database-per-service). The Order service can’t simply open a transaction that also covers the Payment database.
  • The same problem appears after sharding: one transaction can’t easily cover rows on two different shards. See the Database Sharding topic.

Without any plan, you call the services one by one and hope nothing fails. Here is what goes wrong:

  1. Order service creates the order. ✔
  2. Payment service charges ₹2,000. ✔
  3. Inventory service says “out of stock”. ✘

Now the customer has paid for something you can’t ship. The databases disagree with each other. Someone has to notice and fix it by hand.

Both 2PC and sagas exist to prevent this. They make different promises:

  • 2PC promises nobody ever sees the half-done state. The cost: databases must hold locks while waiting for everyone to agree, and if the coordinator fails at the wrong moment, those locks can stay stuck.
  • A saga promises the system will end up correct (either fully done or fully undone). The cost: for a short time, the half-done state is real and visible, and you must write the undo logic yourself.

So the question is: do you need strict all-or-nothing at every moment, or is “correct in the end” good enough? For most business workflows across services, “correct in the end” is acceptable, which is why sagas are common in microservices.

2PC: a wedding ceremony

The officiant is the coordinator. The two people getting married are the participants.

  1. Phase 1 (prepare): the officiant asks each person, “Do you take…?” Each one must answer. Once someone says “I do,” they can’t change their mind or walk away. They are now waiting.
  2. Phase 2 (commit): only if both said “I do,” the officiant says, “I now pronounce you married.” If either said no, the wedding is off for both.

Now imagine the officiant faints right after both said “I do” but before the final words. The two people are stuck. They can’t leave (they promised), and they can’t declare themselves married (only the officiant can decide). They wait until the officiant wakes up. This is exactly 2PC’s famous weakness: blocking.

Saga: booking a trip

You book a flight, a hotel, and a rental car from three different companies. No one can book all three as a single unit, so you go step by step:

  1. Book the flight. ✔
  2. Book the hotel. ✔
  3. Book the car. ✘ None available.

So you cancel the hotel, then cancel the flight. Notice:

  • For a while, you really held a flight seat and a hotel room. Other people couldn’t book them. That visible in-between state is normal in a saga.
  • Cancelling isn’t the same as “it never happened.” The airline may charge a fee. Undo can be imperfect.
  • If the airline’s line is busy when you try to cancel, you must keep trying. Undo steps must be retried until they succeed.

2PC between two PostgreSQL databases

Say you move ₹500 from an account in database A to an account in database B. PostgreSQL supports 2PC with PREPARE TRANSACTION. Here your Node.js app acts as the coordinator.

// transfer-2pc.ts  (simplified, to show the idea)
import { Client } from 'pg';

export async function transfer(a: Client, b: Client, txId: string) {
  const idA = txId + '-a', idB = txId + '-b';
  try {
    // PHASE 1: do the work, then "prepare" (vote yes) on each database
    await a.query('BEGIN');
    await a.query('UPDATE accounts SET balance = balance - 500 WHERE id = $1 AND balance >= 500', [1]);
    await a.query("PREPARE TRANSACTION '" + idA + "'");

    await b.query('BEGIN');
    await b.query('UPDATE accounts SET balance = balance + 500 WHERE id = $1', [2]);
    await b.query("PREPARE TRANSACTION '" + idB + "'");

    // Both voted yes. Save the decision durably BEFORE telling anyone.
    await decisionLog.save(txId, 'COMMIT');

    // PHASE 2: commit everywhere
    await a.query("COMMIT PREPARED '" + idA + "'");
    await b.query("COMMIT PREPARED '" + idB + "'");
  } catch (err) {
    await decisionLog.save(txId, 'ABORT');
    // roll back whatever was prepared (ignore "does not exist" errors)
    await a.query("ROLLBACK PREPARED '" + idA + "'").catch(() => {});
    await b.query("ROLLBACK PREPARED '" + idB + "'").catch(() => {});
    throw err;
  }
}

Things this code shows:

  • After PREPARE TRANSACTION, the changes are saved to disk but not visible, and the rows stay locked until COMMIT PREPARED or ROLLBACK PREPARED.
  • If the app crashes between prepare and commit, those prepared transactions stay in PostgreSQL holding locks. You must have a recovery job that reads the decision log and finishes them. You can see stuck ones in the pg_prepared_xacts view.
  • Prepared transactions are disabled by default (max_prepared_transactions = 0). PostgreSQL’s docs suggest most applications shouldn’t use this directly; it is mainly for transaction managers.

In practice, few teams hand-write 2PC like this. You meet 2PC inside tools: Java XA transaction managers, distributed databases (they use it internally between their own nodes), and Kafka’s transactions, which use a 2PC-style protocol internally.

Saga for placing an order

Same order example, with NestJS services talking over RabbitMQ or Kafka. This is an orchestrated saga: one place runs the steps and knows how to undo them.

// place-order.saga.ts  (simplified, to show the idea)
type Step = {
  name: string;
  run: (ctx: OrderCtx) => Promise<void>;
  compensate: (ctx: OrderCtx) => Promise<void>;
};

const steps: Step[] = [
  { name: 'createOrder',
    run: ctx => orders.create(ctx.orderId, 'PENDING'),
    compensate: ctx => orders.setStatus(ctx.orderId, 'CANCELLED') },
  { name: 'reserveStock',
    run: ctx => inventory.reserve(ctx.orderId, ctx.items),
    compensate: ctx => inventory.release(ctx.orderId) },
  { name: 'chargePayment',
    run: ctx => payments.charge(ctx.orderId, ctx.amount),
    compensate: ctx => payments.refund(ctx.orderId) },
  { name: 'confirmOrder',
    run: ctx => orders.setStatus(ctx.orderId, 'CONFIRMED'),
    compensate: async () => {} },
];

export async function placeOrder(ctx: OrderCtx) {
  const done: Step[] = [];
  for (const step of steps) {
    try {
      await step.run(ctx);
      done.push(step);
      await sagaLog.save(ctx.orderId, step.name, 'DONE'); // remember progress
    } catch (err) {
      for (const s of done.reverse()) {
        await retryUntilSuccess(() => s.compensate(ctx));
      }
      return { status: 'FAILED', reason: String(err) };
    }
  }
  return { status: 'CONFIRMED' };
}

Why this order? Reserving stock is easy to undo. Charging money is harder to undo (refunds cost money and annoy customers). So the hard-to-undo step goes later, after the cheap checks pass.

This sketch keeps progress inside a running function. If the server crashes mid-saga, that is lost. Real systems store saga state in a database and resume after restart, or use a workflow engine such as Temporal, Camunda, or AWS Step Functions.

How 2PC works, step by step

Roles: one coordinator (decides) and several participants (the databases doing the work).

Phase 1: prepare (voting)

  1. The coordinator sends “prepare” to every participant.
  2. Each participant does the work, writes everything needed to disk, and locks the affected rows.
  3. Each participant votes: YES (“I can commit and I promise I will, even if I crash and restart”) or NO.

Phase 2: commit or abort (decision)

  1. If every vote is YES, the coordinator writes “COMMIT” to its own log on disk. This moment is the real decision point.
  2. The coordinator sends “commit” to every participant. Each one commits and releases its locks.
  3. If any vote is NO (or a participant doesn’t answer in time), the coordinator decides “ABORT” and tells everyone to roll back.

What happens when things fail

FailureWhat happens
A participant votes NOCoordinator aborts. Everyone rolls back. Safe.
A participant crashes before votingCoordinator times out and aborts. Safe.
A participant crashes after voting YESWhen it restarts, it finds the prepared transaction on disk and asks the coordinator what was decided. It must not decide alone.
Coordinator crashes after logging COMMITWhen it restarts, it reads its log and sends “commit” again. Participants wait until then.
Coordinator crashes after votes, before decidingThe bad case. Participants voted YES, so they can’t abort on their own (maybe the coordinator decided commit). They can’t commit either (maybe it decided abort). They stay blocked, holding locks, until the coordinator comes back.

That last row is why people say 2PC is a blocking protocol. It is safe (it never commits on one side and aborts on the other), but it can stop making progress.

How a saga works, step by step

  1. User sends POST /orders.
  2. Order service saves the order as PENDING, starts the saga, and replies right away: “Order received.”
  3. Orchestrator tells Inventory to reserve stock. Inventory commits its local transaction and replies “reserved”.
  4. Orchestrator tells Payment to charge. Payment commits and replies “charged”.
  5. Orchestrator marks the order CONFIRMED. The user sees the final status by refresh or a push update.

If payment fails at step 4: the orchestrator tells Inventory to release the stock, then marks the order CANCELLED with a reason.

The outbox problem (important for sagas)

Each saga step usually does two things: update its database and send a message (“stock reserved”). If the database commit succeeds but the app crashes before sending, the saga gets stuck. If the message is sent but the commit fails, others act on something that didn’t happen.

The common fix is the transactional outbox: write the message into an outbox table in the same local transaction as the business change. A separate relay process reads the outbox and publishes to RabbitMQ or Kafka.

BEGIN;
  UPDATE stock SET reserved = reserved + 2 WHERE sku = 'SKU-1';
  INSERT INTO outbox (id, topic, payload)
  VALUES (gen_random_uuid(), 'stock.reserved', '{"orderId":"o-42"}');
COMMIT;
-- a relay process later publishes outbox rows and marks them sent

The relay may publish a message twice (for example, it crashes after publishing but before marking it sent). So every consumer must be idempotent: handling the same message twice has the same effect as once. A simple way is to store processed message IDs and skip duplicates.

Two styles of saga

1. Choreography. No central controller. Each service listens for events and decides what to do next. Order publishes OrderCreated → Inventory reserves and publishes StockReserved → Payment charges and publishes PaymentCompleted → Order confirms. On failure, Payment publishes PaymentFailed, and Inventory listens for it to release stock.

  • Good: services stay loosely connected; no extra component; easy for 2–3 steps.
  • Bad: the overall flow isn’t written down anywhere; it is spread across services. Hard to answer “where is order 42 stuck?” Gets messy beyond a few steps.

2. Orchestration. One orchestrator (a service or workflow engine) sends commands to each participant, waits for replies, and tracks state. This is the style in the code example.

  • Good: the whole flow lives in one place; easier to add timeouts, retries, and to debug.
  • Bad: another component to build and run; it must store its state durably; risk of stuffing too much business logic into it.
ChoreographyOrchestration

Related ideas around 2PC

  • Three-phase commit (3PC) adds an extra round to reduce blocking. It relies on assumptions about network timing that real networks don’t always meet, so it is rarely used in practice.
  • 2PC with a highly available coordinator. Distributed databases like Google Spanner run 2PC where each participant and the coordinator is a replicated group (using a consensus algorithm like Paxos). If one machine dies, another copy continues, so the blocking problem mostly goes away. This is how modern distributed SQL databases give you real transactions across shards. You get this “for free” when you use such a database; it is hard to build yourself.

2PC: how long locks are held

Assumptions (illustrative, inside one data center): a network round trip takes about 2 ms, and each disk flush (making data safe on disk) takes about 3 ms.

  • Prepare round: send + participant flushes + vote ≈ 2 + 3 = 5 ms.
  • Coordinator logs the decision ≈ 3 ms.
  • Commit round ≈ 2 ms to send the decision.
  • So each row stays locked for roughly 10 ms or more, compared with maybe 1–3 ms in a single-database transaction.

If many transactions update the same row (a popular account balance, a stock counter for a hot product), they must wait for each other. At ~10 ms per lock, that row can handle at most about 100 transactions per second. Across regions, where a round trip can be 100+ ms, that drops to single digits.

And in the bad case: if the coordinator crashes and takes 2 minutes to come back, those rows stay locked for 2 minutes. Every request touching them waits or times out.

2PC: availability

2PC needs every participant up at the same moment. If each of 3 services is up 99.9% of the time (independently), all three are up about 0.999 × 0.999 × 0.999 ≈ 99.7% of the time. That’s about 26 hours a year when the action can’t run at all, versus about 9 hours for one service.

A saga built on queues can still accept the order while Payment is briefly down; the payment step simply waits in the queue and runs when it’s back.

Saga: how often compensations run

Assumptions (illustrative): an order saga has 4 steps, each succeeds 99.9% of the time, and you get 1,000 orders per minute.

  • Chance all 4 succeed = 0.9994 ≈ 0.996, so about 0.4% hit at least one failure.
  • At 1,000 orders/min, that’s about 4 sagas per minute needing a retry or compensation (roughly 5,700 per day).

Failure handling isn’t an edge case at scale. Compensations run constantly and must be reliable, logged, and monitored. Many failures are temporary (timeouts), so retry a step a few times before compensating, and set an overall saga timeout so orders don’t stay PENDING forever.

2PC

You gain: true all-or-nothing. No one ever sees half-done work. No undo code to write.

You give up:

  • Speed under contention: locks are held across network round trips.
  • Availability: every participant must be reachable at the same time.
  • Progress during failures: a coordinator crash can block participants with locks held.
  • Reach: only works with systems that support a “prepare” step. Most message brokers, SaaS APIs, and payment gateways don’t.
  • Independence: services become tightly tied to one shared transaction manager.

Saga

You gain: no cross-service locks, independent services, works with external APIs, keeps working when one service is briefly down.

You give up:

  • Isolation: other requests can see half-done work (stock reserved for an order that will be cancelled). Teams handle this with semantic locks: status fields like PENDING that other code respects.
  • Simplicity: every step needs a compensation, and both need retries and idempotency.
  • Perfect undo: some things can’t be undone (an email sent). You can only send a correction, so put such steps last.
  • Easy debugging: you need correlation IDs, stored saga state, and tracing across services.

Decision guide

  1. Is all the data in one database? Use a normal transaction. It is simpler and stronger than both. Stop here.
  2. Do you need cross-shard transactions inside one database system? Prefer a database that does it for you (distributed SQL like CockroachDB, YugabyteDB, Spanner, or Citus for PostgreSQL). They use 2PC internally with the hard parts solved.
  3. A few databases you control, fast network, must be strictly atomic, low volume? 2PC (for example XA or PostgreSQL prepared transactions with a proper transaction manager) can work. Plan for recovery of stuck transactions.
  4. Several microservices, external APIs, or long-running steps? Use a saga.

Signals you need a saga

  • One user action changes data owned by two or more services.
  • Partial success is unacceptable and must be cleaned up (paid but not shipped).
  • Steps call external systems that can’t join a transaction.
  • The process can take seconds, minutes, or days (approvals, bookings).

When you probably need neither

  • A failed step can simply be retried later with no harm (updating a search index, sending analytics). A reliable message with retries (outbox + idempotent consumer) is enough; no undo needed.
  • Two services always have to change together. That may mean the boundary between them is wrong, and merging them removes the problem.

With 2PC

  • No recovery plan for stuck prepared transactions. They hold locks forever and can block vacuum and other work in PostgreSQL. Monitor pg_prepared_xacts.
  • Not logging the decision durably before sending it. After a crash, the coordinator can’t know what it decided.
  • Using 2PC across slow or unreliable networks (across regions, over the internet). Lock times and blocking get much worse.
  • Assuming 2PC can include a payment gateway or a message broker. Most can’t take part.

With sagas

  • Treating compensation like a rollback. Others may have seen or used the data. Design compensations as real business actions.
  • Non-idempotent steps. Messages get delivered twice; without idempotency a customer can be charged twice. Use idempotency keys (for example, the order ID) with payment providers.
  • Sending messages outside the transaction. Leads to lost or phantom events. Use the outbox pattern.
  • Keeping saga state only in memory. A crash or deploy loses in-flight sagas.
  • Compensations that give up. They must retry until success, with alerts for a human when they can’t.
  • Bad step order. Hard-to-undo steps (charging money, sending emails) belong after easy-to-undo ones.
  • No timeouts. If a service never replies, the saga hangs forever.

With both

  • Reaching for either when one database would do. Distributed transactions are a cost you only pay when data truly lives apart.

Common questions

“How do you keep data consistent across microservices when placing an order?”
Use a saga: a chain of local transactions with compensations. Walk through the steps, which step can fail, and what gets undone. Mention the outbox pattern and idempotency for reliable messaging, and a PENDING status for the in-between state.

“Explain two-phase commit.”
A coordinator asks all participants to prepare. Each one does the work, saves it, locks the rows, and votes. If all vote yes, the coordinator logs commit and tells everyone to commit; otherwise everyone aborts. It is atomic, but participants are blocked if the coordinator dies after they vote yes.

“Why not use 2PC between microservices?”
Locks held across network calls, all services must be up together, coordinator failure blocks everyone, and brokers and external APIs don’t support it. Sagas trade strict consistency for availability and independence.

“Choreography or orchestration?”
Choreography for short, simple flows; orchestration when there are many steps, timeouts, or you need clear visibility.

Follow-ups to expect

  • In 2PC, what exactly happens if the coordinator crashes after receiving all YES votes? (Participants block; on restart the coordinator reads its log; if no decision was logged, it aborts.)
  • Why can’t a participant decide on its own after voting YES?
  • How do distributed databases make 2PC practical? (Replicated, consensus-backed coordinators and participants.)
  • In a saga, what if a compensation fails? (Retry with backoff; store state; alert and allow manual fixes.)
  • How do you avoid charging twice? (Idempotency keys, deduplication.)
  • Which step can’t be compensated, and where do you place it?

How it fits a bigger design

In e-commerce checkout, travel booking, or wallet transfers, interviewers want to hear that you noticed the action crosses service boundaries, and that you chose deliberately: one database and a normal transaction if possible, a saga for cross-service workflows, and 2PC mostly inside databases that handle it for you.

  • A distributed transaction changes data in more than one database or service.
  • 2PC: prepare and vote, then commit or abort together. Atomic and isolated.
  • 2PC’s weakness: locks held across network calls, and blocking if the coordinator fails after votes.
  • Saga: a chain of local transactions; compensations undo earlier steps on failure.
  • Sagas give eventual consistency and no isolation between steps.
  • Choreography: services react to events. Orchestration: one controller drives the steps.
  • Outbox pattern + idempotent consumers make saga messaging reliable.
  • Prefer one database and a normal transaction when you can; use distributed SQL for cross-shard transactions; use sagas across services.
