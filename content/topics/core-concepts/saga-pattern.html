Sometimes one user action has to change data in more than one database. Placing an order creates the order, takes payment and reserves stock, and each of those lives in a different service with its own database.

You want it to behave like one unit: all of it, or none of it. That is a distributed transaction, and there are two ways to get there.

  • Two-Phase Commit (2PC): a coordinator asks every database “can you commit?”. Only if all say yes does it say “commit now”. Truly all-or-nothing.
  • Saga: run the steps one by one, each committing immediately. If a later step fails, run compensating actions to undo the earlier ones — refund the payment, release the stock.

One-line version: 2PC = “everyone agrees first, then everyone commits together”. Saga = “commit step by step, and clean up if something goes wrong”.

Without a plan you call the services in order and hope. Order created ✔, ₹2,000 charged ✔, inventory says “out of stock” ✘. The customer has now paid for something you can’t ship, and a human has to find it and fix it.

Both approaches prevent that, but they promise different things:

  • 2PC promises nobody ever sees the half-done state. It pays with locks held across network calls, and a stuck coordinator freezes everyone.
  • A saga promises the system ends up correct. It pays by letting the half-done state be real and visible, and you write the undo yourself.

So the question is: do you need all-or-nothing at every instant, or is “correct in the end” enough? For business workflows across services it is usually enough, which is why sagas won in microservices.

2PC is a wedding. The officiant is the coordinator, the couple are the participants. Phase one, each is asked “do you take…?” — and once you say “I do”, you can’t walk away. Phase two, only if both said yes, the officiant pronounces them married.

Now the officiant faints between the two phases. Nobody can leave, because they promised. Nobody can declare themselves married, because only the officiant decides. They wait. That is 2PC’s famous weakness: blocking.

A saga is booking a trip from three companies that will never coordinate with each other. Flight ✔, hotel ✔, no cars left ✘. So you cancel the hotel, then the flight. Notice that you really did hold that seat and that room for a while, that cancelling isn’t “it never happened” (the airline keeps a fee), and that if their line is busy you keep trying until the cancellation goes through.

2PC between two PostgreSQL databases, moving ₹500 from an account in A to one in B. Your app is the coordinator.

// transfer-2pc.ts (simplified)
-- on each database, after doing its half of the work:
PREPARE TRANSACTION 'tx-a';     -- phase 1: vote yes, hold the locks
-- app saves its COMMIT decision durably, then:
COMMIT PREPARED 'tx-a';         -- phase 2

After PREPARE TRANSACTION the changes are on disk but invisible, and the rows stay locked. If your app dies here, those prepared transactions sit in PostgreSQL holding locks until a recovery job finishes them — watch pg_prepared_xacts. It is off by default (max_prepared_transactions = 0).

A saga for the same order, orchestrated: one place runs the steps and knows how to undo each one.

// place-order.saga.ts (simplified)
const steps = [
  { run: ctx => orders.create(ctx.id, 'PENDING'),
    compensate: ctx => orders.setStatus(ctx.id, 'CANCELLED') },
  { run: ctx => inventory.reserve(ctx.id, ctx.items),
    compensate: ctx => inventory.release(ctx.id) },
  { run: ctx => payments.charge(ctx.id, ctx.amount),
    compensate: ctx => payments.refund(ctx.id) },
];

for (const step of steps) {
  try { await step.run(ctx); done.push(step); await sagaLog.save(ctx, step); }
  catch (err) {
    for (const s of done.reverse()) await retryUntilSuccess(() => s.compensate(ctx));
    return { status: 'FAILED' };
  }
}

Why that order? Releasing stock is cheap to undo. Refunding money is not. The expensive undo goes last, after the cheap checks pass.

This sketch holds progress in a running function, so a crash loses it. Real systems store saga state in a database, or use a workflow engine like Temporal, Camunda or AWS Step Functions.

2PC. One coordinator decides, the participants do the work.

  1. Coordinator sends “prepare” to everyone.
  2. Each does the work, flushes it to disk, locks the rows, and votes YES (“I can commit even if I crash”) or NO.
  3. All yes? The coordinator writes COMMIT to its own log. That write is the decision.
  4. Everyone commits and releases locks. One NO, or one silence, aborts all.
FailureWhat happens
A participant votes NO, or crashes before votingCoordinator aborts everyone. Safe.
A participant crashes after voting YESOn restart it asks the coordinator what was decided. It must not decide alone.
Coordinator crashes after logging COMMITOn restart it reads its log and resends “commit”. Participants wait.
Coordinator crashes after the votes, before decidingThe bad case. Participants can’t abort (it may have decided commit) and can’t commit (it may have decided abort). They sit blocked, holding locks.

That last row is why 2PC is called a blocking protocol. It is always safe. It just stops making progress.

A saga runs forward and, on failure, backward:

The outbox problem. Each step updates its database and sends a message. Commit without the message and the saga stalls; send without committing and others react to something that never happened. The fix: write the message into an outbox table in the same transaction, and let a relay publish it.

BEGIN;
  UPDATE stock SET reserved = reserved + 2 WHERE sku = 'SKU-1';
  INSERT INTO outbox (id, topic, payload)
  VALUES (gen_random_uuid(), 'stock.reserved', '{"orderId":"o-42"}');
COMMIT;

The relay can publish a row twice, so consumers must be idempotent: store handled message ids and skip repeats.

Two styles of saga

Choreography has no controller: each service reacts to events. OrderCreated → Inventory reserves → publishes StockReserved → Payment charges. Loosely coupled, fine for two or three steps, but the flow isn’t written down anywhere, so “where is order 42 stuck?” is hard to answer.

Orchestration has one component sending commands and holding the state. Timeouts, retries and debugging get easy; the price is another service with durable state.

Distributed SQL databases (Spanner, CockroachDB) run 2PC where every role is a consensus-replicated group. That is what makes it practical — you get it by using the database, not by building it.

How long 2PC holds locks. Assumptions, illustrative, inside one data centre: a network round trip is about 2 ms and a disk flush about 3 ms.

  • Prepare 2 + 3 = 5 ms, decision log 3 ms, commit round 2 ms: a row stays locked about 10 ms, against 1–3 ms locally.
  • Transactions on the same row queue behind that, so one hot row tops out near 100 transactions/s. Across regions it falls to single digits.
  • If the coordinator crashes and takes 2 minutes to return, those rows stay locked for 2 minutes.

Availability. 2PC needs everyone up at once. Three services at 99.9% each are all up about 0.999³ ≈ 99.7% — roughly 26 hours a year when the action can’t run at all, against 9 hours for one service. A queue-based saga takes the order anyway and charges when Payment returns.

How often compensations run. Four steps at 99.9%, 1,000 orders a minute: 0.999⁴ ≈ 0.996, so 0.4% fail somewhere — 4 sagas a minute, 5,700 a day. Compensation is not an edge case. Retry temporary failures before compensating, and give every saga a deadline.

  • Isolation vs availability. 2PC hides the in-between state. A saga shows it, but keeps working when a participant is down.
  • Locks vs compensations. 2PC holds locks across network calls, so contention is the limit. A saga holds none, but you write and test every undo.
  • Built-in undo vs real-world undo. Rollback is exact. Compensation is a business action: a refund costs money, a sent email can only be corrected.
  • Reach. 2PC needs “prepare”, ruling out payment gateways, brokers and most SaaS APIs.
  • Debuggability. A saga needs correlation ids, stored state and tracing before you can answer simple questions. Teams also patch the missing isolation with semantic locks: a PENDING status other code agrees to respect.
  1. All the data in one database? Use a normal transaction. Simpler and stronger than both. Stop here.
  2. Need transactions across shards of one system? Use a database that does it for you — CockroachDB, YugabyteDB, Spanner, Citus. They run 2PC internally with the hard parts solved.
  3. A few databases you control, fast network, low volume? 2PC can work, with a real transaction manager and a recovery job for stuck transactions.
  4. Several services, external APIs, or steps that take minutes? Saga.

Signals for a saga: one action changes data owned by two or more services, partial success must be cleaned up, steps call systems that can’t join a transaction, or the process runs for minutes.

When you need neither: a failed step that can simply be retried — a search index update, analytics — only needs a reliable message. And if two services always change together, the boundary between them may be wrong.

  • No recovery for stuck prepared transactions. They hold locks forever and block vacuum. Monitor pg_prepared_xacts.
  • Not logging the 2PC decision before sending it. After a crash the coordinator can’t know what it decided.
  • Treating compensation as rollback. Others already saw the data. Compensations are business actions.
  • Non-idempotent steps. Messages arrive twice, so customers get charged twice. Use idempotency keys.
  • Messages sent outside the transaction. Lost or phantom events. Use the outbox.
  • Saga state only in memory. A deploy loses every in-flight saga.
  • Bad step order. Charging and emailing belong after the easy-to-undo steps.
  • Reaching for either when one database would do.

Common questions

“How do you keep data consistent across microservices when placing an order?”
A saga: local transactions with compensations. Walk the steps, say which can fail and what gets undone, then mention the outbox, idempotency and a PENDING status.

“Explain two-phase commit.”
Coordinator asks everyone to prepare; each does the work, locks rows and votes. All yes, it logs commit and tells them to commit. Atomic, but they block if it dies after the votes.

“Why not 2PC between microservices?”
Locks across network calls, everyone up at once, coordinator failure blocks all of them, and brokers and external APIs can’t take part.

Follow-ups to expect

  • Coordinator crashes after all YES votes? (They block; on restart it reads its log, and with no decision logged it aborts.)
  • Why can’t a participant decide alone after voting yes?
  • What if a compensation fails? (Retry with backoff, store state, alert a human.)
  • How do you avoid charging twice? (Idempotency keys.)
  • Which step can’t be compensated, and where do you put it?

How it fits a bigger design

In checkout, booking or wallet transfers, the point is that you noticed the action crosses a service boundary and chose deliberately: one database and a plain transaction if you can, a saga across services, 2PC inside a database that handles it for you.

  • A distributed transaction changes data in more than one database or service.
  • 2PC: prepare and vote, then commit or abort together. Atomic and isolated.
  • Its weakness: locks held across network calls, and blocking if the coordinator dies after the votes.
  • Saga: a chain of local transactions, with compensations undoing the earlier ones.
  • Sagas give eventual consistency and no isolation between steps.
  • Choreography means services react to events; orchestration means one component drives.
  • Outbox plus idempotent consumers make saga messaging reliable.
  • Order the steps so the hard-to-undo ones come last.
  • One database and a normal transaction beats both, whenever it is possible.
