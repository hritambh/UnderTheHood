Authentication is proving who you are. Authorisation is deciding what you’re allowed to do. Always in that order: first who is calling, then whether they may do this.

The status codes follow the split. 401 Unauthorized means “I don’t know who you are” (the name is misleading — it means not authenticated). 403 Forbidden means “I know who you are, and the answer is no”.

Authentication has two halves, and the design choices all sit in the second one:

  1. Logging in: proving yourself once, with a password, a one-time code or a passkey.
  2. Staying logged in: the server remembering you, so you don’t send the password again.

Four ways to do the second half: sessions (the server keeps the record, the browser holds a random id), JWTs (you carry a signed token), API keys (a secret that identifies a program), and OAuth / OpenID Connect (a service you trust vouches for you).

One-line version: authentication = “who are you?”, authorisation = “what can you do?”. Session = the server remembers you. JWT = you carry a signed note that says who you are.

HTTP has no memory. Every request arrives alone, so the server can’t tell two requests came from the same person. After login, every request must carry proof.

Why not send the password each time? Checking one is slow on purpose (see the numbers), the app would have to keep it around, and a password is all-or-nothing — no limited or short-lived access.

So you log in once and get something weaker back. Which weak thing you pick comes down to: where do you keep the proof, and how fast can you take it away?

An office building with a front desk and a guard on every floor. The desk checking your ID is authentication; the floor-5 guard checking you may enter is authorisation. How do the guards know you passed the desk?

  • Session: a plain badge numbered 4417. The number means nothing, so every guard phones the desk: “who is 4417?” Get fired at 2 pm, the desk crosses it out, and the badge dies on the next check.
  • JWT: a pass saying “Asha, engineer, floors 1–5, valid until 6 pm”, with a stamp that’s hard to fake. No phone calls — guards read it and check the stamp. Fast, works even when the desk phone is down. Get fired at 2 pm and the pass still works until 6.
  • API key: a loading-bay card given to the courier company. It belongs to a company, not a person, and it works for months.
  • OAuth: a visitor shows a letter from a company the building trusts — “this is Ravi, meeting room 2 only”. The building never sees Ravi’s password.

The costs are in the story too. Badges ring the desk phone constantly, and a busy desk blocks everyone. Stamped passes make no calls but can’t be cancelled early — unless guards carry a list of cancelled passes, which is the phone call again.

A food-delivery app on NestJS: users see their own orders, admins see all. Login checks the password the same way either way — argon2.verify(user.passwordHash, password), against a slow salted hash (a one-way scramble, with a random value mixed in per user so identical passwords differ).

Session version: the login lives in Redis, the browser gets a cookie holding only an id.

// main.ts — cookie holds only the id; the data sits in Redis
app.use(session({ store: new RedisStore({ client: redis }),
  cookie: { httpOnly: true, secure: true, sameSite: 'lax' } }));

req.session.userId = user.id;
req.session.destroy(() => {});   // logout: gone from Redis, so gone now

JWT version: the server signs a token and stores nothing.

// auth.service.ts
return { accessToken: await this.jwt.signAsync(
  { sub: user.id, role: user.role }, { expiresIn: '15m' }) };

// jwt.guard.ts — signature and expiry only, no lookup
req.user = await this.jwt.verifyAsync(token);

The client sends Authorization: Bearer <token>. “Bearer” means whoever carries it gets in.

Neither of those is authorisation. That is the check people forget:

// orders.controller.ts
@UseGuards(JwtGuard)                       // 401 if we don't know who you are
@Get(':id')
async getOrder(@Param('id') id: string, @Req() req) {
  const order = await this.orders.findById(id);
  if (order.userId !== req.user.sub && req.user.role !== 'admin')
    throw new ForbiddenException();        // 403: known, but not allowed
  return order;
}

A valid login does not make the order yours. Every endpoint that takes an id needs its own check, and no library writes that for you.

Session: the server makes a long random id, stores id → user, expiry in Redis, and returns Set-Cookie: sid=…. The browser attaches that cookie to every request by itself; the server looks it up each time. Logout deletes the record, and the cookie becomes a useless number.

JWT: the server builds a token holding the user id, role and expiry, and signs it with a key. The client sends it in a header. The server checks the signature and the expiry — pure maths on the token, no lookup — and then trusts what it says.

A JWT is header.payload.signature: the signing method, the facts (claims) like {"sub":"user_42","role":"admin"}, and a signature over both. Change one character and the signature stops matching, and nobody can forge a new one without the key.

Header and payload are encoded, not encrypted. Anyone holding the token can read them. Never put private data in a JWT.

Because a JWT can’t be cancelled, keep it short — 15 minutes — and pair it with a refresh token: a long-lived random string in your database, sent only to POST /refresh. Logout deletes that row, so the access token dies within 15 minutes.

OAuth 2.0 and OpenID Connect

OAuth is about access: an app reads your calendar and nothing else, never seeing your password. Those limits are scopes. OpenID Connect adds identity: an ID token saying who you are. That is “Login with Google”.

Step 5 is the one people miss: Google only handles the login. Your app still needs its own session or JWT afterwards. Apps that can’t keep a secret — mobile, single-page — add PKCE, proving at step 4 that they made the request, so a stolen code is useless.

Deciding what they can do

  • Ownership checks: “is this order yours?” Every app needs these.
  • RBAC: roles like admin or support, each with allowed actions. Enough for most apps.
  • ABAC: rules over attributes — “a manager approves expenses under ₹50,000 in their own department”. Flexible, hard to test.

Assumptions, made up: 2,000 requests/s, 1 million logged-in users, every request authenticated.

  • Sessions: 2,000 Redis lookups/s, about 1 ms per request. At 200 bytes each, 1,000,000 sessions = 200 MB, one small Redis.
  • JWTs: 0 lookups, but a 300-byte token on every request is 600 KB/s of headers, three times the cookie.
  • Refreshes: 15-minute tokens, 100,000 active users → 100,000 ÷ 900 s ≈ 111 refresh calls/s, which do hit the database. So JWTs cut lookups from 2,000/s to 111/s, not to zero.

Why you don’t re-check the password. Hashes are slow on purpose, say 100 ms of CPU. 50 logins/s keeps 5 cores busy. If all 2,000 requests/s carried a password: 200 seconds of CPU every second, 200 cores. That number is the reason for the whole design.

  • Lookups vs cancellation. A session dies the moment you delete it, but every service must reach the store. A JWT is checked anywhere, and can’t be killed early.
  • Short life vs fewer refreshes. A 5-minute token limits theft damage. A 24-hour one is easy on the servers and a gift to a thief — a cancelled login keeps working that long.
  • Cookies vs the Authorization header. Browsers send cookies by themselves, which is handy and exactly why CSRF works. SameSite and CSRF tokens stop it. A header token has no CSRF, but JavaScript must hold it, and XSS can read it.
  • Shared secret vs key pair. With HS256 anything that verifies can also mint. With RS256 only the auth service signs; everyone else gets the public key.
  • Roles vs rules. Roles are easy to test. Attribute rules express anything, and make “who can see this?” hard to answer.
  • Sessions: a web app with one backend, or a few sharing one Redis, where logout and bans must work at once. The safe default.
  • JWT: several services need to know the user, or the clients are mobile apps where cookies are awkward. Short access token plus refresh token.
  • API keys: the caller is a script or a server. One key per customer, cancellable on its own.
  • OAuth / OIDC: “Login with Google”, single sign-on, or letting other apps act for your users.

You don’t need JWTs for one backend and a browser. The common mistake is picking them because they sound modern, then adding a database check per request so logout works — that is sessions, rebuilt with extra code.

For authorisation, start with ownership checks and a few roles. Add attribute rules only when roles turn into admin-but-only-for-billing-in-europe.

  • Checking login but not ownership. GET /orders/124 returns someone else’s order. Called IDOR, and one of the most common real data leaks.
  • Trusting the frontend. Hiding the Delete button is not authorisation. Anyone can call the API.
  • Storing passwords badly. Never plain text, never a fast hash like MD5. Argon2, bcrypt or scrypt, salted.
  • Secrets in a JWT, or long-lived JWTs with no refresh token. A 30-day token that can’t be cancelled is a 30-day problem when it leaks.
  • Tokens in localStorage. Any script on the page can read one. An HttpOnly cookie can’t.
  • Not fixing the signing method. Old JWT bugs accepted "alg":"none". Name the algorithm you accept.
  • Keeping the session id after login. An attacker who planted it now shares your session. Issue a new one.
  • Login errors that say too much. “No account with this email” tells an attacker which emails exist.
  • No limit on login attempts. Rate limit per account and per IP.

Common questions

“Sessions or JWTs?”
Depends who checks the login. One backend with a browser: sessions in Redis, since logout is instant. Many services: a short JWT each can verify alone, plus a refresh token in the database so logins can still be cancelled.

“How do you log out with JWTs?”
Short access tokens, and delete the refresh token. If logout must be instant, keep a blocklist in Redis keyed by jti — and admit that is a lookup per request, the thing JWTs were avoiding.

“How does Login with Google work?”
Authorization code flow: redirect, user logs in at Google, one-time code comes back, your backend swaps it for tokens, you read the ID token and start your own session.

Follow-ups to expect

  • Where do you store a token in a browser? (HttpOnly, Secure, SameSite cookie. Not localStorage.)
  • How do other services verify a JWT? (The auth service’s public key, checked locally.)
  • What is refresh token rotation? (Each refresh kills the old one; an old one reappearing means it was copied.)
  • Where do authorisation checks live across services? (The gateway says who; each service decides what.)

How it fits a bigger design

An API gateway is the front door: it checks the session or token and passes the user id back. An auth service owns users, hashes and refresh tokens. Each service still does its own ownership checks.

  • Authentication proves who you are; authorisation decides what you may do.
  • Failed authentication is 401. Failed authorisation is 403.
  • A session keeps the login on the server, and the browser holds only a random id.
  • A JWT keeps the login in a signed token, so the server checks signature and expiry with no lookup.
  • Sessions can be cancelled instantly. JWTs live until they expire, so keep them short and pair them with a refresh token.
  • JWT payloads are readable by anyone holding the token.
  • API keys identify programs, not people.
  • OAuth gives limited access to data elsewhere; OpenID Connect adds identity on top.
  • Cookies need CSRF protection; tokens JavaScript can read are exposed to XSS.
  • Check ownership on every request, not just that someone is logged in.
