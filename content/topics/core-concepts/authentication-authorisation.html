Authentication is proving who you are. You type an email and password, and the server checks them.

Authorisation is deciding what you’re allowed to do. You are logged in, but can you delete this order? Can you see that invoice?

They always run in that order. First the server works out who is calling. Then it checks if that person can do the thing they asked for.

HTTP status codes follow the same split:

  • 401 Unauthorized: “I don’t know who you are.” Authentication failed. (The name is confusing. It really means “not authenticated”.)
  • 403 Forbidden: “I know who you are, and the answer is no.” Authorisation failed.

Authentication has two parts, and people often mix them up:

  1. Logging in: you prove who you are once, with a password, a one-time code, or a passkey.
  2. Staying logged in: the server remembers you for the next requests, so you don’t send your password every time.

This topic is mostly about part 2, because that is where the design choices are. The common ways to do it are:

  • Sessions: the server keeps a record of your login and gives the browser a random ID.
  • JWT (JSON Web Token, usually said “jot”): the server gives you a signed token that holds your details. The server keeps nothing.
  • API keys: a long secret string that identifies a program, not a person.
  • OAuth 2.0 and OpenID Connect: another service you already trust, like Google, tells the app who you are. This is “Login with Google”.

One-line version: authentication = “who are you?”, authorisation = “what can you do?”. Session = the server remembers you. JWT = you carry a signed note that says who you are.

HTTP has no memory. Every request shows up alone, with no link to the one before it. The server can’t tell if two requests came from the same person.

So after you log in, every request has to carry some proof of who you are. The server checks that proof again each time.

Without authentication, anyone can say they are anyone. Without authorisation, any logged-in user can read anyone else’s data. Both end the same way: leaked data and taken-over accounts.

Why not just send the password with every request? Three reasons:

  • Checking a password is slow on purpose. The numbers section shows how slow.
  • The app would have to keep your password around, which is one more place to steal it from.
  • You can’t give limited or short-lived access with a password. It is all or nothing until it’s changed.

So you log in once and get something weaker and short-lived in return: a session ID or a token. The choice between them matters because they differ on a few things:

  • Where the login lives: on the server (session) or inside the token the client holds (JWT).
  • How fast you can cancel it: right now, or only when it expires.
  • How many servers need to check it: one app, or twenty services.
  • Who is calling: a browser, a mobile app, or another company’s server.

The real question is: where do I keep the proof of login, and how fast can I take it away?

Think of an office building with a front desk and a guard on every floor.

  • Authentication is the front desk checking your ID card when you walk in.
  • Authorisation is the guard on floor 5 checking if you’re allowed on floor 5.

Now, how do the guards know you already showed your ID at the desk?

  • Session: the desk gives you a plain badge with a number on it, say 4417. The number means nothing by itself. Every guard phones the desk and asks, “Who is 4417?” The desk looks in its register and answers. If you get fired at 2 pm, the desk crosses out 4417, and the badge stops working on the very next check.
  • JWT: the desk gives you a pass that says “Asha, engineer, floors 1 to 5, valid until 6 pm”, with an official stamp that is hard to fake. Guards don’t phone anyone. They read the pass and check the stamp. This is fast, and it works even if the desk phone is down. But if you get fired at 2 pm, the pass still looks fine until 6 pm.
  • API key: the building gives the courier company a key card for the loading bay. It belongs to the company, not to one person, and it works for months.
  • OAuth / “Login with Google”: a visitor has no ID from this building. They show a letter from a company the building trusts. It says “this is Ravi, and he may use meeting room 2 only”. The building never sees Ravi’s own company password. It trusts the letter.

The costs show up here too:

  • With badges, the desk phone rings on every single check. If the desk is busy or down, nobody gets through.
  • With stamped passes, there are no phone calls. But you can’t cancel a pass early, unless guards also carry a list of cancelled passes. And a list they must check every time is just the phone call again.
  • If someone steals a badge or a pass, they can use it. Short expiry times limit the damage.

Say you’re building a food-delivery app with a NestJS backend. Users log in and see their own orders. Admins can see all orders.

Below is the same login done two ways, and then the permission check.

Checking the password (same for both options)

// auth.service.ts
async checkPassword(email: string, password: string) {
  const user = await this.users.findByEmail(email);
  if (!user) return null;
  // the database stores a slow, salted hash, never the password
  const ok = await argon2.verify(user.passwordHash, password);
  return ok ? user : null;
}

A hash is a one-way scramble. You can turn a password into its hash, but you can’t turn the hash back into the password. Salted means a random value is mixed in for each user, so two users with the same password get different hashes.

Option 1: session login

The session lives in Redis, a fast in-memory store. The browser only gets a cookie with the session ID.

// main.ts  (session setup, connect-redis v8)
import * as session from 'express-session';
import { RedisStore } from 'connect-redis';
import { createClient } from 'redis';

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

app.use(session({
  store: new RedisStore({ client: redis }),
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,   // page JavaScript can't read the cookie
    secure: true,     // sent over HTTPS only
    sameSite: 'lax',  // not sent on cross-site POSTs
    maxAge: 7 * 24 * 60 * 60 * 1000,  // 7 days
  },
}));
// auth.controller.ts  (session version)
@Post('login')
async login(@Body() dto: LoginDto, @Req() req: Request) {
  const user = await this.auth.checkPassword(dto.email, dto.password);
  if (!user) throw new UnauthorizedException();
  req.session.userId = user.id;  // saved in Redis, not in the cookie
  return { ok: true };
}

@Post('logout')
logout(@Req() req: Request) {
  req.session.destroy(() => {});  // gone from Redis = logged out now
}

After login, the browser sends the cookie by itself on every request. The server reads req.session.userId to know who is calling.

Option 2: JWT login

The server signs a token and hands it over. It stores nothing.

// auth.service.ts  (JWT version)
async login(email: string, password: string) {
  const user = await this.checkPassword(email, password);
  if (!user) throw new UnauthorizedException();
  const payload = { sub: user.id, role: user.role };
  return {
    accessToken: await this.jwt.signAsync(payload, { expiresIn: '15m' }),
  };
}
// jwt.guard.ts
@Injectable()
export class JwtGuard implements CanActivate {
  constructor(private readonly jwt: JwtService) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const req = ctx.switchToHttp().getRequest();
    const [type, token] = (req.headers.authorization ?? '').split(' ');
    if (type !== 'Bearer' || !token) throw new UnauthorizedException();
    try {
      // checks the signature and the expiry time
      req.user = await this.jwt.verifyAsync(token);
    } catch {
      throw new UnauthorizedException();
    }
    return true;
  }
}

The client sends the token in a header on every request: Authorization: Bearer <token>. “Bearer” means “whoever carries this token gets in”.

Authorisation: the check people forget

// orders.controller.ts
@UseGuards(JwtGuard)            // authentication: who is calling?
@Get(':id')
async getOrder(@Param('id') id: string, @Req() req) {
  const order = await this.orders.findById(id);
  if (!order) throw new NotFoundException();

  // authorisation: can this user see THIS order?
  const isOwner = order.userId === req.user.sub;
  const isAdmin = req.user.role === 'admin';
  if (!isOwner && !isAdmin) throw new ForbiddenException();

  return order;
}

The guard answers “who is this?” and fails with 401. The check inside answers “can they see this order?” and fails with 403. You need both. A valid login doesn’t mean the order is theirs.

Notice what is now harder:

  • With sessions, every request does a Redis lookup. Redis becomes something your whole app depends on.
  • With JWTs, logout is not real. The token works until it expires, unless you add a second piece like a refresh token. The next section covers this.
  • Either way, every endpoint that returns data needs its own “is this theirs?” check. No library does that for you.

NestJS also has @nestjs/passport, which wraps the Passport library and gives you ready-made “strategies” for sessions, JWTs, and Google login. The hand-written guard above shows what those do inside.

Session flow

  1. Browser sends POST /login with email and password.
  2. Server finds the user and checks the password against the stored hash.
  3. Server makes a long random session ID and saves session ID → user ID, expiry in Redis or the database.
  4. Server replies with Set-Cookie: sid=…; HttpOnly; Secure; SameSite=Lax.
  5. From now on, the browser adds that cookie to every request to this site. Your frontend code does nothing.
  6. On each request, the server reads the ID from the cookie, looks it up in the store, and gets the user. If the ID isn’t there, it replies 401.
  7. Logout deletes the record from the store. The cookie is now a useless number.

JWT flow

  1. The start is the same: the browser sends the password and the server checks it.
  2. Server builds a token with the user’s ID, role, and an expiry time, and signs it with a secret key.
  3. Server sends the token back. The client keeps it.
  4. On each request, the client sends Authorization: Bearer <token>.
  5. Server checks the signature and the expiry time. Both are just maths on the token itself. There is no lookup.
  6. If the signature is good and the token hasn’t expired, the server trusts what the token says.

What is inside a JWT

A JWT is three parts joined by dots: header.payload.signature.

  • Header: which signing method was used, for example {"alg":"HS256","typ":"JWT"}.
  • Payload: the facts about the user, called claims. For example {"sub":"user_42","role":"admin","exp":1798761600}. Here sub is the user ID and exp is the expiry time.
  • Signature: what you get when you run the header and payload through a signing function with the server’s secret key.

Say someone changes one character of the payload, like "role":"user" to "role":"admin". The signature no longer matches, and the server rejects the token. They can’t make a new signature, because they don’t have the key.

The header and payload are only encoded (Base64URL), not encrypted. Anyone who has the token can read them. Paste one into jwt.io and you’ll see what is inside. Never put passwords or private data in a JWT.

Access tokens and refresh tokens

A JWT can’t be cancelled, so you keep it short-lived, often 15 minutes. But nobody wants to log in every 15 minutes. So login returns two things:

  1. An access token: the short-lived JWT, sent on every request.
  2. A refresh token: a long-lived random string, saved in the server’s database. It is only ever sent to one endpoint, POST /refresh.

When the access token expires, the client calls /refresh. The server looks up the refresh token in the database. If it is still there, the server gives out a new access token.

To log someone out, delete their refresh token. Their access token dies within 15 minutes and can’t be renewed.

1. Sessions

How: the server stores the login. The browser holds a random ID in a cookie.

Use when: you have a web app where the browser talks to your own backend. This is the simple default.

Good: logout and “ban this user” work at once. The cookie holds nothing readable. You can list a user’s active logins and end any of them.

Bad: a store lookup on every request. Every server has to reach the same store. Cookies also need protection against an attack called CSRF, where another website makes your browser send a request with your cookie attached.

2. JWT

How: the client holds a signed token with the user’s details. The server only checks the signature.

Use when: many services need to check the user without calling a central auth service each time. Also common for mobile apps and public APIs.

Good: no lookup, so any service with the key can check it. Works the same for browsers, mobile apps, and other servers.

Bad: can’t be cancelled before it expires. Bigger than a session ID. If the user’s role changes, the old token still says the old role until it expires.

3. API keys

How: you create a long random string for a customer or a service. They send it in a header like X-API-Key on every call. The server keeps a hash of the key and looks that up.

Use when: the caller is a program, not a person. A cron job, a partner’s server, a developer using your public API.

Good: very simple. Each key can have its own permissions and its own rate limit (a cap on calls per minute). It is easy to cancel one key.

Bad: keys live for months, so a leaked key works until someone notices. Keys end up pasted in code and chat messages. A key identifies the app, not the person using it.

4. OAuth 2.0 and OpenID Connect

These two are often mixed up.

  • OAuth 2.0 is about access. It lets an app get limited access to your data on another service, without ever seeing your password for that service. Example: a calendar app that can read your Google Calendar, and nothing else. The limits are called scopes.
  • OpenID Connect (OIDC) is a thin layer on top of OAuth that adds identity. Along with the access token, the app gets an ID token: a JWT that says who the user is. This is what “Login with Google” uses.

The usual flow is called the authorization code flow:

  1. You click “Login with Google”. The app sends your browser to Google, with the app’s ID and the scopes it wants.
  2. You log in at Google and approve. The app never sees your Google password.
  3. Google sends your browser back to the app with a one-time code in the URL.
  4. The app’s backend sends that code to Google, along with the app’s own secret, and gets tokens back.
  5. The app reads your Google user ID and email from the ID token. It finds or creates your account, and starts its own session or JWT for you.

Step 5 is easy to miss. Google only handles the login. After that, your app still needs sessions or JWTs to keep the user logged in.

Use when: you want “Login with Google” or “Login with GitHub”. Or your company wants one login for all its tools, which is called single sign-on (SSO). Or other apps need limited access to your users’ data.

Good: you don’t store passwords at all. Users don’t need one more password.

Bad: more moving parts, and you depend on the other service. If Google login is down, so is yours.

Mobile apps and single-page apps can’t keep a secret, because users can open them up and look inside. They add a step called PKCE (said “pixy”). The app makes a random value at the start, and at step 4 it proves it knows that value. A stolen code is useless without it.

Authorisation models

Once you know who the user is, there are three common ways to decide what they can do. Most apps mix them.

  • Ownership checks: “is this order yours?” Compare the user ID on the record with the user ID of the caller. Every app needs this.
  • RBAC (role-based access control): each user has a role like admin, support, or customer, and each role has a list of allowed actions. Simple, and enough for most apps.
  • ABAC (attribute-based access control): rules that look at facts about the user, the record, and the request. For example, “a manager can approve expenses under ₹50,000 from their own department”. Flexible, but harder to test and to explain.

Assumptions (made up for this example, not benchmarks): the app gets 2,000 requests per second, and 1 million users are logged in. Every request needs an authentication check.

Sessions

  • Lookups: 2,000 requests/s = 2,000 Redis lookups/s.
  • Extra time: if one lookup takes about 1 ms on the same network, every request gets about 1 ms slower.
  • Memory: say one session takes 200 bytes. 1,000,000 × 200 bytes = 200 MB. That fits on one small Redis server.
  • Cookie size: say 100 bytes per request. 2,000 × 100 = 200,000 bytes/s = 200 KB/s of request headers.

JWTs

  • Lookups: 0. Checking a signature is CPU work, and it takes a tiny part of a millisecond.
  • Token size: say 300 bytes for a small payload. 2,000 × 300 = 600,000 bytes/s = 600 KB/s of request headers. That is three times the session cookie, and it grows with everything you add to the payload.
  • Refresh calls: tokens last 15 minutes, which is 900 seconds. Say 100,000 of those users are active. That is 100,000 ÷ 900 ≈ 111 refresh calls/s, and each one does hit the database.

So JWTs don’t remove the lookups completely. In this example they cut them from 2,000/s to about 111/s.

How long does a cancelled or stolen login keep working?

  • Session: until the next request. You delete it and it’s gone.
  • JWT with a 15-minute life: up to 15 minutes. About 7.5 minutes on average, if the token was made at a random moment.
  • JWT with a 24-hour life: up to 24 hours. This is why long-lived JWTs are risky.

Why you log in once, and not on every request

Password hashes are slow on purpose, so that guessing millions of passwords takes far too long. Say one check takes 100 ms of CPU time.

  • 50 logins/s × 100 ms = 5 seconds of CPU work every second. That keeps 5 CPU cores busy just for logins.
  • If all 2,000 requests/s carried a password, that would be 2,000 × 100 ms = 200 seconds of CPU work every second, or 200 cores.

That is the reason for the whole design. Do the slow check once at login, then use a cheap proof (a session ID or a token) after that.

  • Server memory vs no lookups. Sessions keep the login on the server and pay a lookup per request. JWTs keep it in the token and pay nothing per request.
  • Instant cancel vs independence. A session can be killed at once, but every service has to reach the session store. A JWT can be checked by any service alone, but it can’t be killed early.
  • Short life vs fewer refreshes. A 5-minute token limits the damage if it’s stolen, but clients refresh more often. A 24-hour token is easy on the servers and a gift to a thief.
  • Cookies vs the Authorization header. The browser sends cookies by itself. That is handy, but it also means another website can make your browser send a request with your cookie attached. This attack is CSRF (cross-site request forgery). SameSite cookies and CSRF tokens stop it. A token in a header is never sent by itself, so there is no CSRF. But your JavaScript has to keep that token somewhere. If an attacker gets a script onto your page, which is called XSS (cross-site scripting), that script can read the token and send it away.
  • One shared secret vs a key pair. With HS256, the same secret signs tokens and checks them. So every service that can check a token can also make one. With RS256 or ES256, a private key signs and a public key checks. Only the auth service can make tokens, and everyone else gets the public key. Use a key pair when more than one service checks tokens.
  • Simple roles vs detailed rules. Roles are easy to understand and to test. Detailed rules can say anything, but it gets hard to answer “who can see this?”
  • Build it vs buy it. Writing login yourself teaches you a lot and has no monthly bill. A hosted service or an open-source server (Auth0, Clerk, Amazon Cognito, Keycloak) comes with password reset, email checks, two-step login, and Google login already done. For a real product, most teams should not write all of this from scratch.

Signals for each choice

  • Sessions: a web app with one backend, or a few backends that share one Redis. You want logout and bans to work at once. You want the simplest thing that is safe.
  • JWT: several services each need to know who the user is. Or your clients are mobile apps and other servers, where cookies are awkward. Use a short access token with a refresh token.
  • API keys: the caller is a script or a server. Give each customer their own key, so you can limit and cancel them one by one.
  • OAuth / OIDC: you want “Login with Google”, company single sign-on, or to let other apps act for your users.

When you probably don’t need JWTs

If you have one backend and a browser frontend, sessions are simpler and safer.

A common mistake is to pick JWTs because they sound modern, and then add a database check on every request so that logout works. At that point you have built sessions again, with more code.

For authorisation

Start with ownership checks plus a few roles. Move to detailed rules only when your roles keep growing into things like admin-but-only-for-billing-in-europe.

  • Checking login but not ownership. GET /orders/124 returns someone else’s order, because the code only checked that the caller is logged in. This bug is called IDOR (insecure direct object reference), and it is one of the most common ways real apps leak data. Check ownership on every endpoint that takes an ID.
  • Trusting the frontend. Hiding the “Delete” button from normal users is not authorisation. Anyone can call the API directly. The server must check every time.
  • Storing passwords badly. Never store them as plain text, and never with a fast hash like MD5 or SHA-256. Use a slow, salted password hash: Argon2, bcrypt, or scrypt.
  • Putting secrets in a JWT. Anyone who holds the token can read the payload.
  • Long-lived JWTs with no refresh token. A 30-day token that can’t be cancelled is a 30-day problem when it leaks.
  • Keeping tokens in localStorage. Any script on the page can read it, including a bad one that got in through XSS. An HttpOnly cookie can’t be read by scripts at all.
  • Not fixing the signing method. Old JWT bugs let attackers send a token with "alg":"none" and no signature. When you check a token, tell the library exactly which method you accept.
  • Cookies without CSRF protection. Set SameSite, and use CSRF tokens on requests that change data.
  • Keeping the same session ID after login. If an attacker planted a session ID in the victim’s browser before login, they now share the logged-in session. This is called session fixation. Make a new session ID at login.
  • Login errors that say too much. “No account with this email” tells an attacker which emails are registered. Say “wrong email or password” for both cases.
  • No limit on login tries. Without a rate limit, a script can try thousands of passwords. Limit tries per account and per IP address.
  • Mixing up 401 and 403. 401 means “log in first”. 403 means “you are logged in, and the answer is still no”.

Common questions

“Sessions or JWTs? Which would you pick?”
It depends on who checks the login. One backend with a browser: sessions in Redis, because logout is instant and the cookie holds nothing readable. Many services: a short-lived JWT so each service can check it alone, plus a refresh token in the database so logins can still be cancelled. Say the trade-off out loud: a lookup on every request vs not being able to cancel early.

“How do you log a user out if you use JWTs?”
Keep access tokens short (5 to 15 minutes) and delete the refresh token on logout. If logout must be instant, keep a blocklist of cancelled tokens in Redis until they expire, and check it on each request. A JWT can carry its own ID for this, in the jti claim. Admit the cost: that check is a lookup, which is what JWTs were meant to avoid.

“How does ‘Login with Google’ work?”
Walk through the authorization code flow. Redirect to Google. The user logs in there. Google redirects back with a one-time code. Your backend swaps the code for tokens. You read who the user is from the ID token and start your own session.

“What is the difference between authentication and authorisation?”
Authentication is who you are, and it fails with 401. Authorisation is what you can do, and it fails with 403. Give the IDOR example to show you know they are separate checks.

Follow-ups to expect

  • Where do you store the token in a browser? (An HttpOnly, Secure, SameSite cookie is the safest default. Avoid localStorage.)
  • How do other services check a JWT? (They get the auth service’s public key and check the signature themselves. No call to the auth service per request.)
  • What is refresh token rotation? (Every refresh gives a new refresh token and cancels the old one. If an old one shows up again, someone copied it, so you cancel all of that user’s tokens.)
  • What do you put in the JWT payload? (User ID, role, expiry. Keep it small, and no private data.)
  • How do you store passwords? (Argon2 or bcrypt, salted, never plain text.)
  • How do you stop password guessing? (Rate limits, lockouts, and two-step login.)
  • Where do authorisation checks live when you have many services? (The gateway checks who the caller is. Each service checks what they can do with its own data.)

How it fits a bigger design

In most system designs there is an API gateway, the single front door that all requests pass through. It checks the session or token on the way in and passes the user ID to the services behind it. An auth service owns users, password hashes, and refresh tokens. Redis holds sessions or the blocklist.

Each service still does its own ownership and role checks, because only it knows its data. In an interview, one or two sentences on this is usually enough, unless the question is about auth itself.

  • Authentication proves who you are. Authorisation decides what you are allowed to do.
  • A failed authentication returns 401. A failed authorisation returns 403.
  • A session keeps the login on the server. The browser holds only a random ID in a cookie, and the server looks it up on every request.
  • A JWT keeps the login inside a signed token. The server checks the signature and the expiry time, with no lookup.
  • A session can be cancelled at once by deleting it. A JWT works until it expires, so keep it short-lived and pair it with a refresh token.
  • Anyone can read a JWT payload, so it must never hold secrets.
  • API keys identify programs, not people.
  • OAuth 2.0 gives an app limited access to a user’s data on another service. OpenID Connect adds login on top, which is how “Login with Google” works.
  • Cookies need CSRF protection. Tokens that JavaScript can read can be stolen through XSS.
  • The server must check ownership on every request, not only that the user is logged in.
