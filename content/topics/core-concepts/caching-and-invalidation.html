A cache is a copy of an answer kept somewhere fast, so the next request for it doesn't pay full price. The copy lives in memory; the real data stays where it was.

Invalidation is getting rid of that copy once the real data changes. Without it the cache keeps handing out an answer that stopped being true.

They are two halves of one job, and only the first half is easy. Examples use Redis as the cache and PostgreSQL as the truth, but nothing below depends on either.

One-line version: a cache is a bet that the same question gets asked again. Invalidation is how you stop winning that bet with an answer that is out of date.

Some answers are expensive and asked for constantly. A product page joins four tables and takes 20 ms. Ten thousand people load it an hour, so the database does that work ten thousand times for a row that changed once last Tuesday.

Without a cache you buy your way out with a bigger database, and pay for it on every request forever. With one, the first request pays and the rest are nearly free.

But the same fact now lives in two places, and the moment someone edits that product one of them is lying. So the real question is not “should I cache this?” — it is how wrong may this be, and for how long?

A café keeps its real price list in the office. Out front is a chalkboard.

Customers read the board, not the office list. That is the point: the board is three steps away and the office is upstairs. Hundreds read it a day and nobody waits.

  • The board is the cache. The office list is the database.
  • Wiping the board each night is eviction. Rewriting it each morning is a cache fill.
  • Raising a price in the office is a write. Until someone walks down and changes the board it is wrong, and that gap is the staleness window.

The costs show up fast. Somebody has to update the board every time, and forgetting is silent — customers just get quoted yesterday's price. And on the morning the board is blank, the first twenty customers are all sent upstairs at once: the exact queue the board existed to prevent.

A product endpoint, cache-aside: the app checks the cache and fills it on a miss.

// products.service.ts
async findOne(id: number): Promise<Product> {
  const key = `product:v2:${id}`;
  const hit = await this.redis.get(key);
  if (hit) return JSON.parse(hit);                 // cache hit

  const row = await this.repo.findOneBy({ id });   // miss: go to Postgres
  if (row) await this.redis.set(key, JSON.stringify(row), 'EX', 300);
  return row;
}

async update(id: number, patch: Partial<Product>) {
  await this.repo.update(id, patch);               // database first
  await this.redis.del(`product:v2:${id}`);        // then drop the copy
}

Three things there are deliberate. Database first, cache second — the other order can cache a write that then fails. Delete, don't overwrite: two writers racing to set can leave the older value in the cache, while two racing to del cannot. And EX 300 is a backstop, not the plan — it caps the damage when a del never runs.

What is now harder: two stores to keep in step, a second schema in Redis that deploys must match, and twice as many answers to “why is this page wrong?”

  1. A request arrives. The app builds a key from whatever makes the answer unique: product:v2:42.
  2. Hit — the key is there, so parse it and return. The database is never touched.
  3. Miss — nothing under that key, so the app queries the database itself.
  4. The row comes back and is served.
  5. The app writes it into the cache with a TTL, so the next reader hits.
  6. A write updates the database first, while the stale copy is still being served.
  7. Then the key is deleted, and the next reader refills from the new truth.

None of this is automatic. The cache is a plain key-value store doing what it is told; every step above is code someone has to keep right.

Three ways to stop serving a stale answer.

Let it expire (TTL)

Give every entry a lifetime and let it die on its own. One argument on the set, nothing to wire up — and wrong for up to a whole TTL after every write. Shortening the TTL to fix that throws away hit rate.

Delete on write

Whoever changes the row deletes the key, so the wrong window shrinks to milliseconds. It only covers the paths you remember: a job or an admin tool writing straight to the database will not, and nothing tells you.

Versioned keys

Put something that changes on every write into the key, like product:42:v7 or the row's updated_at. The old key becomes unreachable rather than wrong — nothing to delete, no race — but you need the version before you can build the key.

Two things fall out. Hit rate is the whole feature: 90% to 50% costs four times the latency and five times the database load. And the last row is the cache stampede — in the 20 ms the first reader takes to refill a hot key, 40 more find it missing and go to the database for the same row.

  • Speed vs truth. Every cache serves what was true a moment ago. You choose how long a moment may be.
  • Long TTL vs short TTL. Long keeps the hit rate up and the staleness window open; short does the opposite. A very short TTL is a slow database with extra parts. Caching everything costs memory, while the hot few per cent usually gets most of the win.
  • Delete on write vs let it expire. Deleting is nearly always right, and has to be wired into every write path. Expiring is one line and wrong more often.
  • One more thing to break. If a Redis outage takes the site down with it, the cache stopped being an optimisation and became a dependency.

Reach for it when

  • The same answers are asked over and over, and reads heavily outnumber writes — a product page read 10,000 times and edited once a week.
  • The answer is expensive: a big join, an external API call, a rendered page.
  • Being a few seconds out of date costs nothing anyone notices.

You don't need one when

  • The query is already fast. A 1 ms indexed lookup needs no 0.5 ms cache in front of it.
  • Every read must be exact. Account balances, stock at checkout, anything a decision is made on.
  • Writes are as common as reads. Invalidation costs more than the reads save.
  • Nobody asks twice. A per-user feed nobody reloads has nothing to hit.
  • Writing the new value into the cache instead of deleting it. Two writers can finish in one order and set in the other, leaving the older value cached. Delete and let the next reader refill.
  • No TTL behind the delete. One missed invalidation, from a job or a manual UPDATE, is wrong forever. A TTL turns “forever” into “five minutes”.
  • The same TTL on everything. Fill a cache in one batch and it empties in one batch. Add a random spread, 300 seconds plus up to 60, so they expire apart.
  • Ignoring the stampede. Those 40 queries for one row arrive exactly when the key is hottest. Let one request refill while the rest wait or serve the old value.
  • Caching failures. A null from a timeout, cached for five minutes, turns a blip into an outage.
  • Keys with no shape. Without a prefix and a version you can't clear one kind of entry, and a deploy that changes the JSON breaks every reader holding the old shape.

Common questions

  • Why is invalidation hard? The cache has no idea the data changed. Something outside it must catch every write on every path, and missing one is silent.
  • Delete the key or update it? Delete — two writes can set in the wrong order, and deleting has no such race.
  • What is a cache stampede? A hot key expires and every request in the refill window hits the database at once. Fix it with a lock so one request refills, or serve the stale value meanwhile.
  • Cache-aside or write-through? Cache-aside keeps the cache out of the write path and survives a cache outage. Write-through keeps the two in step, but every write now depends on the cache.

Follow-ups to expect

  • How would you measure the hit rate, and what would you do at 40%?
  • What happens to your service when Redis goes down?

How it fits a bigger design

Caching is the second answer, not the first: fix the query and the index first, because a cache in front of a bad query hides it until the day the cache is cold. When it does go in, every write path has to know about it — which is why “who invalidates this?” is a fair question about any box with a cache next to it.

  • A cache is a copy of an expensive answer kept somewhere fast; invalidation is dropping that copy when the real data changes. The design question is not whether to cache, but how stale the answer may be.
  • Cache-aside means the app checks the cache, and on a miss queries the database and fills the cache.
  • On a write, update the database first, then delete the key. Overwriting it lets two racing writers leave the older value behind.
  • Three ways to invalidate: a TTL, a delete on write, or a version in the key so old entries can't be found. Most systems do the second with the first underneath.
  • Hit rate is the whole feature: 90% hits gave 2.5 ms and 200 queries/s, 50% gave 10.5 ms and 1,000.
  • When a hot key expires, every request during the refill hits the database — 40 in the example. That is a cache stampede.
  • Give every entry a TTL with some random spread, never cache a timeout for long, and put a prefix and a version in every key.
  • Skip it when the query is already fast, when reads must be exact, or when writes are as common as reads.
