Every part fails sooner or later. Disks die, servers crash, a data centre loses power. You can’t stop that; you can decide what happens next.

  • Redundancy: having more of something than the job needs, so there is a spare.
  • Fault tolerance: what you want from those spares — a part fails and the system keeps working. A fault is one part going wrong; a failure is the user noticing.
  • High availability: the measured version, up 99.99% of the time, with a short blip allowed while a spare takes over. Strict fault tolerance allows no blip and costs far more.
  • Single point of failure: any part whose death takes everything down, because there is no second one.

One-line version: redundancy is having spares, fault tolerance is carrying on when a part dies — and a spare only helps if the same problem can’t reach it, and if the switch to it works.

One server, one database, working fine — until the disk dies and you spend hours restoring last night’s backup with today’s data gone. Or every deploy takes the app down for a minute. The more parts a system has, the more often one is broken: at a hundred servers, a failure isn’t an accident, it’s a normal week.

But spares cost money while doing nothing, and the switch to them is new machinery that can fail too. So the question is: which failures must users never notice, how long may the rest last, and what will we pay?

How a hospital handles a power cut.

  • The generator in the basement does nothing until the mains fail, then takes about half a minute to start. One source works, a second waits: a standby.
  • The batteries in the operating theatre are always connected and take over instantly. Half a minute of dark is fine in a corridor, not mid-operation. That is high availability against strict fault tolerance — and the hospital only pays for the second where it matters.
  • The nurses. A ward needs four, so five are on the rota. All five work. Nobody is “the spare”, there is just one more than needed.
  • The patient notes. One ward writes on carbon-copy pads and files the copy immediately — slower, but the folders always match. Another has a clerk copy the day’s notes each evening — faster, but a folder lost at 4 pm takes the day with it.

The costs are in the story. The generator runs a few hours a year for a lot of money, and won’t start on the day unless someone tests it monthly. If it sits in the same basement as the switchboard, one flood takes both — two sources, one failure. And something has to notice the cut and flip the switch.

A product page shows the product, read from PostgreSQL, and a row of “you may also like” from a recommendations service. Without the product there is no page. Without recommendations the page is still useful. So they get protected differently.

// product-page.service.ts
// Redundancy: if the first copy can't answer, ask the second.
private async readProduct(id: string) {
  const sql = 'SELECT id, name, price FROM products WHERE id = $1';
  try       { return (await this.primary.query(sql, [id])).rows[0]; }
  catch     { return (await this.replica.query(sql, [id])).rows[0]; }
}

// Graceful degradation: no spare, so give a smaller answer.
private async readRecs(id: string): Promise<string[]> {
  try {
    const res = await fetch(url, { signal: AbortSignal.timeout(300) });
    return res.ok ? await res.json() : [];
  } catch { return []; }
}

The primary takes writes; the replica gets a copy of every change. Giving a smaller answer when a part is missing is graceful degradation. The timeouts matter: a dead server refuses instantly, a sick one hangs, and without a limit the spare never gets asked.

What got harder: the replica may lag (fine for a product page, not for a balance); this covers reads only, since writing again needs failover; and the page keeps working while the primary has been down for two days, so every fallback needs an alert.

Having the spare is the easy half. The switch is the other half: a primary in one zone, a standby in another (a zone is a separate building with its own power and network).

  1. Normal running. Clients reach a proxy, which gives the database one fixed address and sends everything to the primary. The primary copies each write to the standby.
  2. Watching. Monitors send an “are you alive?” heartbeat every 2 seconds.
  3. Deciding. One missed beat could be a hiccup, so the monitors wait for three, then vote. With three monitors, two must agree — a quorum, so one confused monitor can’t start a failover alone.
  4. Fencing. Cut the old primary off before anything else. If it wasn’t dead, only unreachable, and it comes back while the standby takes writes, you get two primaries with different data: split brain, which is worse than being down.
  5. Promoting and redirecting. The standby becomes primary, the proxy points at it, and clients retry what failed in the gap.

The monitors and the proxy are now critical parts too, so each needs copies. And the gap is never zero — those steps take seconds at best. Stateless servers are easy: a health check spots a dead one and traffic goes elsewhere. Data is the hard case, because the spare must hold what the dead one held.

Active-passive keeps one in charge — what a database needs — and pays double for an idle machine that may be quietly broken. Active-active sizes as N+1 (one more than carries the peak), wastes less and is tested all day by real traffic, but only works if the survivors have room: two servers at 80% are not redundant, because losing one asks the other for 160%.

Where copies live matters as much as how many. A problem hitting several at once is a correlated failure: different machines cover a dead disk, racks a failed switch, zones a building outage, regions a flood. Some causes ignore distance — a bad deploy breaks every copy.

Assumptions, made up: every part on its own is up 99.9%, and failures are unrelated until we say otherwise. A year is 8,760 hours.

  • In a row, availability multiplies: 0.999³ = 99.7%, about 26 hours a year. Three good parts in a row are worse than any one.
  • Side by side, only the failures multiply: 0.001 × 0.001, so a pair is up 99.9999% — 32 seconds a year. For n copies: 1 − (1 − a)n.
  • All three layers doubled: 99.9997%, about 1.6 minutes a year. On paper.

Why reality is worse. Switching takes time: 6 s to notice, 20 s to fence and promote, 5 s to reconnect — 31 seconds a failover. Four a year already beats the 1.6 minutes the formula promised, though it still beats four 2-hour restores.

And failures share causes. If a tenth of each server’s down time is shared, both are down together 0.0001 of the time whatever the formula says: 99.99%, 53 minutes a year, not 32 seconds. A third copy on the same deploy changes almost nothing.

Cost: N+1 on four servers is 25% more; an active-passive pair is 100% more for the same protection. A standby 200 ms behind at 500 writes/s loses about 100 confirmed writes. RTO is how long you may be down, RPO how much data you may lose.

  • Availability vs cost. Every nine costs more than the last. One copy to two removes most down time; two zones to two regions can double the bill for a failure that comes once in years.
  • Availability vs complexity. Heartbeats, quorums, fencing and failover are machinery, and machinery breaks. A bad failover causes more outages than it prevents.
  • No lost data vs fast writes. Synchronous never loses a confirmed write, but every write waits and a sick standby can block the primary.
  • Fast failover vs false alarms. Act on one missed heartbeat and you fail over on every hiccup. Wait for ten and real outages last longer.
  • Automatic vs manual. Automatic is fast and works at 3 am. A wrong call means split brain. Manual is slower and safer.
  • A spare vs doing less. Not everything needs a second copy. For parts users can live without, graceful degradation is cheaper.

Signals you need it:

  • Down time costs money or trust by the minute: payments, checkout, login.
  • You promised an uptime number in a contract.
  • Deploys cause down time, because there is one server.
  • Losing the data would end the business.

To start, draw one request’s path and mark every box there is only one of. Fix the one whose failure costs most — usually the database.

When you don’t need it: an internal tool used in office hours; a batch job you can run again; a new product with few users, where one managed database with backups is a fair start; a part users can do without, which should degrade instead. Keep backups either way — a spare protects against a part dying, a backup against losing the data.

  • Never testing the switch. A failover that has never run is a guess, like the generator nobody starts. Fail over on purpose, on a normal working day.
  • Both copies in the same place. Two servers in a rack, two databases in a zone, every copy on the same deploy. Spread them, and roll changes to one copy first.
  • Treating a replica as a backup. A replica copies mistakes too — drop a table and it’s gone everywhere a moment later. Keep real point-in-time backups and test the restore.
  • Spares with no room. Two servers at 80% look redundant and aren’t. Size for the peak with one copy missing.
  • Missing the hidden single points. One DNS provider, one config store, one deploy tool, one person who knows how failover works.
  • Failover with no fencing. The old primary wasn’t dead, just unreachable, and now the data splits.
  • Fallbacks that hide the problem. Running on the spare for weeks unnoticed means the next failure is an outage. Alert whenever a spare is in use.

Common questions

“How would you make this design highly available?”
Walk the request path and name each single point of failure. Stateless parts: N+1 behind a load balancer across zones. Database: primary plus standby in another zone, automatic failover. Then say what you are not covering, like a whole region.

“Redundancy, fault tolerance, high availability?”
The means (spare parts), the property (keeps working), the measured goal (up 99.9x%, short gaps allowed).

“What does 99.99% mean?”
About 52 minutes a year. Parts in a row multiply, so every layer must beat the target: two of everything in different zones, a tested failover, careful rollouts.

Follow-ups to expect

  • What is split brain, and how do you stop it? (Fencing, plus a quorum so only a majority can promote.)
  • Why three monitors, not two? (A majority needs an odd number.)
  • What if a whole region goes down? (A copy elsewhere, asynchronous, with a slower manual switch.)
  • How do you know failover works? (You run it on purpose, regularly.)

How it fits a bigger design

It shows up twice: when you draw the boxes, saying each is several copies and where they live, and in “what can go wrong”, saying what users see when each dies. The strong move is treating parts differently — which get spares, which degrade, and which failures you live with.

  • Redundancy is spare parts; fault tolerance is carrying on; high availability is the measured uptime with short gaps allowed.
  • A single point of failure is any part there is only one of.
  • Active-passive keeps a spare waiting and needs a switch. Active-active has every copy working, sized N+1 or N+2.
  • Failover: notice with heartbeats, decide by majority, fence the old primary, promote the spare, redirect. Skipping the fence risks split brain.
  • Synchronous copies lose no confirmed write but slow every write; asynchronous copies are fast and can lose the last moments.
  • Parts in a row multiply (0.999³ = 99.7%); copies side by side give 1 − (1 − a)n.
  • Real numbers are worse, because switching takes time and failures share causes.
  • Copies in the same rack, zone or deploy are not really separate copies.
  • A replica is not a backup, and an untested failover is a guess.
