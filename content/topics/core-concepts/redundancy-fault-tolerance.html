Every part of a system fails sooner or later. Disks die, servers crash, network cables get cut, a whole data centre loses power. You can’t stop that. What you can decide is what happens next.

Redundancy means having more of something than you need to do the job, so there is a spare when one breaks. Two servers where one would do. Three copies of the data. Two network links.

Fault tolerance is the result you want from those spares: a part fails, and the system keeps working. A fault is one part going wrong. A failure is the user noticing. Fault tolerance is about stopping the first from becoming the second.

A third term gets mixed in. High availability means the system is up almost all the time, measured as a percentage like 99.99%. It allows a short blip while a spare takes over. Strict fault tolerance allows no blip at all, and costs a lot more. Most web systems aim for high availability and call it fault tolerance.

The enemy has a name: a single point of failure. That is any one part whose failure takes down everything, because there is no second one.

One-line version: redundancy is having spares, fault tolerance is carrying on when a part dies, and the spare only helps if it is somewhere the same problem can’t reach, and if the switch to it works.

Say your app runs on one server with one database. It works well. Then one of these happens:

  • The server’s disk dies. The app is down until someone sets up a new machine and restores last night’s backup. That is hours, and today’s data is gone.
  • You deploy a new version. The app is down for a minute, every time.
  • The data centre has a network problem. Nothing you can do but wait.

With one of everything, each of those is an outage. And the more parts a system has, the more often one of them is broken. At a hundred servers, a failure is not an accident. It is a normal week.

Spares fix this, but they are not free. A spare costs money while it does nothing, and the switch to it is new machinery that can go wrong too. So the real question for a designer is: which failures must users never notice, how long may the others last, and how much are we willing to pay for that?

Think about how a hospital deals with a power cut.

The backup generator. The hospital runs on mains power. A diesel generator sits in the basement doing nothing. When the mains fail, the generator starts and takes over. It takes about half a minute to get going. This is a standby: one source does the work, a second one waits.

The battery in the operating theatre. Half a minute of darkness is fine in a corridor. It is not fine in the middle of an operation. So the theatre also has batteries that are always connected and take over in an instant. That is the difference between high availability (a short gap) and strict fault tolerance (no gap). The hospital only pays for the second one where it matters.

The nurses. A ward needs four nurses on a shift. The hospital puts five on the rota. All five work. If one is off sick, the ward still runs. Nobody is “the spare”. There is just one more than needed.

The patient notes. In one ward, every note is written on a pad that makes a carbon copy, and the copy is filed before the nurse moves on. Slower, but the two folders always match. In another ward, a clerk copies the day’s notes into the archive each evening. Faster for the nurses, but a folder lost at 4 pm takes that day’s notes with it.

The costs show up in the story too:

  • The generator cost a lot and runs for a few hours a year.
  • If nobody starts it once a month to test it, it won’t start on the day it is needed.
  • If the generator sits in the same basement as the mains switchboard, one flood takes out both. Two sources, but one failure.
  • Something has to notice the power cut and flip the switch. If that switch is broken, the generator is useless.

Take a product page in an online shop. It shows two things: the product itself, read from PostgreSQL, and a row of “you may also like” items from a separate recommendations service.

Without the product there is no page. Without recommendations, the page is still useful. So we protect them in two different ways.

  • The product data has a spare. The database has a primary, the copy that takes writes, and a replica, a second server that receives a copy of every change. If the primary can’t answer, we read from the replica.
  • The recommendations have no spare. If that service is slow or down, we show the page without them. Giving a smaller answer when a part is missing is called graceful degradation.
// product-page.service.ts
import { Injectable } from '@nestjs/common';
import { Pool } from 'pg';

@Injectable()
export class ProductPageService {
  // Two copies of the same data, on servers in different places.
  private primary = new Pool({
    host: process.env.DB_PRIMARY_HOST,
    connectionTimeoutMillis: 500,
    statement_timeout: 1000,
  });
  private replica = new Pool({
    host: process.env.DB_REPLICA_HOST,
    connectionTimeoutMillis: 500,
    statement_timeout: 1000,
  });

  async getPage(productId: string) {
    const product = await this.readProduct(productId);          // must work
    const recommendations = await this.readRecs(productId);     // nice to have
    return { product, recommendations };
  }

  // Redundancy: if the first copy can't answer, ask the second.
  private async readProduct(id: string) {
    const sql = 'SELECT id, name, price FROM products WHERE id = $1';
    try {
      return (await this.primary.query(sql, [id])).rows[0];
    } catch {
      return (await this.replica.query(sql, [id])).rows[0];
    }
  }

  // Graceful degradation: no spare, so give a smaller answer.
  private async readRecs(id: string): Promise<string[]> {
    try {
      const url = `${process.env.RECS_URL}/products/${id}`;
      const res = await fetch(url, { signal: AbortSignal.timeout(300) });
      return res.ok ? await res.json() : [];
    } catch {
      return [];
    }
  }
}

The timeouts matter. A dead server refuses the connection at once, but a sick one may hang for a minute. Without a time limit, the spare never gets asked.

Notice what is now harder:

  • The replica may be a moment behind. Fine for a product page. Maybe not for an account balance.
  • This only covers reads. A replica can’t take writes. To keep writing after the primary dies, the replica has to be turned into the new primary. That is failover, and it is the subject of the next section.
  • Problems get hidden. The page keeps working, so nobody notices the primary has been down for two days. Every fallback needs an alert.
  • There are two code paths to test. The fallback runs once a year, on the worst day.

Redundancy has two halves. The first is having the spare. The second is the switch: noticing the failure and moving the work across. Here is that switch for a database with a primary in one zone and a standby in another. A standby is a replica kept ready to take over. A zone is a separate data centre building in the same city, with its own power and network.

  1. Normal running. Clients talk to a proxy, which gives the database one fixed address. The proxy sends everything to the primary. The primary sends a copy of every write to the standby.
  2. Watching. A set of monitors sends a small “are you alive?” message to both databases every 2 seconds. This is a heartbeat.
  3. The primary dies. Its heartbeats stop being answered.
  4. Deciding. One missed heartbeat could be a network hiccup. So the monitors wait for three in a row, then vote. With three monitors, two must agree. This majority is called a quorum. It stops one confused monitor from starting a failover by itself.
  5. Fencing. Before anything else, the old primary is cut off so it can’t accept writes any more. This is fencing. Maybe it wasn’t dead, only unreachable. If it comes back while the standby is also taking writes, you have two primaries with different data. That is split brain, and it is worse than being down.
  6. Promoting. The standby is told it is now the primary and starts accepting writes.
  7. Redirecting. The proxy starts sending traffic to the new primary. Clients keep using the same address.
  8. Catching up. Requests that failed in the gap are retried by the clients. Later, a fresh standby is built. Until it is ready, there is no spare.

The monitors and the proxy are now critical parts too, so each needs more than one copy. And the gap is not zero: steps 3 to 7 take seconds at best.

The “Load Balancer” topic shows the same idea for stateless servers, where it is much easier: health checks spot a dead server, and traffic just goes to the others. Data is the hard case, because the spare has to hold the same data as the one that died.

There are two questions here. How do the spares share the work? And for data, how does the copy stay up to date?

1. Active-passive

How it works: one copy does all the work. A second one waits and takes over when the first fails. The waiting one can be hot (running and up to date, takes over in seconds), warm (running but needs to catch up, takes minutes), or cold (switched off, takes much longer).

When to use it: when only one copy may be in charge at a time. A database primary is the usual case.

Good: there is never a question of who is in charge.

Bad: you pay double and half of it sits idle. The switch takes time. And the idle side can be broken without anyone knowing.

2. Active-active

How it works: every copy does real work all the time. When one dies, the rest pick up its share. You size it as N+1: if N copies can carry the peak, run one more. N+2 lets you lose one during a deploy and another to a crash.

When to use it: for parts that keep no data of their own between requests, like API servers and proxies.

Good: no idle spare, and every copy is tested all day by real traffic. It is cheaper too: one extra on top of four is 25% more, not 100%.

Bad: it only works if the others have room. Two servers each at 80% are not redundant: when one dies, the other is asked for 160%. For data it is hard, because two copies taking writes at once can disagree.

3. Synchronous replication

How it works: the primary sends each write to the standby and waits for it to say “saved” before telling the client “done”.

When to use it: for data you can’t lose even one confirmed write of. Payments, orders.

Good: a write the client was told about is on two machines. Failover loses nothing that was confirmed.

Bad: every write waits for a network trip. And if the standby is down, the primary must either stop taking writes or quietly stop waiting. The spare can now cause an outage.

4. Asynchronous replication

How it works: the primary says “done” to the client straight away, and sends the write to the standby a moment later.

When to use it: when speed matters more than the last second of data, and for far-away copies.

Good: writes are as fast as with no standby, and a dead standby doesn’t hurt the primary.

Bad: the standby is always a little behind. If the primary dies, the writes it hadn’t sent yet are lost, even though clients were told they were saved.

Where the copies live matters as much as how many

Two copies only count as two if one problem can’t hit both. A problem that takes out several copies at once is a correlated failure. So spread the copies out:

  • Different machines cover a dead disk or a crashed server.
  • Different racks cover a failed power strip or network switch.
  • Different zones cover a building losing power or network.
  • Different regions, meaning cities far apart, cover a flood or a whole cloud region going down. At that distance the copy is usually asynchronous.

Some shared causes ignore distance. A bad deploy or config change sent to every copy at once breaks every copy at once.

Assumptions (made up for this example, not measurements): every single part, on its own, is up 99.9% of the time. Failures of different parts have nothing to do with each other, until we say otherwise.

What the percentages mean

Availability is counted in “nines”. A year has 8,760 hours.

AvailabilityCalledDown time in a year
99%two nines3.65 days
99.9%three nines8.76 hours
99.99%four nines52.6 minutes
99.999%five nines5.3 minutes

Parts in a row make it worse

A request goes through a load balancer, then an app server, then a database. One of each. If any of the three is down, the request fails. So you multiply:

  • 0.999 × 0.999 × 0.999 = 0.997, which is 99.7%.
  • Down time: 0.3% of 8,760 hours ≈ 26 hours a year.

Three good parts in a row give a system worse than any one of them.

Parts side by side make it better

Now run two app servers, where either one can do the job. The pair is only down when both are down at the same moment. One server is down 0.1% of the time, which is 0.001.

  • Both down: 0.001 × 0.001 = 0.000001.
  • So the pair is up 1 − 0.000001 = 99.9999%. That is about 32 seconds a year, down from 8.76 hours.
  • The general rule for n copies: 1 − (1 − a)n, where a is how often one copy is up.

Do that at all three layers and multiply again: 0.999999 × 0.999999 × 0.999999 ≈ 99.9997%, about 1.6 minutes a year. From 26 hours to under 2 minutes, on paper.

Why real systems don’t reach that

The switch takes time. For the database in the last section: 3 missed heartbeats at 2 seconds is 6 seconds. Say fencing and promoting take 20 seconds, and clients reconnecting takes 5.

  • One failover: 6 + 20 + 5 = 31 seconds.
  • Four of those a year: 4 × 31 = 124 seconds. That alone is more than the 1.6 minutes the formula promised for the whole system.
  • Still, compare it with no standby: four failures at 2 hours each to restore from backup is 8 hours.

Failures are not independent. Say one tenth of each server’s down time comes from something shared, like a bad deploy that hits both. That is 0.0001 of the time when both are down together, whatever the formula says.

  • Both down: 0.0001 (shared) + 0.0009 × 0.0009 (separate) ≈ 0.0001.
  • So the pair is up about 99.99%: 53 minutes a year, not 32 seconds. That is 100 times worse.

Once you have two copies, shared causes are almost all of your down time. A third copy on the same deploy changes nearly nothing.

What the spare costs, and what can be lost

  • Four servers carry the peak. With N+1 you run 5: 25% more cost, and each runs at 80% at peak. With N+2 you run 6: 50% more, each at 67%.
  • An active-passive pair is 100% more for the same protection against one failure.
  • With an asynchronous standby that is 200 milliseconds behind, at 500 writes a second, a failover loses about 0.2 × 500 = 100 writes that clients were told were saved.

Two of these have names. RTO, recovery time objective, is how long you may be down: the 31 seconds. RPO, recovery point objective, is how much recent data you may lose: the 100 writes.

  • Availability vs cost. Every nine costs more than the last. Going from one copy to two removes most of the down time. Going from two zones to two regions can double the bill for a failure that may come once in years.
  • Availability vs complexity. Failover, heartbeats, quorums and fencing are all extra machinery, and machinery breaks. A badly built failover causes more outages than the failures it was meant to cover.
  • No lost data vs fast writes. Synchronous copies never lose a confirmed write, but every write is slower and a sick standby can block the primary. Asynchronous copies are fast and can lose the last moments.
  • Fast failover vs false alarms. Declare a server dead after one missed heartbeat and you fail over on every network hiccup. Wait for ten and users are down for longer on a real failure.
  • Automatic vs manual failover. Automatic is fast, and works at 3 am. But a wrong call can mean split brain. Manual is slower and safer.
  • Active-active vs active-passive. Active-active wastes less and is always tested. It needs parts that can share the work, which is easy without data and hard with it.
  • A spare vs doing less. Not every part needs a second copy. For things users can live without for a while, graceful degradation is cheaper than redundancy.

Signals that you need it

  • Being down costs real money or trust by the minute: payments, checkout, login.
  • You have promised customers an uptime number in a contract.
  • Deploys cause down time, because there is only one server to restart.
  • Losing the data would end the business. Then data needs several copies, in more than one place, before anything else does.
  • You run enough machines that one of them is broken most weeks.

To start, draw the path of one request and mark every box there is only one of. Fix the one whose failure costs most. Usually that is the database.

When you don’t need it

  • An internal tool used in office hours. An hour of down time a few times a year is fine. Good backups and a tested restore are enough.
  • A batch job that can simply run again. If it fails, start it again. Nothing has to stay up.
  • A new product with few users. One server and one managed database with backups is a fair start. Add spares when down time starts to cost something.
  • A part users can do without. Degrade instead, like the recommendations in the example.

Even then, keep backups. A spare protects against a part dying. A backup protects against losing the data. They are not the same thing.

  • Never testing the switch. A failover that has never run is a guess. It fails on the day you need it, like the generator nobody started. Fix: fail over on purpose, on a normal working day, on a schedule.
  • Putting both copies in the same place. Two servers in one rack, two databases in one zone, every copy on the same deploy at the same moment. One problem takes them all. Fix: spread copies across zones, and roll changes out to one copy first.
  • Treating a replica as a backup. A replica copies everything, mistakes included. Delete a table by accident and it is gone from every replica a moment later. Fix: keep real backups that you can restore to an earlier point in time, and test the restore.
  • Spares with no room. Two servers each at 80% look redundant and are not. When one dies, the other falls over too. Fix: size for the peak with one copy missing.
  • Missing the hidden single points. You doubled the servers and the database. But there is still one DNS provider, one config store, one deploy tool, or one person who knows how failover works. Fix: follow the whole request path, and the path of a deploy too.
  • Failover with no fencing. The old primary was only cut off, not dead. Now two primaries accept writes, and the data splits. Fix: always cut off the old one before promoting the new one.
  • Fallbacks that hide the problem. The system runs on its spare for weeks and nobody knows. The next failure is an outage. Fix: alert every time a spare is in use.

Common questions

“How would you make this design highly available?”
Walk the request path and name each single point of failure. For parts with no data, run N+1 behind a load balancer across two or three zones. For the database, a primary and a standby in another zone, with automatic failover. Then say what you are not covering, like a whole region going down, and why.

“What is the difference between redundancy, fault tolerance and high availability?”
Redundancy is the means: spare parts. Fault tolerance is the property: the system keeps working when a part fails. High availability is the measured goal: up for some percentage of the time, with short gaps allowed during a switch.

“What does 99.99% mean, and how would you get there?”
About 52 minutes of down time a year. Parts in a row multiply, so every layer has to beat the target. That means two of everything in different zones, a tested failover, and careful rollouts, because shared causes like bad deploys become the main source of down time.

Follow-ups to expect

  • What is split brain, and how do you stop it? (Two primaries at once. Fencing, and a quorum so only a majority can promote.)
  • Why three monitors and not two? (With two, a tie can’t be broken. A majority needs an odd number.)
  • What are RTO and RPO? (How long you may be down, and how much recent data you may lose.)
  • What if the whole region goes down? (A copy in a second region, usually asynchronous, with a slower and often manual switch.)
  • How do you know failover works? (You run it on purpose, regularly.)
  • Synchronous or asynchronous copies? (It depends on how much data you may lose. No confirmed write: synchronous. A second of data: asynchronous.)

How it fits a bigger design

In a system design interview, this shows up twice. When you draw the boxes, say once that each box is several copies and where they live. Then in the “what can go wrong” part, go through the boxes and say what the user sees when each one dies. The “Load Balancer” and “Notification Service” designs both do this in a table.

The strong move is to treat parts differently: which get spares, which degrade, and which failures you have decided to live with.

  • Redundancy is having spare parts. Fault tolerance is the system carrying on when a part fails. High availability is being up nearly all the time, with short gaps allowed.
  • A single point of failure is any part there is only one of, whose failure takes everything down.
  • Active-passive keeps a spare waiting and needs a switch. Active-active has every copy working, sized as N+1 or N+2, and needs room for the others to take the load.
  • Failover is: notice with heartbeats, decide by majority, cut off the old primary, promote the spare, redirect traffic. Skipping the cut-off risks split brain.
  • Synchronous copies lose no confirmed write but slow every write. Asynchronous copies are fast and can lose the last moments.
  • Parts in a row multiply, so three 99.9% parts give 99.7%. Parts side by side give 1 − (1 − a)n, so two 99.9% copies give 99.9999% on paper.
  • Real numbers are worse, because the switch takes time and failures share causes. Copies in the same rack, zone or deploy are not really separate.
  • Not everything needs a spare. Graceful degradation gives a smaller answer when a part is missing.
  • A replica is not a backup, and a failover that has never been tested is a guess.
