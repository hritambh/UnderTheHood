Normal HTTP goes one way: the browser asks, the server answers, the conversation ends. The server can’t start one on its own.

That’s a problem when the server has new information you should see now: a chat message, a live score, “your order is out for delivery”. There are four common ways around it.

  • Short polling: the browser asks “anything new?” every few seconds.
  • Long polling: the browser asks, and the server holds the request open until it has news.
  • Server-Sent Events (SSE): one long HTTP connection the server keeps writing updates to. Server to browser only.
  • WebSockets: one long connection where both sides can send at any time.

One-line version: polling = “keep asking”, SSE = “server keeps talking”, WebSocket = “both keep talking”.

Users expect apps to feel live. If a teammate sends you a message, you expect it in about a second, not after a refresh.

The four options differ mostly in what they waste:

  • Polling too often wastes server work. Most replies are empty.
  • Polling too rarely makes updates feel slow.
  • Long-lived connections remove the waste, but each one holds memory on a server, and they are harder to load balance.

So the real question is: how fresh must the data be, which direction does it flow, and how many users are connected at once?

You ordered food at a busy counter and you’re waiting.

  • Short polling: every 30 seconds you walk up and ask “ready yet?” Usually: no. Your time and theirs, wasted.
  • Long polling: you ask once, and the staff say “wait here, I’ll tell you the moment it’s ready”.
  • SSE: a screen shows order numbers as they’re ready. It talks to you; you can’t talk back through it. To order again you walk to the counter (a normal HTTP request).
  • WebSocket: you have a walkie-talkie with the kitchen. Either side speaks whenever.

The costs show up in the story too. A walkie-talkie per customer is great for chatting, but the kitchen has to keep every one of them switched on. The screen is cheap because information only flows one way.

A food-delivery app on NestJS has two live features, and they want different tools:

  1. Order status (“Preparing” → “Out for delivery”). Server pushes, browser listens. That’s SSE.
  2. Chat with the driver. Both sides send often. That’s WebSockets.
// orders.controller.ts  — GET /orders/123/events
@Sse(':id/events')
stream(@Param('id') id: string): Observable<MessageEvent> {
  return this.orderEvents.forOrder(id).pipe(
    map(status => ({ data: { status } }))
  );
}
// browser — EventSource reconnects by itself if the link drops
const source = new EventSource('/orders/123/events');
source.onmessage = (e) => showStatus(JSON.parse(e.data).status);
// chat.gateway.ts — both sides send, so a socket fits
@SubscribeMessage('chat:send')
onMessage(@MessageBody() msg: { orderId: string; text: string }) {
  this.server.to('order:' + msg.orderId).emit('chat:new', msg);
}

NestJS gateways use Socket.IO by default. That’s a library on top of WebSockets (rooms, auto reconnect, polling fallback), so a plain browser WebSocket can’t talk to it. There is a raw ws adapter if you want the plain thing.

What each one actually does on the wire:

  1. Short polling. Browser sends a normal GET. Server replies at once, even with nothing new. Browser waits N seconds and repeats.
  2. Long polling. Browser sends a GET. The server holds it open until there is news or a timeout (say 30 s), replies, and the browser immediately asks again.
  3. SSE. Browser opens a GET with EventSource. The server replies Content-Type: text/event-stream and never finishes the response, writing data: {...} blocks as news arrives. On a drop the browser reconnects itself, and sends Last-Event-ID so your server can resend what was missed.
  4. WebSocket. Browser sends an HTTP request with Upgrade: websocket (the handshake). The server replies 101 Switching Protocols and the connection stops being HTTP. Both sides then send frames, with ping/pong frames to spot dead links. Nothing reconnects on its own.

Two questions pick the option for you: which way does the data flow, and how fresh must it be?

  • Short polling: a timer calls a normal API. Works everywhere, stateless, easy to cache. Costs: empty requests, and up to N seconds of delay.
  • Long polling: mostly a fallback when the others are blocked by old proxies. Low delay, plain HTTP, but the server must buffer anything that arrives between one reply and the next request.
  • SSE: plain HTTP, so normal auth and HTTP/2 just work, and reconnect is built in. One direction, text only. EventSource can’t set an Authorization header, so people use cookies or a fetch-based SSE library.
  • WebSocket: two-way, cheap per message, handles binary. You build reconnect, heartbeats and “resend what I missed” yourself, and some corporate proxies interfere.

Assumptions, made up for this example, not benchmarks: 10,000 users online, each getting 1 real update per minute.

Short polling every 5 seconds

  • 10,000 users ÷ 5 s = 2,000 requests/s.
  • Useful updates = 10,000 ÷ 60 ≈ 167/s.
  • So over 90% come back empty, and each one still costs auth, routing and maybe a query.
  • Average delay 2.5 s, worst case 5 s. Polling every second makes it 10,000 requests/s.

SSE or WebSocket

  • 10,000 open connections, 167 messages/s, all useful, delay under a second.
  • The new cost is memory per connection. How many one Node.js server holds depends on memory, message rate and per-connection state — load test it, don’t trust a number from a blog.

Run 4 servers with 2,500 connections each and a new problem appears: user A on server 1 messages user B on server 3. Server 1 doesn’t hold B’s connection, so servers need a shared channel like Redis pub/sub to pass it along.

  • Simplicity vs freshness. Polling is the simplest and stateless, but it either wastes requests or feels slow.
  • One-way vs two-way. SSE is simpler because it stays plain HTTP. If the browser mostly listens, SSE plus normal POSTs is usually enough.
  • Stateless vs stateful servers. With polling any server answers. With SSE and sockets a user is tied to one server, so every deploy drops their connection.
  • Speed vs delivery. None of these guarantee delivery. Messages sent while a user is away are lost unless you store them and replay by event id.
  • Your code vs your infrastructure. Load balancers and gateways close idle connections and sometimes buffer streams, so long connections need heartbeats and the right settings.
  • Short polling: data changes once a minute or less, or you need something working today.
  • SSE: server pushes, browser listens. Notifications, order tracking, build logs, streaming AI tokens.
  • WebSocket: both sides send often, or you need binary. Chat with typing indicators, games, shared whiteboards.
  • Long polling: a fallback when the others are blocked.

When you don’t need real-time at all: if users stay on a page briefly, or the data changes hourly, a refresh button or 60-second polling is fine. Don’t run socket infrastructure for a report that updates once an hour.

On mobile, the system stops your connections once the app is in the background. Reaching those users needs push notifications (APNs, FCM), not sockets.

  • Reaching for WebSockets by default. If data flows one way, SSE is simpler and enough.
  • No reconnect logic. Connections drop on Wi-Fi changes, deploys and timeouts. Plain sockets need your own reconnect with backoff.
  • Forgetting missed messages. After reconnecting the client should ask “what did I miss since id X?”, or users silently lose updates.
  • No heartbeats. A dead connection looks open for a long time. Ping/pong frames, or SSE comment lines starting with :, catch it.
  • Several servers with no shared channel. Works on one dev machine, breaks in production.
  • Proxy buffering SSE. Nginx buffers responses by default, so events arrive in delayed chunks. Turn it off for those routes (proxy_buffering off, or the X-Accel-Buffering: no header).
  • Checking auth only at the handshake. Check permissions on every message and room join too.

Common questions

“How would you build live notifications?”
SSE: the server pushes, the browser listens. Store notifications in the database as well, so a user who was offline can fetch what they missed, and use Redis pub/sub so any server can reach any user.

“Design a chat app.”
WebSockets, because both sides send often. Save the message first, publish it to the recipient’s server, forward it on their socket, and fall back to a push notification if they are offline.

“Why not just poll?”
Fine at small scale. At 10,000 users it is 2,000 requests/s for 167 useful updates. Show the maths.

Follow-ups to expect

  • How do you load balance sockets? (Any server accepts the connection; a shared pub/sub routes messages. Sticky sessions only if the library needs them.)
  • What happens during a deploy? (Everything drops. Clients reconnect with jitter and fetch what they missed.)
  • How do you know a user is online? (Track connections in Redis with an expiry that heartbeats refresh.)

How it fits a bigger design

The connection is only the last hop. Behind it sit the database as the source of truth, a pub/sub or broker to move events between servers, and a gateway layer whose only job is holding connections.

  • HTTP alone can’t let the server start a conversation.
  • Short polling: ask every N seconds. Simple, wasteful, delayed.
  • Long polling: the server holds the request open until there is news.
  • SSE: one long HTTP response, server to browser only, auto reconnect, text.
  • WebSocket: upgrade handshake, then two-way frames, text or binary.
  • Pick by direction first, then by how fresh the data must be.
  • Long connections tie a user to one server, so you need pub/sub to reach users elsewhere.
  • None of them guarantee delivery. Store messages and replay after a reconnect.
