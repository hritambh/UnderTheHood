Normal HTTP works like this: the browser asks, the server answers, and the conversation ends. The server cannot start a conversation on its own.

That is a problem when the server has new information the user should see right away: a new chat message, a live score, a “your order is out for delivery” update.

There are four common ways to solve this:

  • Short polling: the browser asks “anything new?” every few seconds.
  • Long polling: the browser asks, and the server waits before answering until it actually has something new.
  • Server-Sent Events (SSE): the browser opens one long HTTP connection, and the server keeps sending updates down it. One direction only: server to browser.
  • WebSockets: the browser and server open one long connection, and both sides can send messages at any time.

One-line version: polling = “keep asking”, SSE = “server keeps talking”, WebSocket = “both keep talking”.

Users expect apps to feel live. If a teammate sends you a message, you expect to see it in about a second, not after refreshing the page.

Without one of these techniques, the only option is the user pressing refresh. That gives stale data and a poor experience.

The choice between the four matters because they have very different costs:

  • Polling too often wastes server work. Most requests come back empty.
  • Polling too rarely makes updates feel slow.
  • Long-lived connections (SSE, WebSockets) remove the waste, but each open connection uses memory on the server, and they are harder to load balance and scale.

So the real question is: how fresh must the data be, which direction does it flow, and how many users are connected at once?

Imagine you ordered food at a busy counter and you are waiting for it.

  • Short polling: every 30 seconds you walk to the counter and ask, “Is my order ready?” Usually the answer is “no”. You waste your time and the staff’s time.
  • Long polling: you ask once, and the staff member says, “Wait here, I’ll tell you the moment it’s ready.” When it’s ready, you take it, and if you order something else you ask again.
  • SSE: the restaurant has a screen that shows order numbers as they become ready. The screen talks to you, but you cannot talk back through it. To place another order, you still go to the counter (a normal HTTP request).
  • WebSocket: you have a walkie-talkie with the kitchen. Either side can speak at any time: “Make it spicy”, “Your order is ready”.

Notice the costs too. A walkie-talkie for every customer is great for chatting, but the kitchen must keep every one of them switched on. A display screen is cheaper, because information only flows one way.

Say you are building a food-delivery app with a NestJS backend. Two features need live updates:

  1. Order status (“Preparing” → “Out for delivery”). Only the server sends updates. A good fit for SSE.
  2. Chat with the delivery driver. Both sides send messages often. A good fit for WebSockets.

SSE in NestJS

// orders.controller.ts
import { Controller, Param, Sse, MessageEvent } from '@nestjs/common';
import { Observable, map } from 'rxjs';

@Controller('orders')
export class OrdersController {
  constructor(private readonly orderEvents: OrderEventsService) {}

  // GET /orders/123/events  (response type: text/event-stream)
  @Sse(':id/events')
  stream(@Param('id') id: string): Observable<MessageEvent> {
    return this.orderEvents.forOrder(id).pipe(
      map(status => ({ data: { status } }))
    );
  }
}
// browser
const source = new EventSource('/orders/123/events');
source.onmessage = (e) => showStatus(JSON.parse(e.data).status);
// If the connection drops, EventSource reconnects by itself.

WebSocket in NestJS

// chat.gateway.ts
import { WebSocketGateway, SubscribeMessage, MessageBody,
         ConnectedSocket, WebSocketServer } from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';

@WebSocketGateway()
export class ChatGateway {
  @WebSocketServer() server: Server;

  @SubscribeMessage('chat:send')
  onMessage(@MessageBody() msg: { orderId: string; text: string },
            @ConnectedSocket() client: Socket) {
    // send to everyone in this order's chat room
    this.server.to('order:' + msg.orderId).emit('chat:new', msg);
  }
}

NestJS uses Socket.IO by default for gateways. Socket.IO is a library on top of WebSockets with extra features (rooms, auto reconnect, fallback to polling). A plain browser WebSocket cannot talk to a Socket.IO server directly; you need the Socket.IO client. NestJS also has a plain ws adapter if you want raw WebSockets.

Short polling

  1. Browser sends GET /orders/123.
  2. Server reads the database and replies immediately, even if nothing changed.
  3. Browser waits N seconds (a timer) and repeats.

Long polling

  1. Browser sends GET /orders/123/updates.
  2. Server does not reply right away. It keeps the request open and waits for a change.
  3. When a change happens, or a timeout is reached (for example 30 seconds), the server replies.
  4. Browser immediately sends a new request. Repeat.

Server-Sent Events

  1. Browser opens a normal HTTP GET with new EventSource(url).
  2. Server answers with header Content-Type: text/event-stream and never “finishes” the response.
  3. Whenever there is news, the server writes a small text block like data: {"status":"OUT_FOR_DELIVERY"} followed by a blank line.
  4. If the connection drops, the browser reconnects automatically. If the server gave events an id:, the browser sends a Last-Event-ID header so the server can resend what was missed (only if your server code supports that).

WebSockets

  1. Browser sends an HTTP request with Upgrade: websocket headers. This is called the handshake.
  2. Server replies 101 Switching Protocols. From now on, the TCP connection is no longer HTTP.
  3. Both sides send small frames (text or binary) at any time, in both directions.
  4. To detect dead connections, sides send ping/pong frames (heartbeats).
  5. If the connection drops, nothing reconnects automatically in the plain browser API. Your code (or a library like Socket.IO) must reconnect.

1. Short polling

How: a timer in the browser calls a normal API every N seconds.

Use when: updates are rare, a few seconds of delay is fine, and you want the simplest thing. Example: refreshing a dashboard every 60 seconds.

Good: works everywhere, stateless, easy to cache and load balance. Bad: many empty requests; delay of up to N seconds.

2. Long polling

How: the server holds each request open until there is news or a timeout.

Use when: you need near-real-time updates but cannot use SSE or WebSockets (old proxies, strict networks). Socket.IO used it as a fallback for this reason.

Good: low delay, plain HTTP. Bad: each waiting user still holds a connection; messages that arrive between one response and the next request must be buffered by the server, or they are lost; more complex than it looks.

3. Server-Sent Events

How: one long HTTP response that streams text events.

Use when: data flows from server to browser only. Notifications, live feeds, progress bars, streaming AI responses.

Good: plain HTTP (works with normal auth, cookies, HTTP/2), auto-reconnect built into the browser, simple server code. Bad: one direction only; text only (binary must be encoded, for example as base64); the browser EventSource API cannot set custom headers like Authorization, so people use cookies or a token in the URL, or a fetch-based SSE library.

Old limit to know: on HTTP/1.1, browsers allow about 6 open connections per domain, shared across tabs. Many tabs with SSE can use them all up. HTTP/2 sends many streams over one connection, so this mostly goes away.

4. WebSockets

How: HTTP handshake, then a two-way connection that stays open.

Use when: both sides send frequent, small messages with low delay. Chat, multiplayer games, collaborative editing, live trading screens.

Good: two-way, low overhead per message, supports binary. Bad: stateful connections are harder to scale and load balance; you build reconnect, heartbeats, and “resend what I missed” yourself (or use a library); some corporate proxies and firewalls interfere with it.

Assumptions (made up for this example, not benchmarks): 10,000 users are online. On average, each user gets 1 real update per minute.

Short polling every 5 seconds

  • Requests per second = 10,000 users ÷ 5 s = 2,000 requests/s.
  • Useful updates per second = 10,000 ÷ 60 ≈ 167/s.
  • So about 167 of every 2,000 requests carry news. Over 90% are empty, but each still costs auth, routing, and maybe a database query.
  • Average delay ≈ 2.5 s, worst case 5 s.

Polling every 1 second for fresher data makes it 10,000 requests/s. The waste grows fast.

SSE or WebSocket

  • 10,000 open connections at all times.
  • About 167 messages/s are pushed, all useful.
  • Delay is roughly network time, usually well under a second.
  • The new cost is memory per connection and the effort to spread connections across servers. How many connections one Node.js server can hold depends on memory, message rate, and per-connection state; measure with a load test rather than trusting a number from a blog.

Several servers

Say you run 4 app servers with 2,500 connections each. User A (on server 1) sends a chat message to user B (on server 3). Server 1 does not have B’s connection. So servers need a shared channel, like Redis pub/sub: server 1 publishes, all servers receive it, and server 3 forwards it to B. The Socket.IO Redis adapter does exactly this.

  • Simplicity vs freshness. Polling is the simplest and is stateless, but either wastes requests or is slow.
  • One-way vs two-way. SSE is simpler than WebSockets because it is plain HTTP. If the browser only needs to receive, SSE plus normal POST requests for the rare upload is often enough.
  • Stateless vs stateful servers. With polling, any server can answer any request. With SSE and WebSockets, a user is tied to one server for the life of the connection. Deploys and restarts drop all connections on that server, and clients must reconnect.
  • Delivery guarantees. None of these guarantee delivery on their own. If a user is offline for a moment, messages sent in that gap are lost unless you store them and replay them (event IDs, “give me everything after message 812”).
  • Infrastructure. Load balancers, proxies, and API gateways often close idle connections after a timeout, and some buffer streaming responses. Long connections need heartbeats and the right settings.

Signals for each choice

  • Short polling: data changes every minute or less often, a few seconds of delay is fine, or you need something working today.
  • SSE: server pushes, browser mostly listens. Notifications, order tracking, logs, build progress, streaming AI tokens.
  • WebSocket: both sides send often, or you need binary or very low delay. Chat with typing indicators, games, shared whiteboards.
  • Long polling: mostly as a fallback when the others are blocked.

When you probably don’t need real-time at all

If users look at a page for a short time, or the data changes rarely, a refresh button or polling every 30–60 seconds is fine. Don’t add WebSocket infrastructure for a report that updates hourly.

Mobile apps

When the app is closed or in the background, mobile systems usually stop your connections. To reach those users you need push notifications (APNs on iOS, FCM on Android), not WebSockets.

  • Choosing WebSockets by default. If data only flows one way, SSE is usually simpler and enough.
  • No reconnect logic. Connections will drop (Wi-Fi changes, deploys, timeouts). Plain WebSockets need your own reconnect with backoff (wait a bit longer after each failed try).
  • Forgetting missed messages. After reconnecting, the client should ask “what did I miss since ID X?” Otherwise users silently miss updates.
  • No heartbeats. A dead connection can look open for a long time. Ping/pong or periodic SSE comments (lines starting with :) keep it alive and detect failures.
  • Multiple servers without a shared channel. Works in development with one server, breaks in production with several.
  • Proxy buffering SSE. Nginx and some gateways buffer responses, so events arrive in big delayed chunks. Turn buffering off for SSE routes (for Nginx, proxy_buffering off or the X-Accel-Buffering: no header).
  • Skipping auth on the socket. Check the user during the handshake, and check permissions for every message or room join, not just once.
  • Thundering herd after a deploy. When a server restarts, thousands of clients reconnect at the same moment. Add random delay (jitter) to reconnects.

Common questions

“How would you build live notifications?”
Start with SSE: the server pushes, the browser only listens. Store notifications in a database too, so a user who reconnects or was offline can fetch what they missed. Use Redis pub/sub so any server can deliver to any user.

“Design a chat app. How do messages reach the other user?”
WebSockets, because both sides send often. Save each message to the database first, then publish it to the recipient’s server (via Redis pub/sub or a message broker), which forwards it on the socket. If the recipient is offline, send a push notification.

“Why not just poll?”
Polling is fine at small scale or for slow-changing data. At scale it creates mostly empty requests and still has delay. Show the math (users ÷ interval).

Follow-ups to expect

  • How do you load balance WebSockets? (Any server can accept a new connection; you need a shared pub/sub to route messages, and sticky sessions only if your library needs them, like Socket.IO when it falls back to polling.)
  • What happens during a deploy? (Connections drop; clients reconnect with jitter and fetch missed messages.)
  • How do you know a user is online? (Presence: track connections in Redis with an expiry refreshed by heartbeats.)
  • How many connections per server? (Say it depends on memory and message rate, and you would measure with a load test.)

How it fits a bigger design

The real-time connection is usually only the last step. Behind it sits a database (the source of truth), a message broker or pub/sub (to move events between servers), and a gateway layer that only holds connections.

  • HTTP alone can’t let the server start a conversation.
  • Short polling: ask every N seconds. Simple, wasteful, delayed.
  • Long polling: server waits to answer until there is news.
  • SSE: one long HTTP response, server → browser only, auto reconnect, text.
  • WebSocket: upgrade handshake, then two-way messages, text or binary.
  • Long connections tie a user to one server; use pub/sub to reach users on other servers.
  • None of them guarantee delivery: store messages and replay after reconnect.
  • Pick the simplest option that meets the freshness and direction needs.
