Sharding means splitting the rows of a table across several database servers. Each server holds only part of the data. Each part is called a shard.

All shards have the same tables and columns. They just hold different rows. For example, users 1 to 1 million on shard A, users 1 million to 2 million on shard B.

The column used to decide which shard a row goes to is called the shard key (for example user_id or tenant_id).

Quick background, since sharding builds on these ideas:
  • Vertical scaling: give the one database server more CPU, RAM, and faster disks. Simple, but there is a ceiling and it gets expensive.
  • Replication: keep copies of the same data on several servers. Usually one primary takes writes, and replicas serve reads. Every server still holds all the data.
  • Partitioning: splitting a table into pieces. If the pieces stay on one server (like PostgreSQL’s built-in table partitioning), that is partitioning but not sharding. Sharding is partitioning across servers.

So: replication = same data, many copies. Sharding = different data, many pieces. Real systems often use both: each shard has its own replicas.

A single database server has limits:

  • Writes. Read replicas help with reads, but every write still goes to the one primary. If writes grow beyond what one machine can handle, replicas don’t help.
  • Storage. The data might grow larger than one machine can store comfortably. Large tables also make backups, restores, index builds, and schema changes slow.
  • Working set. Databases are fast when the frequently used data and indexes fit in memory. When they no longer fit, more queries hit disk and slow down.

Sharding solves these by dividing the work. With 4 shards, each server stores roughly a quarter of the data and takes roughly a quarter of the writes, if the shard key spreads the load evenly.

Without it, once you hit the ceiling of the biggest machine you can buy, the only options left are to delete or archive data, or to slow down growth.

Think of a city library that has grown too big for one building.

Replication is building three identical libraries with the same books. More people can read at once, but every new book must be added to all three buildings. And each building still needs room for every book.

Sharding is splitting the collection: authors A–H in the north branch, I–P in the central branch, Q–Z in the south branch. Each branch holds fewer books, and new books only go to one branch.

The trade-offs show up immediately:

  • To find a book, you need to know the rule (“authors starting with M are central”). That rule is the shard key.
  • A question like “list every book published in 2020” means visiting all three branches. That is a cross-shard query.
  • If authors starting with S are hugely popular, the south branch gets crowded while others are quiet. That is a hot shard.
  • Opening a fourth branch means moving books around. That is resharding.

Say you run a multi-tenant SaaS product on PostgreSQL. Each customer company is a tenant. Almost every query is about one tenant: “show this tenant’s invoices”.

That makes tenant_id a natural shard key: all data for one tenant lives on one shard, so most queries touch only one database.

A simple version uses a lookup table that says which shard each tenant lives on:

// shard-router.ts
import { Pool } from 'pg';

const shards: Record<string, Pool> = {
  shard_1: new Pool({ connectionString: process.env.SHARD_1_URL }),
  shard_2: new Pool({ connectionString: process.env.SHARD_2_URL }),
};

// tenant -> shard mapping, stored in a small "directory" database,
// cached in memory or Redis because it is read on every request
async function shardFor(tenantId: string): Promise<Pool> {
  const name = await directory.getShardName(tenantId); // e.g. "shard_2"
  return shards[name];
}

export async function getInvoices(tenantId: string) {
  const db = await shardFor(tenantId);
  const res = await db.query(
    'SELECT * FROM invoices WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 50',
    [tenantId]
  );
  return res.rows;
}

Notice what is now harder:

  • “Total revenue across all tenants” must query every shard and add up the results in your app.
  • You can’t rely on one SERIAL sequence for IDs across shards, because each shard has its own. Use UUIDs (UUIDv7 sorts by time), or another globally unique scheme.
  • A transaction that changes data on two shards is no longer a normal single-database transaction. (The Saga Pattern and 2PC topic covers how to handle this.)

Tools: you don’t always write this routing yourself. For PostgreSQL, the Citus extension shards tables across nodes. For MySQL, Vitess does it. MongoDB and Cassandra shard built-in. Many teams still route in the app for full control.

Flow of one request in an app-level sharded system:

  1. The user sends GET /invoices with their auth token.
  2. The API server reads the shard key from the request (here, tenant_id from the token).
  3. The router works out which shard holds that key: by a formula (hash or range) or by looking it up in the directory.
  4. The server sends the query to that one shard only.
  5. The shard runs the query on its smaller dataset and returns rows.
  6. The server returns the result to the user.

For a query without the shard key (“find invoice by invoice number” when you don’t know the tenant), the router must send it to all shards and merge the results. This is called scatter-gather. It is slower and gets worse as you add shards.

Each shard is usually a full database setup on its own: one primary plus replicas, its own backups, and its own monitoring.

1. Range-based sharding

What: each shard owns a range of key values. IDs 1–1M on shard 1, 1M–2M on shard 2. Or dates: 2024 on one shard, 2025 on another.

Good: range queries (“orders from March”) touch few shards. Easy to understand.

Bad: new data often goes to the newest range, so one shard takes all the writes (a hot shard). Uneven data needs ranges to be split later.

2. Hash-based sharding

What: run the key through a hash function and use the result to pick a shard. Simplest form: hash(user_id) % N.

Good: spreads keys evenly, so load is usually balanced.

Bad: range queries must hit every shard. With plain % N, changing N moves most keys (see the numbers section). Consistent hashing or a fixed large number of virtual buckets (for example 1,024 buckets mapped onto however many servers you have) reduces how much data moves.

How consistent hashing helps

The one-minute version: consistent hashing is a way to assign keys to servers so that when you add or remove a server, only a small share of keys move, instead of almost all of them.

The problem it solves. With hash(key) % N, the shard for every key depends on N. Change N from 8 to 9 and the answer changes for most keys. Most of your data now sits on the “wrong” shard and must be copied. While that copy runs, reads may look in the wrong place. With terabytes of data, that is hours or days of risky work.

The idea: a ring. Imagine all possible hash values arranged in a circle, like the numbers on a clock, where the largest value wraps back to the smallest.

  1. Hash each server’s name (for example hash("shard-A")) to get its position on the ring.
  2. Hash each key (for example hash(user_id)) to get its position on the same ring.
  3. To find a key’s shard, start at the key’s position and walk clockwise until you reach a server. That server owns the key.

The important part: a key’s owner depends only on its nearest server clockwise, not on the total number of servers.

Adding a server. When D joins the ring, it lands between two existing servers. Only the keys on the arc just before D (keys that used to walk past that spot to B) now stop at D. Every other key still reaches the same server as before. In the diagram, only k1 moves.

Removing a server. If a server leaves (or fails), only its keys move, to the next server clockwise. Everyone else stays put.

The catch, and the fix: virtual nodes

With only a few servers, their random positions on the ring are rarely evenly spaced. One server might own a huge arc and get far more keys than the others. Also, when a server leaves, all its keys land on just one neighbour, which can overload it.

The usual fix is virtual nodes: put each physical server on the ring many times (for example, hash "shard-A#1", "shard-A#2", … up to 100 or more). Now each server owns many small arcs spread around the ring. This gives two benefits:

  • Load is much more even, because many small random arcs average out.
  • When a server leaves, its keys spread across many other servers instead of one neighbour.

It also lets you give a bigger machine more virtual nodes, so it takes a bigger share.

A small code sketch

// consistent-hash-ring.ts  (to show the idea, not production code)
import { createHash } from 'crypto';

const hash = (s: string) =>
  createHash('md5').update(s).digest().readUInt32BE(0); // 0 .. 2^32-1

class HashRing {
  private ring: { pos: number; server: string }[] = [];

  constructor(servers: string[], private vnodes = 100) {
    servers.forEach(s => this.add(s));
  }

  add(server: string) {
    for (let i = 0; i < this.vnodes; i++) {
      this.ring.push({ pos: hash(server + '#' + i), server });
    }
    this.ring.sort((a, b) => a.pos - b.pos);
  }

  remove(server: string) {
    this.ring = this.ring.filter(n => n.server !== server);
  }

  // first ring position at or after the key's hash; wrap to the start if none
  serverFor(key: string): string {
    const h = hash(key);
    const node = this.ring.find(n => n.pos >= h) ?? this.ring[0];
    return node.server;
  }
}

const ring = new HashRing(['shard-A', 'shard-B', 'shard-C']);
ring.serverFor('user-42'); // e.g. 'shard-B'

A real implementation would use binary search instead of find, because the ring can have thousands of entries and this lookup runs on every request.

Assume 10 million keys spread evenly (illustrative).

The consistent hashing column is the minimum possible: the new server must receive its fair share from somewhere. Those figures assume a well-balanced ring (virtual nodes); with few virtual nodes the real share can be noticeably higher or lower.

A popular alternative: fixed slots

Many systems get the same benefit in a simpler way. They split the hash space into a fixed, large number of slots (buckets) that never changes, and keep a small table saying which server owns each slot. Adding a server means handing it some slots. Example: Redis Cluster uses 16,384 hash slots. This is easy to reason about and lets you move exactly the slots you choose.

What consistent hashing does not solve

  • It decides which keys move. You still have to actually copy that data to the new shard while live traffic continues, then switch routing.
  • It doesn’t fix hot keys. If one user or tenant gets huge traffic, they are still one key on one server.
  • Range queries still need to hit many shards, because hashing scatters neighbouring keys.
  • Every app server must use the same ring (same hash function, same server list, same virtual node count). If two servers disagree, they route the same key to different shards.

Where you will see it: Amazon’s Dynamo paper, Cassandra (token ring with virtual nodes), many caching clients for spreading keys across Memcached or Redis servers, and load balancers that need “same user → same server” without a lookup table.

3. Directory-based (lookup) sharding

What: a lookup table maps each key (or tenant) to a shard.

Good: very flexible. You can move one big tenant to its own shard. Common for multi-tenant SaaS.

Bad: the directory is an extra component on every request. It must be fast (cached) and highly available, or it becomes a single point of failure.

4. Geographic sharding

What: shard by region: Indian users in an India data center, EU users in the EU.

Good: lower delay for users, and helps with data residency laws.

Bad: regions are rarely equal in size; users who move or interact across regions are tricky.

Choosing a shard key

This is the most important decision, and it is hard to change later. A good shard key:

  • Appears in most queries (so most queries hit one shard).
  • Has many distinct values and spreads load evenly.
  • Keeps data that is used together on the same shard (all of one tenant’s rows together).

Assumptions (illustrative only, not benchmarks): your database has 2 TB of data and must handle 20,000 writes per second at peak. Load tests showed one primary handles about 5,000 writes per second comfortably for your workload.

  • Minimum shards for writes: 20,000 ÷ 5,000 = 4.
  • You want headroom for growth and uneven traffic, so plan for 8 shards: about 2,500 writes/s and 250 GB each.

Why % N hurts when you add a shard

With shard = hash(key) % 8, going from 8 to 9 shards changes the result for most keys. On average about 8 out of 9 keys (≈ 89%) move to a different shard. Moving most of 2 TB while serving live traffic is risky and slow.

With consistent hashing, adding the 9th shard moves only about 1/9 of keys (≈ 11%): just enough to fill the new shard.

Hot shard example

Say 1,000 tenants are spread evenly across 8 shards (125 each). One tenant is a huge customer producing 30% of all writes: 6,000 writes/s. Whatever shard holds them now gets 6,000 + about 1,750 (its share of the rest) = ~7,750 writes/s, far over the 5,000 limit, while other shards sit at ~1,750.

Even sharding by tenant count did not give even load. With directory-based sharding you can give that tenant its own shard. If one tenant alone exceeds a shard’s capacity, you need a finer key for them (for example tenant plus customer ID).

What you gain

  • Write capacity and storage that grow by adding servers.
  • Smaller datasets per server: faster backups, restores, index builds.
  • Failure isolation: one shard down affects only part of the users.

What you give up

  • Cross-shard queries become scatter-gather; slower and more complex.
  • Joins across shards aren’t done by the database for you (unless a tool like Citus handles some cases).
  • Transactions across shards lose simple ACID guarantees. You need two-phase commit or patterns like sagas.
  • Unique constraints and foreign keys only work inside one shard.
  • Operations multiply: N shards means N sets of backups, migrations, monitoring, and failovers. Schema migrations must run on every shard.
  • Resharding later is one of the hardest operations in backend engineering.

Sharding is a big, mostly one-way step. Most teams treat it as a last resort.

Signals you may need sharding

  • Write load is near the limit of your largest reasonable primary, even after tuning.
  • Data size makes backups, restores, or migrations unacceptably slow.
  • Your growth forecast clearly passes one machine’s limits soon.
  • You need data in specific regions for legal reasons.

Try these first (usually in this order)

  1. Fix slow queries and add the right indexes.
  2. Add caching (for example Redis) for hot reads.
  3. Add read replicas for read-heavy load.
  4. Scale the server up (vertical scaling). Modern machines are very large.
  5. Archive or delete old data; use table partitioning on one server.
  6. Split by feature: move a separate domain (like analytics or logs) to its own database. This is sometimes called vertical partitioning or functional partitioning.

Many large products run for years on one well-tuned PostgreSQL primary plus replicas. Only shard when you have numbers showing you need it.

  • Sharding too early. You pay the complexity cost long before you get any benefit.
  • A bad shard key. For example created_at (all new writes go to one shard) or country (one country dominates).
  • Using % N without a plan for growth. Adding a shard then means moving most of the data.
  • Confusing sharding with replication. Replicas add read capacity and availability; they don’t add write capacity or reduce data per server.
  • Ignoring queries without the shard key. Admin search, reporting, and analytics often need a separate system (a search index like Meilisearch/Elasticsearch, or a data warehouse fed by change events).
  • Relying on auto-increment IDs. Two shards both create order #1001.
  • Forgetting each shard needs replicas. Without them, losing one shard’s server loses that part of the data until restore.

Common questions

“Your database can’t keep up. What do you do?”
First find out why: reads or writes? Fix queries and indexes, add caching, add read replicas for reads, scale up. Shard only when writes or data size exceed one machine. Interviewers like hearing that order.

“How would you shard the users table?”
Choose a key used in most queries and spread evenly, like user_id, with hashing. Mention how you’d handle lookups by email (a separate lookup table from email to user_id) and how you’d add shards later (buckets or consistent hashing).

“What’s the difference between sharding and replication?”
Replication copies the same data to more servers (helps reads and availability). Sharding splits the data across servers (helps writes and storage). They are usually combined.

Follow-ups to expect

  • How do you handle a celebrity user or a huge tenant (hot shard)?
  • How do you do a transaction across two shards? (2PC or sagas; ideally design so it isn’t needed.)
  • How do you generate unique IDs?
  • How do you add a shard with no downtime? (Copy data in the background, keep it in sync with change capture or double writes, then switch routing.)
  • How do you run a report across all users? (Scatter-gather for small cases; a separate analytics store for real reporting.)

How it fits a bigger design

In a design like “Twitter” or “Uber”, sharding usually appears when you estimate storage and write rates. Show the numbers that justify it, pick the key, and name the trade-off you accept.

  • Sharding splits rows across several database servers; each part is a shard.
  • Replication copies data; sharding divides it. They are often combined.
  • The shard key decides where each row lives, and it is hard to change later.
  • Range, hash, directory, and geographic are the main strategies.
  • Queries with the shard key hit one shard; queries without it hit all.
  • Cross-shard joins, transactions, and unique constraints get harder.
  • Plain % N moves most data when N changes; buckets or consistent hashing help.
  • Shard last, after indexes, caching, replicas, and vertical scaling.
