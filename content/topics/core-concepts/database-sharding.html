Sharding means splitting the rows of a table across several database servers. Each server holds only part of the data, and each part is a shard.

Every shard has the same tables and columns. They just hold different rows: users 1 to 1 million on shard A, 1 to 2 million on shard B. The column that decides where a row goes is the shard key, usually something like user_id or tenant_id.

Three words that get mixed up:
  • Vertical scaling: one bigger server. Simple, with a ceiling.
  • Replication: copies of the same data. One primary takes writes, replicas serve reads. Every server still holds everything.
  • Sharding: different data on each server. Partitioning across machines.

One-line version: replication = same data, many copies. Sharding = different data, many pieces. Big systems use both, since each shard gets its own replicas.

One database server runs into three walls:

  • Writes. Read replicas don’t help. Every write still lands on the single primary.
  • Storage. Huge tables make backups, restores, index builds and schema changes painfully slow.
  • Working set. Databases are fast while the hot data and indexes fit in memory. Once they don’t, queries start hitting disk.

Sharding divides all three. With 4 shards each server holds about a quarter of the data and takes about a quarter of the writes — if the shard key spreads load evenly, which is the whole difficulty.

So the real question is: which column can you put nearly every query behind?

A city library that outgrew its building.

  • Replication is three identical libraries. More people can read at once, but every new book goes into all three, and each building still needs room for everything.
  • Sharding is splitting the collection: authors A–H north, I–P central, Q–Z south. Each branch holds less, and a new book goes to one branch.
  • To find a book you must know the rule (“M is central”). That rule is the shard key.
  • “List every book published in 2020” means visiting all three branches: a cross-shard query.
  • If S authors are wildly popular, the south branch is packed while the others are quiet: a hot shard.
  • Opening a fourth branch means moving books around: resharding, the operation everyone dreads.

A multi-tenant SaaS on PostgreSQL. Each customer company is a tenant, and almost every query is about one tenant, so tenant_id is the natural shard key.

// shard-router.ts
const shards: Record<string, Pool> = {
  shard_1: new Pool({ connectionString: process.env.SHARD_1_URL }),
  shard_2: new Pool({ connectionString: process.env.SHARD_2_URL }),
};

// tenant -> shard, kept in a small directory database and cached,
// because this runs on every single request
async function shardFor(tenantId: string): Promise<Pool> {
  return shards[await directory.getShardName(tenantId)];
}

export async function getInvoices(tenantId: string) {
  const db = await shardFor(tenantId);
  const res = await db.query(
    'SELECT * FROM invoices WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 50',
    [tenantId]);
  return res.rows;
}

What just got harder:

  • “Total revenue across all tenants” has to query every shard and add up in your app.
  • SERIAL ids break, because each shard counts on its own. Use UUIDs (UUIDv7 sorts by time) or another global scheme.
  • A transaction touching two shards is no longer one database transaction. That is what sagas and two-phase commit are for.

You don’t always write the routing yourself. Citus shards PostgreSQL, Vitess shards MySQL, and MongoDB and Cassandra shard built-in. Plenty of teams still route in the app, for control.

  1. The request arrives with the shard key in it — here tenant_id, read from the auth token.
  2. The router works out which shard owns that key, by formula (hash or range) or by looking it up in a directory.
  3. The query goes to that one shard, which runs it against its smaller dataset.
  4. The server returns the rows.

A query without the shard key — “find invoice 8812” when you don’t know the tenant — has to go to every shard and merge the answers. That is scatter-gather, and it gets worse with every shard you add.

Each shard is a full database setup of its own: a primary, replicas, backups, monitoring.

The trap in each: range puts every new write on the newest shard. Hash can’t do range queries. A directory sits on every request, so it must be cached and always up. Regions are never equal.

Why % N hurts, and what consistent hashing does

With shard = hash(key) % 8, every key’s answer depends on 8. Move to 9 and most keys belong somewhere else, so most of your data moves while traffic is live.

Consistent hashing fixes that. Put all hash values on a circle, and hash each server name onto the same circle. A key belongs to the first server clockwise from it, so a new server only takes the arc just before it.

Two things make it practical. Virtual nodes: each server sits on the ring 100+ times, so arcs even out. Fixed slots: a large fixed set of buckets with a table of who owns each — Redis Cluster uses 16,384.

It only decides which keys move. Copying them live is still your problem, and it does nothing for one hot key.

Assumptions, illustrative, not benchmarks: 2 TB of data, 20,000 writes/s at peak, and load tests showing one primary handles about 5,000 writes/s for this workload.

  • Minimum shards for writes: 20,000 ÷ 5,000 = 4.
  • With headroom for growth: 8 shards, about 2,500 writes/s and 250 GB each.

Growing from 8 to 9 shards. With hash(key) % N, about 8 of every 9 keys (89%) move — nearly 2 TB in flight while the site is up. With consistent hashing, about 1 in 9 (11%) moves: just enough to fill the new shard.

The hot shard. 1,000 tenants spread evenly over 8 shards is 125 each. Now one huge customer makes 30% of all writes, 6,000/s on its own. Its shard gets 6,000 + its ~1,750 share of the rest = 7,750 writes/s, far past the 5,000 limit, while the other shards sit at 1,750. Even counts did not give even load, which is why directory sharding exists: give that tenant a shard to itself.

  • Capacity vs query power. You get write and storage headroom by adding servers, and you lose joins, cross-shard transactions, unique constraints and foreign keys across shards.
  • Smaller pieces vs more pieces. Each shard backs up and rebuilds fast, but now you run N sets of backups, migrations, failovers and dashboards, and every schema change runs N times.
  • Isolation vs blast radius. One shard down takes out some users instead of all of them — unless the directory is down, which takes out everyone.
  • Even spread vs locality. Hashing spreads load but scatters neighbouring rows. Ranges keep them together but create hot spots.
  • Now vs later. Resharding live is one of the hardest operations in backend work, so the key you pick today is the key you live with.

Picking the key is the part that is hard to undo. A good one is in most queries, has many distinct values, and keeps data used together on one shard.

Signals you actually need it:

  • Write load is near the limit of the biggest reasonable primary, after tuning.
  • Data size makes backups, restores or migrations unacceptably slow.
  • Growth clearly passes one machine within your planning horizon.
  • Law requires data to sit in a particular region.

Try these first, in this order: fix slow queries and indexes → cache hot reads → add read replicas → scale the server up → archive old data or partition on one server → move a separate domain like analytics to its own database.

Plenty of large products run for years on one well-tuned primary plus replicas. Shard when you have numbers, not a feeling.

  • Sharding too early. You pay all the complexity long before you get any benefit.
  • A bad shard key. created_at sends every new write to one shard. country gives one shard most of the users.
  • Using % N with no plan for growth. The day you add a shard, almost everything moves.
  • Confusing sharding with replication. Replicas add read capacity and availability. They add no write capacity at all.
  • Ignoring queries without the shard key. Admin search and reporting usually need a separate search index or warehouse fed by change events.
  • Auto-increment ids. Two shards both happily create order #1001.
  • Forgetting replicas per shard. Lose one shard’s server and that slice of your data is gone until a restore finishes.

Common questions

“The database can’t keep up. What do you do?”
Find out whether it’s reads or writes first. Queries and indexes, then caching, then replicas for reads, then a bigger machine. Shard when writes or size pass one machine. Interviewers want that order, not the word “shard” in sentence one.

“How would you shard the users table?”
Hash on user_id, since it is in most queries and spreads evenly. Handle login by email with a small email → user_id lookup table, and plan growth with buckets or consistent hashing rather than % N.

“Sharding vs replication?”
Replication copies the same data for reads and availability. Sharding splits data for writes and storage. Real systems do both.

Follow-ups to expect

  • What about a celebrity user or a giant tenant? (Directory sharding, or a finer key for them.)
  • A transaction across two shards? (Saga, or two-phase commit. Better: design so it isn’t needed.)
  • Adding a shard with no downtime? (Copy in the background, keep in sync with change capture, then switch routing.)
  • A report across all users? (Scatter-gather for small cases, a separate analytics store for real reporting.)

How it fits a bigger design

In a “design Twitter” style question, sharding shows up the moment you estimate storage and write rate. Show the numbers that justify it, name the key, and say which trade-off you are accepting.

  • Sharding splits rows across database servers; each piece is a shard.
  • Replication copies data, sharding divides it. Most systems use both.
  • The shard key decides where a row lives, and it is the hardest thing to change later.
  • Range, hash, directory and geographic are the four strategies.
  • Queries with the shard key hit one shard; queries without it hit all of them.
  • Cross-shard joins, transactions and unique constraints stop working.
  • % N moves most data when N changes; consistent hashing or fixed slots move a fair share.
  • Even row counts don’t mean even load. One big tenant can swamp a shard.
  • Shard last: after indexes, caching, replicas and a bigger machine.
