An origin is scheme + host + port. Change any one of the three and it is a different origin:

  • https://app.example.com and https://api.example.com: the host differs.
  • http://localhost:3000 and http://localhost:4000: the port differs.

Browsers follow the same-origin policy: a script from one origin can’t read a response from another origin. Without it, any page you open could read your mail using the cookies already in your browser.

CORS is how a server makes an exception for origins it trusts. It adds headers such as Access-Control-Allow-Origin to its response. The browser reads them and decides whether the script gets the response. Only browsers do this check. curl, Postman, mobile apps and other servers don’t.

One-line version: the browser blocks cross-origin reads by default, and CORS headers are the server saying “this origin may read my responses”.

Say you are logged in to your bank, and you open another site in a new tab. Its script calls the bank’s API. The browser attaches your bank cookie, because that is what browsers do with cookies.

Step 3 is the same-origin policy. But it is too strict for normal apps: your own frontend on app.example.com has to read your API on api.example.com. CORS is the controlled exception.

So the question is: which origins may read this API, with which methods and headers, and with cookies or without?

You hire an assistant who carries your bank card. Salespeople visit your house and hand the assistant notes: “go to her bank and bring me her statement”.

  • The assistant is the browser, the salespeople are web pages, the bank is an API, and the card is your cookie.
  • Simple errand: the assistant goes, but reads the reply to a salesperson only if the bank wrote “OK to share with them” on it. That note is Access-Control-Allow-Origin.
  • Risky errand, like closing an account: the assistant phones the bank first and asks if it accepts this from that salesperson. That call is the preflight.
  • Using your card: the bank must name the salesperson exactly. “Anyone” is not accepted.

The costs show too. Every phone call takes time. And a thief who walks into the bank alone never meets the assistant, so the bank still needs its own ID check.

A React app on https://app.example.com calls a NestJS API on https://api.example.com. The first call fails in the browser console:

// browser console
Access to fetch at 'https://api.example.com/orders' from origin
'https://app.example.com' has been blocked by CORS policy: No
'Access-Control-Allow-Origin' header is present on the
requested resource.

The API never said who may read it. The fix is on the server, not in the frontend:

// main.ts
const app = await NestFactory.create(AppModule);

app.enableCors({
  origin: ['https://app.example.com'],   // exact origins, no wildcard
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true,                     // allow cookies
  maxAge: 600,                           // cache the preflight 10 min
});

await app.listen(3000);

What is now harder: the allow list is config you maintain. Every new frontend domain, preview URL and local port has to be added per environment, and a missing one looks like “the API is down” to the frontend team.

A script on app.example.com sends DELETE /orders/42 with an Authorization header.

  1. The browser sees a cross-origin call that is not “simple”, so it holds the real request.
  2. It sends a preflight: an OPTIONS request with Origin, Access-Control-Request-Method and Access-Control-Request-Headers. No cookies, no token, no body.
  3. The server answers with what it allows: origin, methods, headers, and Access-Control-Max-Age.
  4. If anything is missing, the real request is never sent. The script only gets a network error.
  5. Otherwise the browser sends the real request.
  6. That response needs Access-Control-Allow-Origin too. Only then does the script get the data.

Simple request

A GET, HEAD or form-style POST with no custom headers. The browser sends it straight away and only hides the response if the header is missing. Good: no extra trip. Bad: the server still ran the request.

Preflighted request

Anything else: PUT, PATCH, DELETE, a JSON body, or an Authorization header. Most JSON APIs land here. Good: the server can say no before anything runs. Bad: an extra round trip.

Request with credentials

The script asks for cookies to be sent (credentials: 'include'). The server must reply with Access-Control-Allow-Credentials: true and the exact origin. Use it for cookie sessions across origins.

What preflights cost. Assumptions, made up for the example: a dashboard polls GET /orders every 10 s with an Authorization header, a round trip takes 80 ms, and 10,000 dashboards are open.

  • Polls per dashboard per hour: 3,600 ÷ 10 = 360.
  • With no Access-Control-Max-Age, browsers cache a preflight for only 5 s. Every poll needs a new one: 360 extra requests, and each poll takes 80 + 80 = 160 ms.
  • Across all dashboards: 10,000 × 360 = 3,600,000 OPTIONS an hour, which is 1,000 a second of pure overhead.
  • With Max-Age: 600: one preflight per 10 minutes, so 6 an hour per dashboard. 10,000 × 6 = 60,000 an hour, about 17 a second. Polls are back to 80 ms.

The cache is kept per URL, so /orders/1 and /orders/2 each need their own preflight. Browsers also cap the value: Chrome at 2 hours, Firefox at 24.

  • Wildcard vs allow list. * works for every caller at once, but can’t be used with cookies. A list is safe, but someone has to keep it up to date.
  • Long cache vs fast changes. A long Max-Age removes most preflights. A browser that cached the old answer keeps using it until it expires.
  • Separate API domain vs one origin. Two domains deploy and scale apart, and pay for CORS on every call. One origin behind a reverse proxy needs no CORS at all.
  • Cookies vs tokens. Cross-origin cookies need credentials mode and an exact origin. A token in a header skips that, but always triggers a preflight.

You need it when a browser page on one origin reads an API on another:

  • a frontend on app. and an API on api.
  • local development, where the two run on different ports
  • a public API or widget that other people’s pages call

You don’t need it when:

  • the caller is not a browser: another service, a mobile app, a script
  • the frontend and the API share one origin, for example a reverse proxy that sends /api to the backend

And never use it as access control. It decides which pages may read a response in a browser. Who may call the API is the job of login and permissions, covered in Authentication and Authorisation.

  • Thinking CORS protects the API. Anything that is not a browser ignores it. Every endpoint still checks who is calling.
  • Echoing back any origin, with credentials on. Now every website can read a logged-in user’s data. Compare the origin against a fixed list.
  • Loose matching. origin.endsWith('example.com') also matches evil-example.com. Compare the whole string.
  • Putting the auth check before the preflight. OPTIONS carries no token, so it gets a 401 and every call fails. Answer preflights first.
  • No CORS headers on error responses. A 500 from a proxy shows up as a CORS error and hides the real one. Check the status in the Network tab.
  • Forgetting Vary: Origin. If the header changes per origin, a CDN can serve one origin’s copy to another.
  • Counting on it to stop CSRF. A simple cross-origin POST still runs on the server. Only the response is hidden.

Common questions

“What is CORS, and why does it exist?”
Browsers block scripts from reading other origins, so one site can’t read another using your cookies. CORS is the set of response headers a server uses to allow chosen origins.

“What is a preflight?”
An OPTIONS request the browser sends before a non-simple call, asking if the method and headers are allowed. The real request goes out only if the answer says yes.

“Why does it work in Postman but not in the browser?”
Only browsers apply the same-origin policy. The server answered both times. The browser refused to pass the answer to the script.

How it fits a bigger design

In a design with a single-page app and an API gateway, CORS sits at the edge. The gateway answers preflights and adds the headers in one place, before authentication runs. Say which origins are on the list for each environment, or put the app and the API behind one domain and skip CORS.

  • An origin is scheme + host + port. Change any one and it is a different origin.
  • The same-origin policy stops a script from reading responses from another origin.
  • CORS is the server’s exception list, sent as Access-Control-Allow-* response headers.
  • Only browsers enforce it. curl, mobile apps and other servers are not affected.
  • Simple requests are sent straight away. The server runs them even when the response is hidden.
  • Other requests get an OPTIONS preflight first, with no cookies or token.
  • Cookies need Allow-Credentials: true and an exact origin. * is refused.
  • Access-Control-Max-Age caches the preflight per URL and removes most of the overhead.
  • Match origins against a fixed list. Never echo back whatever origin arrives.
  • CORS is not access control and does not stop CSRF.
