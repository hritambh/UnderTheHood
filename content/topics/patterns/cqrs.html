CQRS stands for Command Query Responsibility Segregation. A command is a request to change something, like “place this order”. A query is a request to read something, like “show my orders”.

Most apps use one model for both: the same tables and the same classes. CQRS splits them. The write model is built to check rules and save changes safely. The read model is built to answer screens fast, often as a ready-made copy of the data in the shape a screen needs.

It grew out of an older rule called CQS: a method should either change state or return data, not both. CQRS applies that to a whole part of a system.

One-line version: writes go through a model built to enforce rules, and reads come from a separate model built to answer screens fast.

Take an online shop with tidy, normalised tables: orders, order_items, customers, payments, shipments. That shape is right for writes. Each fact is stored once.

The “My orders” page wants something else: one line per order with the customer name, total, payment status and delivery date. That is a five-table join for every page view.

On a sale day (numbers made up for the example) that 400 ms query runs thousands of times a minute and fills the database. Checkout writes queue behind it and start timing out. Adding indexes for the page makes every write slower, and the order class keeps growing fields that only one screen needs.

Think of a busy restaurant.

  • The kitchen is the write side. It takes order tickets, refuses what it can’t make (“no fish left”), and cooks. Its ticket rail is laid out for cooking, not for customers.
  • The order screen above the counter is the read side. It shows “order 42: ready” in big letters. It is built to be read at a glance, and it knows no kitchen rules.
  • The cook pressing “done” is the event that updates the screen.

Customers look at the screen and leave the cooks alone, so the kitchen stays fast. The cost is in the story too: the screen is a few seconds behind. Your food can be ready before the screen says so, and somebody has to keep that screen working.

  1. The client sends a command, such as PlaceOrder, to the write side.
  2. The command handler loads the current state, checks the rules and saves to the write database in one transaction.
  3. The change is published as an event, such as OrderPlaced.
  4. A projector listens for events and updates the read model: one ready-made row per order, per screen.
  5. The client sends a query to the read side.
  6. The query handler reads straight from the read model. No joins and no rules.

That gap is eventual consistency: the read side catches up, but not instantly.

Before: one service does everything, and the list endpoint pays for the joins on every call.

// orders.service.ts (before)
async listForCustomer(customerId: string) {
  return this.db.query(`
    SELECT o.id, o.status, c.name, p.status AS payment,
           s.eta, SUM(i.qty * i.price) AS total
    FROM orders o
    JOIN customers c   ON c.id = o.customer_id
    JOIN order_items i ON i.order_id = o.id
    JOIN payments p    ON p.order_id = o.id
    LEFT JOIN shipments s ON s.order_id = o.id
    WHERE o.customer_id = $1
    GROUP BY o.id, c.name, p.status, s.eta`, [customerId]);
}

After: three small pieces. The list is now a single-table read.

// place-order.handler.ts (write side)
async execute(cmd: PlaceOrderCommand) {
  await this.db.transaction(async (tx) => {
    const order = Order.place(cmd);            // rules live here
    await tx.orders.insert(order);
    await tx.outbox.insert(new OrderPlaced(order));
  });
}

// order-summary.projector.ts (keeps the read model fresh)
async onOrderPlaced(e: OrderPlaced) {
  await this.db.query(`
    INSERT INTO order_summary
      (order_id, customer_id, customer_name, status, total)
    VALUES ($1, $2, $3, 'PLACED', $4)
    ON CONFLICT (order_id) DO NOTHING`,
    [e.orderId, e.customerId, e.customerName, e.total]);
}

// list-orders.handler.ts (read side)
async execute(q: ListOrdersQuery) {
  return this.db.query(
    `SELECT * FROM order_summary WHERE customer_id = $1`,
    [q.customerId]);
}

The event is saved in an outbox table in the same transaction, so it can’t be lost. ON CONFLICT DO NOTHING makes a repeated event harmless. Later events, like a payment or a shipment, update the same row.

Split code only

Command handlers and query handlers are separate classes on one database. Queries use hand-written SQL or views. Start here: the code gets cleaner and nothing can drift.

Separate read store

The read model lives in its own tables or its own database, updated by events. Pick it when reads need a different shape, or far more capacity, than writes.

With event sourcing

The write side stores every event instead of the current state. Pick it only when you need the full history, such as an audit trail. CQRS does not need it.

  • Stale reads. A user saves, the list reloads, and the change is not there yet. The UI has to plan for that.
  • More moving parts. Events, projectors and a second store all have to be deployed, monitored and kept running.
  • Every change touches more places. One new field means a command, an event, a projector and a read table.
  • Rebuilds. A projector bug leaves wrong rows behind. You fix the code, then rebuild the read model from the events or the write database.
  • Harder debugging. “Why is this row wrong?” now crosses the write side, the event and the projector.

Use it when

  • Reads far outnumber writes, and you want to scale them apart.
  • Screens need shapes that the write tables can’t give cheaply: dashboards, search, feeds.
  • Write rules are complex and read code keeps getting tangled in them.
  • One part of the system has this problem. Use it there, not everywhere.

Skip it when

  • It is a CRUD app whose screens look like its tables.
  • An index, a read replica or a cache already fixes the slow query.
  • Users must see their own change the instant they save, on every screen.
  • The team is small and nobody will own the projectors.
  • Using it for the whole system. Most of an app is simple forms. Keep those simple and use CQRS only for the hot part.
  • Ignoring the lag in the UI. The user places an order and the list is empty. Show the result from the command’s own response, or read that one item from the write side.
  • Checking rules against the read model. It can be stale, so “is it in stock?” gets a wrong yes. Commands check the write model.
  • Publishing events outside the transaction. One lost event and the read model is wrong forever. Use an outbox.
  • Projectors that can’t take a repeat. Events get delivered twice, so counters double. Use upserts, or store handled event ids.
  • No way to rebuild. If you can’t recreate the read model from scratch, every projector bug is permanent.
  • Outbox goes with it. It gets the event out reliably after the write. The Saga Pattern topic explains it.
  • Event sourcing is often paired with it, but answers a different question: how the write side stores data. CQRS is about splitting reads from writes.
  • Read replicas get confused with it. A replica is the same tables copied to another server. A read model has a different shape.
  • Materialised views are a read model the database maintains for you. Inside one database, that is the cheapest form of CQRS.
  • Caching also serves reads from a copy. A cache can be thrown away and refilled at any time. A read model is designed, stored and kept in sync on purpose.
  • Saga coordinates writes across several services. CQRS splits reads from writes inside one.

Common questions

“What is CQRS, and when would you use it?”
Separate models for writes and reads. Use it when reads need a different shape or scale from writes. Skip it for plain CRUD.

“How does the read model stay in sync?”
The write side saves the change and an event in one transaction. A projector applies the event to the read model, and it has to be safe to run twice.

“The user saved, but doesn’t see the change. Now what?”
That is the lag. Show the result from the command’s response, or read that one item from the write side.

Follow-ups to expect

  • Do you need event sourcing? (No.)
  • What if a projector falls behind or crashes? (Monitor the lag. It resumes from the last event it handled.)

Where it fits in a design

It fits read-heavy parts with rich screens: order history, feeds, dashboards, search. Keep the write path small and strict, and prepare the read path ahead of time. Say out loud that the read side is eventually consistent, and how the UI copes with that.

  • A command changes something. A query reads something.
  • CQRS gives each its own model: a write model for rules, a read model shaped for screens.
  • The problem it fixes: one model serving both, where heavy reads slow down writes.
  • Commands save to the write database. An event then updates the read model through a projector.
  • The read side lags a little. That is eventual consistency, and the UI has to handle it.
  • Start by splitting the code only. Add a separate read store when reads need another shape or scale.
  • Event sourcing is optional. CQRS works without it.
  • Use an outbox so events are not lost, and make projectors safe to run twice.
  • Commands check rules against the write model, never the read model.
  • Skip it for plain CRUD, or when an index, replica or cache fixes the problem.
