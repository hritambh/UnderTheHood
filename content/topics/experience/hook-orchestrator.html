This was at Neutrinos, on a low-code platform. Customers model their own entities — a lead, a claim, a policy — and a shared data service handles create, update and delete for all of them. One codebase, many tenants, each with their own schemas.

That shared service is the problem and the opportunity. Every customer wants slightly different behaviour on the same entity, and none of them want to wait for a release to get it.

One-line version: I built a hook orchestrator that lets each tenant attach rules and side effects to entity events as configuration — some of them able to block the write, most of them running after it, and some firing days later.

Business rules were ending up inside the data service. “Reject a lead over a certain value unless an external system approves it.” “Message the team channel when a claim is approved.” “Chase the customer two days after the quote goes out.”

Each one is small. Together they are a mess:

  • A rule meant a deploy. One tenant’s policy change went through code review, a release and a regression pass.
  • The data service collected everyone’s logic. The service that should only know how to write a row knew about approvals, channels and reminders.
  • Tenants bled into each other. A rule written for one customer sat in code shared with all of them.

If nobody fixed it, the data service would keep growing a branch per customer, and the release that broke one tenant would break all of them.

  • Writes had to stay fast. Most events must not pay for the rules engine at all.
  • Some rules must block. “Don’t let this row be written” can’t be done after the transaction commits.
  • Most rules must not block. A Teams message failing must never fail a customer’s save.
  • Events already flowed over RabbitMQ. The data service published entity events, so the async path had a pipe to use.
  • The broker delivers at least once, and sends events in bulk batches. Duplicates were a given, not an edge case.
  • Multi-tenant. A tenant must never see, or be affected by, another tenant’s hooks.

A hook is a row that ties a trigger to a list of actions. The trigger is an entity, an operation (create, update, delete) and a timing (before, on success, on failure). The actions are things to do: call an API, evaluate an expression, send a message, create a calendar item.

The decision that shaped everything else: one flag, awaits_response, decides which path a hook takes. True means the data service blocks on an HTTP call and honours the answer. False means the hook rides the queue and can never hurt the write.

NestJS and TypeScript, PostgreSQL for the hook configuration and the audit trail, RabbitMQ for events, Redis for locks and short-lived caching. The data service and the broker already existed; the orchestrator and its database did not.

Three tables carry the whole thing. A hook, its actions, and a row for every execution.

-- re-created here as a small example of the shape, not the real schema
CREATE TABLE hooks (
  id              uuid PRIMARY KEY,
  tenant_id       text NOT NULL,
  entity_name     text NOT NULL,          -- "lead", "claim"
  trigger_event   text NOT NULL,          -- CREATE | UPDATE | DELETE
  trigger_timing  text[] NOT NULL,        -- BEFORE | ON_SUCCESS | ON_FAILURE
  awaits_response boolean NOT NULL,       -- true = it can refuse the write
  execution_order int NOT NULL DEFAULT 0,
  schedule        jsonb                   -- null = run now
);

CREATE TABLE hook_actions (
  id              uuid PRIMARY KEY,
  hook_id         uuid REFERENCES hooks(id) ON DELETE CASCADE,
  action_type     text NOT NULL,          -- HTTP_REQUEST, SEND_EMAIL, ...
  configuration   jsonb NOT NULL,
  execution_order int NOT NULL DEFAULT 0
);

The lookup on every event is tenant + entity + operation + timing + awaits_response, so that is the index. Tenant comes first, which also keeps one customer’s hooks out of another’s results.

Each action type gets a class behind one small interface, and the processor holds a map from action type to class. Adding “send a Slack message” is a new class and a map entry, not a change to the engine. Conditions are a list of path, operator, value rows joined by AND or OR, so a rule like “amount is over 700 and status is not rejected” is config, not code.

Fail closed, not open

On the blocking path, anything unexpected means deny. A hook naming an action type with no executor behind it refuses the write rather than waving it through. A rules engine that allows when it is confused is worse than none.

The same event arriving twice

At-least-once delivery means a redelivered event would send the email twice. Every event takes a Redis lock keyed on the transaction, record, phase and operation. No lock, no work.

The blocking path also caches an allow per transaction, so a retried write doesn’t pay for the external approval call twice. Only an allow is cached: a deny is cheap to recompute, and caching one would be a nasty way to make a block stick.

Jobs that outlive their configuration

A job registered today fires in two days, by which time the hook may have been edited or deleted. The job carries its audit row id, and on firing the orchestrator re-reads the hook. If the row is cancelled, or the schedule no longer matches what was registered, the job is deregistered instead of run.

Recurring jobs need two kinds of row: a template saying the schedule exists, and an instance per firing. Without the split you can’t tell “the schedule is live” from “this run failed”.

To fill in: the numbers — how many hooks or tenants ended up using it, and how long a new rule took before and after.
  • A rule became a row. Changing one tenant’s behaviour stopped needing a release of the shared data service.
  • A new action type became one class. The engine stopped changing every time the list of things a hook could do grew.
  • Every run got a record. Each execution writes its status and response, so “did the reminder go out?” is a query, with a timeline covering past runs and the ones still scheduled.
  • The data service shrank back to writing rows and publishing events.
  • A blocking hook puts a network call in the write path. It is opt-in per hook, but every tenant that opts in makes the orchestrator a hard dependency of their writes.
  • Config in JSONB means we own the validation. The database won’t catch a malformed action, so the API has to, and the rules for what a synchronous hook may contain live in code.
  • The audit table grows with traffic, not with the number of hooks. It needs a retention plan from day one.
  • Power to misconfigure. A wrong condition in a blocking hook can refuse perfectly good writes, and the person who wrote it is not an engineer.

What I’d do differently: make the blocking path degrade on its own. Today a configured sync hook is a dependency; a per-hook “on timeout, allow” setting with a circuit breaker would let a tenant choose availability over strictness instead of the choice being made for them.

  • Fail closed on anything that can say no. The default answer of a validation path has to be the safe one, including on bugs it doesn’t understand.
  • At-least-once delivery makes idempotency the feature. It isn’t a hardening pass at the end; the key you dedupe on is part of the design.
  • Separate the schedule from the firing. A template row plus instance rows answered questions that one row per job could not.
  • Configuration is a product. Once rules are data, they need validation, export and import, and a history, or you have moved the problem rather than solved it.

  4. “Scheduled rules register a job and come back through the queue later.”
  5. “The two things I’d call out are failing closed on the blocking path, and idempotency, because the broker delivers at least once.”

Questions it invites

  • What if the orchestrator is down? Async hooks queue and catch up. Blocking hooks are the real exposure, and that is the trade a tenant makes by using one.
  • Why not run the blocking check over the queue? The caller is waiting on a response. A queue gives no answer in time.
  • Duplicate side effects? The Redis lock, plus caching an allow per transaction.
  • Tenant isolation? Tenant is the first column of the lookup index, and another tenant’s hook answers as not found.

Traps

  • Calling it “a workflow engine”. It is narrower, and the narrowness is the point.
  • Glossing over the blocking path. It is the interesting half and the risky half.
  • Claiming the whole platform. Be clear which parts were mine.
  • A shared data service was collecting per-tenant business rules, so every rule change meant a release.
  • A hook is a row: an entity event plus an ordered list of actions, scoped to one tenant.
  • One flag, awaits_response, decides whether a hook can refuse the write or merely reacts to it.
  • Blocking hooks run as a synchronous call before the transaction; everything else runs off the event queue after it commits.
  • Scheduled hooks register a job with a scheduler and come back through the queue when they are due.
  • An executor class per action type keeps the engine closed to change as the action list grows.
  • The blocking path fails closed: anything it doesn’t understand is a deny, never an allow.
  • At-least-once delivery was handled with a Redis lock per transaction, record, phase and operation.
  • Only an allow is cached, never a deny.
  • Scheduled jobs are re-checked against the live hook when they fire, and a recurring schedule keeps a template row plus one instance row per run.
