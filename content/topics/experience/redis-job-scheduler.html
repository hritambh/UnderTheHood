Same platform at Neutrinos as the hook orchestrator. Several services had grown their own version of “do this later”: a reminder two days after a quote, a nightly sync, an SLA timer that has to fire if nobody responds in four hours.

Each service had solved it for itself with timers inside the process. That works until the process restarts.

One-line version: I built a scheduler service where a Redis sorted set is the clock, a Lua script makes sure exactly one worker gets each due job, and the job is delivered as an ordinary queue message so callers didn’t have to change how they receive work.

In-process timers look free and then quietly cost you everything:

  • A restart loses them. A deploy at 4pm silently dropped every reminder due that evening.
  • Two replicas both fire. Scale a service to three pods and the nightly job runs three times.
  • Nothing can be cancelled. Once a timer is set in memory there is no way to reach it from an API.
  • No record. “Did the four-hour SLA timer fire?” had no answer.

Left alone, every new service would write a fourth version of the same broken thing, and the bugs would be per-service.

  • Must survive restarts and run with several replicas, with no job firing twice and none lost.
  • Delays from seconds to months. An SLA timer is minutes away; a renewal reminder is a year away.
  • Callers shouldn’t change how they receive work. Everything already consumed RabbitMQ, so a due job should arrive as a normal message.
  • Cancellable and pausable from an API, including while a job is being handed out.
  • Working hours matter. An SLA timer must not expire on a Sunday, so due times are computed against a per-project calendar.
  • Redis and PostgreSQL were already running. No appetite for a new piece of infrastructure.

The shape: PostgreSQL holds what a job is, so it survives anything. Redis holds when it is next due, because a sorted set answers “what is due now?” and “what is due next?” in one cheap call. RabbitMQ delivers it, so consumers see a message like any other.

NestJS and TypeScript, PostgreSQL for the durable row, Redis for the timing state, RabbitMQ for delivery. The worker and the reaper run in the same service, and several replicas of it can run at once.

Three keys carry the timing. A sorted set of jobs waiting, a sorted set of jobs currently being handed out, and a hash per job.

-- what the keys hold (names simplified for this write-up)
ready    ZSET   member = job id, score = due time in ms
claimed  ZSET   member = job id, score = when it was claimed
job:ID   HASH   status, payload, runAtMs, attempts

Taking work is one Lua script, so Redis runs it start to finish with nothing in between:

-- claim up to N jobs that are due, re-created and trimmed for this write-up
local ids = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1],
                       'LIMIT', 0, ARGV[2])
for _, id in ipairs(ids) do
  redis.call('ZREM', KEYS[1], id)                 -- out of ready
  redis.call('ZADD', KEYS[2], ARGV[1], id)        -- into claimed, stamped now
  redis.call('HSET', ARGV[3] .. id, 'status', 'claimed')
  redis.call('HINCRBY', ARGV[3] .. id, 'attempts', 1)
end
return ids

Reading what is due and moving it are one operation. Two workers running this at the same moment cannot come away with the same job: whichever gets there second finds the ready set already empty of it.

A worker that dies holding a job

Claiming is only half the problem. A pod killed mid-deploy leaves its jobs sitting in the claimed set, owned by nobody.

That is why claimed is a sorted set and not a list: its score is when the claim happened. A reaper runs every half minute, takes anything claimed longer ago than the timeout, and puts it back in the ready set at its original due time. The attempt counter on the hash means a job that keeps killing its worker can be spotted rather than looping forever.

Sleeping exactly long enough

No polling loop. After draining everything due, the worker asks the ready set for the lowest score and arms a single timer for that moment. Registering a job that is due sooner re-arms it. When nothing is due, nothing runs at all.

The one trap: a timer can’t be set further out than about 24 days, so anything beyond that is capped and re-armed on waking. A year-long reminder is a few sleeps, not one.

  • Timers stopped dying on deploy. A restart loses nothing, because the schedule was never in the process.
  • Replicas stopped duplicating work. Services could finally scale out without their nightly jobs multiplying.
  • Jobs became things you can ask about — cancel one, pause one, see what fired and what is still coming.
  • Nobody wrote a fourth timer. New services register a job instead of rolling their own.
  • Redis is in the critical path now. The schedule lives in memory, so it has to be persisted and replicated or a failover quietly loses every pending timer.
  • Two stores must agree. A row in the table and an entry in the sorted set can drift apart, so a reconcile path is needed, not optional.
  • Lua is hard to test. The hardest logic in the service is in a language the rest of the codebase doesn’t use and the type checker can’t see.
  • Delivery is still at-least-once. A reaped job can fire twice, so every consumer has to be idempotent. The scheduler makes that easier, not unnecessary.

What I’d do differently: make the sorted set a cache of the table rather than a second source of truth. Rebuilding it from the table on boot would turn a whole class of “they disagree” bugs into a startup step.

  • Put the move in one atomic step. “Read what’s due, then mark it taken” is two steps and a race. One script makes it one step, and the race stops existing.
  • In-flight work needs a timestamp. Knowing a job is being worked on is useless; knowing since when is what makes a crash recoverable.
  • Timers beat polling. Asking “anything due?” on a loop costs the same whether there is work or not. Sleeping until the next known due time costs nothing when idle.
  • Cancel and pause are a state machine. Bolted on afterwards they are a nightmare, because a job can be mid-claim when the request arrives.

The two-minute version

  1. “Every service had its own in-process timers. A restart lost them, replicas duplicated them, and nothing could be cancelled.”
  2. “So we built one scheduler. Postgres holds what a job is. A Redis sorted set holds when it is next due, scored by due time.”
  3. “A worker sleeps until the lowest score, then claims due jobs with a Lua script, so the read and the move are atomic.”
  4. “Claimed jobs sit in a second sorted set scored by claim time, and a reaper puts back anything held too long. That covers a worker dying mid-job.”
  5. “Due jobs go out on RabbitMQ, so consumers receive them like any other message.”

Questions it invites

  • Why not poll a table? It works, but it costs the same idle as busy, and the poll interval becomes your accuracy.
  • What if Redis loses the set? That is the weak point. The table is the durable record, and I’d rebuild the set from it on boot.
  • Exactly once? No. At-least-once, because a reaped job can fire twice. Consumers stay idempotent.
  • Cancel a job mid-flight? Waiting, it is removed. Already claimed, the pause is recorded as a request and the worker parks it at the next safe point.

  • Saying “exactly once”. It isn’t, and the follow-up will find that out.
  • Skipping the reaper. The claim is the easy half.
  • Claiming the whole platform. Be clear which parts were mine.
