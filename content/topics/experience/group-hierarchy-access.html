This was at Vymo, a sales engagement platform used by banks, insurers and lenders. Their field teams are organised by geography, and so is everything they are allowed to see.

A typical client hierarchy runs five levels deep:

Zone → Region / Cluster → State → City → Branch, for example WEST → MP 2 → MP → BHOPAL → HOSHANGABAD.

One-line version: I replaced walking the org tree on every read with two flat arrays — what a user may see, and which groups a record belongs to — so authorisation became a single indexed array intersection.

Every list, search and report has the same question behind it: which rows is this person allowed to see? And the answer depends on where they sit:

  • A field officer sees their own branch.
  • An area head sees every branch in their city.
  • A zonal head sees everything under their zone, which is hundreds of branches.

Done the obvious way, that is a tree walk on every request: find the user’s node, collect every node beneath it, then filter the records by that set. With 10,000-plus users and millions of leads, loans and collection accounts, the authorisation check costs more than the query it is protecting. It also has to work the same way across more than one datastore, which rules out anything clever that only one of them can do.

  • Five levels, and the shape differs per client. One client’s “cluster” is another’s “region”.
  • Reads dominate heavily. People scroll lists all day; the hierarchy changes rarely.
  • It had to hold in every store. The same rule applies to the document store and to the search index behind list and search APIs.
  • Exceptions are normal, not rare. A manager covering two branches during a handover isn’t a special case, it’s Tuesday.
  • Nothing may leak. A visibility bug here shows one bank’s branch the wrong customers.

Every record already belongs to a branch, and a branch has exactly one path up to its zone. That path never changes between reads. So compute it once, at write time, and store it.

So each user carries authorised_regions: the groups they may see. Each record carries granted_regions: its full lineage upward, plus any explicit grants. A user may see a record when those two arrays share at least one id.

Groups are created up front, one per node, per client. A user’s role and posting decide which group ids land in authorised_regions. A record’s branch decides its lineage.

The whole rule is “do these two arrays share anything?”, which every store we used can answer from an index:

-- PostgreSQL: overlap operator, backed by a GIN index on the array
CREATE INDEX leads_granted_regions ON leads USING gin (granted_regions);

SELECT * FROM leads
WHERE  granted_regions && $1      -- $1 = the user's authorised_regions
AND    status = 'open';
// MongoDB: $in against a multikey index on granted_regions
db.leads.find({
  granted_regions: { $in: user.authorised_regions },
  status: 'open',
});

In the search index it is a terms filter on the same field. Three stores, one rule, and no join or recursion in any of them.

The check never changes shape, whatever the user is. A zonal head’s array has one element, the same as a field officer’s. Depth in the tree costs nothing at read time, because the lineage was written down when the record was written.

The check itself is the easy half

The hard half is keeping both arrays true as the business moves underneath them.

When the hierarchy itself is re-mapped

Move a branch from one cluster to another and every record under it is now carrying a stale lineage. There is no clever trick: the affected records have to be recomputed and backfilled, in the background, in batches. The job has to be restartable and idempotent, because it will be interrupted.

When a person moves

A promotion or a transfer changes authorised_regions. That part is one record. The catch is anything that cached the old array — a session, a token, a warm cache — because until it is invalidated the person keeps their old view. Caching the array is the obvious optimisation and the obvious bug.

  • Authorisation stopped scaling with depth. A zonal head’s query costs the same as a field officer’s.
  • One rule, three stores. The document store, the relational store and the search index all express the same check natively.
  • Exceptions stopped being code. A manager covering two branches is two ids in an array, not a branch in the query builder.
  • The hierarchy got out of the request path. Reads no longer touched the group tree at all.
  • Write amplification. One branch re-map can touch an enormous number of records. The cost didn’t go away, it moved to where it is paid rarely instead of constantly.
  • A window of being wrong. Between the re-map and the end of the backfill, some records answer with the old lineage. Correctness is now eventual, and that has to be stated out loud rather than discovered.
  • Grants only, no denies. The model can say “you may see this”. It cannot say “you may see everything in the zone except this one branch”, which would need a second, opposite check.
  • The arrays are a derived copy. The tree is still the truth, so a reconcile job that re-derives and compares isn’t optional.

What I’d do differently: build the verifier before the backfill. A job that walks the tree and reports records whose lineage disagrees is what makes the whole design trustworthy, and it is the thing that gets written last.

  • Put the cost where the traffic isn’t. When reads outnumber writes by orders of magnitude, almost any amount of write-time work is a good trade.
  • A tree you only ask one question of is a set. “Is this record under that node?” doesn’t need a tree at read time — it needs the ancestors written down.
  • Make the exception use the normal path. Cross-region access needed no new code because it was the same array with another id in it.
  • Derived data needs a verifier, not just a writer. Anything you compute and store will drift, and you want to find out before a customer does.

The two-minute version

  1. “Field teams are organised five levels deep, and what you can see depends on where you sit in that tree.”
  2. “The naive version walks the tree on every read, and the heaviest users are the ones highest up.”
  3. “So we flattened it. Each record stores its full lineage as an array of group ids; each user stores the ids they’re allowed to see.”
  4. “Visibility is then one indexed array intersection, which Postgres, Mongo and Elasticsearch all do natively.”
  5. “The cost moves to write time: re-mapping a branch means backfilling its records, and moving a person means invalidating anything that cached their array.”

Questions it invites

  • What happens during a re-map? A window where some records are stale. Eventual, and known.
  • Can you express a deny? No. It is a grant model, and that is a real limit.
  • Why not a recursive query? Correct, but paid on every read by the busiest users.
  • How do you know the arrays are right? A reconcile job that re-derives from the tree and reports disagreements.

Traps

  • Selling it as free. It is a trade, and the write-time half is the interesting half.
  • Forgetting the cache. The first thing anyone does is cache the user’s array.
  • Claiming the whole platform. Be clear which parts were mine.
  • Field teams sit in a five-level geography, and row visibility follows that tree.
  • Walking the tree per request makes authorisation cost more than the query it protects, and hurts senior users most.
  • Each record stores granted_regions: its full lineage upward, plus explicit grants.
  • Each user stores authorised_regions: the group ids their role and posting allow.
  • Access is granted when the two arrays share at least one id.
  • That intersection is one indexed operation in Postgres, Mongo and Elasticsearch alike.
  • Depth stops mattering: a zonal head’s check costs the same as a field officer’s.
  • Exceptions like a cross-region manager are extra ids, not extra query logic.
  • The cost moves to write time: re-mapping a branch means an asynchronous backfill of its records.
  • The arrays are derived data, so they need a reconcile job and careful cache invalidation.
