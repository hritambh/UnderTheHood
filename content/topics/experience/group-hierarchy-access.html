This was at Vymo, a sales engagement platform used by banks, insurers and lenders. Their field teams are organised by geography, and so is everything they are allowed to see.

A typical client hierarchy runs five levels deep:

Zone → Region / Cluster → State → City → Branch, for example WEST → MP 2 → MP → BHOPAL → HOSHANGABAD.

One-line version: I replaced walking the org tree on every read with flat arrays of group ids on both sides — expanded downward for people, upward for records — so authorisation became a single indexed overlap check.

Every list, search and report has the same question behind it: which rows is this person allowed to see? And the answer depends on where they sit:

  • A field officer sees their own branch.
  • A state manager sees every city and branch in their state.
  • A zonal head sees everything under their zone, which is hundreds of branches.

Done the obvious way, that is a tree walk on every request: find the user’s node, collect every node beneath it, then filter the records by that set. With 10,000-plus users and millions of leads, loans and collection accounts, the authorisation check costs more than the query it is protecting. It also has to work the same way across more than one datastore, which rules out anything clever that only one of them can do.

  • Five levels, and the shape differs per client. One client’s “cluster” is another’s “region”.
  • Reads dominate heavily. People scroll lists all day; postings and hierarchies change rarely.
  • It had to hold in every store. The same rule applies to the document store and to the search index behind list and search APIs.
  • Exceptions are normal, not rare. A manager covering two branches during a handover isn’t a special case, it’s Tuesday.
  • Nothing may leak. A visibility bug here shows one bank’s branch the wrong customers.

The tree walk is the same every time until something is re-organised. So do it off the request path and store the answer.

Three fields carry it, and it is worth keeping them straight:

  • user.granted_regions — what the person was assigned. A state manager gets a zone, a region and a state, so their profile holds ga_west, ga_MP_2, ga_MP. Nothing below that.
  • user.authorised_regions — what that expands to. A cron walks down from the deepest assigned node and writes back every group under it.
  • record.accessible_regions — the record’s lineage. A lead in Hoshangabad carries its whole path upward, plus any explicit grants.

Groups are created up front, one per node, per client. The cron is what makes a posting mean something: without it a state manager holds three ids that match no record, because a record never stores an assignment id.

At read time the whole rule is “do these two arrays share anything?”, which every store we used can answer from an index:

-- PostgreSQL: overlap operator, backed by a GIN index on the array
CREATE INDEX leads_accessible_regions ON leads USING gin (accessible_regions);

SELECT * FROM leads
WHERE  accessible_regions && $1   -- $1 = the user's authorised_regions
AND    status = 'open';
// MongoDB: $in against a multikey index on accessible_regions
db.leads.find({
  accessible_regions: { $in: user.authorised_regions },
  status: 'open',
});

In the search index it is a terms filter on the same field. Three stores, one rule, no join and no recursion in any of them.

Both sides being flattened means a match can land at any level. It also means an exception works from either end: give a person an extra branch id, or give one record an extra region id, and the same query honours it with no new branch in the code.

The check is the easy half. Keeping both arrays true as the business moves underneath them is the rest of it.

The fifteen-minute window

A new joiner, a promotion or a transfer changes granted_regions immediately, but they can see nothing new until the cron expands it. Fifteen minutes of “I’ve been moved and the app disagrees” is a support ticket, so the expansion also has to be triggerable on demand for the cases people actually notice.

Re-mapping a branch moves work at both ends

Move a branch under a different cluster and two things are now stale: every record beneath it is carrying the old lineage, and every user whose expansion included it has the wrong set. Records need an asynchronous backfill in batches; users get fixed by the next cron run. The backfill has to be restartable and idempotent, because it will be interrupted.

Senior users carry enormous arrays

A zonal head’s expansion is every group in the zone. That array is big in the user record, big in the cache, and big as the right-hand side of the query. It is the cost of making depth free at read time, and it lands hardest on exactly the users who read the most.

  • Authorisation stopped scaling with depth. A zonal head’s query is the same shape as a field officer’s.
  • One rule, three stores. The document store, the relational store and the search index all express the same check natively.
  • Exceptions stopped being code. A manager covering two branches is two ids in an array, not a branch in the query builder.
  • The hierarchy left the request path. Reads no longer touch the group tree at all; only the cron and the backfill do.
  • Access is eventually consistent. Up to fifteen minutes between a posting change and the view that matches it. Fine for a transfer, awkward for a new joiner on day one.
  • Two derived arrays, not one. Strictly, the overlap only needs one side flattened. Doing both buys exceptions from either end, and costs a second thing that can drift.
  • Write amplification. One branch re-map can touch an enormous number of records. The cost didn’t go away; it moved to where it is paid rarely instead of constantly.
  • Grants only, no denies. The model can say “you may see this”. It cannot say “everything in the zone except this one branch”, which needs a second, opposite check.

What I’d do differently: build the verifier before the backfill. A job that walks the tree and reports every user and record whose array disagrees with it is what makes the design trustworthy, and it is the thing that gets written last.

  • Put the cost where the traffic isn’t. When reads outnumber writes by orders of magnitude, almost any amount of background work is a good trade.
  • A tree you only ask one question of is a set. “Is this record under that node?” doesn’t need a tree at read time, it needs the membership written down.
  • A periodic job needs a manual trigger. Fifteen minutes is fine on average and unacceptable in the one case a person is watching.
  • Derived data needs a verifier, not just a writer. Anything you compute and store will drift, and you want to find out before a customer does.

  5. “The cost moves off the request path: a posting change waits for the cron, and a branch re-map means backfilling records.”

Questions it invites

  • Why a cron and not compute it on assignment? Because the tree moves too, not just the person. A periodic re-derive catches both; on-demand is the optimisation on top.
  • Why flatten both sides? One would do for the basic rule. Both lets an exception be added from either end.
  • Can you express a deny? No. It is a grant model, and that is a real limit.
  • How do you know the arrays are right? A reconcile job that re-derives from the tree and reports disagreements.

Traps

  • Saying “union”. It is an overlap: the two arrays must share an id. A union would match everything.
  • Selling it as free. The write-time half is the interesting half.
  • Claiming the whole platform. Be clear which parts were mine.
  • Field teams sit in a five-level geography, and row visibility follows that tree.
  • Walking the tree per request makes authorisation cost more than the query it protects, and hurts senior users most.
  • A user’s granted_regions is only what they were assigned — a state manager gets zone, region and state, nothing below.
  • A cron every fifteen minutes walks down from the deepest assigned node and writes every group beneath it into authorised_regions.
  • A record’s accessible_regions holds its lineage upward, plus explicit grants.
  • Access is granted when the user’s expanded array and the record’s array overlap — share at least one id.
  • That overlap is one indexed operation in Postgres, Mongo and Elasticsearch alike.
  • Exceptions work from either end, because both sides are flat arrays.
  • The price is eventual consistency: up to fifteen minutes between a posting change and the matching view.
  • Re-mapping a branch leaves records stale until a backfill, and users stale until the next cron run.
