Every app has to keep its data somewhere, and the first fork in the road is this one. Do you use a SQL database like PostgreSQL or MySQL? Or a NoSQL database like MongoDB, DynamoDB or Cassandra?

The question comes up at three moments:

  • At the start of a project, when there is no data yet and everything is a guess.
  • When a new feature brings data that looks nothing like the rest. Chat messages in a shopping app, say.
  • When the current database is struggling, and someone says “we should have used the other kind”.

It is hard for one reason. At small size, both work fine. The differences only show up later: when the data is big, when the questions you ask of it change, or when two things must be updated together. By then, switching is expensive. So you are choosing based on a future you can’t fully see.

One-line version: SQL gives you any question and safe changes on one main machine. NoSQL gives you a few planned questions at almost any size. Pick by how you’ll read the data and how big it will really get.

SQL (relational databases)

Data lives in tables with fixed columns, and rows in one table point to rows in another. You ask questions in the SQL language, and a join lets one question pull matching rows from several tables. A transaction lets you change several rows as one step: all of it happens, or none of it. PostgreSQL, MySQL and SQL Server are the usual names. It is best at data with many links, questions you didn’t plan for, and changes that must never be half done.

NoSQL (non-relational databases)

This is a family, not one thing. Key-value stores (Redis, DynamoDB) fetch a value by its key. Document stores (MongoDB) keep whole JSON-like objects. Wide-column stores (Cassandra) keep huge sorted lists of rows per key, and graph stores (Neo4j) keep things and the links between them. What most share: no joins, a shape you design around your queries, and data split across many machines from day one. It is best at simple lookups by key, at a size or write rate one machine can’t hold.

Think about two ways to keep a town’s paperwork.

A records office. Every paper goes on a standard form and into the right cabinet. Forms point to each other: a house record names its owner, and the owner has a record of their own. A clerk can answer almost anything. “Which houses on this street changed owner in the last five years?” takes a few minutes of cross-checking. But nothing gets in without the right form. And it is one building. When it fills up, growing it is a real project.

A self-storage warehouse. You get a numbered unit and put in whatever you like, in any shape. Give the number and your box is in your hands in seconds. When the warehouse fills up, the company opens another one down the road, and nobody notices. But ask “which units have a red bicycle in them?” and the answer is to open every unit. Unless you kept your own list from the start.

  • The records office is SQL: strict forms, cross-references, any question, one main building.
  • The warehouse is NoSQL: any shape, instant by number, grows by adding buildings, and bad at questions you didn’t plan for.

Neither is the better place. A land registry in a warehouse would be a mess. A records office for ten million boxes of household stuff would never keep up.

Six questions decide this. For each one, here is which answer points which way.

1. How will you read the data?

This is the biggest one.

  • Many different questions, and new ones every month (reports, filters, admin screens, “show me all X where Y”): this points to SQL. You store the data once and ask anything later.
  • A few fixed questions, each by a known key (“get this user’s cart”, “latest 50 messages in this chat”): this points to NoSQL. You lay the data out for exactly those reads, and they stay fast at any size.

2. What shape is the data?

  • Many kinds of things that point to each other (customers, orders, products, payments): SQL. Links and joins are what it is built around.
  • Self-contained items that are read whole, often with different fields per item (a product page, a user’s settings, a sensor reading): NoSQL, usually a document store.

Here is one order, stored both ways.

-- SQL: the order is rows in three tables, joined when read
SELECT o.id, c.name, i.product_id, i.qty
FROM orders o
JOIN customers c   ON c.id = o.customer_id
JOIN order_items i ON i.order_id = o.id
WHERE o.id = 8812;
// Document store: the same order is one document, read in one go
{
  "_id": 8812,
  "status": "paid",
  "customer": { "id": 42, "name": "Asha", "city": "Pune" },
  "items": [
    { "productId": 7,  "name": "Desk lamp", "qty": 2 },
    { "productId": 19, "name": "USB cable", "qty": 1 }
  ]
}

The document has a copy of the customer’s name inside it. Keeping copies like this is called denormalising. The read is one fast lookup. The price: if Asha changes her name, every order holding a copy still has the old one, until your code updates them all.

3. Must several things change together?

  • Yes, across different records (take money from one account and add it to another, reduce stock and create the order): SQL. Transactions across any rows are its normal mode.
  • No, each write touches one item (save this message, update this profile): NoSQL is fine. Every NoSQL store can update one item safely.

The same question covers reads. A SQL database answers from one main machine by default, so you read what you just wrote. Many NoSQL stores keep copies on several machines and may answer from one that is a moment behind. That is eventual consistency: all copies agree in the end, but not at every instant. If a stale read would be a bug, that pushes towards SQL. If a short delay is harmless, it doesn’t matter.

4. How big, and how many writes?

  • It fits on one good machine, now and for the next few years: SQL. One machine is the simplest thing to run, and SQL gets everything out of it.
  • More writes or more data than one machine can take: NoSQL. It splits data across machines by itself, and you grow by adding machines. SQL can be split too, but you do the work. The topic “Database Sharding” shows how much work that is.

5. How often does the structure change?

  • The structure is known and many programs write to it: SQL. The database checks every write against the schema, the declared list of tables, columns and types. Bad data is refused at the door.
  • The structure is still moving, or differs per item: NoSQL. You can save a new field today without changing anything first. Your code now does the checking.

6. What does the team know, and what can it run?

  • A small team with general skills: SQL. Nearly every developer has used it, and the tools are decades old.
  • A team that already runs a NoSQL store well, or uses a cloud service that runs it for them: NoSQL costs them much less than it would cost a team starting cold.

Let’s take one feature and one number, and watch the answer change. The feature is chat inside an app. The number is how many people use it.

Assumptions (made up for this example, not benchmarks):

  • Each active user sends 20 messages a day. A stored message is about 300 bytes.
  • The busiest moment is 5 times the average.
  • One well-sized SQL machine is comfortable up to 5,000 small writes a second and 2 TB of data. Real limits depend on the hardware and the queries.
  • The main read is always the same: the latest messages in one conversation.

Case 1: 50,000 daily users

  • Messages: 50,000 × 20 = 1 million a day.
  • Writes: 1,000,000 ÷ 86,400 ≈ 12 a second. At the peak, 12 × 5 ≈ 58 a second.
  • Storage: 1,000,000 × 300 bytes = 300 MB a day, so about 110 GB a year.

With SQL: 58 writes a second is about 1% of what one machine can take. 2 TB ÷ 110 GB means the disk lasts 18 years. One table, with an index on conversation and time, does the job. And you get extras for free. Show sender names with a join. Let a moderator search one user’s messages. Delete everything a user wrote with one statement.

With NoSQL: it works, but you are paying for size you don’t have. A wide-column store wants at least three machines, here to hold 110 GB. The moderator’s search needs a second copy of the data laid out by user, planned ahead. Sender names need a second lookup from your code.

At this size, SQL is the easy pick.

Case 2: 50 million daily users

Same feature. One number changed: a thousand times the users.

  • Messages: 50,000,000 × 20 = 1 billion a day.
  • Writes: 1,000,000,000 ÷ 86,400 ≈ 11,600 a second. At the peak, about 58,000 a second.
  • Storage: 300 GB a day, so about 110 TB a year.

With SQL: 58,000 ÷ 5,000 means about 12 machines just for the writes. Storage is worse: 110 TB ÷ 2 TB is 55 more machines’ worth every year. So you split the table by conversation across a growing fleet, and build the routing and the moving of data yourself. It can be done, and tools exist to help. But joins and transactions now only work inside one piece. Those were the reasons to pick SQL.

With NoSQL: this is the job a wide-column store was built for. The conversation ID is the partition key, the value that decides which machine holds a row. Writes spread across the machines by themselves. The main read hits one machine and finds the rows already sorted by time. To grow, you add machines. The costs are still there: the moderator’s search needs its own layout or a search system, and a message may show up a moment late on another copy.

At this size, NoSQL is the easy pick.

Where does it flip?

  • Storage flips first. 2 TB a year is 2,000 ÷ 110 ≈ 18 times case 1, so about 900,000 daily users. From there, one machine fills up within a year.
  • Writes flip later. 5,000 a second at peak is 5,000 ÷ 58 ≈ 86 times case 1, so about 4.3 million daily users.

So below a few hundred thousand users, SQL without a second thought. Above a few million, NoSQL. In between, it depends on how fast you are growing and how much you use joins on this data. Notice what never changed: the feature. Only the number did.

Pick SQL when

  • You don’t know yet what questions you’ll ask of the data.
  • The data is full of links: this belongs to that, which belongs to something else.
  • Money, stock, bookings, or anything where a half-done change is a real problem.
  • You need reports and admin screens straight from the live data.
  • The data will fit on one machine for years. Do the sum before you assume it won’t.
  • Several services or teams write to the same data, and you want one place to enforce the rules.

Pick NoSQL when

  • You can write down the three or four reads you need, and each one is by a key.
  • The write rate or the data size is past one machine, or the sum says it will be soon.
  • Items are self-contained and read whole: carts, sessions, profiles, events, messages, sensor readings.
  • Fields differ a lot from item to item, like products in a catalogue.
  • Staying up and fast matters more than every read being perfectly fresh.
  • The data is naturally a graph, like who follows whom. That points to a graph store.

Pick both when

One product often has two kinds of data. Then use two databases, each for the part it suits. The “Notification Service” design does this: PostgreSQL for the small settings tables, Cassandra for the huge inbox.

When it doesn’t matter much

  • A small app with a few GB of simple data. Either will run it for years. Pick the one your team knows.
  • You only need a few flexible fields. PostgreSQL and MySQL have a JSON column type. One loose column inside a normal table covers this without changing database.
  • A prototype you’ll throw away. Use whatever gets it running today.

SQL costs that show up later

  • Changing a huge table. Adding a column or an index to a table with a billion rows can take hours and may block writes. Teams end up using special tools and planning it like a release.
  • The day one machine is not enough. Splitting a SQL database across machines is a project of months, and it takes away some joins and transactions.
  • One main machine for writes. When it fails, a copy takes over. Writes stop for seconds to minutes while that happens, and someone has to have tested it.
  • Slow queries you didn’t know you wrote. “Any question” includes very expensive ones. One careless report can slow the whole app.
  • Code shaped like objects, data shaped like tables. The tools that map one to the other are handy, and they quietly fire hundreds of small queries when you’re not looking.

NoSQL costs that show up later

  • The question nobody planned for. A new way to read the data often means a new table or index, plus a job to fill it from all the old data.
  • Copies that drift apart. The same fact is stored in several places for speed. Your code has to update every copy, and when it misses one, nothing complains.
  • The schema didn’t go away. It moved into your code. Five years of items in five slightly different shapes are all still there, and every reader has to handle each one.
  • Stale-read bugs. They don’t show up on a laptop. They show up under load, once in ten thousand requests.
  • Reports need another system. Without joins, analysis usually means copying the data out to a warehouse first.
  • One busy key. If one partition key gets most of the traffic, one machine is overloaded while the rest sit idle. Adding machines doesn’t help.

Moving is possible in both directions. It is never quick, and one direction is harder.

From SQL to NoSQL

You rarely move everything. You move the one table that has outgrown the machine, and the rest stays.

  1. Rewrite the code that joins to that table, or uses it in transactions, so it no longer does. This is most of the work.
  2. Design the new layout around the reads you actually have.
  3. Write to both databases for a while. Copy the old data across. Compare the two.
  4. Switch reads to the new store, then stop writing to the old table.

What helps: the data you are moving is clean. The schema made sure every row has the same shape and every link points at something real.

From NoSQL to SQL

The steps are the same, with one extra job in front: cleaning.

  • Items written over the years have different shapes. Each one has to be mapped to the new columns.
  • Copies of the same fact disagree. You have to decide which one is right.
  • Some items point at things that were deleted long ago. A SQL database will refuse those rows.

In return, once the data is in, the database guards all of this for you from then on.

Which way is easier?

SQL to NoSQL is the easier direction, for one table at a time. You start from clean data and a known list of reads. Going the other way, you find out how messy the data is while you move it.

So when you can’t tell which you need, that is a reason to start with SQL: it is the easier side to leave. When you can tell, because the size and the reads are clear from day one, this doesn’t apply. Start where you’ll end up.

Keeping the door open

  • Keep all database calls for one kind of data in one place in the code. Then a move changes one file, not two hundred.
  • Make your own IDs, like UUIDs. Don’t depend on an ID format only one database produces.
  • In NoSQL, check the shape of every item before you save it, and store a version number in each one.
  • In SQL, go easy on joins to a table you think may have to move out one day.
  • Choosing for scale you don’t have. A cluster built for a billion rows is a lot of running cost for a table with a million. Do the sum first, as in the chat example.
  • Thinking NoSQL means no schema. The data always has a structure. The only question is whether the database checks it or your code does.
  • Treating NoSQL as one thing. Redis, MongoDB and Cassandra have less in common with each other than MongoDB has with PostgreSQL. “Should we use NoSQL?” is not a full question. Which kind?
  • Using a NoSQL store like a SQL one. Splitting data into many linked collections and joining them in your code gives you the slow parts of both.
  • Believing SQL can’t grow. A bigger machine, copies for reads, and splitting old data off carry a SQL database a very long way. Most apps never get past that.
  • Going by old labels. Several NoSQL stores now have transactions across items. SQL databases store JSON. Check what the actual product does today.
  • Forcing one database to do everything. When two parts of the app have very different data, two databases can be simpler than one bent out of shape.
  • Picking by fashion. “That big company uses it” says nothing about your data. Their problem is probably not yours.

How to answer “which would you pick?”

Don’t name a database first. Go in this order:

  1. Ask about the reads. “What are the main queries? Are they by key, or do we need filters and joins?”
  2. Ask about the size. Work out writes per second and storage per year, out loud.
  3. Ask what must be exact. “Is there anything here where a half-done change or a stale read is a real problem?”
  4. Then pick, and give the reason. “Orders and payments go in PostgreSQL, because they need transactions and fit on one machine. The activity feed goes in Cassandra, because it is 50,000 writes a second and always read by user.”
  5. Say what would change your mind. “If the feed were a hundred times smaller, I’d keep it in PostgreSQL too.”

Follow-ups to expect

  • What does ACID mean? The four promises of a SQL transaction. All of it happens or none of it. The rules of the schema always hold. Two transactions don’t trip over each other. And once it says “saved”, it stays saved.
  • Can SQL scale across machines? Yes. Copies take the reads, and sharding splits the writes. It is more work than in a store built for it.
  • Can NoSQL do transactions? One item, always. Across items, some products can, with limits and a speed cost.
  • Why are NoSQL writes fast? Each write touches one item on one machine, with no links to check and usually no waiting for every copy.
  • What is eventual consistency? Copies of the data agree in the end, but a read just after a write may get the old value.
  • Would you ever use both? Often. Different data in one product can suit different stores.

What a strong answer includes

  • The reads and the numbers come before the choice.
  • A named kind of NoSQL store, not “NoSQL” in general.
  • One cost of the option you picked, said without being asked.
  • The signal that would flip the decision.
  • No claim that one side is always better.
  • SQL keeps data in linked tables with a schema the database enforces. It can answer almost any question, and can change many rows as one step.
  • NoSQL is a family: key-value, document, wide-column and graph stores. Most drop joins and spread data across many machines by design.
  • The biggest question is how you’ll read the data. Many changing questions point to SQL. A few fixed reads by key point to NoSQL.
  • Linked data and changes that must happen together point to SQL. Self-contained items, read whole, point to NoSQL.
  • If the data fits on one machine for years, SQL is simpler. Past one machine, NoSQL grows by adding machines, while SQL has to be split by hand.
  • The same chat feature is an easy SQL pick at 50,000 users and an easy NoSQL pick at 50 million. Do the sum before choosing.
  • NoSQL still has a schema. It lives in your code, along with the job of keeping copied data in step.
  • Moving one table from SQL to NoSQL is easier than the reverse, because SQL data is already clean. So SQL is the safer start when you can’t tell.
  • One product can use both, each for the data it suits.
