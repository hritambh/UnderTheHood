Every app has to keep its data somewhere, and the first fork is this one. A SQL database like PostgreSQL or MySQL, or a NoSQL one like MongoDB, DynamoDB or Cassandra? It comes up at three moments:

  • At the start of a project, when there is no data yet.
  • When a new feature brings data unlike the rest — chat messages in a shopping app.
  • When the database is struggling and someone says “we should have used the other kind”.

It is hard for one reason: at small size both work fine. The differences only show up when the data is big, when the questions change, or when two things must change together — and by then switching is expensive.

One-line version: SQL gives you any question and safe changes on one main machine. NoSQL gives you a few planned questions at almost any size. Pick by how you'll read the data and how big it will really get.

SQL (relational)

Data lives in tables with fixed columns, and rows point at rows in other tables. A join pulls matching rows from several tables in one question; a transaction changes several rows as one step, all or nothing. Best at data with many links, questions you didn't plan for, and changes that must never be half done.

NoSQL (non-relational)

A family, not one thing. Key-value (Redis, DynamoDB) fetches a value by its key. Document (MongoDB) keeps whole JSON-like objects. Wide-column (Cassandra) keeps huge sorted lists of rows per key. Graph (Neo4j) keeps things and the links between them. What most share: no joins, a shape designed around your queries, data split across machines from day one. Best at simple lookups by key at a size one machine can't hold.

Two ways to keep a town's paperwork. A records office: every paper on a standard form in the right cabinet, forms pointing at each other — a house record names its owner, who has a record of their own. A clerk can answer almost anything; “which houses on this street changed owner in five years?” is a few minutes of cross-checking. But nothing gets in without the right form, and it is one building that is a real project to grow.

A self-storage warehouse: a numbered unit holding whatever you like, any shape. Give the number and your box is in your hands in seconds, and when it fills the company opens another down the road. But ask “which units hold a red bicycle?” and the answer is to open every unit — unless you kept your own list from the start.

The records office is SQL; the warehouse is NoSQL. Neither is better. A land registry in a warehouse would be a mess; a records office for ten million boxes of household stuff would never keep up.

Six questions decide it. The first is by far the biggest.

Where does it flip? Storage first, writes later.

Storage flips at 2,000 ÷ 110 ≈ 18 times case 1, about 900,000 users. Writes flip at 5,000 ÷ 58 ≈ 86 times, about 4.3 million. In between it depends on how fast you are growing and how much you join on this data. Notice what never changed: the feature.

Pick SQL when

  • You don't know yet what questions you'll ask.
  • Money, stock or bookings, where a half-done change is a real problem.
  • You need reports and admin screens off the live data.
  • It fits one machine for years. Do the sum before assuming it won't.

Pick NoSQL when

  • You can write down the three or four reads you need, each by a key.
  • The write rate or data size is past one machine, or soon will be.
  • Fields differ a lot between items, like catalogue products.
  • Staying up and fast matters more than every read being fresh.

Pick both, or neither

One product often has two kinds of data, so use two databases: the Notification Service design uses PostgreSQL for the settings tables and Cassandra for the huge inbox. And sometimes it barely matters — a few GB of simple data runs on either for years, a prototype should use whatever ships today, and “a few flexible fields” is answered by a JSON column in a normal table.

SQL costs that show up later

  • Changing a huge table. Adding a column or index to a billion rows can take hours and block writes.
  • The day one machine isn't enough. Splitting across machines is months of work, and takes away some joins and transactions.
  • One main machine for writes. When it fails a copy takes over, and writes stop for seconds to minutes — so someone must have tested it.

NoSQL costs that show up later

  • The question nobody planned for. A new way to read means a new table or index, plus a job to fill it from all the old data.
  • Copies that drift apart. The same fact lives in several places for speed, and when your code misses one, nothing complains.
  • The schema didn't go away, it moved into your code. Five years of items in five shapes are all still there, and every reader handles each one.
  • One busy key. If one partition key takes most of the traffic, one machine is overloaded while the rest idle.

Moving is possible both ways. Neither is quick, and one is harder.

From SQL to NoSQL

You rarely move everything — only the table that outgrew the machine. Rewrite the code that joins to it or uses it in transactions, which is most of the work. Design the new layout around the reads you have, write to both stores while you copy the old data across and compare, switch reads over, stop writing to the old table. What helps: the data is clean, because the schema made sure of it.

From NoSQL to SQL

Same steps, with a cleaning job in front. Items written over the years have different shapes, each needing a mapping. Copies of the same fact disagree. Some point at things deleted long ago, which SQL will refuse. In return, once it is in, the database guards all of that.

SQL to NoSQL is the easier direction: you start from clean data and a known list of reads. So when you can't tell which you need, that is a reason to start with SQL — it is the easier side to leave. To keep the door open: hold all database calls for one kind of data in one place, make your own IDs, check the shape of every item before saving it, and go easy on joins to a table that may move out one day.

  • Choosing for scale you don't have. A cluster built for a billion rows is a lot of cost for a table with a million.
  • Thinking NoSQL means no schema. The data always has a structure. The only question is whether the database checks it or your code does.
  • Treating NoSQL as one thing. Redis, MongoDB and Cassandra have less in common with each other than MongoDB has with PostgreSQL. “Should we use NoSQL?” is not a full question.
  • Using a NoSQL store like a SQL one. Linked collections joined in your code gives you the slow parts of both.
  • Believing SQL can't grow. A bigger machine, read copies and splitting old data off carry it a long way. Most apps never get past that.
  • Going by old labels. Several NoSQL stores now do transactions across items, and SQL databases store JSON.

How to answer “which would you pick?”

Don't name a database first. Go in this order:

  1. The reads. “What are the main queries? By key, or filters and joins?”
  2. The size. Work out writes per second and storage per year, out loud.
  3. What must be exact. “Is a half-done change or a stale read a real problem?”
  4. Then pick, with the reason. “Orders in PostgreSQL, because they need transactions and fit on one machine. The feed in Cassandra, because it is 50,000 writes a second and always read by user.”
  5. Say what would change your mind. “A hundred times smaller and I'd keep the feed in PostgreSQL too.”

Follow-ups to expect

  • What does ACID mean? A transaction's four promises: all or nothing, the schema's rules always hold, transactions don't trip over each other, and once saved it stays saved.
  • Can SQL scale across machines? Yes: copies take the reads, sharding splits the writes. More work than in a store built for it.
  • Can NoSQL do transactions? One item always; across items some can, with limits and a speed cost.

A strong answer puts the reads and the numbers before the choice, names a kind of NoSQL store, volunteers one cost of its own pick, and says what would flip it.

  • SQL keeps data in linked tables with an enforced schema: almost any question, and many rows changed as one step.
  • NoSQL is a family — key-value, document, wide-column, graph. Most drop joins and spread data across machines by design.
  • The biggest question is how you'll read it: many changing questions point to SQL, a few fixed reads by key to NoSQL.
  • Linked data and changes that go together point to SQL; self-contained items read whole point to NoSQL.
  • If it fits one machine for years, SQL is simpler. Past that, NoSQL grows by adding machines; SQL must be split by hand.
  • The same chat feature is an easy SQL pick at 50,000 users and an easy NoSQL pick at 50 million.
  • NoSQL still has a schema; it lives in your code, with the job of keeping copies in step.
  • Moving one table from SQL to NoSQL is easier than the reverse, because SQL data is already clean. So SQL is the safer start when you can't tell.
  • One product can use both, each for the data it suits.
