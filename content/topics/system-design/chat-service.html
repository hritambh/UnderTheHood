You type “on my way”, hit send, and a grey tick turns into two blue ones. The other person is on a train with one bar of signal, or their phone has been off for two days. Either way they get it, once, in the right order, and the app remembers everything.

WhatsApp, Slack and Telegram are the versions everyone knows. On screen it is a text box and a list. Underneath, the interesting problems are not about messages at all: they are about holding fifty million open connections, finding exactly one of them in a few milliseconds, and agreeing on an order when every phone’s clock is slightly wrong.

One-line version: a message is cheap to store and cheap to send. Everything expensive is in the connection layer in front of it.

Must do

  1. Send a message between two people and show it in under a second when both are online.
  2. Do the same for a group of up to 200 people.
  3. Hold messages for someone who is offline and give them the backlog, in order, when they return.
  4. Show delivery and read receipts.
  5. Show who is online, and when the rest were last seen.

Must be

  • Fast: under 500 ms from send to screen at the 95th percentile, for an online recipient.
  • In one order: everyone in a conversation sees the same messages in the same order.
  • Never lost: once the sender sees a tick, the message survives a crash, a restart and a bad deploy.
  • One bubble per message: a phone that retries on a flaky network must not produce two.
  • Up: 99.95%. People notice a chat app being down within seconds.

Not doing

  • Voice and video calls. Moving live media is a different system with different hardware.
  • End-to-end encryption. It barely changes the transport, but it takes away server-side search, server-side moderation and any ability to help a user who lost their phone. That is a product decision, not a design detail.
  • Photos and files. The phone uploads to storage directly and sends a link, the same pattern as any upload-heavy product.
  • Search across history. A separate index over the same messages.

Assumptions, made up: 100 million daily users, 50 million connected at peak, 40 messages sent per user per day, 300 bytes per stored message, peak 3× average. One in ten messages goes to a group, and groups average 50 people, so one send becomes about six deliveries.

Two things fall out of this. First, the fan-out is six to one, so the delivery path is the one that has to be cheap, not the write path. Second, 500 machines exist purely to hold open connections before a single message is processed. That is the real cost of this product, and it is why the connection layer gets its own tier.

Most of the traffic is not REST. The phone holds one WebSocket and sends frames down it — see WebSockets vs Polling vs SSE for why that beats polling here. REST handles the things that happen once, not continuously.

  • The ack carries the sequence number. That is what the phone stores, and what it sends back on reconnect to say how far it got.
  • The client id is how retries stay one bubble. The phone makes it before the first attempt and reuses it on every retry. The server keeps recent client ids in Redis for a few minutes and returns the original msgId instead of writing a second message.
  • History is a cursor, not a page number. Messages arrive while you scroll, so offsets shift under you — see Pagination in Backend Systems.

Three stores, because three very different jobs. Cassandra holds messages: 46,000 writes a second that never stop, 438 TB a year, and every read is “the last 50 of this conversation”. That is a single partition read in sorted order, which is the one thing a wide-column store is unbeatable at. PostgreSQL holds conversations and membership: small, relational, and the place a real foreign key is worth having. Redis holds presence and the connection registry, which is throwaway data with a heartbeat. SQL vs NoSQL covers the general choice.

-- messages, in Cassandra. One conversation is one partition, and the
-- rows inside it are already stored in the order we read them.
CREATE TABLE messages (
  conv_id   uuid,
  seq       bigint,         -- per conversation, assigned by the server
  msg_id    uuid,
  sender_id uuid,
  body      text,
  sent_at   timestamp,
  PRIMARY KEY ((conv_id), seq)
) WITH CLUSTERING ORDER BY (seq DESC);
-- conversations and membership, in PostgreSQL
CREATE TABLE members (
  conv_id       UUID NOT NULL,
  user_id       UUID NOT NULL,
  last_read_seq BIGINT NOT NULL DEFAULT 0,   -- one number, not one row
  joined_at     TIMESTAMPTZ NOT NULL,        -- per message per person
  PRIMARY KEY (conv_id, user_id)
);
CREATE INDEX members_user_idx ON members (user_id);

last_read_seq is worth stopping on. Read receipts look like they need a row per message per person — in a group of 200 that is 200 writes for every message anyone sends. One number per member says the same thing: everything up to 8829 has been read. Unread counts are subtraction, not a query.

Sending a message. The phone writes one frame down the socket it already has. Its gateway hands it to the chat service, which takes the next sequence number for that conversation, writes the row to Cassandra, and acks the sender. Only then does it fan out: it reads the member list from PostgreSQL, asks Redis where each member is connected, and pushes the message to those gateways, which write it down the right sockets.

Anyone not connected is handed to the push service — the one in Notification Service — and nothing else happens for them. There is no queue waiting with their name on it. Receipts travel the same way in reverse: a receipt frame moves last_read_seq forward and is pushed to the sender. Presence rides on the same heartbeat that keeps the registry alive — a live Redis key means online, its absence plus a timestamp means last seen — and changes are pushed as presence frames to whoever is looking at that chat.

How do you find one socket out of fifty million?

  • Ask every gateway. 500 internal calls per delivery, 830,000 deliveries a second at peak. That is 415 million calls a second to find one socket.
  • Hash the user id to a gateway. No lookup at all, and a box that dies rehashes its users onto neighbours while they are still reconnecting.
  • Keep a registry in Redis: user id to gateway, written on connect, refreshed by a heartbeat, with a 60-second TTL so a dead box’s entries clean themselves up.

We take the registry. It can be stale, and being stale is cheap: the push goes to a gateway that answers “not mine”, and the message falls through to the offline path, which is where it belonged anyway.

How does everyone see the same order?

Phone clocks disagree by seconds, and the network reorders things anyway. So no clock decides anything. The chat service takes the next number from one counter per conversation — a single Redis INCR on seq:g_19 — and that number is the order.

A global counter would be a bottleneck for every conversation at once. Per conversation, the contention is only between people typing in the same chat, which is a handful of writes a second even in a busy group. The numbers do a second job for free: a client holding 8829 that receives 8831 knows it missed one, and asks for the gap instead of silently showing a hole.

What about someone who was offline for two days?

The tempting answer is a queue per user. With 100 million users that is 100 million queues, nearly all empty, all needing to be created, drained and cleaned up.

We already have something better. The messages are in Cassandra, in order, grouped by conversation, and every member row carries last_read_seq. So the backlog is not stored anywhere — it is computed. The phone reconnects and says “conversation g_19, I have up to 8829”, and the server reads forward from there. Two days offline and two minutes offline are the same code path, and a user on three devices is just three different numbers.

  • Per-conversation order vs global order. One counter per chat scales and is all a reader can perceive. We give up any true global ordering across conversations, which nothing in the product needs.
  • Registry lookup vs hashing users to gateways. One Redis read per delivery buys free reconnection anywhere. Hashing would skip the read and make a dead box everyone else’s problem.
  • Computed backlog vs a queue per user. No per-user storage, and one code path for two minutes or two days offline. The cost is a Cassandra read on every reconnect instead of a drain.
  • Cassandra vs PostgreSQL for messages. Sustained writes and single-partition reads, at the price of no joins and no transactions over message rows.
  • Push on write vs pull on open. Pushing is why chat feels instant. It stops paying above a few thousand members, which is where broadcast channels start.
  • Readable messages vs end-to-end encryption. We can search, moderate and restore history. We can also read everything, and so can anyone who takes the database.

The order to go in

  1. Scope, 3 min. One-to-one, groups to 200, offline backlog, receipts. Calls, media and encryption are out.
  2. Numbers, 4 min. 46,000 sends, six deliveries each, and 500 boxes holding nothing but sockets. The last one reframes the problem.
  3. Diagram, 4 min. Gateways separate from the chat service. Follow one send all the way to a second phone.
  4. Finding the socket, 6 min. Broadcast, hashing, registry. Pick the registry and say why stale is cheap.
  5. Ordering, 5 min. Why clocks lose, and why the counter is per conversation.
  6. Offline, 4 min. No queues. last_read_seq plus a read forward.
  7. Failure, 4 min. A gateway dies, and why jitter on reconnect is not a detail.

Questions to ask first

  • How big can a group get? 200 and 100,000 are different designs, and the number decides where push stops.
  • Is history kept for ever, or does it expire? It is the difference between 438 TB a year and almost nothing.
  • One device per user, or several? Several makes last_read_seq per device, not per user.
  • Is end-to-end encryption required? If yes, say early what it takes away.

Follow-ups to expect

  • How does “typing…” work? A frame with a short TTL that is never stored. If it is lost, nothing is wrong.
  • Online status for 50 million people? A Redis key with a TTL refreshed by the heartbeat. Absence of the key is “offline”, and last seen is one more field.
  • Why not Kafka between the gateways and the chat service? It would add durability we already have from Cassandra, and tens of milliseconds to a path we promised in 500.
  • Deleting a message for everyone? A tombstone row with a higher sequence number. Clients that already have it hide it; clients reading history never see it.
  • The expensive part of chat is not messages, it is holding 50 million open sockets: 500 machines before any work happens.
