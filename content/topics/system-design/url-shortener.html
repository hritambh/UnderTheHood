You paste a 180-character tracking URL into a message and get back sho.rt/aK3dPq2. Anyone who clicks that lands on the original page. That is the whole product.

Bitly and TinyURL are the well-known versions. It looks like a one-table CRUD app, and the create side nearly is. The redirect side is the interesting half: it sits inside somebody else’s page load, it is read a hundred times for every write, and once a link is printed on a poster you can never take it back.

One-line version: creating a link is one row. Following one is a cache hit that must be fast, correct, and still working in five years.

Must do

  1. Take a long URL and give back a short code.
  2. Send a browser that asks for that code to the original URL.
  3. Let the creator pick their own alias, like /launch.
  4. Let a link carry an expiry date, after which it stops working.
  5. Count clicks per link, by day and country.

Must be

  • Fast: redirect in under 50 ms at the 99th percentile. It is dead time in someone else’s page load.
  • Correct forever: a code points at one URL and never drifts to another.
  • Up: 99.99% on redirects. Every link ever shared breaks when we are down.
  • Not walkable: you can’t guess the next code and read everyone’s links.
  • Cheap per click: a redirect should not cost a database write.

Not doing

  • Checking the destination is safe. We call a safe-browsing API and store its verdict. We don’t build the scanner.
  • Editing where a link points. A short link is a promise. Changing it is how phishing works.
  • Link previews. Fetching and rendering the target page is a separate crawler.
  • A full analytics product. We count clicks. Funnels and attribution are someone else’s job.

Assumptions, made up: 100 million new links a month, 100 clicks per link over its life, 500 bytes per row, peak 3× average.

Two numbers decide the design. 39 writes a second is nothing, so the write path can be a plain relational database. The hot set is 3 GB, so almost every redirect can be answered from memory without touching that database at all.

  • The redirect returns no body. It is a header. That is why it can be answered from memory in a millisecond.
  • A deleted code is never handed out again. Old posters still point at it, and they must get 410 Gone, not somebody else’s page.

PostgreSQL holds the links. 39 writes a second is a rounding error for it, we need a real unique constraint on the code so two custom aliases can’t collide, and 600 GB a year is comfortable. Redis holds the hot codes as plain strings, code to URL, with LRU eviction — see In-Memory Cache Service. The redirect path reads Redis and nothing else when it hits.

CREATE TABLE links (
  code       TEXT PRIMARY KEY,        -- 7 base62 chars, or a custom alias
  long_url   TEXT NOT NULL,
  owner_id   BIGINT,
  created_at TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ,             -- null means forever
  deleted_at TIMESTAMPTZ              -- set, never dropped: the code stays burnt
);

CREATE INDEX links_owner_idx ON links (owner_id, created_at DESC);
CREATE INDEX links_expiry_idx ON links (expires_at)
  WHERE expires_at IS NOT NULL AND deleted_at IS NULL;

-- the counter that hands out id ranges, one row in the whole database
CREATE TABLE code_counter (next_id BIGINT NOT NULL);

-- clicks are rolled up by a worker, and never read by a redirect
CREATE TABLE click_daily (
  code    TEXT NOT NULL,
  day     DATE NOT NULL,
  country TEXT NOT NULL,
  clicks  BIGINT NOT NULL,
  PRIMARY KEY (code, day, country)
);

There is no index on long_url. We never ask “which code points here” on a hot path, and indexing a text column 1.2 billion rows deep to answer it would cost more than the table.

Creating a link: the create service takes the next id from the block it already holds, encodes it to seven base62 characters (or takes the alias the caller asked for, which is why the code column is unique), inserts the row, and writes the code into Redis straight away so the first click is a hit.

Following a link: the redirect service asks Redis for the code. On a hit it checks the expiry and answers 302 in about a millisecond. On a miss it reads PostgreSQL, fills the cache, and answers. Either way it drops a click event on the queue and forgets about it; the rollup worker adds those up into click_daily once a minute.

Where does the code come from?

  • Hash the URL and take the first seven characters. Collisions are real, and the same URL always gives the same code — so two people sharing one page share one set of click counts and one expiry.
  • Random seven characters, then check the database. A read before every write, forever, to guard against a collision that almost never happens.
  • Count up from a shared number. No collisions by construction, but the codes come out in order, so anyone can walk them and read every link.

We count up, but in blocks. A server takes 10,000 ids in one UPDATE … RETURNING and then creates 10,000 links with no coordination at all. To stop the walking, the id is run through a fixed reversible scramble before encoding — multiply by a large odd number and wrap at 627. Same count, no collisions, scattered output.

Why 302 and not 301?

A 301 is cheaper for us and faster for the user: the browser remembers it and skips us next time. It also takes away expiry, click counts and the ability to kill a link that turned out to be malware. Browsers cache a 301 for a long time and there is no way to call it back. We take the traffic and send 302.

How do you count clicks without writing to the database?

At 3,900 clicks a second, one UPDATE links SET clicks = clicks + 1 per click is 3,900 row locks a second on the rows everyone else is reading. So the redirect never writes. It pushes (code, day, country) onto a queue and answers. Each service also counts in its own memory and flushes once a second, which turns a thousand clicks on one viral link into one message. The worker adds them into click_daily. Counts run about a minute behind, and nobody has ever needed them sooner.

  • 302 vs 301. We take every click, so we keep counts, expiry and a kill switch. We pay for the traffic and add a hop to every visit.
  • Id blocks vs random codes. No collision check on any write, and a server that restarts throws away the ids left in its block. Gaps in a code space of 3.5 trillion don’t matter.
  • Cache first vs database first. Almost every redirect avoids the database. The cost is that a deleted link lives on until its cache key is dropped, so deletes have to delete both.
  • Approximate counts vs exact. Counting off the hot path keeps redirects at a millisecond, and a crashed pod loses up to a second of clicks.
  • One code space vs per-user namespaces. Short codes stay short. Custom aliases are first come, first served, and good ones run out.

The order to go in

  1. Scope, 2 min. Create, redirect, custom alias, expiry, counts. Safety scanning is out.
  2. Numbers, 4 min. 39 writes against 3,900 reads, and a 3 GB hot set. Both answers fall out of these.
  3. Codes, 5 min. Hash, random, or counter, and why blocks of ids win. Interviewers want this part.
  4. Diagram, 4 min. Draw it, then follow a create and a click through it.
  5. Deep dive, 8 min. 301 against 302, then counting clicks off the hot path.
  6. Scaling and failure, 5 min. 10× and 100×, then what a click does when Redis is gone.

Questions to ask first

  • How long must a link live? Forever changes the storage answer and kills reuse of codes.
  • Do we need custom aliases? They force a real unique constraint, not just a generator.
  • Are counts exact or roughly right?
  • Is this one region or global? Global makes the redirect an edge problem.

Follow-ups to expect

  • Why not a UUID? 36 characters in a product whose whole job is being short.
  • Two people shorten the same URL? Two codes. Each gets its own expiry and its own counts.
  • How do you delete expired links? A sweeper on links_expiry_idx. The row stays, so the code is never reissued.
  • Could you drop PostgreSQL and keep only a key-value store? Yes, and you would hand-build the unique constraint that custom aliases need.
