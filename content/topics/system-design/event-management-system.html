An organiser sets up a concert, adds two ticket tiers, and puts it on sale at 10:00 on Friday. At 09:59 fifty thousand people have the page open. Twenty minutes later it is sold out. Three weeks after that, five thousand of them walk through a gate while someone scans their phone.

Eventbrite, BookMyShow and Ticketmaster are the well-known versions. Most of the time this system is nearly idle. For about sixty seconds per popular event it is one of the busiest things you will ever run, and every request wants the same number.

One-line version: a quiet system with a brutal spike. The design is about absorbing a crowd that all wants one row, then getting them through a door on bad wifi.

Must do

  1. An organiser creates an event with ticket tiers, prices and quantities, then publishes it.
  2. Anyone can browse published events by city and date.
  3. Buy tickets: hold them, pay, get a ticket with a scannable code.
  4. Scan a ticket at the door. Each one works exactly once.
  5. The organiser sees sales and attendance as they happen.

Must be

  • Correct: never sell more tickets than exist. Not once, not by one.
  • On-sale: survive 50,000 people arriving in sixty seconds. Nobody gets a blank error page.
  • Checkout: the buyer knows within 3 seconds whether they have tickets.
  • Door: a scan answers in under 500 ms, and keeps working when the venue wifi dies.
  • Uptime: 99.9%. During an on-sale, buying matters more than browsing.

Not doing

  • Taking the money. We call a payment provider and keep a reference.
  • Reserved seating. Tiers are a count, not a seat map. Picking seat J14 is the one-slot-one-buyer problem from Doctor Appointment Booking.
  • Refunds and resale. Both change who owns a ticket, and both deserve their own design.
  • Sending the emails. We hand a job to the notification service.

Assumptions, made up: 2 million tickets sold a month, 50,000 people hitting one big on-sale in the first minute, 3 requests each while they retry, 5,000 attendees through a gate in 20 minutes, 300 bytes per ticket row.

That third row is the whole topic. A system averaging 0.77 writes a second needs no cleverness at all. But the peak is 3,250 times the average, it lands in one minute, and every request wants the same counter. Capacity is not the problem. Contention on one row is.

  • 202 is the normal answer during an on-sale. You are in the queue, here is your place. Not an error, and the client must not retry it.
  • The idempotency key is a name the client invents for this attempt. A retry on a dropped connection returns the same order, not a second one.
  • The hold, not the ticket, comes first. You have ten minutes to pay.

PostgreSQL holds the truth: 7.2 GB a year, and an order is a small transaction across three tables. Redis holds the live ticket count and the waiting room, because one row in a relational database cannot take 2,500 writes a second and a Redis key can.

CREATE TABLE events (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  organiser_id BIGINT NOT NULL,
  city_id      INTEGER NOT NULL,
  starts_at    TIMESTAMPTZ NOT NULL,
  on_sale_at   TIMESTAMPTZ NOT NULL,
  status       TEXT NOT NULL            -- draft|published|closed
);

CREATE TABLE tiers (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id  BIGINT NOT NULL REFERENCES events(id),
  name      TEXT NOT NULL,
  price     INTEGER NOT NULL,          -- in paise, never a float
  quantity  INTEGER NOT NULL,          -- how many exist
  sold      INTEGER NOT NULL DEFAULT 0,
  CHECK (sold <= quantity)             -- the guard that cannot be skipped
);

CREATE TABLE orders (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tier_id    BIGINT NOT NULL REFERENCES tiers(id),
  buyer_id   BIGINT NOT NULL,
  quantity   SMALLINT NOT NULL,
  status     TEXT NOT NULL,            -- held|paid|expired|cancelled
  held_until TIMESTAMPTZ,
  idem_key   TEXT NOT NULL UNIQUE
);

CREATE TABLE tickets (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id BIGINT NOT NULL REFERENCES orders(id),
  code     TEXT NOT NULL UNIQUE,       -- signed, this is what the QR holds
  used_at  TIMESTAMPTZ,
  device   TEXT                        -- which scanner let them in
);

CREATE INDEX events_browse_idx ON events (city_id, starts_at)
  WHERE status = 'published';
CREATE INDEX orders_sweep_idx ON orders (held_until) WHERE status = 'held';

Redis is fast but it can lose its last few writes (see How Redis Saves Data to Disk). So CHECK (sold <= quantity) stays in the schema. If the counter is ever wrong, the database refuses the sale rather than printing a ticket nobody can use.

Buying during an on-sale: the order service asks Redis for a place. If the queue is short it decrements the ticket counter atomically, writes a held order to PostgreSQL, and returns a hold. If the queue is long the buyer gets a 202 and a position. Paying calls the payment provider, then flips the order to paid and writes the ticket rows.

At the door: the scanner app pulled this event’s codes before doors opened. It checks the signature on the phone, lets the person in, and tells the check-in service, which stamps used_at in PostgreSQL. Browsing and the organiser’s sales view are plain reads through the event service.

How do 50,000 people buy 5,000 tickets at once?

A transaction that locks the tier row takes about 2 ms, so one row can serve roughly 500 buyers a second however many servers you add. At 2,500 a second the wait grows until everything times out.

  • Lock the row (SELECT ... FOR UPDATE): correct, and capped at that 500/s.
  • Update without a lock (UPDATE ... WHERE sold + 2 <= quantity): no waiting, but it is still one hot row, and losers retry and make it worse.
  • Count in Redis: one DECRBY per buy, atomic, and a single key handles tens of thousands a second.

We take Redis, with a waiting room in front: a token queue that lets about 500 buyers a second through and tells everyone else their position. Postgres then sees a calm 500 writes a second instead of 2,500, and its CHECK is the last word if the counter ever drifts.

How does the door keep moving when the wifi dies?

Sending every scan to the server sounds right until the uplink drops and a queue of two thousand people stops moving. So the scanner is offline-first. The code is signed, so a forged one fails on the phone, and a code used twice on the same device is caught instantly.

Two people with the same code at two gates both get in, and the clash only shows up at sync. We accept that: a door that stops is a worse failure than a handful of duplicates an organiser can investigate afterwards.

What if payment hangs?

The hold is what makes this safe. The ticket is already counted out of Redis and the order is held for ten minutes. If the provider times out, we neither sell nor cancel — we ask it about our order by its idempotency key, because a timeout means “unknown”, not “failed”. A sweeper over orders_sweep_idx releases holds that expire and puts the count back.

  • Redis counter vs database row. We get 2,500 buys a second against one key instead of 500, and pay by keeping the count in two places. The database CHECK keeps us honest.
  • Waiting room vs first come, first served. Everyone gets a place in line instead of a timeout, but the honest cost is that some people wait twenty minutes to be told it is sold out.
  • Offline scanning vs server-checked scanning. The door never stops. A cloned ticket can admit two people, and we only find out at sync.
  • Holds vs instant purchase. A ten-minute hold stops people losing tickets at the payment step, and briefly hides tickets nobody ends up buying.
  • Tiers vs seat maps. A count is one number and scales easily. Sell seat J14 and it becomes one row per seat, a different design.

The order to go in

  1. Scope, 3 min. The five things it does, and that seating, refunds and payments are out.
  2. Numbers, 5 min. 0.77/s average against 2,500/s peak on one row. Say the ratio out loud.
  3. API and schema, 6 min. Show the hold, the idempotency key and CHECK (sold <= quantity).
  4. Diagram, 4 min. Draw it, then walk a purchase and a scan through it.
  5. Deep dive, 12 min. The on-sale spike first. That is what they want.
  6. Scaling and failure, 5 min. 10× and 100×, then what breaks when Redis dies mid-sale.

Questions to ask first

  • General admission or numbered seats? They are different systems.
  • Is a waiting room acceptable, or must it be pure first come, first served?
  • Do we take the money, or hand off to a provider?
  • How bad is overselling — refund and apologise, or never?

Follow-ups to expect

  • Stopping bots? Queue tokens tied to an account, a cap per buyer in the same Redis step, and rate limits per IP.
  • Live sales dashboard? Read the Redis counter, not the database. It is the number that changes.
  • What if Redis says 0 but Postgres says 4,998 sold? Postgres wins — it is the only copy that cannot oversell. Rebuild from it.
  • Multiple tiers selling together? One key per tier, so they never contend with each other.
