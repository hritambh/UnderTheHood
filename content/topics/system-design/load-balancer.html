One server handles only so many requests, so you run many copies. Users know one address, shop.example.com, but 600 servers sit behind it. Which one gets the next request? And what happens when one dies?

A load balancer answers both. It sits between users and servers and hands each request to one that is alive and not too busy. The servers behind it are backends; a group running the same app is a pool.

Nginx, HAProxy and Envoy you run yourself; AWS Elastic Load Balancing you rent. Here we design the box itself — the thing every other design diagram draws and then skips over.

One-line version: it takes traffic on one address, hands each request to a healthy server, and is built so no single machine dying, including its own, takes the site down.

Must do

  1. Take requests on one public address, forward each to a backend.
  2. Spread load across a pool by a chosen method.
  3. Drop a dead backend, bring it back when it recovers.
  4. Add and remove backends without dropping requests in flight.
  5. End HTTPS, and route by host and path.

Must be

  • Nearly invisible: under 1 ms added per request.
  • More available than anything behind it: 99.99%. If it is down, everything is down.
  • Fast to react: a dead backend out within 6 seconds, most failures hidden before that.
  • Safe to change: no config change or deploy cuts a connection.

Not doing

  • Choosing a region. A layer above, usually DNS.
  • Starting and stopping backends. We are given the list.
  • Attacks, caching, login checks. A firewall, a CDN, an API gateway.

Assumptions, made up: 1.7 billion requests a day, peak 5× average, 2 KB in and 10 KB out, 600 backends, 20,000/s per L7 machine, 500 config changes a day.

Every change returns a config version, so a deploy tool can wait until all 7 machines report 4182. And DELETE answers 202: the backend stops taking new requests while in-flight ones finish. That is draining.

Three kinds of data, in three places, for three reasons.

Config: PostgreSQL

CREATE TABLE pools (
  pool_id        TEXT PRIMARY KEY,
  method         TEXT NOT NULL,       -- 'least_connections'
  health_path    TEXT NOT NULL,
  drain_seconds  INT  NOT NULL
);

CREATE TABLE backends (
  pool_id     TEXT NOT NULL REFERENCES pools (pool_id),
  backend_id  TEXT NOT NULL,
  address     INET NOT NULL,
  port        INT  NOT NULL,
  weight      INT  NOT NULL DEFAULT 1,
  state       TEXT NOT NULL,          -- 'active' | 'draining'
  PRIMARY KEY (pool_id, backend_id)
);

-- rules: (lb_id, priority) -> host, path_prefix, pool_id
-- config_versions: version BIGINT PRIMARY KEY, snapshot JSONB

120 KB changing 500 times a day, so pick for safety, not speed. PostgreSQL refuses a rule aimed at a pool that doesn't exist, and saves each change with its config_versions row in one transaction. That is how a bad change is undone in one step: push the previous snapshot again.

Live state: memory, per machine

Each machine also holds what moves every second: per backend, healthy or not, requests open now, recent failures. None of it is stored — it is one machine's own view, and a restart just counts again from zero.

Logs: a pipeline, then object storage

510 GB a day goes to a log pipeline, which writes files to object storage, deleted after 30 days.

The data plane is two layers, named after the network level they work at. Layer 4 (L4) sees only addresses and ports, moving packets without reading them: simple and very fast. Layer 7 (L7) reads the HTTP request, so it can end HTTPS, route by path and retry. We call these the proxies — the 7 machines from the estimates, with three L4 machines in front.

Request 1: a user opens shop.example.com/orders/8812

  1. The router picks one of three L4 machines from the connection's addresses and ports, so every packet of a connection lands on the same one.
  2. The L4 balancer picks one of the 7 proxies, remembers the choice, forwards packets unread.
  3. The L7 proxy ends HTTPS and reads the request. Rules are checked in order; host plus /orders matches pool orders-api.
  4. It picks a healthy backend, reuses an open connection, and adds X-Forwarded-For so the backend sees the client's IP, not the proxy's.
  5. The backend answers, the proxy passes it back, then logs one line and updates counters.

Request 2: a deploy removes backend orders-7

  1. The control plane marks it draining, saves version 4184, answers 202.
  2. It pushes 4184 to every proxy, over a connection each keeps open for this.
  3. Each proxy swaps config in memory: no new request goes there, running ones carry on.
  4. After 30 seconds the proxies close what is left.

1. Which backend gets the next request?

Round robin counts a slow report the same as a quick lookup. Plain least connections is better, but each proxy sees only its own connections, and all 7 flood a new backend sitting at zero.

The pick: least connections with power of two choices — take two backends at random, send to the less busy one. Random stops every proxy jumping on the same server; the compare still steers away from busy ones.

function pickBackend(healthy: Backend[]): Backend {
  const i = rand(healthy.length);
  let j = rand(healthy.length - 1);
  if (j >= i) j += 1;             // two different backends
  const a = healthy[i], b = healthy[j];
  return a.active / a.weight <= b.active / b.weight ? a : b;
}

A new backend also gets slow start, its weight climbing to normal over 30 seconds.

2. How do we know a backend is dead?

Use both kinds of check, because each covers the other's gap.

  • Active: GET /healthz every 2 s, out after 3 failures. Slow alone — a backend dying just after a pass fails at 2, 4 and 6 seconds: 6 × 167 ≈ 1,000 failed requests.
  • Passive: watch real traffic, set it aside after 5 failures in a row. Catches it in about 35 requests, but never notices recovery, because nothing is sent to it.

Retry elsewhere only when a repeat is safe: a POST that may have arrived could charge a card twice. Cap retries at 10% of traffic, and keep /healthz shallow — a deep one turns a database blip into every backend failing at once.

3. What stops the load balancer itself taking us down?

Seven proxies, one address. DNS with seven addresses fails: clients cache answers for minutes. An active-standby pair fails: one machine works, capping us at 20,000/s.

The pick: a thin L4 layer. Each L4 machine tells the router “send this IP to me”, so the router spreads connections across equally good paths. That is ECMP — how Maglev and Katran work.

Every L4 machine must pick the same proxy for a given connection, because the router hands a dead machine's connections to ones that never saw them. So they share one consistent hash, where removing a proxy moves only its share. And responses skip L4, answering through the router — direct server return — so L4 carries only the 1.6 Gbit/s coming in.

At a tenth of this size, one machine carries the peak and the simple active-standby pair is right.

The request path is not what breaks first — proxies share nothing, so you add more. At 10×: 1,000,000/s ÷ 20,000 = 50, plus 2 spare = 52 proxies. The things around the path break instead.

  • L4 vs L7. We use both. L4 is fast but blind to HTTP; L7 routes and retries but costs far more per request. The price is two layers to understand.
  • Building vs renting. For most teams the cloud provider's load balancer is right: less control, pay per hour and per GB, skip this whole page.
  • Ending HTTPS at the proxy. We can read paths and reuse backend connections; in return the proxy holds the private key, and backend traffic is plain text unless encrypted again.
  • No pinning vs sticky sessions. Any request can go anywhere, so load stays even and a dead backend is harmless. The cost: backends can't keep sessions in their own memory.
  • PostgreSQL vs etcd. etcd would tell proxies the moment a key changed, with no push system to build. We chose checked links and plain transactions.

The order to go in

  1. Scope (5 min). One site or many? L4, L7 or both? Build or rent?
  2. Numbers (5 min). Peak rate, traffic each way, machine count. Call out the 3.4 million reads per change.
  3. API and data (6 min). Split data plane from control plane, then pools, backends, rules.
  4. High level (10 min). Draw the boxes, walk a request, then a removal.
  5. Deep dives (14 min). Open with “what if the load balancer dies?” — it is what the interviewer is waiting for.
  6. Wrap up (5 min). What breaks first, what you'd watch.

Questions to ask first

  • How much traffic, how spiky?
  • HTTP only, or any TCP?
  • Do backends keep per-user state in memory?
  • One data centre, or several regions?

Follow-ups to expect

  • Sticky sessions? A cookie naming the backend. Cost: uneven load, lost sessions when it dies.
  • How does the backend learn the client IP? X-Forwarded-For, trusted only from the proxy.
  • Why not DNS with several addresses? Answers are cached for a long time, and DNS knows nothing about health or load.
  • A load balancer gives many backends one address, and must be more reliable than anything behind it.
  • The data plane carries traffic; the control plane holds settings and pushes them. Traffic survives the control plane being down.
  • Config is read millions of times per change, so every machine keeps a full copy in memory.
  • L4 forwards packets by address and port. L7 reads HTTP, so it ends HTTPS, routes by path and retries.
  • To pick a backend, look at two at random and take the less busy one. Add slow start for new servers.
  • Active checks remove a dead backend in about 6 seconds; passive checks react after a few real failures. Use both.
  • L4 machines share one IP through ECMP and the same consistent hash, so connections survive one dying.
  • Responses skip the L4 layer, so it carries only the small half of the traffic.
  • Backends are drained, not cut off. Config goes to one proxy first and rolls back if errors jump.
