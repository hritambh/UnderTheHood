One server can only handle so many requests. So you run many copies of your app. Now you have a new problem: users know one address, like shop.example.com, but there are 600 servers behind it. Which one gets the next request? And what happens when one of them dies?

A load balancer answers both. It sits between the users and the servers. Every request arrives at the load balancer, and it passes each one to a server that is alive and not too busy. Users never see the servers. They see one address that always works.

The servers behind it are called backends. A group of backends that run the same app is a pool.

Nginx, HAProxy and Envoy are load balancers you run yourself. AWS Elastic Load Balancing is one you rent. Here we design the thing itself: the box that every other design diagram draws and then skips over.

One-line version: a load balancer takes traffic on one address, hands each request to a healthy server, and is built so that no single machine dying, including its own, takes the site down.

Must do

  1. Accept requests on one public address and forward each one to a backend.
  2. Spread the load across a pool with a chosen method, like round robin or least connections.
  3. Notice when a backend is down, stop sending to it, and bring it back when it recovers.
  4. Let teams add and remove backends, and change settings, without dropping requests that are in flight.
  5. Handle HTTPS for the backends, and send requests to different pools by host name and path. So /orders goes to the orders servers and /search goes to the search servers.

Must be

  • Nearly invisible. It should add less than 1 millisecond to a typical request.
  • More available than anything behind it. Target 99.99% uptime. If the load balancer is down, everything is down, however healthy the backends are.
  • Quick to spot a dead backend. Stop sending to it within about 6 seconds, and hide most of the failed requests from users before that.
  • Able to grow by adding machines. No single machine should carry all the traffic.
  • Safe to change. A config change or a deploy must not cut connections.

Not doing

  • Choosing between data centres or regions. Sending a user in Mumbai to the Mumbai site is a layer above this, usually done with DNS. We design the load balancer for one site.
  • Starting and stopping backends. Something else decides how many servers to run. We are told the list and work with it.
  • Blocking attacks. Filtering bad requests and absorbing floods of junk traffic is a separate product.
  • Caching responses. That is a CDN or a cache.
  • Login checks and per-user limits. Checking tokens and capping calls per user is the job of an API gateway. The topic “Authentication and Authorisation” covers the checks themselves.

Assumptions (made up for this design, not real figures):

  • The site gets 1.7 billion requests a day.
  • At the busiest moment, traffic is 5 times the average.
  • A request is about 2 KB coming in. A response is about 10 KB going out.
  • There are 600 backends behind the load balancer.
  • One load balancer machine that reads HTTP and handles HTTPS can do 20,000 requests per second.
  • Teams make about 500 config changes a day, mostly servers added and removed during deploys.

How many requests?

  • On average: 1,700,000,000 ÷ 86,400 seconds ≈ 20,000 per second.
  • At the peak: 20,000 × 5 = 100,000 per second.
  • Per backend at the peak: 100,000 ÷ 600 ≈ 167 per second.

How much data on the wire?

  • Coming in: 100,000 × 2 KB = 200 MB per second. Times 8 bits = 1.6 Gbit/s.
  • Going out: 100,000 × 10 KB = 1 GB per second. Times 8 bits = 8 Gbit/s.
  • So five sixths of the bytes are responses. That shapes the design later.

How many load balancer machines?

  • To carry the peak: 100,000 ÷ 20,000 = 5 machines.
  • We run 7. One can be down for a deploy and another can crash, and the 5 that are left still carry the peak.

How many health checks?

A health check is a small request the load balancer sends to a backend to ask “are you alive?”. Say each of the 7 machines checks each backend every 2 seconds.

  • In total: 7 × 600 ÷ 2 = 2,100 checks per second.
  • Per backend: 7 ÷ 2 = 3.5 checks per second. Next to 167 real requests, that is nothing. For now.

How much storage?

  • Config: 600 backends × about 200 bytes = 120 KB. Tiny.
  • Logs: about 300 bytes per request. 1,700,000,000 × 300 bytes = 510 GB a day, or about 186 TB a year. So we keep 30 days: 510 GB × 30 = 15.3 TB.

Reads or writes?

  • Every request looks up the config: which pool, which backends. That is 1.7 billion lookups a day, against 500 changes.
  • 1,700,000,000 ÷ 500 = 3.4 million lookups for every change. So the config must sit in memory on every machine, not in a database we ask on each request.

A load balancer has two sides, and it helps to name them now.

  • The data plane is the part that carries user traffic. It has no API of its own. It takes whatever HTTP requests arrive and forwards them.
  • The control plane is the part that teams and deploy tools talk to. It holds the settings and tells the data plane what to do. This is where the API lives.

Two things to notice:

  • Every change returns a config version. The whole config has one number that goes up by one on each change. A deploy tool can wait until every machine is on version 4183 before it moves on.
  • DELETE answers 202, not 204. The backend is not gone yet. It stops getting new requests, and the ones in flight get time to finish. That is draining, and deep dive 4 covers it.

There are three kinds of data here. They live in three different places, for three different reasons.

The config: PostgreSQL

-- PostgreSQL: the settings, owned by the control plane
CREATE TABLE pools (
  pool_id            TEXT PRIMARY KEY,
  method             TEXT NOT NULL,   -- 'round_robin', 'least_connections'
  health_path        TEXT NOT NULL,   -- '/healthz'
  health_interval_s  INT  NOT NULL,
  fail_after         INT  NOT NULL,
  pass_after         INT  NOT NULL,
  drain_seconds      INT  NOT NULL
);

CREATE TABLE backends (
  pool_id     TEXT NOT NULL REFERENCES pools (pool_id),
  backend_id  TEXT NOT NULL,
  address     INET NOT NULL,
  port        INT  NOT NULL,
  weight      INT  NOT NULL DEFAULT 1,
  state       TEXT NOT NULL,          -- 'active', 'draining'
  PRIMARY KEY (pool_id, backend_id)
);

CREATE TABLE rules (
  lb_id        TEXT NOT NULL,
  priority     INT  NOT NULL,         -- lower number is checked first
  host         TEXT,                  -- 'shop.example.com'
  path_prefix  TEXT,                  -- '/orders'
  pool_id      TEXT NOT NULL REFERENCES pools (pool_id),
  PRIMARY KEY (lb_id, priority)
);

CREATE TABLE config_versions (
  version     BIGINT PRIMARY KEY,
  created_at  TIMESTAMPTZ NOT NULL,
  created_by  TEXT  NOT NULL,
  snapshot    JSONB NOT NULL          -- the full config at this version
);

Why PostgreSQL?

  • From the estimates, the config is 120 KB and changes 500 times a day. Any database can hold that. So we pick for safety, not speed.
  • The tables point at each other. A rule names a pool, and a pool has backends. A relational database stops us from saving a rule that points at a pool that doesn’t exist.
  • A change and its new row in config_versions are saved in one transaction. So there is never a version number without a matching config.

The primary keys are the only indexes we need. backends is read by pool_id and rules by lb_id, and each is the first part of its key.

config_versions keeps every old config in full. That is how we undo a bad change in one step: push the previous snapshot again.

The live state: memory, on each machine

Each load balancer machine keeps a full copy of the config in memory, because of that 3.4 million to 1 ratio. Next to it, the machine keeps things that change every second:

  • For each backend: is it healthy, how many requests are open on it right now, and how many of its last few requests failed.
  • The open connections to clients and to backends.

None of this goes into the database. It changes far too fast, and it is one machine’s own view. After a restart, the machine just counts again from zero.

The logs: a log pipeline, then cheap file storage

510 GB a day of log lines doesn’t belong in a database either. Each machine sends its lines to a log pipeline, which writes them as files to object storage (cheap storage for large files, like Amazon S3). Files older than 30 days are deleted.

The data plane is split into two layers. They are named after the level of the network they work at.

  • Layer 4 (L4) balancers only look at addresses and ports. They move packets without reading what is in them. That makes them simple and very fast.
  • Layer 7 (L7) balancers read the whole HTTP request. So they can handle HTTPS, look at the path, and retry a failed request. They do much more work per request. We’ll call these the proxies. A proxy is a program that takes a request and makes it again on your behalf.

The 7 machines from the estimates are the L7 proxies. Three L4 machines in front spread connections across them. Deep dive 3 explains why.

Request 1: a user opens shop.example.com/orders/8812

  1. The client looks up the name and gets one public IP address. It opens a connection to that address.
  2. The connection reaches the router at the edge of our network. The router knows three machines that all accept traffic for that IP: the three L4 balancers. It picks one from the connection’s addresses and ports, so every packet of one connection goes to the same machine.
  3. The L4 balancer picks one of the 7 proxies for this connection, remembers the choice, and forwards the packets. It never reads them.
  4. The L7 proxy does the HTTPS handshake with the client and reads the request. It goes through its rules in order. Host shop.example.com with path /orders matches the pool orders-api.
  5. The proxy picks one healthy backend from that pool, using the pool’s method. It sends the request over a connection it already has open to that backend. It adds an X-Forwarded-For header holding the client’s real IP address. Without it, the backend would only see the proxy’s address.
  6. The backend answers. The proxy sends the response back to the client.
  7. The proxy writes one line to logs and updates its counters: one more request for this pool, how long it took, and whether it worked.

Each proxy also sends a health check to every backend every 2 seconds. That is the curved arrow, and deep dive 2 covers it.

Request 2: a deploy takes backend orders-7 out

  1. The deploy tool calls DELETE /v1/pools/orders-api/backends/orders-7 on the control plane.
  2. The control plane sets that backend’s state to draining in PostgreSQL and saves config version 4184, in one transaction. It answers 202.
  3. The control plane pushes version 4184 to every L7 proxy. Each proxy keeps a connection open to the control plane just for this. The L4 balancers get a push only when the list of proxies changes.
  4. Each proxy swaps to the new config in memory. From that moment, no new request goes to orders-7. Requests already running on it carry on.
  5. After 30 seconds, the proxies close whatever is left. The control plane deletes the row and saves another version. The deploy tool can now stop the server.

1. Which backend gets the next request?

The options:

  • Round robin. Take turns: server 1, 2, 3, then 1 again. Fair when every request costs the same. But a slow report and a quick lookup count the same, so one backend can get five slow ones in a row.
  • Least connections. Send the request to the backend with the fewest requests open right now. A backend stuck on slow work has many open, so it gets fewer new ones.
  • Hash. Hash a key, like the user ID, and let the result pick the backend. The same user always lands on the same server. It spreads load badly when a few keys are very busy.

The pick: least connections. But the plain version has two problems here. Each of our 7 proxies only sees its own connections, so a backend that looks idle to one may be busy with the other six. And a new backend starts at zero, so every proxy picks it at the same moment and floods it.

So we use a small twist called power of two choices. Pick two backends at random, then send the request to the less busy of the two.

// pick-backend.ts
// Look at two random backends and take the less busy one.
function pickBackend(healthy: Backend[]): Backend {
  if (healthy.length === 0) throw new NoHealthyBackendError();
  if (healthy.length === 1) return healthy[0];

  const i = Math.floor(Math.random() * healthy.length);
  let j = Math.floor(Math.random() * (healthy.length - 1));
  if (j >= i) j += 1;              // makes sure the two are different

  const a = healthy[i];
  const b = healthy[j];
  // Divide by weight, so a server with weight 2 may hold twice as many.
  return a.active / a.weight <= b.active / b.weight ? a : b;
}

The random step stops the proxies all jumping on the same backend. The compare step still steers traffic away from busy ones. For a new backend we also add slow start: its weight begins low and climbs to normal over about 30 seconds.

2. How do we know a backend is dead?

The options:

  • Active checks. The proxy calls GET /healthz on each backend every 2 seconds and waits up to 1 second. Three failures in a row and the backend is out. Two passes in a row and it is back in.
  • Passive checks. The proxy watches real traffic. If 5 requests in a row to one backend fail to connect or time out, that backend is put aside for 30 seconds.
  • Both.

The pick: both, because each one covers the other’s gap.

Active checks alone are too slow. A backend that dies just after passing a check fails the next three, at 2, 4 and 6 seconds. From the estimates, that is 6 × 167 ≈ 1,000 failed requests.

Passive checks catch it after 5 failures on each proxy, so about 7 × 5 = 35 in total. But they can’t tell when a backend is healthy again, because nothing is being sent to it. The active check does that.

Two more pieces hide failures from most users:

  • Retry on another backend. If a request fails before the backend sent any answer, the proxy tries once more on a different one. Only when a repeat is safe: a GET, or a request that never left the proxy. A POST that may have reached the backend is not retried. It could charge a card twice.
  • A retry budget. Retries are capped at 10% of normal traffic. Without a cap, a struggling pool gets double the load and falls over completely.

And two traps:

  • Keep /healthz shallow. It should only answer “is this process up?”. If it also checks the database, one short database blip fails every backend at once, and we remove the whole pool.
  • Don’t trust the checks when most of the pool looks dead. If more than half the backends fail, the checks are more likely wrong than the servers. The proxy then sends to all of them. Some requests fail, but that beats crushing the few that are left.

3. What stops the load balancer from being the one thing that takes us down?

We need 7 proxies to carry the traffic, but users have one address. Something has to spread connections across the 7, and it must not be a single machine.

The options:

  • Give DNS seven addresses. Simple, but clients remember DNS answers for minutes or hours. When a proxy dies, some users keep trying the dead address.
  • Two machines, one address. One does all the work. The second watches it and takes over the address if the first dies. Simple to run, but only one machine works at a time. That caps us at 20,000 requests per second, and we need 100,000.
  • A thin L4 layer in front of the proxies. Several L4 machines all tell the router, “send traffic for this IP to me.” The router sees several equally good paths and spreads connections across them. This is ECMP, equal-cost multi-path routing.

The pick: the L4 layer. Every machine works, and any one of them can die. Google’s Maglev and Meta’s Katran are built this way. Two details make it work.

Every L4 machine picks the same proxy for the same connection. When an L4 machine dies, the router moves its connections to the others, which have never seen them. If they pick a different proxy, the connection breaks. So all L4 machines hash the connection’s addresses and ports the same way, over the same list of proxies. They use consistent hashing, where removing one proxy only moves that proxy’s connections. The topic “Database Sharding” explains why a plain “hash mod N” moves nearly everything.

Responses skip the L4 layer. The proxy answers the client straight through the router. This is direct server return. From the estimates, 8 of every 9.6 Gbit/s is responses, so the L4 machines only carry the 1.6 Gbit/s coming in. Say one L4 machine can forward 10 Gbit/s (made up). One is enough, and we run three so two can fail.

At a tenth of this size, one machine can carry the peak. Then the pair of machines with one address is the right design.

4. How do we change things without cutting connections?

Something changes 500 times a day. Each change is a chance to drop requests, or to break everything at once.

Taking a backend out. We could cut it off at once, but that fails every request in flight. So we drain it, as in request 2 above: no new requests, and 30 seconds for the running ones to finish. Long-lived connections like WebSockets never finish by themselves. They are closed at the 30-second mark, and the client connects again and lands on another backend. The topic “WebSockets vs Polling vs SSE” covers reconnecting.

Changing the config. We could restart the proxy, but that cuts every connection on it. So the proxy builds the new config next to the old one in memory, then switches over in one step.

Pushing a bad config. This is the dangerous one. A broken rule pushed to all 7 proxies at once takes the whole site down in a second, and no health check on the backends will save us. So every push goes in stages:

  1. The control plane checks the new config: every rule points at a real pool, and no pool is left empty.
  2. It pushes to one proxy and waits a minute.
  3. If that proxy’s error rate stays normal, it pushes to the rest.
  4. If the error rate jumps, it pushes the previous snapshot from config_versions back out.

New versions of the proxy software go out the same way: drain one proxy, update it, put it back, then do the next. This is why we run 7 when 5 carry the peak.

The design holds for today’s peak of 100,000 requests per second. As that grows, the request path is not what breaks first. Proxies share nothing with each other, so we just add more. The things around the request path break first.

The numbers to watch at every size: the time the proxy adds to a request, proxy CPU, and the count of “no healthy backend” answers. That last one should be zero.

  • L4 vs L7. We use both. L4 is fast but knows nothing about HTTP. L7 can route by path and retry, but costs much more per request. The price is two layers to build, run and understand.
  • Building it vs renting it. We designed our own. For most teams, the cloud provider’s load balancer is the right call. You give up some control and pay per hour and per GB. You skip everything on this page.
  • Least connections with two choices vs round robin. Ours reacts to slow backends. It needs slow start to protect new servers, and it is harder to reason about than “take turns”.
  • Ending HTTPS at the proxy vs passing it through. The proxy decrypts, so it can read the path and reuse backend connections. In return, the proxy holds the site’s private key, and traffic to the backends is plain text unless we encrypt it a second time.
  • No pinning vs sticky sessions. Any request can go to any backend. That keeps load even and makes a dead backend harmless. It means backends can’t keep a user’s login session in their own memory. The session goes in a shared store, or in a token the client sends each time.
  • PostgreSQL vs a key-value store with watches. Stores like etcd can tell every proxy the moment a key changes, so there is no push system to build. We chose PostgreSQL for checked links between tables and plain transactions, and built the push ourselves.

The order to go in

For a 45-minute interview:

  1. Ask questions and fix the scope (5 minutes). One site or many? L4, L7 or both? Build or rent?
  2. Numbers (5 minutes). Requests per second at peak, traffic in and out, how many machines. Say out loud that config is read millions of times for each change.
  3. API and data (6 minutes). Split data plane from control plane first. Then pools, backends and rules, and where live state is kept.
  4. High-level design (10 minutes). Draw router, L4, L7, backends and the control plane. Walk one request through, then one backend removal.
  5. Deep dives (14 minutes). Start with “what if the load balancer itself dies?”, because the interviewer is waiting for it. Then the balancing method and health checks.
  6. Wrap up (5 minutes). What breaks first as it grows, and what you’d watch.

Questions to ask first

  • How much traffic, and how spiky is it?
  • Is it HTTP only, or any TCP traffic?
  • Do we need routing by host and path, and HTTPS handled here?
  • Do backends keep per-user state in memory, so the same user must reach the same server?
  • One data centre, or several regions?

Follow-ups to expect

  • What is the difference between L4 and L7? L4 sees addresses and ports and forwards packets. L7 reads the HTTP request, so it can route by path, handle HTTPS and retry.
  • How would you do sticky sessions? The proxy sets a cookie that names the backend, and sends later requests with that cookie to the same one. The cost: load gets uneven, and when that backend dies its users lose their session.
  • How does the backend learn the client’s IP? The proxy adds it in the X-Forwarded-For header. The backend should only trust that header when the request comes from the proxy.
  • Why not just use DNS with several addresses? DNS answers are remembered for a long time, and DNS doesn’t know which servers are healthy or busy.
  • What changes for WebSockets? Connections last hours, so counting open connections matters more than counting requests. Draining must close them at the time limit.
  • A load balancer gives many backends one address, sends each request to a healthy one, and must be more reliable than anything behind it.
  • The data plane carries traffic. The control plane holds the settings and pushes them out. Traffic keeps flowing when the control plane is down.
  • Config is read millions of times for each change, so every machine keeps a full copy in memory.
  • L4 balancers forward packets by address and port without reading them. L7 proxies read the HTTP request, so they handle HTTPS, route by host and path, and retry.
  • To pick a backend, look at two at random and take the less busy one. It reacts to slow backends and stops many proxies from flooding the same server.
  • Active health checks take about 6 seconds to remove a dead backend. Passive checks watch real traffic and react after a few failures. We use both.
  • Safe requests are retried once on another backend, with a cap on total retries.
  • Several L4 machines share one IP through the router, and all use the same consistent hash, so a connection survives when one of them dies.
  • Backends are drained, not cut off. Config changes go to one proxy first, and are rolled back to the previous saved version if errors jump.
  • As traffic grows, the request path scales by adding proxies. Health checks, logs and config pushes are what break first.
