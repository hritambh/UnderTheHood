Almost every app needs to tell users things. “Your order has shipped.” “Your login code is 481920.” “Someone replied to your comment.”

Without a shared service, every team builds this alone. The orders team talks to the email provider. The payments team talks to the SMS provider. Each one handles retries, user settings and duplicates in its own way, and each gets some of it wrong.

A notification service fixes that. Other services just say, “tell user 42 that order 8812 has shipped.” The notification service decides which channels to use, writes the message, sends it, retries if needed, and records what happened.

Every large product has one. It is what sends you a shipping update from a shopping app, or a one-time login code (an OTP) from your bank.

We’ll cover four channels:

  • Push: the pop-up on a phone. These go through Apple’s service (APNs) for iPhones and Google’s (FCM) for Android. You can’t reach the phone any other way.
  • Email and SMS: sent through outside companies, called providers.
  • In-app: the list behind the bell icon inside the app.

One-line version: other services say what happened and to whom. The notification service works out how to tell them, exactly once, on the right channels.

Must do

  1. Accept a “send this” request from any internal service.
  2. Deliver it by push, email, SMS and in-app.
  3. Respect each user’s settings. If they turned off offer emails, they get no offer emails.
  4. Never send the same notification twice, and retry the ones that fail.
  5. Show a user their recent notifications in the app, and let services check if a notification went out.

Must be

  • Fast for urgent messages. Login codes and security alerts should leave our system within 5 seconds.
  • Patient for the rest. Offers and digests can take a few minutes.
  • Hard to lose. Once we answer “accepted”, the notification must not vanish, even if a server crashes right after.
  • Available. Accepting requests should work 99.9% of the time. Other services should never have to wait on us.
  • Fair under load. A big marketing send must not slow down login codes.

Not doing

  • Deciding what to send, or to whom. A marketing tool picks the audience and the wording. We only deliver.
  • Running our own email or SMS delivery. We use providers. Getting email into inboxes and SMS onto phone networks is a business of its own.
  • Chat messages between users. That is a different system with different needs.
  • The live connection to the app. Getting a new in-app notification onto an open screen at once uses SSE or WebSockets. The topic “WebSockets vs Polling vs SSE” covers that. Here we store the notification and hand it over.
  • Reports on opens and clicks. We record sent, delivered and failed. Nothing more.

Assumptions (made up for this design, not real figures):

  • 10 million users use the app each day.
  • Each user gets 5 notifications a day on average.
  • At the busiest moment, traffic is 5 times the average.
  • One stored notification record takes about 500 bytes.
  • We keep records for 90 days.

How many notifications?

  • Per day: 10,000,000 users × 5 = 50 million notifications/day.
  • On average: 50,000,000 ÷ 86,400 seconds ≈ 580 per second.
  • At the peak: 580 × 5 ≈ 2,900 per second.

A marketing send on top

Say marketing wants to reach 2 million users within 10 minutes.

  • 2,000,000 ÷ 600 seconds ≈ 3,300 per second, for those 10 minutes.
  • That is more than our normal peak. So one campaign can double the load. Keep this number in mind for the deep dives.

How much storage?

  • Per day: 50,000,000 × 500 bytes = 25 GB/day.
  • For 90 days: 25 GB × 90 = 2.25 TB.

Reads or writes?

  • Writes: each notification is written once, then its status changes about twice (sent, then delivered). That is 50 million + 100 million = 150 million writes/day, or about 1,700 per second on average.
  • Reads: say each user opens the bell icon 3 times a day. 10,000,000 × 3 = 30 million reads/day, or about 350 per second.
  • So there are about 5 writes for every read. Most systems are the other way round. This one is write-heavy.

Three things to notice:

  • The caller sends a type and data, not the text. The words live in a template inside the notification service. So wording and translations can change without touching the orders service.
  • The answer is 202 Accepted, not 200 OK. It means “we have it and will send it”, not “it has been sent”. The caller doesn’t wait for the email provider.
  • The idempotency key. This is a name the caller makes up for this one notification. If the caller sends the same key twice, because of a timeout and a retry, we send only once. Idempotent means doing it twice has the same result as doing it once.

The inbox uses cursor pagination, so new notifications arriving while the user scrolls don’t cause repeats. The Pagination topic explains why.

There are two very different kinds of data here, so we use two databases.

Small data that changes rarely: PostgreSQL

-- PostgreSQL: settings, devices and templates
CREATE TABLE settings (
  user_id   BIGINT  NOT NULL,
  category  TEXT    NOT NULL,   -- 'orders', 'security', 'offers'
  channel   TEXT    NOT NULL,   -- 'push', 'email', 'sms', 'in_app'
  enabled   BOOLEAN NOT NULL,
  PRIMARY KEY (user_id, category, channel)
);

CREATE TABLE devices (
  user_id     BIGINT NOT NULL,
  device_id   TEXT   NOT NULL,
  platform    TEXT   NOT NULL,  -- 'ios', 'android', 'web'
  push_token  TEXT   NOT NULL,
  updated_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (user_id, device_id)
);

CREATE TABLE templates (
  type      TEXT NOT NULL,      -- 'order_shipped'
  channel   TEXT NOT NULL,
  locale    TEXT NOT NULL,      -- 'en', 'hi'
  category  TEXT NOT NULL,
  title     TEXT,
  body      TEXT NOT NULL,      -- 'Order {{orderId}} arrives {{eta}}'
  PRIMARY KEY (type, channel, locale)
);

A push token is the address of one app on one phone. Apple or Google hands it to the app, and the app sends it to us. One user can have several devices, so several tokens.

These tables are small and are read by their primary key. PostgreSQL handles that easily, and we get normal transactions when a user changes their settings.

Big, write-heavy data: Cassandra

-- Cassandra: what the bell icon shows
CREATE TABLE inbox_by_user (
  user_id          BIGINT,
  created_at       TIMESTAMP,
  notification_id  UUID,
  type             TEXT,
  title            TEXT,
  body             TEXT,
  read             BOOLEAN,
  PRIMARY KEY ((user_id), created_at, notification_id)
) WITH CLUSTERING ORDER BY (created_at DESC, notification_id DESC)
  AND default_time_to_live = 7776000;   -- 90 days, in seconds

-- Cassandra: what happened on each channel
CREATE TABLE deliveries (
  notification_id  UUID,
  channel          TEXT,
  user_id          BIGINT,
  status           TEXT,       -- queued, sent, delivered, failed
  attempts         INT,
  updated_at       TIMESTAMP,
  PRIMARY KEY ((notification_id), channel)
) WITH default_time_to_live = 7776000;

Why Cassandra for these two?

  • From the estimates, this data takes 150 million writes a day and grows by 25 GB a day. Cassandra is built for heavy writes and grows by adding servers.
  • We only ever read it two ways: “the newest notifications for this user” and “the status of this notification”. Each table is laid out for exactly one of those, so each read touches one group of rows on one server.
  • Rows delete themselves after 90 days. That is the default_time_to_live setting, so no clean-up job is needed.

The first part of the primary key, in double brackets, is the partition key. All rows with the same partition key are stored together. So one user’s inbox sits in one place, already sorted newest first.

We store the finished text in the inbox, not the template name. If the template changes next month, the user still sees what they were really sent.

Short-lived data: Redis

Redis, a fast in-memory store, holds things that only matter for a short time: idempotency keys (for 24 hours), counters for rate limits, and a cached copy of each user’s settings. A rate limit is a cap on how many calls are allowed per second.

A queue is a waiting line for messages. One program puts messages in, and other programs, called workers, take them out and do the work. If the workers are slow or down, messages wait in line. They are not lost. Kafka and Amazon SQS are common choices.

Request 1: “order 8812 has shipped”

  1. The orders service calls POST /v1/notifications with type order_shipped, user 42, and an idempotency key.
  2. The API asks Redis if it has seen that key. If yes, it returns the same notification ID as before and stops. If no, it saves the key and goes on.
  3. The API puts the request on the queue for its priority and answers 202. The orders service is done.
  4. A processor takes the request off the queue. It loads user 42’s settings and devices from PostgreSQL (usually from the cached copy in Redis). It drops any channel the user turned off.
  5. For each channel that is left, the processor fills in the template: “Order 8812 arrives Friday.” It writes a row to deliveries in Cassandra with status queued. For in-app, it also writes the inbox row.
  6. The processor puts one message on each channel’s queue: one for push, one for email.
  7. A sender for that channel takes the message, checks it is within the provider’s rate limit, and calls the provider.
  8. The provider answers. On success, the sender sets the status to sent. On a short-term error, it tries again later. On a permanent error, like a push token that no longer exists, it sets failed and deletes the token.
  9. Later, email and SMS providers call us back to say “delivered” or “bounced” (the address rejected it), and we update the status. Push providers only tell us they accepted the message. They don’t confirm that the phone showed it.

Request 2: the user taps the bell icon

  1. The app calls GET /v1/users/42/inbox?limit=20.
  2. The API reads the newest 20 rows for user 42 from inbox_by_user in Cassandra. They are already stored together and sorted, so this is one quick read.
  3. The API returns the rows with a cursor for the next page.

1. How do we avoid sending the same thing twice?

Duplicates come from two places.

The caller retries. The orders service times out and sends the request again. The idempotency key handles this:

// notifications.service.ts
async accept(req: SendRequest) {
  const key = `idem:${req.source}:${req.idempotencyKey}`;
  const id = randomUUID();
  // NX = only write if the key is not there yet. EX = forget it in 24 hours.
  const isNew = await this.redis.set(key, id, 'EX', 86400, 'NX');
  if (!isNew) return { notificationId: await this.redis.get(key) };

  try {
    await this.queue.publish(queueFor(req.priority), { id, ...req });
  } catch (err) {
    await this.redis.del(key);   // let the caller's retry start clean
    throw err;
  }
  return { notificationId: id };
}

Our own queue delivers a message twice. Queues promise at-least-once delivery: every message is handed out one or more times. If a sender crashes after calling the provider but before telling the queue “done”, the queue hands the message to another sender.

The options:

  • Exactly-once. Not possible here. We can’t make “call the email provider” and “mark the message done” happen as one step.
  • At-most-once. Mark it done first, then send. No duplicates, but a crash loses the notification. That breaks “hard to lose”.
  • At-least-once, plus a check before sending. Before calling the provider, the sender writes a key like sent:{notificationId}:{channel} to Redis with NX. If the key is already there, it skips the send.

The pick: the third one. A tiny gap is left: a crash after writing the key but before the provider call means that one send is skipped. So the key is written with a short expiry, and the retry goes through after it runs out. For push, we also pass the notification ID as the provider’s collapse key, so two copies show as one on the phone.

2. How do login codes stay fast during a marketing send?

From the estimates, one campaign adds 3,300 per second on top of a 2,900 per second peak. If everything shares one line, a login code waits behind two million offers.

The options:

  • One queue, more workers. Simple, but the login code still waits its turn.
  • One queue per priority. Three queues: high (login codes, security), normal (order updates), low (offers). Each has its own workers.
  • A separate service for urgent messages. Full isolation, but two systems to build and run.

The pick: one queue per priority, and the high queue has workers that never do anything else. Offers can pile up in the low queue for minutes. The high queue stays nearly empty, so a login code is picked up at once.

The same split happens again after the processor: each channel has its own queue. If the SMS provider is slow, push and email keep moving.

3. What happens when a provider is slow or down?

The options:

  • Retry at once, forever. A provider that is struggling gets hit even harder, and one bad message blocks the line.
  • Give up on the first error. Simple, but most errors pass in a few seconds. We would lose notifications for no reason.
  • Retry a few times with growing waits, then set the message aside.

The pick: the third one. It also needs us to tell two kinds of failure apart.

  • Short-term errors (a timeout, “try again later”, “too many requests”). Retry, but not right away. Wait 1 second, then 2, then 4, then 8. This is exponential backoff. Add a small random extra wait, called jitter, so thousands of failed sends don’t all retry in the same instant.
  • Permanent errors (the push token is gone, the email address doesn’t exist). Retrying can never work. Mark it failed and remove the bad address.

After 5 failed tries, the message goes to a dead-letter queue. That is a separate queue for messages that could not be handled. They sit there for a person to look at, and they stop blocking the line.

If a provider keeps failing, the sender stops calling it for a short while and lets messages wait in the queue. This is the circuit breaker pattern. For email and SMS, we can also switch to a second provider. For push there is no second choice: only Apple can reach an iPhone.

4. How do we send to 2 million users at once?

The marketing tool calls POST /v1/notifications/batch with 2 million user IDs. We can’t do all of that inside one request. It would take minutes, and one crash would lose the whole send. So we cut it into small pieces that can each be retried alone.

  1. The API saves the list, answers 202 with a batch ID, and puts one “start batch” message on the low queue.
  2. A splitter worker reads the list and cuts it into chunks of 1,000 users. That makes 2,000 chunk messages. Turning one request into many is called fan-out.
  3. Processors take chunks and create the single notifications, at a capped rate. The cap is the 3,300 per second from the estimates.

Two more protections for users:

  • A daily cap. A counter in Redis allows, say, 3 offers per user per day. More than that are dropped.
  • Quiet hours. Low-priority messages due between 10 pm and 8 am in the user’s time zone are held until morning.

The design holds for today’s peak of 2,900 per second. Here is what breaks as that number grows. The worker numbers assume one sender can do 200 sends per second. That is made up for the example.

Today: 2,900 per second

  • Senders needed: 2,900 ÷ 200 = 14.5, so 15 senders. With a campaign running: (2,900 + 3,300) ÷ 200 = 31 senders.
  • Senders keep nothing in memory between messages. So we add more when the queue grows and remove them when it is empty.

  • The inbox for very active users gets long. Cap it at the newest few hundred rows per user.

  • Answer at once vs wait for the send. We reply 202 and send later. Callers are never slowed down by a provider. In return, they don’t know if it worked unless they check the status.
  • At-least-once vs at-most-once. We chose never to lose a notification. The price is a duplicate check on every send, and a rare duplicate when that check is down.
  • Cassandra vs PostgreSQL for the big tables. Cassandra takes the write load and deletes old rows by itself. But it can only answer the two questions the tables were built for. A new question like “all failed emails yesterday” needs a new table or another tool. At a tenth of this size, PostgreSQL with one table per day would be simpler and enough.
  • Many queues vs one queue. Queues per priority and per channel keep problems apart. They also mean more things to watch and more worker groups to size.
  • Providers vs doing it ourselves. Providers save us years of work. We pay per message, and their limits and outages become ours.
  • Keep going vs stop when Redis is down. We keep sending and risk duplicates. A bank might choose the opposite for payment alerts.
  • Storing the finished text vs the template name. The inbox shows what was really sent. It costs more storage per row.

The order to go in

For a 45-minute interview:

  1. Ask questions and fix the scope (5 minutes). Channels, urgent vs marketing, rough size.
  2. Numbers (5 minutes). Notifications per day, per second at peak, storage. Say out loud that it is write-heavy.
  3. API and data (8 minutes). The send endpoint with its idempotency key, then the tables.
  4. High-level design (10 minutes). Draw the boxes, then walk one notification through them.
  5. Deep dives (12 minutes). Duplicates, priorities, and provider failures. Let the interviewer pick, or start with duplicates.
  6. Wrap up (5 minutes). What breaks first as it grows, and what you’d watch.

Questions to ask first

  • Which channels do we need? Push, email, SMS, in-app?
  • Are there urgent messages, like login codes, mixed with marketing?
  • How many users, and how many notifications each per day?
  • Is it fine if a notification is late? Is it fine if one is lost?
  • Do we send through providers, or run our own?
  • Do users need a list of past notifications?
  • Can users turn notifications off, and at what level?

Follow-ups to expect

  • A user has three devices. What happens? There are three rows in devices, so the push sender sends three times. When the user reads it on one device, the inbox row is marked read for all.
  • How do you handle time zones for quiet hours? Store the user’s time zone with their settings. The processor works out their local time and delays low-priority messages.
  • How do you know an email was opened? The provider can report it. We left it out of scope, but it would arrive the same way “delivered” does.
  • Must notifications arrive in order? Usually not. If “delivered” must never show before “shipped”, send both through the same queue partition for that user, so they are handled in order.
  • How would you add a new channel, like WhatsApp? Add a queue, a sender, and templates for it. Nothing before the processor changes.
  • What if a team sends too much? Give each calling service its own rate limit at the API.
