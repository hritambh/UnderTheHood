Almost every app needs to tell users things. “Your order has shipped.” “Your login code is 481920.”

Without a shared service every team builds this alone — orders wires up email, payments wires up SMS — and each handles retries, settings and duplicates its own way. Each gets some of it wrong.

A notification service fixes that. Other services just say “tell user 42 that order 8812 has shipped”. It picks the channels, writes the message, sends it, retries, and records what happened. We cover four channels:

  • Push: the pop-up on a phone, through Apple's APNs or Google's FCM. There is no other way in.
  • Email and SMS, sent through outside companies called providers.
  • In-app: the list behind the bell icon.

One-line version: other services say what happened and to whom. The notification service works out how to tell them, exactly once, on the right channels.

Must do

  1. Accept a “send this” request from any internal service.
  2. Deliver it by push, email, SMS and in-app.
  3. Respect each user's settings. Offers off means no offer emails.
  4. Never send the same notification twice, and retry the ones that fail.
  5. Show a user their recent notifications.

Must be

  • Fast for urgent messages: login codes and security alerts leave within 5 seconds.
  • Patient for the rest: offers and digests can take minutes.
  • Hard to lose: once we answer “accepted”, it must survive a crash.
  • Available: 99.9% on accepting requests.
  • Fair under load: a marketing send must not slow down login codes.

Not doing

  • Deciding what to send, or to whom. A marketing tool picks the audience.
  • Running our own email or SMS delivery. That is a business of its own.
  • The live connection to the app. Pushing a row onto an open screen is SSE or WebSockets, a topic of its own.
  • Chat between users, and open and click reports. We record sent, delivered, failed. Nothing more.

  • A type and data, not the text. Wording lives in a template here, so copy and translations change without touching the orders service.
  • 202, not 200. “We have it and will send it”, not “it has been sent”. The caller never waits on a provider.
  • The idempotency key is a name the caller invents for this one notification. Send it twice, we send once. Idempotent means doing it twice has the same result as once.

Two very different kinds of data, so two databases, plus Redis for what is short-lived.

Small and rarely changing: PostgreSQL

CREATE TABLE settings (
  user_id, category, channel,      -- 'orders' | 'security' | 'offers'
  enabled  BOOLEAN NOT NULL,
  PRIMARY KEY (user_id, category, channel)
);

CREATE TABLE devices (
  user_id     BIGINT NOT NULL,
  device_id   TEXT   NOT NULL,
  platform    TEXT   NOT NULL,     -- 'ios' | 'android' | 'web'
  push_token  TEXT   NOT NULL,
  PRIMARY KEY (user_id, device_id)
);

-- templates: (type, channel, locale) -> title, body
--   body: 'Order {{orderId}} arrives {{eta}}'

A push token is the address of one app on one phone, handed over by Apple or Google. One user, several devices, several tokens. These tables are small, read by primary key, and give us plain transactions when a setting changes.

Big and write-heavy: Cassandra

CREATE TABLE inbox_by_user (
  user_id BIGINT, created_at TIMESTAMP, notification_id UUID,
  type TEXT, title TEXT, body TEXT, read BOOLEAN,
  PRIMARY KEY ((user_id), created_at, notification_id)
) WITH CLUSTERING ORDER BY (created_at DESC)
  AND default_time_to_live = 7776000;   -- 90 days

CREATE TABLE deliveries (
  notification_id UUID, channel TEXT,
  status TEXT,          -- queued | sent | delivered | failed
  attempts INT, updated_at TIMESTAMP,
  PRIMARY KEY ((notification_id), channel)
);

150 million writes a day growing 25 GB a day is what Cassandra is built for. We ask it two things — “newest for this user” and “status of this notification” — and each table is laid out for exactly one, so a read hits one group of rows on one server. The part in double brackets is the partition key: rows sharing it are stored together. Rows expire after 90 days, so there is no clean-up job.

We store the finished text, not the template name, so a template change doesn't rewrite history. Redis holds the short-lived things: idempotency keys for 24 hours, rate-limit counters, and a cached copy of each user's settings.

A queue is a waiting line: one program puts messages in, workers take them out. If the workers are down, messages wait rather than vanish. Kafka and Amazon SQS are the usual choices.

Request 1: “order 8812 has shipped”

  1. The orders service calls POST /v1/notifications with a type, a user and an idempotency key.
  2. The API asks Redis whether it has seen that key. If so it returns the original ID and stops.
  3. Otherwise it puts the request on the queue for its priority and answers 202. The caller is done.
  4. A processor picks it up, loads settings and devices (usually from Redis), and drops every channel the user turned off.
  5. For each channel left it fills the template, writes a deliveries row as queued, plus the inbox row for in-app, and puts one message on each channel's queue.
  6. A sender checks the rate limit and calls the provider. On success the status becomes sent; a dead push token means failed and the token is deleted.
  7. Email and SMS providers call back later with “delivered” or “bounced”. Push providers only confirm they accepted it, never that the phone showed it.

Request 2: the user taps the bell icon

GET /v1/users/42/inbox?limit=20 reads the newest 20 rows from inbox_by_user. They are already stored together and sorted newest first, so it is one quick read, returned with a cursor for the next page.

1. How do we avoid sending the same thing twice?

Duplicates come from two places. The caller retries after a timeout, handled by the idempotency key:

const key = `idem:${req.source}:${req.idempotencyKey}`;
const id = randomUUID();
// NX = only write if absent. EX = forget after 24 hours.
const isNew = await redis.set(key, id, 'EX', 86400, 'NX');
if (!isNew) return { notificationId: await redis.get(key) };
try {
  await queue.publish(queueFor(req.priority), { id, ...req });
} catch (err) {
  await redis.del(key);   // let the caller's retry start clean
  throw err;
}
return { notificationId: id };

Our own queue delivers twice. Queues promise at-least-once: a sender that crashes after calling the provider but before saying “done” has its message handed to another. Exactly-once isn't available, because the call and the mark can't be one step, and at-most-once loses notifications on a crash.

The pick: at-least-once plus a check. Before calling the provider the sender writes sent:{id}:{channel} with NX and skips if it is there. One gap remains — a crash between key and call skips that send — so the key expires quickly and the retry goes through. For push we also pass the notification ID as the collapse key, so two copies show as one.

2. How do login codes stay fast during a marketing send?

A campaign adds 3,300/s on top of a 2,900/s peak. In one shared line a login code waits behind two million offers, and more workers don't help. The pick: one queue per priority, and the high queue's workers do nothing else.

The same split happens after the processor: one queue per channel, so a slow SMS provider never holds up push. The campaign is cut up — a splitter turns the list into chunks of 1,000 users (fan-out) processed at a capped rate, so one crash costs one chunk. Users also get quiet hours and a Redis-counted cap of 3 offers a day.

3. What happens when a provider is slow or down?

Retrying forever hammers a struggling provider; giving up at once loses notifications that would have worked seconds later. So retry with growing waits, then set the message aside. That needs two kinds of failure told apart.

  • Short-term (timeout, “too many requests”): wait 1 s, then 2, 4, 8 — exponential backoff — plus a random jitter, so thousands of failures don't retry in the same instant.
  • Permanent (dead push token, non-existent address): retrying can never work. Mark failed, drop the address.

After 5 tries a message moves to a dead-letter queue, where it waits for a person instead of blocking the line. If a provider keeps failing the sender stops calling it for a while: the circuit breaker pattern. Email and SMS can fail over to a second provider; push cannot, because only Apple reaches an iPhone.

Say one sender does 200 sends per second: today's 2,900/s peak needs 15 senders, or 31 with a campaign running. Senders keep nothing between messages, so they are added when a queue grows and removed when it empties.

  • Answer at once vs wait for the send. 202 means callers are never slowed by a provider, but they don't know it worked unless they check the status.
  • At-least-once vs at-most-once. We chose never to lose one. The price is a duplicate check on every send, and a rare duplicate when that check is down.
  • Cassandra vs PostgreSQL for the big tables. Cassandra takes the write load and expires rows itself, but only answers the two questions its tables were built for. At a tenth of this size, PostgreSQL would be simpler and enough.
  • Many queues vs one. Per priority and per channel keeps problems apart; it also means more to watch and more worker groups to size.
  • Storing the finished text vs the template name. The inbox shows what was really sent, at the cost of storage per row.

The order to go in

  1. Scope (5 min). Which channels? Urgent mixed with marketing? Rough size?
  2. Numbers (5 min). Per day, per second at peak, storage. Call out that it is write-heavy.
  3. API and data (8 min). The send endpoint with its idempotency key, then the tables.
  4. High level (10 min). Draw the boxes, walk one notification through.
  5. Deep dives (12 min). Duplicates, priorities, provider failures — start with duplicates.
  6. Wrap up (5 min). What breaks first, what you'd watch.

Questions to ask first

  • Which channels — push, email, SMS, in-app?
  • Are login codes mixed in with marketing?
  • How many users, how many notifications each?
  • Is late acceptable? Is lost acceptable?

Follow-ups to expect

  • A user has three devices? Three rows in devices, so push sends three times; reading on one marks it read for all.
  • Quiet hours across time zones? Store the time zone with the settings; the processor delays low-priority messages.
  • Must they arrive in order? Usually not. If “delivered” must never precede “shipped”, send both through the same queue partition for that user.
  • Adding WhatsApp? A queue, a sender and templates. Nothing before the processor changes.
