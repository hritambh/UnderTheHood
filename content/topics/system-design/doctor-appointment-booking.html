A patient opens the app and types “dermatologist near me”. They get a list of doctors with a fee, a distance and the next free slot. They tap a doctor, see that day's open times, pick 4:30 pm and get a confirmation. A reminder arrives the evening before.

Practo and Zocdoc are the well-known versions. From the outside it looks like a search box and a calendar. The interesting part is that those two things pull in opposite directions: search wants data copied everywhere so it is fast, and booking wants one copy of the truth so a slot can't be sold twice.

One-line version: a search problem and a correctness problem sharing one product. Search is read-heavy and can be slightly stale; booking is low-volume and must never be wrong.

Must do

  1. Search doctors by specialty and city, filtered to those with a free slot on a date.
  2. Show a doctor's free slots for a chosen day.
  3. Book a free slot. One slot goes to exactly one patient.
  4. Cancel or reschedule, which puts the slot back.
  5. Send a reminder before the appointment.

Must be

  • Search: under 300 ms at the 95th percentile. Stale by a minute is fine.
  • Booking: never double-booked. This is the one thing we will not trade away.
  • Confirmation: the patient knows within 2 seconds whether they got the slot.
  • Uptime: 99.9%. Search staying up matters more than booking staying up.

Not doing

  • Payments and refunds. A different system with its own rules; we only mark an appointment paid.
  • Video consultations. Streaming is its own design.
  • Medical records and prescriptions. Regulated data, kept well away from a search index.
  • Doctor-side clinic management. We take the slots a clinic gives us and nothing more.

Assumptions, made up: 200,000 doctors, 30 slots each per day, slots opened 60 days ahead, 20 million searches a day, 500,000 bookings a day, peak 5× average, 100 bytes per slot row and 500 bytes per appointment.

Two numbers decide the whole design. Peak booking is 30 writes a second — nothing for one PostgreSQL machine, so we can afford the strictest correctness we like. And reads outnumber writes 40 to 1, so search gets its own copy of the data rather than fighting the booking database for it.

  • Book by slot ID, not by time. The server already decided what a slot is. A client sending a time would have to be trusted to round it the same way.
  • The idempotency key is a name the client invents for this one booking. A retry after a dropped connection returns the same appointment instead of making a second one.
  • 409 is a normal answer, not a failure. Someone was faster. We hand back the next free time so the app can offer it.

PostgreSQL holds the truth. The one requirement we cannot bend — a slot going to exactly one patient — is a uniqueness rule, and a relational database enforces that for us at 30 writes a second without breaking a sweat.

CREATE TABLE slots (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doctor_id  BIGINT NOT NULL REFERENCES doctors(id),
  starts_at  TIMESTAMPTZ NOT NULL,
  held_until TIMESTAMPTZ,                    -- a short hold while booking
  UNIQUE (doctor_id, starts_at)
);

CREATE TABLE appointments (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id     BIGINT NOT NULL REFERENCES slots(id),
  patient_id  BIGINT NOT NULL,
  status      TEXT NOT NULL,                 -- booked | cancelled
  idem_key    TEXT NOT NULL UNIQUE
);

-- the whole guarantee: one live booking per slot, cancelled rows kept
CREATE UNIQUE INDEX appt_one_per_slot ON appointments (slot_id)
  WHERE status = 'booked';

CREATE INDEX slots_free_idx ON slots (doctor_id, starts_at)
  WHERE held_until IS NULL;
CREATE INDEX appt_patient_idx ON appointments (patient_id, id DESC);

appt_one_per_slot is the design. Two bookings for one slot are not a bug we catch in code — the second INSERT simply fails. Cancelling sets status to cancelled, which drops the row out of that index and frees the slot, while keeping the history.

Search runs on a separate search index (Elasticsearch or OpenSearch), one document per doctor, holding the fields people filter on plus a summary of when they are next free. See Inverted Indexes for how that index works.

A search (1): the load balancer picks a search service box. It checks the cache for this specialty, city and date. On a miss it asks the search index, which returns 20 doctors already filtered to those free that day, and caches the answer for 60 seconds.

A booking (2): the booking service opens one transaction against PostgreSQL, inserts the appointment row and commits. The unique constraint decides the winner. The commit also writes a job to the queue for the reminder worker, and the change feed carries “this slot is gone” across to the search index within a few seconds.

How do two patients not get the same slot?

Two requests arrive within a millisecond for slot 90183371.

Reading first and writing second is wrong however carefully you code it: both requests read before either writes. The options are a row lock (SELECT ... FOR UPDATE) or letting the database refuse the second write. We take the second. It is one INSERT, it holds no lock while the request thinks, and the guarantee lives in the schema where nobody can forget it. The duplicate key error becomes a 409.

How does search stay fast while availability changes all day?

Filtering on “free this Thursday” means joining 200,000 doctors against 360 million slot rows, over and over.

  • Query PostgreSQL live. Always right, far too slow at 1,150 searches a second, and it puts read load on the database that must stay healthy for bookings.
  • Index every slot as its own document. Exact, but 6 million documents change every day and the index never stops rewriting itself.
  • Index one document per doctor, carrying a small summary: the dates they have anything free, and the next free time. 200,000 documents, updated only when a doctor's first free slot on a day changes.

We take the third. Search is then one index lookup with no join. The cost is staleness: for a few seconds a listing can show a slot that was just taken. The booking 409 is what catches that, which is why it is a normal answer and not an error.

What stops a slot being taken while a patient is filling in the form?

Without a hold, patients lose the slot at the last step and blame the app. With a long hold, bad actors park every slot. We set held_until to two minutes when the booking screen opens; free slot queries skip held rows, and a sweeper clears holds that expire. Two minutes is short enough that a stuck hold costs one slot for one cycle.

The pleasant surprise is that the part everyone worries about — booking correctness — is the last thing to break. Sharding by doctor_id works because the unique constraint only ever covers one doctor's slots.

  • Separate search index vs one database. We got fast search and protected the booking database. We pay with a copy that can be stale and a feed that can break.
  • Unique index vs row lock. The index is simpler and holds no lock while the user thinks, but losers find out only after trying, so the client must treat 409 as a normal path.
  • Short holds vs instant booking. Holds stop the last-step disappointment and make a slot briefly invisible to everyone else.
  • SQL vs NoSQL. At 30 writes a second there is no scale reason for NoSQL, and we would have to build uniqueness ourselves. We would revisit this past 100×.
  • Per-doctor summaries vs per-slot documents. Far fewer index updates, and we can't answer “free at exactly 4:30 pm” from search alone — that needs the slots call.

The order to go in

  1. Scope, 3 min. Five things it must do, and the list of what you are leaving out.
  2. Numbers, 5 min. Get to 1,150 searches a second against 30 bookings a second. That ratio drives everything after it.
  3. API and schema, 7 min. Put the unique index on appointments.slot_id and say out loud why it is there.
  4. Diagram, 5 min. Draw it, then walk a search and a booking through it.
  5. Deep dive, 10 min. Double booking first. It is the question they are waiting for.
  6. Scaling and failure, 5 min. 10× and 100×, then what the patient sees when each box dies.

Questions to ask first

  • One city or many, and do we need distance ranking?
  • Are payments part of booking, or separate?
  • Can a doctor overbook on purpose, the way clinics really work?
  • How far ahead can slots be booked?

Follow-ups to expect

  • What if the clinic cancels? Free the slot, mark the appointment cancelled, notify through the same queue as reminders.
  • How do you stop a bot grabbing every slot? Rate limit bookings per patient and per IP, and cap the number of live holds.
  • Timezones? Store TIMESTAMPTZ, show in the clinic's local time, since that is the time the patient has to be there.
  • Would you ever allow a double booking? Only if the product asks for it. Then it becomes a count per slot, not a unique row.
