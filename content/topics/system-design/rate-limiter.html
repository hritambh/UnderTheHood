Every public API has a line in its docs like “100 requests a minute per key”. Go over it and you get 429 Too Many Requests and a Retry-After header telling you when to come back.

The reason is not fairness, it is survival. One client with a bad loop can use the capacity of ten thousand good ones. Stripe, GitHub and Cloudflare all publish limits like this. We are building the component that enforces them, shared by every service in the company.

One-line version: a rate limiter is a counter with a deadline. The entire design is about where that counter lives and who is allowed to touch it.

Must do

  1. Answer allow or deny for one request, keyed by API key, user id or IP.
  2. Hold different limits per rule: 100 a minute on search, 5 an hour on password reset.
  3. Tell the caller what is left and when to retry, in response headers.
  4. Let an operator change a limit without a deploy.
  5. Count across the whole fleet, so a client hitting 50 servers still gets one budget.

Must be

  • Fast: under 2 ms added at the 99th percentile. It runs before every single request.
  • Harmless when broken: if the limiter is down, normal traffic flows. It must never be the outage.
  • Cheap: one network round trip per request, not three.
  • Accurate enough: letting 105 through on a limit of 100 is fine. Letting 1,000 through is not.
  • Burst-friendly: a quiet client may spend saved-up budget in one go. Real clients come in bursts.

Not doing

  • Billing quotas. “10,000 calls this month, then we invoice you” must be exact and durable. That is a ledger, not a counter you are happy to lose.
  • Bot detection. Deciding who a caller really is belongs in a WAF.
  • Queueing. We reject over-limit requests. Holding them and releasing them slowly is traffic shaping, and it hides the problem.
  • Network floods. A volumetric attack never reaches us. That is the edge provider’s job.

Assumptions, made up: 20,000 requests a second across the fleet, peak 3×, 2 million distinct callers active in any minute, 100 bytes per counter, 80 bytes to log one decision.

  • Send the headers on success too, not only on a 429. A client that can see it has 7 left can slow down on its own. One that only learns at zero cannot.
  • Retry-After is not optional. Without it every blocked client retries immediately, and a limiter that triggers a retry storm has made things worse.
  • Cost lets one endpoint count as ten. A report that runs for 30 seconds should not cost the same as a key lookup.

Redis holds the counters. It has per-key expiry built in, it does atomic maths in one round trip, and losing every counter on a restart costs one window of over-permissiveness — not data. PostgreSQL holds the rules: 20 rows, edited by humans, read into each pod’s memory and refreshed every 10 seconds. Nothing about the counters is durable, and that is on purpose.

-- rules live in PostgreSQL: tiny, human-edited, versioned
CREATE TABLE rules (
  id       TEXT PRIMARY KEY,       -- 'search', 'login', 'password-reset'
  scope    TEXT NOT NULL,          -- api_key | user | ip
  limit_n  INTEGER NOT NULL,       -- tokens added per window
  window_s INTEGER NOT NULL,
  burst    INTEGER NOT NULL,       -- the most a caller may save up
  enabled  BOOLEAN NOT NULL DEFAULT true,
  version  BIGINT NOT NULL
);
# counters live in Redis: one small hash per rule and caller
rl:search:ak_19f  ->  { tokens: 37.5, ts: 1764051000.412 }

# the TTL is twice the refill time, so idle callers clean themselves up
EXPIRE rl:search:ak_19f 120

Two fields per caller, not a list of timestamps. That choice is the next section, and it is the difference between 200 MB and 20 GB.

An allowed request: the gateway already has the rules in memory, so it builds the key rl:search:ak_19f, runs one script against Redis, gets back “yes, 37 left”, adds the headers and forwards to the backend. One round trip, about half a millisecond.

A denied request: same call, different answer. The gateway returns 429 with Retry-After and never touches a backend service. A rule change is written to PostgreSQL, and every gateway picks it up within 10 seconds — no deploy, and no call to the rules service on the hot path.

Which window do you count in?

Way to countMemory per callerProblem
Fixed windowOne numberTwice the limit around every boundary, as above
Sliding log of timestampsOne entry per requestExact, and 100 entries per caller: 20 GB instead of 200 MB
Sliding window counterTwo numbersGood, but it smooths bursts away even when you wanted them
Token bucketTwo numbersBursts are a setting, not an accident

We take the token bucket. Two numbers per caller, no boundary trick, and a client that was quiet for ten minutes can spend its saved budget in one go — on purpose, as a setting, instead of by accident at a window edge.

How is it atomic across fifty gateways?

Read the counter, decide, write it back: fifty pods all read 99 at the same moment, all say yes, and 50 requests pass a limit of 100. INCR plus EXPIRE is two commands, and a pod that dies between them leaves a key that never expires. So the check is one script, which Redis runs with nothing in between.

-- token_bucket.lua, run by Redis itself. KEYS[1] is the caller's bucket.
local rate, burst, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t   = redis.call('TIME')              -- Redis's clock, not the caller's
local now = tonumber(t[1]) + tonumber(t[2]) / 1000000
local b   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or burst
local ts     = tonumber(b[2]) or now

tokens = math.min(burst, tokens + (now - ts) * rate)
local ok = tokens >= cost
if ok then tokens = tokens - cost end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(burst / rate) * 2)
return { ok and 1 or 0, math.floor(tokens) }

It is Lua because that is what Redis runs. Two details earn their place. The clock comes from Redis, so a gateway with a fast clock cannot mint itself free tokens. And the EXPIRE sits inside the same script, so an idle caller’s key always goes away — there is no path where a key is written and its expiry is not.

What happens when Redis dies?

A limiter that fails closed turns a cache problem into a full outage, which is exactly the thing it exists to prevent. So the default is fail open: allow, and raise an alarm. Each pod also keeps a local bucket sized at the rule’s limit divided by the number of pods, so a fleet without Redis is loose but not naked.

The exception is written into the rule itself. login and password-reset fail closed, because letting a credential-stuffing run through unmetered is the damage, not a side effect of it. Which way a rule fails is a column on that rule, not one global setting for the whole service.

  • Token bucket vs sliding log. Two numbers per caller instead of a hundred timestamps, so 200 MB instead of 20 GB. We give up knowing exactly which requests happened when.
  • In the gateway vs its own service. No extra network hop on any request. The cost is that upgrading the limiter means redeploying every gateway.
  • Fail open vs fail closed. Open by default, so the limiter can never cause the outage. Closed for auth rules, where being open is the outage.
  • Shared counter vs per-pod counters. One Redis call gives one true budget across the fleet. Leasing tokens locally is far cheaper and lets a caller overshoot by one lease.
  • Reject vs queue. A 429 is honest and instant. Queueing would hide the problem behind slow responses and tie up memory holding them.

The order to go in

  1. Scope, 2 min. Enforce limits per caller per rule. Billing quotas and bot detection are out.
  2. Numbers, 3 min. 60,000 checks a second, 1 to 1 reads and writes, 200 MB of counters. Say the 1 to 1 out loud; it surprises people.
  3. Algorithms, 6 min. Draw the fixed-window boundary problem, then the four options, then pick the token bucket.
  4. Diagram, 3 min. Gateway, Redis, rules. Follow an allowed and a denied request.
  5. Atomicity, 6 min. Why read-modify-write races, and why it ends up as one script.
  6. Failure, 5 min. Fail open or closed, and why the answer is per rule.

Questions to ask first

  • What are we limiting by: API key, user, IP, or all three at once?
  • Is a small overshoot acceptable? If not, this is a quota problem, not a limiter.
  • Should bursts be allowed, or should traffic be perfectly smooth?
  • One region or several? Global counters across regions cost a cross-region hop on every request.

Follow-ups to expect

  • Limiting by IP? Fine for abuse, bad for fairness. A whole office shares one address.
  • Several limits on one request? Check them in one script and deny on the first failure, so it is still one round trip.
  • Counters across regions? Keep them regional and divide the limit. A global counter pays a cross-region hop on every single request, to be exact about a number that tolerates being wrong.
  • Why not a sliding window counter? It is a good answer. It just smooths bursts away, and for an API bursts are normal traffic.
