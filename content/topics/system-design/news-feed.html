You open the app. Within a second you are looking at recent posts from the few hundred accounts you follow, newest first, and you can scroll back for as long as you have patience.

The timeline on X, the Instagram feed and the LinkedIn feed all work this way. The thing to notice is that your feed is not a thing anyone stored. It is a mix of other people’s posts, and your mix is different from everyone else’s. Someone has to assemble it, and the only real question in this design is when.

One-line version: build the feed when someone posts, or build it when someone looks. Both break somewhere, so real systems do both and switch between them.

Must do

  1. Post text, with links to media that lives elsewhere.
  2. Follow and unfollow an account.
  3. Show a home feed: recent posts from everyone you follow, newest first.
  4. Scroll back through the feed, page after page, without it getting slower.
  5. Show like and comment counts on every post.

Must be

  • Fast to open: first page on screen in under 200 ms at the 95th percentile.
  • Fresh enough: a new post reaches its followers’ feeds within about 10 seconds. Not instantly — nobody can tell, and promising instant costs a great deal.
  • Available over correct: a feed that is five seconds behind beats an error page.
  • Flat to scroll: page 50 costs the same as page 1.
  • Up: 99.9%.

Not doing

  • Ranking. We serve newest first and leave a hook where a ranker would sit. Deciding what you want to see is a machine learning system, not a feed system.
  • Ads. Injecting paid posts is a separate service that edits the page on the way out.
  • Storing media. Photos and video go to object storage; a post holds a link.
  • Notifications. “Someone replied to you” belongs in Notification Service.

Assumptions, made up: 500 million daily users, 50 million posts a day, 300 follows per person on average, 10 feed opens per person per day, 500 bytes per post, peak 3× average.

The last two rows are the whole topic. Pushing posts into followers’ feeds costs 174,000 inserts a second to serve 58,000 feed opens — three writes for every read — and it still wins, because a write is a cheap append and a read is a person waiting. But for one very big account the same approach needs ten minutes to deliver a single post, so that account cannot use it.

  • The cursor is a post id, not a page number. Posts arrive while you scroll, so an offset would show you the same post twice and hide another. Pagination in Backend Systems has the full story.
  • Post ids are time-ordered. The id carries a timestamp in its high bits, so sorting by id sorts by time. One number is the sort key, the cursor and the Redis score, and no clock has to be trusted at read time.
  • Posting returns before the post has reached anyone. Fan-out happens behind a queue. The author sees their own post immediately because their own posts are read directly.

PostgreSQL, sharded by author, holds posts and follows. 580 writes a second is small, 9 TB a year is routine, and the follow graph genuinely is relational. Redis holds one capped sorted set per active user: their feed, as post ids only. The ids are time-ordered, so the sorted set score and the id are the same number, and reading a page is one ZREVRANGEBYSCORE.

CREATE TABLE posts (
  id         BIGINT PRIMARY KEY,       -- time-ordered: sorts by id = by time
  author_id  BIGINT NOT NULL,
  body       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX posts_author_idx ON posts (author_id, id DESC);

CREATE TABLE follows (
  follower_id BIGINT NOT NULL,
  followee_id BIGINT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (follower_id, followee_id)   -- "who do I follow?"
);
-- the other direction, which is the one fan-out actually needs
CREATE INDEX follows_followee_idx ON follows (followee_id, follower_id);

CREATE TABLE authors (
  user_id   BIGINT PRIMARY KEY,
  followers BIGINT NOT NULL,      -- roughly right, not exactly
  push      BOOLEAN NOT NULL      -- false once they get too big to push
);

Both indexes on follows matter, and they do opposite jobs. The primary key answers “who do I follow” for the read path. follows_followee_idx answers “who follows me”, which is the list fan-out walks every time anyone posts.

Posting. The post service writes one row to PostgreSQL, returns 201, and drops a job on the fan-out queue. Workers read “who follows me” and push the post id into each follower’s Redis list, trimming it back to 500. The author waits for none of this.

Opening the feed. The feed service reads 20 ids from the reader’s Redis list, then turns those ids into posts with one batched read from the post cache, falling through to PostgreSQL for anything missing. Like and comment counts ride along in the cached post, so they cost no extra call. Two round trips, no joins, and nothing that gets slower as the site grows.

Following someone is one row in follows and nothing else. It changes who fan-out walks from the next post onwards, and leaves every feed list exactly as it was.

Push the post, or pull it?

Fan-out on read keeps posting cheap and makes every feed open do the work: 300 queries, a merge and a sort, 58,000 times a second, while the reader waits. Fan-out on write turns posting into 300 appends and makes opening a feed one read of a list that is already in the right order.

We push. It costs three writes for every read, which sounds wrong until you remember that the writes happen on a queue with nobody watching, and the read happens with a person staring at a blank screen.

What about the account with 100 million followers?

At 174,000 inserts a second, one post from an account with 100 million followers takes 575 seconds to deliver. Everyone else’s posts queue behind it. Raising the fan-out capacity ten times still leaves a minute, for one post.

So past a threshold — say 100,000 followers — we set push = false and that account is never fanned out. The feed service reads your Redis list as usual, then asks the few big accounts you follow for their recent posts directly, and merges the two by post id. You follow 300 accounts and perhaps five of them are huge, so this is five extra reads, not 300. It is fan-out on read, used exactly where fan-out on write falls over.

Why store ids and not the posts?

Keeping whole posts in every feed list would be 500 entries × 500 bytes × 500 million users: 125 TB of memory, against 4 TB for ids. It is also 300 million copies to fix when someone edits a post, and 300 million to find when someone deletes one.

With ids, a deleted post is one row gone and the stale ids simply resolve to nothing and get dropped from the page. The cost is a second round trip on every feed open, which is one batched read of 20 keys from a cache built for exactly that.

What about page 50?

The Redis list is capped at 500 ids, which is 25 pages. Past that we fall back to fan-out on read for the older pages: query the accounts you follow for posts older than the cursor and merge. It is slow, and almost nobody goes there, so slow is the right answer.

  • Fan-out on write vs on read. We pay three writes for every read, off the hot path, and get a feed open that is one list read. We give up instant delivery and accept about 10 seconds.
  • A hybrid vs one strategy. Both paths exist and both are tested every day, so a dead Redis shard has somewhere to fall. The cost is two code paths that must agree on ordering.
  • Ids vs whole posts in the list. 4 TB instead of 125 TB, and edits and deletes touch one row. The cost is a second round trip on every open.
  • A capped list vs full history. 500 ids covers what anyone actually scrolls. Deeper pages drop to the slow path.
  • Newest first vs ranked. Newest first is explainable and cheap. A ranker needs features, a model and a scoring pass, and changes this design from the feed service outwards.
  • Fresh in 10 seconds vs instant. A queue absorbs every spike and keeps posting fast. The feed is briefly behind, which no reader can detect.

The order to go in

  1. Scope, 2 min. Post, follow, read the feed, scroll. Ranking and ads are out, and say so early.
  2. Numbers, 4 min. 580 posts against 58,000 opens, and 300 followers each. Both answers come straight out of these.
  3. The two strategies, 6 min. Draw push against pull before drawing any boxes. This is the question being asked.
  4. Diagram, 4 min. Post service, queue, Redis lists, feed service. Follow a post and an open.
  5. Celebrities, 6 min. 575 seconds for one post, then the threshold and the merge.
  6. Scaling and failure, 5 min. Memory for feed lists, and what happens when a Redis shard dies.

Questions to ask first

  • Newest first, or ranked? Ranking changes the read path completely.
  • How fresh does a feed have to be? Ten seconds and one second are different systems.
  • What is the biggest follower count we must support? That number sets the threshold.
  • How far back can people scroll? It decides how long the cached list has to be.

Follow-ups to expect

  • What happens when I follow someone? Nothing to the past. Their new posts start arriving; their old ones show up on the read path or on a backfill job.
  • And when I unfollow? Their ids stay in your list until it trims. Filter them at read time rather than hunting through a list.
  • Where would ranking go? Read a few hundred ids instead of 20, score them, return the top 20. The storage design does not change.
  • Like counts on a viral post? Don’t update a row per like. Count in Redis and write the total back every few seconds.
  • A feed is never stored. It is assembled, and the only real question is whether that happens on post or on open.
  • Feed opens outnumber posts 100 to 1, so the work belongs on the write side.
  • Fan-out on write means 174,000 inserts a second to serve 58,000 feed opens: three writes per read, and worth it.
  • Writes happen on a queue with nobody waiting; reads happen with a person staring at a blank screen.
  • One post from an account with 100 million followers would take 575 seconds to fan out.
  • So past a follower threshold an account is never pushed, and its posts are read live and merged in.
  • You follow 300 accounts and maybe five are huge, so the merge costs five reads, not 300.
  • Feed lists hold post ids only: 4 TB instead of 125 TB, and one row to fix on an edit or a delete.
  • Post ids are time-ordered, so the id is the sort key, the cursor and the Redis score all at once.
  • The follows table needs both directions indexed: who I follow for reads, who follows me for fan-out.
  • Lists are capped at 500 ids; deeper scrolling falls back to the read path, which almost nobody reaches.
  • A dead Redis shard falls back to fan-out on read, which is already built and used every day.
  • Only active users get a materialised list. Dormant ones are rebuilt on login.
