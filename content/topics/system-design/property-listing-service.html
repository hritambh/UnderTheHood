You are moving to a new city. You drag the map to the area near your office, set rent between ₹30,000 and ₹60,000 and two bedrooms, and get a list of flats with a photo and a price. You tap one, swipe through twenty photos, and send the owner your number.

Zillow, Rightmove and 99acres are the well-known versions. On the surface it is a search box over a map. The weight is somewhere else: the text of ten million listings fits in 20 GB, while the pictures are 80 TB and almost all the traffic.

One-line version: two problems wearing one coat. Finding flats is a map problem; showing them is a bytes problem, and the bytes must never travel through your API.

Must do

  1. Post a listing: price, bedrooms, area, a point on the map, up to 20 photos.
  2. Search by map area plus filters — deal, price, bedrooms — sorted by newest or cheapest.
  3. Open one listing and see everything, photos included.
  4. Send the owner an enquiry with your number.
  5. Mark a listing sold or rented, and expire it if nobody touches it.

Must be

  • Search: under 300 ms at the 95th percentile, so the map feels live.
  • Photos: the first photo on screen in under a second, anywhere.
  • Fresh: an approved listing is searchable within a minute.
  • Uptime: 99.9% for browsing. Posting can be down for a few minutes.
  • Durable: once a photo is accepted, it is never lost.

Not doing

  • Payments and deposits. Money has its own rules and its own system.
  • In-app chat. We hand over a phone number; messaging is its own design.
  • Price estimates. That is a model, not a service.
  • Fraud and duplicate scoring. We give moderators a queue; the scoring is its own project.

Assumptions, made up: 10 million live listings, 600,000 new ones a month, 40 million searches a day (dragging the map counts as a search), 8 million listing views a day, 20 photos per listing at 400 KB after resizing, 2 KB per listing row, peak 4× average.

PostgreSQL holds the truth. At 0.23 writes a second and 20 GB of rows there is no scale argument for anything else, and a listing has a lifecycle — draft, pending, live, sold, expired — which is what constraints and transactions are for. Photos live in object storage; search runs on a separate search index with a geo field.

CREATE TABLE listings (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id   BIGINT NOT NULL,
  status     TEXT NOT NULL,          -- draft|pending|live|sold|expired
  deal       TEXT NOT NULL,          -- rent | sale
  price      INTEGER NOT NULL,
  beds       SMALLINT NOT NULL,
  area_sqft  INTEGER NOT NULL,
  lat        DOUBLE PRECISION NOT NULL,
  lng        DOUBLE PRECISION NOT NULL,
  city_id    INTEGER NOT NULL,
  posted_at  TIMESTAMPTZ NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE photos (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  listing_id  BIGINT NOT NULL REFERENCES listings(id),
  storage_key TEXT NOT NULL,         -- where the file is, not the file
  position    SMALLINT NOT NULL,
  state       TEXT NOT NULL          -- awaiting | ready | rejected
);

CREATE TABLE enquiries (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  listing_id BIGINT NOT NULL REFERENCES listings(id),
  buyer_id   BIGINT NOT NULL,
  sent_at    TIMESTAMPTZ NOT NULL,
  UNIQUE (listing_id, buyer_id)      -- one enquiry per buyer per flat
);

-- the fallback list when search is unavailable, and the expiry sweep
CREATE INDEX listings_live_idx ON listings (city_id, posted_at DESC)
  WHERE status = 'live';
CREATE INDEX listings_expiry_idx ON listings (expires_at)
  WHERE status = 'live';
CREATE INDEX photos_listing_idx ON photos (listing_id, position);

Note what is not here: any index on lat or lng. The deep dive says why.

A map search: the load balancer picks a search service box, which rounds the rectangle to a fixed grid and checks its cache. On a miss it asks the search index, which filters by box, deal, price and beds in one query and returns 20 cards. The client pulls each cover photo from the CDN, which only reaches back to object storage on a miss.

Posting a listing: the listing service writes a draft row, hands back upload URLs, and moves the row to pending once the photos are ready. A moderator approves it, the row becomes live, and the change feed carries it into the search index within seconds. Enquiries and a sold flip take the same path: listing service, one row, done.

How do you search a map rectangle?

A B-tree index sorts on one thing, so an index on lat narrows one dimension only. At city zoom that stripe is still a hundred thousand rows, 1,850 times a second.

  • Geohash prefix. Turn each point into a short string where near places share a prefix, then match on prefix with an ordinary index. Cheap, but one screen covers several cells, and two flats either side of a cell border share no prefix.
  • A real geo index — PostGIS GiST, or a geo_point field in a search engine. It splits both dimensions together, so a rectangle is one lookup.

We take the geo index, in the search index rather than the database. Every real query is a box and a price range and a bedroom count and a sort. Split those across two systems and you pull a million ids out of one to filter against the other.

How do 80 TB of photos stay out of our API?

Twenty photos is 8 MB of upload per listing, and 890 MB/s of download at peak. Neither belongs on an API server.

  1. Going in: a pre-signed URL lets the client write exactly one object, for five minutes. Our servers never see the bytes.
  2. Coming out: the key is a hash of the file, so a URL never changes meaning and the CDN caches it for a year.

Putting the files in the database would mean 80 TB in a system sized for 20 GB, dragged along by every backup and replica.

What keeps a flat that went last month off the map?

The standard complaint about every property portal: owners never come back to mark a flat gone, so listings rot.

  • Expiry: expires_at is 60 days out. A nightly sweep over listings_expiry_idx flips stragglers to expired, and the change feed drops them.
  • Renewal: the owner gets one question first — still available? One tap adds 60 days.
  • Buyer reports: a few “already gone” reports in a week push it up the moderation queue.

The cost is real: expiry also kills live flats whose owner ignored the prompt. That is why renewal has to be one tap and not a form.

  • Search index vs querying PostgreSQL. We get a map query that also filters and sorts in one pass, and pay with a second copy and a feed that can fall behind.
  • Geo index vs geohash prefix. The geo index handles a rectangle properly instead of approximating it with cells, but needs a system that has one.
  • Pre-signed upload vs through the API. Our servers never carry image bytes. The price is a two-step upload and a row that is briefly awaiting with no file behind it.
  • Expiry vs trusting owners. Expiry keeps dead flats off the map and sometimes kills a live one. Trusting owners rots the whole index.
  • Grid-snapped cache vs exact boxes. Snapping makes pans share cache keys and hit far more often, and returns a few flats just outside your screen.

The order to go in

  1. Scope, 3 min. The five things it does, then what you are leaving out.
  2. Numbers, 5 min. 20 GB of rows against 80 TB of photos. That gap is the design.
  3. API and schema, 6 min. Show bbox in the search call and state on photos.
  4. Diagram, 5 min. Draw it, then walk a search and a post through it.
  5. Deep dive, 10 min. Map search first, photos second. Those are the two they want.
  6. Scaling and failure, 5 min. 10× and 100×, then what dies when each box does.

Questions to ask first

  • Rent, sale or both? They need different filters and different lifetimes.
  • Is ranking part of this, or just filter and sort?
  • Do owners post directly, or agents in bulk through a feed?
  • One country or many, with the languages and currencies that implies?

Follow-ups to expect

  • Saved searches with alerts? Store the filters and match every new live listing against them by city.
  • Ranking instead of sorting? Score freshness, photo count and completeness in the index, then sort on the score.
  • How do you stop scraping? Rate limit by IP and account, and never put a phone number in a list response.
  • Clustering pins when zoomed out? Ask the index for counts per grid cell, so a country view is a few hundred numbers.
