Your API servers read the same rows over and over: a user profile, a product page, a feature flag. The database answers each in 20 ms and the load keeps climbing, though the answers barely change.

So we build a service that holds those answers in memory and hands them back in under a millisecond. Any API server can ask it, so a row fetched for one request is already there for the next, on a different machine. It holds a fixed amount of memory, and when it fills it throws out whatever has gone coldest.

This is what Redis and Memcached do: a key-value store that lives in RAM, is shared by every server, and is allowed to forget things.

One-line version: a shared hash table on the network, split across a few machines, that evicts the least recently used key when memory runs out.

Must do

  1. Store a value under a key, and read it back.
  2. Delete a key, so a write to the database can clear the stale copy.
  3. Expire a key after a time limit the caller sets.
  4. Throw out cold keys by itself when memory is full, without being asked.
  5. Read many keys in one call, so a page render is one round trip.

Must be

  • Fast. p99 under 2 ms inside the data centre. Slower and the database was fine.
  • Shared. Every API server sees the same entry for a key.
  • Allowed to lose data. A miss costs a database read, not a wrong answer.
  • Predictable on memory. It never grows past its limit. It evicts instead.
  • Available. One machine dying lowers the hit rate; it does not take the site down.

Not doing

  • Durability. Nothing survives a restart. The database is the real copy, so disk would cost latency and buy little. Redis does offer it — see How Redis Saves Data to Disk.
  • Transactions across keys. One key at a time. Multi-key atomicity is a database’s job.
  • Queries. No scans, no “find all keys like this”. Exact key only.
  • Cross-region replication. One cluster per region, each filled from its own database.

All of these are made up, to size the thing. They are not measurements.

  • Peak traffic to the API tier: 200,000 requests a second, 95% reads.
  • Hot set: 20 million keys. Average value 2 KB, key 40 bytes, about 100 bytes of bookkeeping per entry.
  • Target hit rate: 90%.
  • One cache node: 16 GB usable memory, 100,000 operations a second.

Reads and writes. 200,000 × 0.95 = 190,000 reads/s. 200,000 × 0.05 = 10,000 writes/s. That is a read-to-write ratio of 19:1, which is why this is worth caching at all.

Misses. 190,000 × 10% = 19,000 reads/s still reach the database. The cache absorbs the other 171,000.

Memory. Each entry costs 2,048 + 40 + 100 ≈ 2,140 bytes. 20,000,000 × 2,140 = 42.8 GB.

How many nodes. Memory says 42.8 ÷ 16 = 2.7, so 3. Throughput says 200,000 ÷ 100,000 = 2. Memory needs more nodes than speed does, and stays that way as we grow. Run 4 shards for headroom.

DELETE returns 204 even for a key that was never there. The caller clearing a stale copy doesn’t care whether one existed.

Shown as HTTP because it reads clearly. A real cache uses a binary protocol over a kept-open TCP connection: at 200,000 requests a second, HTTP headers cost more than the lookup.

There is no database here, and that is the design. The store is a hash table in RAM. Disk is what we are escaping, and the durable copy already sits in the database behind us.

The index is the hash table itself: key to entry, one step, no scanning. Each entry carries:

FieldWhat it holdsWhy it is there
keythe key, 40 byteseviction finds an entry, then needs its key to remove it from the hash table
valuebytes, 2 KB on averagethe cached answer, stored opaque — the service never parses it
expires_attimestampthe TTL the caller asked for
prev, nexttwo pointersthe entry’s place in the use order, for eviction

Those two pointers link every entry into one list, newest at the front, coldest at the back. Touching a key unhooks its entry and hooks it back at the front.

A read

  1. The API server asks the cache client for user:8821.
  2. The client hashes the key, picks shard 2, and sends it over a connection it already holds open.
  3. Hit: the shard moves the entry to the front of its list and returns the value, well under a millisecond.
  4. Miss: the shard returns 404. The API server reads the database, then PUTs the value back with a TTL.

The cache never talks to the database. It doesn’t know one exists. That is cache-aside: the caller owns the filling, so the cache stays a dumb, fast box.

A write

  1. The API server writes the row to the database.
  2. Then it sends DELETE /v1/keys/user:8821.

Delete, don’t update. Two servers writing the same key race, and the loser can leave a stale value there forever. A delete leaves no value to be wrong. Caching and Invalidation goes into this properly.

Which shard holds a key?

Plain hash(key) % 4 works until we add a fifth shard, when almost every key moves and the hit rate falls off a cliff. So the client uses consistent hashing: shards and keys land on one ring, and a key belongs to the next shard clockwise. Adding a fifth moves roughly 1/5 of the keys. Database Sharding covers the ring itself.

The client does this, not a proxy. A proxy is another hop on every one of 200,000 requests a second, and another thing to keep alive.

What do we throw out when memory is full?

PolicyKeepsCost
Randomnothing in particularfree, but drops hot keys
TTL onlywhatever hasn’t expiredmemory still overflows between expiries
LRUrecently used keystwo pointers per entry
LFUoften-used keysa counter per key, and it clings to yesterday’s hot keys

We pick LRU: throw out the key whose last read or write happened longest ago. It matches how traffic actually behaves — a product that was popular an hour ago usually still is.

The structure in data is what makes it cheap. The hash table finds the key in one step; the coldest entry is simply the one at the back. Both a read and an eviction are a fixed number of pointer writes, O(1), whether the shard holds 10 keys or 10 million. Stamping each entry with a timestamp and scanning for the oldest instead is O(n) per eviction — at 5 million entries a shard, that scan is the whole budget.

A read counts as a use, not just a write. That rule keeps a hot key alive while cold neighbours are dropped around it.

What happens on a cold start?

Restart a shard and it holds nothing. Every request for its keys misses at once and the database takes a spike it was never sized for — a stampede. Two defences: a small random jitter on each TTL, so keys written together don’t expire together, and a short per-key lock on a miss, so one request refills while the rest wait.

  • Cache-aside vs read-through. The caller fills the cache, so the cache knows nothing about the database — but every caller must get the miss-then-fill right. Read-through hides that, at the cost of a cache holding database credentials.
  • Delete vs update on a write. Deleting can’t leave a wrong value, but it guarantees the next reader pays for a miss. Updating keeps the hit rate up and risks two writers landing out of order.
  • LRU vs LFU. LRU is two pointers and follows traffic quickly. LFU would survive a scan of cold keys better, but needs a counter per key and holds on to keys that were hot yesterday.
  • Client-side routing vs a proxy. Routing in the client saves a hop on every request. The cost: the ring lives in every API server, so a shard change must reach all of them.

The order to go in

  1. Scope it, 3 min. Key-value, in memory, allowed to lose data. Say “Not doing” out loud: no durability, no transactions, no queries.
  2. Numbers, 5 min. 19:1 reads to writes, 42.8 GB hot set, 4 shards. Say that memory decides the shard count, not throughput.
  3. API and the read path, 5 min. Five endpoints, then follow a hit and a miss through the diagram.
  4. Sharding and eviction, 10 min. Consistent hashing, then LRU and why the hash table plus linked list makes it O(1).
  5. Failures, 5 min. Lead with the whole cache dying and the database behind it.

Questions to ask first

  • Is losing the cache acceptable, or does this need to survive a restart?
  • Who fills it — the caller, or the cache itself?
  • How stale may a read be? That sets the TTL and decides delete versus update.

Follow-ups to expect

  • Make eviction O(1). Hash table for lookup, linked list for order. Each entry stores its own key, or eviction finds the coldest entry but can’t remove it from the table.
  • Two servers write the same key at once. Delete rather than update, so there is no value left to be stale.
  • Add a shard without losing everything. Consistent hashing: about 1/n of keys move, not all of them.
  • Keep it warm through a deploy. Restart one shard at a time, letting each refill first.
  • A value bigger than one node? Cache the pieces under their own keys, read them in one batch call.
  • A cache service is a shared hash table in RAM between the API servers and the database, and it is allowed to forget things.
  • At 19 reads per write it removes 171,000 of 190,000 database reads a second, leaving 19,000.
  • Memory decides the shard count, not throughput: 42.8 GB needs 3 nodes, while the traffic needs only 2.
  • Cache-aside means the caller reads the database on a miss and writes the value back, so the cache stays simple.
  • On a database write, delete the key rather than update it, so no wrong value can be left behind.
  • Consistent hashing in the client lets you add a shard and move about 1/n of the keys instead of all of them.
  • LRU evicts the key used longest ago, and a read counts as a use. A hash table plus a doubly linked list makes both a read and an eviction O(1), because the coldest entry is the one at the back.
  • Every entry stores its own key, so evicting it can also remove it from the hash table.
  • Losing the whole cache is the real danger: the misses it was absorbing all hit the database at once.
