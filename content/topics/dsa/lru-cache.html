Build a cache that holds at most capacity keys. It needs two operations:

  • get(key) — return the value, or -1 if the key isn’t there.
  • put(key, value) — add the key, or update it if it already exists.

When a put would push it past capacity, throw out the least recently used key: the one whose last get or put happened longest ago. A get counts as a use, not just a put. Both operations have to run in O(1) — the same time whether the cache holds 3 keys or 3,000.

Limits for this version: capacity 1 to 3,000, keys and values are whole numbers, and up to 200,000 calls in total. This is the problem usually listed as “LRU Cache”.

One-line version: a hash map finds the key, a doubly linked list remembers the order, and every touch moves that key to the front.

Questions to ask the interviewer

  • Does a get count as a use? Yes here. If only writes counted, this is a much easier problem.
  • What does a miss return? -1 here. Sometimes it’s null or a thrown error.
  • Does updating an existing key evict anything? No. The size doesn’t grow, so nothing has to go.
  • Is O(1) required, or just asked for? Required. That one word rules out every solution that scans.

What the limits tell you

200,000 calls against a capacity of 3,000. Anything that walks the whole cache on each call does 200,000 × 3,000 = 600 million steps. That is the gap between a few milliseconds and a few seconds.

What the two operations have in common

Each call asks two questions at once: where is this key? and which key is the oldest? A hash map is fast at the first and useless at the second. A sorted list is the other way round. That mismatch is the problem.

The obvious way: store a timestamp with every entry, and when the cache is full, scan for the smallest one.

// lru-cache-slow.ts
class LRUCacheSlow {
  private store = new Map<number, { value: number; used: number }>();
  private clock = 0;

  constructor(private cap: number) {}

  get(key: number): number {
    const e = this.store.get(key);
    if (e === undefined) return -1;
    e.used = ++this.clock;              // touching it refreshes the stamp
    return e.value;
  }

  put(key: number, value: number): void {
    const e = this.store.get(key);
    if (e !== undefined) { e.value = value; e.used = ++this.clock; return; }

    if (this.store.size === this.cap) {
      let oldKey = -1, oldUsed = Infinity;
      for (const [k, v] of this.store) {      // the slow bit
        if (v.used < oldUsed) { oldUsed = v.used; oldKey = k; }
      }
      this.store.delete(oldKey);
    }
    this.store.set(key, { value, used: ++this.clock });
  }
}

get is already O(1). put is O(n) time when the cache is full, because of the scan, and O(n) space.

Push 100,000 fresh keys through a cache of 3,000 and that scan runs 97,000 times over 3,000 entries: about 291 million steps. In a quick run that took around a second, against a few milliseconds for the solution below. Same answers, 70× the work.

Stop trying to make one structure do both jobs. Use two, and keep them pointing at each other.

  • A hash map from key to node. It answers “where is this key?” in one step.
  • A doubly linked list of those same nodes, newest at the front, oldest at the back. It answers “which is the oldest?” in one step: it’s the back one.

A doubly linked list is a chain where each node holds a pointer to the one before it and the one after it. That second pointer is the part that matters. Holding a node, you can unhook it from the chain without walking from the front — just join its two neighbours to each other.

Two details make it work. Guard nodes sit at each end holding nothing, so the front and back are never empty and no step has to check for null. And each node stores its own key: without that you could find the oldest node but not know which map entry to delete.

Step 3 is the one that decides the answer. Without it, 1 sits at the back and step 4 throws out 1 instead of 2.

// lru-cache.ts
class Node {
  prev: Node | null = null;
  next: Node | null = null;
  constructor(public key: number, public value: number) {}
}

class LRUCache {
  private map = new Map<number, Node>();
  private head = new Node(0, 0);      // guard at the front
  private tail = new Node(0, 0);      // guard at the back

  constructor(private cap: number) {
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  private unlink(n: Node): void {     // join its neighbours to each other
    n.prev!.next = n.next;
    n.next!.prev = n.prev;
  }

  private pushFront(n: Node): void {  // hook it in right after head
    n.next = this.head.next;
    n.prev = this.head;
    this.head.next!.prev = n;
    this.head.next = n;
  }

  get(key: number): number {
    const n = this.map.get(key);
    if (n === undefined) return -1;
    this.unlink(n);
    this.pushFront(n);                // a read counts as a use
    return n.value;
  }

  put(key: number, value: number): void {
    const n = this.map.get(key);
    if (n !== undefined) {            // already here: update and move up
      n.value = value;
      this.unlink(n);
      this.pushFront(n);
      return;                         // size didn't grow, so nothing is evicted
    }
    if (this.map.size === this.cap) {
      const last = this.tail.prev!;   // the oldest node
      this.unlink(last);
      this.map.delete(last.key);      // this is why a node stores its key
    }
    const fresh = new Node(key, value);
    this.map.set(key, fresh);
    this.pushFront(fresh);
  }
}

Every touch is the same two moves, unlink then pushFront. The ! marks are only for TypeScript — the guards keep prev and next from ever really being null on a real node.

The technique is pairing two structures so each covers the other’s weak spot. They share the same objects, so a hit in one is a handle into the other.

Signals that point to it

  • The problem asks for O(1) on two operations that pull in different directions, like “find by key” and “find the smallest”.
  • You need to remove something from the middle of an ordering, not just the ends.

How to talk through it

  1. Pin down the rules: a get is a use, and an update evicts nothing.
  2. Name the conflict: each call needs fast lookup and fast ordering, and no single structure gives both.
  3. Offer the scan version: O(n) per eviction, which the O(1) rule forbids.
  4. State the fix in one sentence: “A map from key to node, and a doubly linked list of those nodes in use order.”
  5. Write unlink and pushFront first, then get and put on top. Say why nodes carry their key; interviewers wait for that.

Follow-ups to expect

  • Without a linked list? A JavaScript Map keeps insertion order, so delete then set moves a key to the back. It leans on a language promise instead of your own structure.
  • Thread-safe? One lock around both structures. They must change together, or a lookup finds a node that isn’t in the list.
  • A time limit per key? Put an expiry on the node and treat an expired hit as a miss.
  • Least often used instead? That is LFU: a count per key, and a list per count.

Mistakes people make

  • A singly linked list, so unhooking needs a walk and put is O(n) again.
  • Forgetting that get is a use, which fails the first example.
  • Not storing the key on the node, so eviction can’t clean up the map.
  • Evicting on an update, which shrinks the cache for nothing.
  • An LRU cache holds a fixed number of keys and throws out the one used longest ago.
  • A get counts as a use, so reading a key protects it from the next eviction.
  • Each call asks two questions at once: where is this key, and which key is the oldest.
  • Timestamps plus a scan for the smallest is correct, but put becomes O(n) once the cache is full.
  • A hash map from key to node gives O(1) lookup; a doubly linked list of those nodes gives O(1) reordering.
  • Two pointers per node are what let you unhook a node from the middle without walking the list.
  • Each node stores its own key, so evicting the back node can also delete it from the map.
  • Both operations end up O(1) time, with O(capacity) space.
