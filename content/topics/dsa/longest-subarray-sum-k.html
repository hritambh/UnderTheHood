You get an array of whole numbers, nums, and a target number, k.

Find the longest contiguous subarray whose numbers add up to exactly k. Return its length. If no subarray adds up to k, return 0.

A contiguous subarray is a stretch of neighbours. You pick a start and an end, and take everything in between. You can’t skip a number.

The numbers can be positive, negative, or zero. That one detail decides which technique works, as you’ll see.

Limits on the input:

  • The array has between 0 and 1,000,000 numbers.
  • Each number is between −10,000 and 10,000.
  • k is between −1,000,000,000 and 1,000,000,000.

This is a well-known interview problem. You may see it listed as “Maximum Size Subarray Sum Equals k”.

One-line version: keep a running sum as you walk the array, and remember the first place you saw each running sum. If “running sum − k” was seen before, the stretch since then adds up to k.

The third one is the tricky one. Because of the negative numbers, the sum goes up and down as the stretch grows. The longest answer starts at the very first number, and it passes through sums that are too big on the way.

Questions to ask the interviewer

  • Can the numbers be negative or zero? This is the most important question. If every number is positive, there is a simpler solution. Here the answer is yes, they can.
  • Do you want the length, or the subarray itself? Here, the length.
  • What if nothing adds up to k? Return 0.
  • Can the array be empty? Yes. The answer is then 0.

What the limits tell you

  • Up to 1,000,000 numbers. Checking every pair of start and end is about 500 billion checks. That is too slow, so we need to pass over the array once, or close to it.
  • The biggest possible sum is 1,000,000 × 10,000 = 10,000,000,000. A JavaScript number holds that exactly, so we don’t need anything special for big numbers.

What the examples have in common

  • The words “contiguous” and “sum” together are a strong hint. They usually mean: keep a running sum, the total of everything from the start up to where you are.
  • In every example, more than one stretch works. So finding a stretch is not enough. We need the one that starts earliest for a given end.

The obvious way is to try every start. From each start, walk right, add as you go, and check the sum after each step.

// longest-subarray-slow.ts
function longestSubarrayWithSumSlow(nums: number[], k: number): number {
  let best = 0;
  for (let i = 0; i < nums.length; i++) {       // every start
    let sum = 0;
    for (let j = i; j < nums.length; j++) {     // every end from there
      sum += nums[j];
      if (sum === k) best = Math.max(best, j - i + 1);
    }
  }
  return best;
}

This is correct, and it works with negative numbers. It is a good first answer to say out loud.

What it costs

  • Time: O(n²). For an array of n numbers, the inner step runs n + (n − 1) + … + 1 times. That is n × (n + 1) ÷ 2. “O(n²)” means the work grows with the square of n: 10 times more numbers means 100 times more work.
  • Space: O(1). It only keeps a few variables, no matter how big the array is.

Why it is too slow here

  • With n = 1,000,000, the inner step runs 1,000,000 × 1,000,001 ÷ 2 ≈ 500 billion times.
  • Say a computer does a billion of these a second. That is a generous round number, not a measurement. It would still take 500 seconds, which is more than 8 minutes.
  • A solution that looks at each number once does 1,000,000 steps. That is 500,000 times less work.

The slow way adds the same numbers again and again. The fix is to stop adding stretches, and compare running sums instead.

Say the running sum at position j is S. That is everything from the start of the array up to j.

Now say that somewhere earlier, at position i, the running sum was S − k. Then the numbers after i, up to j, must add up to exactly k. They are the difference between the two running sums.

So at each position we ask one question: “Have I seen the running sum S − k before, and where?”

To answer that fast, we keep a map: a lookup table from a running sum to the position where it showed up. Looking something up in a map takes about the same time no matter how big the map is.

Two details make it correct:

  • Keep only the first position for each sum. We want the longest stretch. The earlier the start, the longer the stretch. So if a running sum shows up again later, we don’t replace the position we already stored.
  • Start the map with sum 0 at position −1. Before the array starts, the running sum is 0. Without this entry, we would miss every answer that begins at the first number.

Now each number is looked at once. No stretch is ever added up twice.

Let’s run it on the tricky example: nums = [1, -1, 5, -2, 3] and k = 3.

The map is called firstSeen. It starts with one entry: sum 0 at position −1. In the table, “0 → −1” means “sum 0 was first seen at position −1”.

Two rows are worth a second look:

  • Row j = 1. The running sum is 0 again. Sum 0 is already in the map at position −1, so we leave it alone. If we had replaced it with position 1, row 3 would have found a length of 3 − 1 = 2, and the final answer would be wrong.
  • Row j = 3. We need sum 0, and the only place it was stored is the starting entry at −1. That is how the stretch from the very first number is found.
// longest-subarray.ts
function longestSubarrayWithSum(nums: number[], k: number): number {
  // running sum -> first position where it appeared
  const firstSeen = new Map<number, number>();
  firstSeen.set(0, -1);          // sum 0, before the array starts

  let sum = 0;
  let best = 0;

  for (let j = 0; j < nums.length; j++) {
    sum += nums[j];

    const need = sum - k;        // the earlier sum we are looking for
    if (firstSeen.has(need)) {
      const i = firstSeen.get(need)!;
      best = Math.max(best, j - i);
    }

    // keep only the first position: an earlier start gives a longer stretch
    if (!firstSeen.has(sum)) firstSeen.set(sum, j);
  }
  return best;
}

A few things to notice:

  • The length is j - i, not j - i + 1. The stretch starts one step after i. It runs from i + 1 to j, which is j − i numbers.
  • We look up need before we store sum. When k is 0, need and sum are the same number, so storing first lets a position match itself. Here that only gives a length of 0, which changes nothing. But in the “how many stretches” version of this problem, it would count an empty stretch. Looking up first is the habit that is always safe.
  • If the array is empty, the loop never runs and the function returns 0.

  • Time O(n). The loop runs once per number. Inside it there are a few map lookups, and each takes about the same time whatever the size of the map. “O(n)” means the work grows in step with n: 10 times more numbers, 10 times more work.
  • Space O(n). In the worst case every running sum is different, so the map ends up with one entry per number, plus the starting one.

So we trade memory for speed. For 1,000,000 numbers, that is up to about a million map entries in return for doing 1,000,000 steps and not 500 billion.

The technique is called prefix sum with a map. “Prefix sum” is another name for the running sum: the sum of the first part, or prefix, of the array.

The move is always the same. A question about a stretch is turned into a question about two running sums. Then a map answers “have I seen the other one?” in one step.

Signals that point to it

  • The problem says “contiguous subarray” or “substring”, and asks about a sum or a count.
  • It asks for the longest, the shortest, how many, or whether one exists.
  • The numbers can be negative. This is the big one, because it rules out the sliding window.
  • The input is too big for checking every pair.

What changes from problem to problem

  • Longest stretch: store the first position of each running sum. That is this problem.
  • Shortest stretch: store the latest position.
  • How many stretches: store how many times each running sum has been seen, and add that count each time.

When a sliding window is enough

If every number is positive, growing a stretch always makes its sum bigger. So you can keep a window with a left and a right edge. Move the right edge to grow the sum, and move the left edge when the sum gets too big. That needs no map, so it uses O(1) space.

With negative numbers this breaks. Adding a number can make the sum smaller, so “too big, shrink from the left” is no longer a safe rule. On the third example, a sliding window throws away the first numbers as soon as the sum passes 3. It never sees that the −2 later brings the sum back down.

How to talk through it

  1. Ask about negative numbers first. It shows you know the answer depends on it.
  2. Say the simple solution. Two loops, O(n²). Say it is correct but too slow for a million numbers. Don’t spend long writing it out unless asked.
  3. Explain the idea before the code. “If the running sum now is S, and I saw S − k earlier, the stretch in between adds up to k.” Draw the two bars.
  4. Name the two details out loud. Keep the first position only, and start with sum 0 at −1.
  5. Write the code, then walk one small example through it by hand.
  6. Give the cost, and say what you traded: O(n) memory for O(n) time.

Follow-ups to expect

  • What if all the numbers are positive? Use a sliding window. It is O(n) time and O(1) space, so it saves the map.
  • Return the subarray, not only its length. When you find a better length, also save the start, i + 1, and the end, j.
  • Count how many subarrays add up to k. Store how many times each running sum has appeared. At each position, add the count for sum − k.
  • Find the shortest one. Store the latest position of each running sum, not the first.
  • What if the sums could get too big for a number? In JavaScript, switch to BigInt. In Java or C++, use a 64-bit type. With these limits it isn’t needed.

Mistakes people make

  • Forgetting the starting entry. Every answer that begins at the first number is then missed.
  • Replacing the stored position. You then get a shorter stretch than the longest.
  • Using a sliding window when numbers can be negative. It looks right on simple examples and fails on mixed ones.
  • Off by one on the length. It is j − i, because the stretch starts after i.
  • Storing the sum before looking up. It is harmless here, but in the counting version it counts an empty stretch when k is 0.
  • The problem asks for the longest stretch of neighbouring numbers that adds up to exactly k, and the numbers can be negative.
  • Trying every start and end is correct but takes O(n²) time, which is about 500 billion steps for a million numbers.
  • A running sum is the total from the start of the array up to the current position.
  • If the running sum now is S and the running sum S − k was seen earlier, the stretch between those two positions adds up to k.
  • A map from running sum to position answers “have I seen S − k, and where?” in one step.
  • Storing only the first position of each running sum gives the longest stretch.
  • Starting the map with sum 0 at position −1 lets a stretch begin at the first number.
  • The fast solution takes O(n) time and O(n) space, because it trades memory for speed.
  • A sliding window only works when every number is positive, because only then does a longer stretch always have a bigger sum.
