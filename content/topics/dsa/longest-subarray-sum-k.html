You get an array of whole numbers, nums, and a target k. Find the longest contiguous subarray whose numbers add up to exactly k, and return its length — or 0 if none does.

A contiguous subarray is a stretch of neighbours: pick a start and an end, take everything in between, skip nothing. The numbers can be positive, negative or zero — that one detail decides which technique works.

Limits: 0 to 1,000,000 numbers, each between −10,000 and 10,000, and k between −1,000,000,000 and 1,000,000,000. You may see this listed as “Maximum Size Subarray Sum Equals k”.

One-line version: keep a running sum as you walk the array, and remember the first place you saw each running sum. If “running sum − k” was seen before, the stretch since then adds up to k.

numskAnswerWhy
[1, 2, 3, 1, 1, 1, 1]33Three kinds of stretch add up to 3: [1, 2], [3], and [1, 1, 1]. The longest has 3 numbers.
[2, 3, 5]52Both [2, 3] and [5] add up to 5. We want the longer one.
[1, -1, 5, -2, 3]34[1, -1, 5, -2] adds up to 3. So do [5, -2] and [3], but they are shorter.

The third one is the tricky one. Because of the negative numbers, the sum goes up and down as the stretch grows. The longest answer starts at the very first number, and it passes through sums that are too big on the way.

Questions to ask the interviewer

  • Can the numbers be negative or zero? The most important question — if every number is positive there is a simpler solution. Here, yes they can.
  • The length, or the subarray itself? The length.
  • Nothing adds up to k, or the array is empty? Return 0.

What the limits tell you

  • Up to 1,000,000 numbers, so every pair of start and end is about 500 billion checks. Too slow: we need one pass, or close to it.
  • The biggest possible sum is 1,000,000 × 10,000 = 10,000,000,000, which a JavaScript number holds exactly.

What the examples have in common

  • “Contiguous” plus “sum” usually means keep a running sum: the total from the start up to where you are.
  • In every example more than one stretch works, so finding a stretch isn't enough. We need the one starting earliest for a given end.

The obvious way is to try every start. From each start, walk right, add as you go, and check the sum after each step.

// longest-subarray-slow.ts
function longestSubarrayWithSumSlow(nums: number[], k: number): number {
  let best = 0;
  for (let i = 0; i < nums.length; i++) {       // every start
    let sum = 0;
    for (let j = i; j < nums.length; j++) {     // every end from there
      sum += nums[j];
      if (sum === k) best = Math.max(best, j - i + 1);
    }
  }
  return best;
}

Correct, works with negative numbers, and a good first answer to say out loud. It costs O(n²) time — the inner step runs n × (n + 1) ÷ 2 times, so 10 times more numbers means 100 times more work — and O(1) space.

Why that's too slow here: at n = 1,000,000 the inner step runs about 500 billion times. At a generous billion steps a second (a round number, not a measurement) that is 500 seconds, over 8 minutes. Looking at each number once is 1,000,000 steps: 500,000 times less work.

The slow way adds the same numbers again and again. The fix is to stop adding stretches and compare running sums instead.

Say the running sum at position j is S: everything from the start of the array up to j. If somewhere earlier, at position i, the running sum was S − k, then the numbers after i up to j must add up to exactly k — they are the difference between the two running sums.

So at each position we ask one question: “Have I seen the running sum S − k before, and where?” To answer fast we keep a map from running sum to the position where it showed up; a map lookup takes about the same time whatever its size.

Two details make it correct:

  • Keep only the first position for each sum. The earlier the start, the longer the stretch, so a repeat of a running sum never replaces what is stored.
  • Start the map with sum 0 at position −1. Before the array starts the running sum is 0. Without it we miss every answer that begins at the first number.

The tricky example: nums = [1, -1, 5, -2, 3], k = 3. The map, firstSeen, starts with one entry: sum 0 at position −1.

The answer is 4. Two rows matter. At j = 1 the running sum is 0 again, and we leave the stored position alone — had we replaced it with 1, row 3 would have found length 3 − 1 = 2 and the answer would be wrong. At j = 3 we need sum 0, and the only place it was stored is the starting entry at −1. That is how a stretch from the very first number is found.

// longest-subarray.ts
function longestSubarrayWithSum(nums: number[], k: number): number {
  // running sum -> first position where it appeared
  const firstSeen = new Map<number, number>();
  firstSeen.set(0, -1);          // sum 0, before the array starts

  let sum = 0;
  let best = 0;

  for (let j = 0; j < nums.length; j++) {
    sum += nums[j];

    const need = sum - k;        // the earlier sum we are looking for
    if (firstSeen.has(need)) {
      const i = firstSeen.get(need)!;
      best = Math.max(best, j - i);
    }

    // keep only the first position: an earlier start gives a longer stretch
    if (!firstSeen.has(sum)) firstSeen.set(sum, j);
  }
  return best;
}

A few things to notice:

  • The length is j - i, not j - i + 1. The stretch starts one step after i. It runs from i + 1 to j, which is j − i numbers.
  • Look up need before storing sum. When k is 0 they are the same number, so storing first lets a position match itself. Harmless here, but in the “how many” version it would count an empty stretch. Looking up first is always safe.
  • If the array is empty, the loop never runs and the function returns 0.

  • Time O(n). The loop runs once per number. Inside it there are a few map lookups, and each takes about the same time whatever the size of the map. “O(n)” means the work grows in step with n: 10 times more numbers, 10 times more work.
  • Space O(n). In the worst case every running sum is different, so the map ends up with one entry per number, plus the starting one.

So we trade memory for speed. For 1,000,000 numbers, that is up to about a million map entries in return for doing 1,000,000 steps and not 500 billion.

The technique is prefix sum with a map — “prefix sum” being another name for the running sum. The move is always the same: a question about a stretch becomes a question about two running sums, and a map answers “have I seen the other one?” in one step.

Signals that point to it

  • “Contiguous subarray” or “substring”, with a question about a sum or a count: longest, shortest, how many, or whether one exists.
  • The numbers can be negative. This is the big one, because it rules out the sliding window.
  • The input is too big for checking every pair.

What changes from problem to problem

  • Longest: store the first position of each running sum. That is this problem.
  • Shortest: store the latest position.
  • How many: store how often each running sum has been seen, and add that count each time.

When a sliding window is enough

With only positive numbers, growing a stretch always grows its sum, so a left and right edge works: move right to grow, move left when the sum is too big. No map, O(1) space. Negatives break it — adding a number can shrink the sum, so “too big, shrink from the left” stops being safe. On the third example the window throws away the first numbers as soon as the sum passes 3, and never sees the −2 bring it back down.

Other well-known problems on the same pattern: Subarray Sum Equals K, Contiguous Array, Subarray Sums Divisible by K.

How to talk through it

  1. Ask about negative numbers first. It shows you know the answer depends on it.
  2. Say the simple solution: two loops, O(n²), correct but too slow for a million numbers. Don't write it out unless asked.
  3. Explain the idea before the code. “If the running sum now is S and I saw S − k earlier, the stretch between adds up to k.” Draw the two bars.
  4. Name the two details out loud: first position only, and sum 0 at −1.
  5. Write the code, walk a small example through it, and give the cost: O(n) memory traded for O(n) time.

Follow-ups to expect

  • All numbers positive? A sliding window: O(n) time, O(1) space, no map.
  • Return the subarray? On a better length, also save the start i + 1 and the end j.
  • Count how many add up to k? Store how many times each running sum appeared, and add the count for sum − k.
  • Find the shortest? Store the latest position of each running sum, not the first.
  • Sums too big for a number? BigInt in JavaScript, a 64-bit type in Java or C++. Not needed at these limits.

The four mistakes to avoid: forgetting the starting entry, replacing a stored position, reaching for a sliding window when numbers can be negative, and getting the length off by one.

  • The problem asks for the longest stretch of neighbouring numbers that adds up to exactly k, and the numbers can be negative.
  • Trying every start and end is correct but takes O(n²) time, which is about 500 billion steps for a million numbers.
  • A running sum is the total from the start of the array up to the current position.
  • If the running sum now is S and the running sum S − k was seen earlier, the stretch between those two positions adds up to k.
  • A map from running sum to position answers “have I seen S − k, and where?” in one step.
  • Storing only the first position of each running sum gives the longest stretch.
  • Starting the map with sum 0 at position −1 lets a stretch begin at the first number.
  • The fast solution takes O(n) time and O(n) space, because it trades memory for speed.
  • A sliding window only works when every number is positive, because only then does a longer stretch always have a bigger sum.
