You get an array of whole numbers, nums, and a number target. Find the two numbers that add up to target, and return their positions in the array.

Two rules. You can’t use the same position twice — [3] with a target of 6 is not an answer. The same value twice is fine, as long as it sits at two different positions.

Limits for this version: 2 to 100,000 numbers, each between −1,000,000,000 and 1,000,000,000. The array is not sorted, it may hold repeats, and exactly one pair works. Return the two positions in any order. This is the problem usually listed as “Two Sum”.

One-line version: walk the array once, and at each number ask a map “have I already seen target − this number?”

numstargetAnswerWhy
[2, 7, 11, 15]9[0, 1]2 + 7 = 9. The pair is right at the front.
[3, 2, 4]6[1, 2]2 + 4 = 6. The tempting wrong answer is 3 + 3, which would use position 0 twice.
[3, 3]6[0, 1]The same value at two positions. Both are real, so this one counts.

The last two rows are the whole difficulty: a position can’t pair with itself, but two equal values can pair with each other.

Questions to ask the interviewer

  • Positions or values? Positions here. It matters, because sorting the array throws the original positions away.
  • Can one position be used twice? No. Can the same value appear twice? Yes.
  • Is it sorted? No. If it were, there is a cheaper solution — see the pattern section.
  • Always exactly one answer? Here, yes. Ask anyway, because “none” and “several” change what you return.

What the limits tell you

  • 100,000 numbers means about 5 billion pairs. Too many, so checking every pair is out.
  • Negative numbers are allowed, so nothing may assume sums only grow.

What the examples have in common

Once you fix one number, the other one is decided: it has to be target − that number. So this is not really a search for a pair. It is a search for one value, repeated for every number in the array.

The obvious way: take each number, and try it against every number after it.

// two-sum-slow.ts
function twoSumSlow(nums: number[], target: number): [number, number] | null {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {   // start at i + 1
      if (nums[i] + nums[j] === target) return [i, j];
    }
  }
  return null;
}

Starting the inner loop at i + 1 is what stops a position pairing with itself, and it means no pair is tried twice. The cost is O(n²) time — the inner step runs n × (n − 1) ÷ 2 times — and O(1) space.

At n = 100,000 that is about 5 billion checks when the pair sits at the end. At a billion steps a second (a round number, not a measurement) that is several seconds for an answer you can get in 100,000 steps.

The slow way searches the rest of the array for the partner. But we don’t need to search: the partner’s value is known the moment we pick a number. For nums[j], the partner must be target − nums[j]. Call it need.

So keep a map of every value seen so far, pointing at the position it was seen at. A map answers “is this value in here?” in about the same time however big it gets. The search becomes one lookup.

One detail makes it correct: look before you store. The map only ever holds numbers from earlier positions, so a number can never find itself. It is the same guard as j = i + 1 in the slow version. It is also why [3, 3] works: the 3 at position 1 looks up a map that already holds the 3 at position 0.

nums = [3, 2, 4], target = 6. The map, seen, starts empty.

Row 0 is the one to notice. The number is 3 and it needs a 3, but nothing is stored yet, so it doesn’t match itself. Had we stored first and looked after, it would have returned [0, 0].

// two-sum.ts
function twoSum(nums: number[], target: number): [number, number] | null {
  const seen = new Map<number, number>();   // value -> position

  for (let j = 0; j < nums.length; j++) {
    const need = target - nums[j];          // the partner we want

    // look first: the map holds earlier positions only
    if (seen.has(need)) return [seen.get(need)!, j];

    seen.set(nums[j], j);                   // then add this one
  }
  return null;                              // no pair
}
  • The order of the two lines is the whole trick. Looking up before storing is what keeps a position from pairing with itself.
  • Repeats overwrite, and that is fine. Only one position per value is ever needed, and a later one works just as well.
  • The ! is only for TypeScript — has already proved the value is there.
  • Returning null covers no pair, one number, or none at all. The limits promise a pair; the function still shouldn’t fall over without one.

Both solutions on this page were run on every row above and on the three examples, and they give the same answers.

The technique is a complement lookup: when two things must combine to a known total, fix one and the other is decided. All that is left is “have I seen that value?”, which a hash map answers in one step. Walk once, look up the partner, then store yourself.

Signals that point to it

  • “Find two things that add up to / differ by / multiply to” some exact value.
  • The input is unsorted, and sorting would lose something you need (here, the positions).
  • The obvious solution is every pair, and the limits make that too slow.

The same move works on stretches of an array instead of single numbers: keep a running sum and look up sum − k. That is the Longest Subarray With Sum K topic, and the family is the same.

Other well-known problems on this pattern: Two Sum II — Input Array Is Sorted, 3Sum, and Subarray Sum Equals K.

How to talk through it

  1. Repeat the two rules back: a position can’t be used twice, equal values at different positions can.
  2. Say the slow solution and its cost: every pair, O(n²), about 5 billion checks at these limits. Don’t write it unless asked.
  3. State the idea in one sentence: “Once I pick a number, its partner is decided, so I look it up instead of searching for it.”
  4. Say the guard out loud: look before you store, so nothing pairs with itself.
  5. Write it, trace [3, 2, 4] through it, and give the cost: O(n) time, O(n) space.

Follow-ups to expect

  • Sorted input? Two pointers from both ends. O(1) extra space.
  • Return every pair, not the first? Don’t return early, and store a list of positions per value.
  • No pair exists? Say what you return — null, an empty array, or an exception — and be consistent.
  • Numbers arrive as a stream? The same map works. It is already one pass and never looks back.
  • Too big to fit in memory? Sort on disk, then two pointers, carrying the original positions along with the values.

Mistakes people make

  • Storing before looking up, so a number pairs with itself.
  • Skipping a value already in the map, which breaks [3, 3].
  • Sorting first, then returning positions from the sorted array.
  • Returning values instead of positions.
