A B-tree is a sorted tree where every node holds many keys, not one. One node fills one disk page, and every leaf sits at the same depth, so no key is further from the top than any other.

The problem it solves: keep millions of keys sorted on disk, supporting three things — find a key, insert a key, walk a range in order — in as few disk reads as possible.

Limits: up to a billion keys, 8 bytes each, 4 KB pages. A disk read costs around 0.1 ms on an SSD; a comparison costs around 100 ns. A read is roughly a thousand times dearer, so disk reads are the unit of cost.

One-line version: make the node as wide as a disk page, and the tree gets short enough that four reads find anything.

Searching this tree, which holds 10, 20, 30, 40, 50, 60, 70, 80:

// root, then its three leaves

30found, 1 node readIt is in the root. Keys sit at every level, not only in leaves, so a search can end early.

Row three is the one people get wrong: a B-tree stores real keys in its internal nodes. A B+ tree, which is what most databases use, keeps keys only in the leaves.

Questions to ask the interviewer

  • Memory or disk? It decides everything. In memory, a plain balanced tree is fine.
  • B-tree or B+ tree? If range scans matter, you want B+. Say which you’re building.
  • Duplicate keys? Here, no — inserting a key that exists does nothing.
  • Do we need delete? It needs merging and borrowing, and doubles the code. Ask before writing it.

What the limits tell you

You never read 8 bytes from a disk — you read a whole 4 KB page for the same price. A node holding one key wastes 99% of what you paid for.

What the three operations have in common

All three walk from the top down to a leaf, so the cost of everything is the height. Make the tree shorter and all three get faster at once.

The obvious way: a balanced binary search tree. One key per node, two children.

// bst.ts — node holds one key, and a left and right child
function has(root: BstNode | null, key: number): boolean {
  let n = root;
  while (n) {                       // one disk read per step
    if (key === n.key) return true;
    n = key < n.key ? n.left : n.right;
  }
  return false;
}

That is O(log₂ n) comparisons, which sounds fine. But each step lands somewhere else on disk, so it is also O(log₂ n) disk reads.

For a billion keys that is about 30 reads, so 3 ms to find one key — and 30 pages of 4 KB, 120 KB in all, read to return 8 bytes.

The tree is tall because each node answers one yes-or-no question. Make the node bigger and it answers a better one: not “left or right?” but “which of these 256 ranges?”

A 4 KB page fits 4096 ÷ 16 = 256 entries at 8 bytes for a key and 8 for a child pointer. So every node has up to 256 children, and the height is log base 256, not log base 2.

256³ = 16.7 million, 256⁴ = 4.29 billion. Four levels cover a billion keys, and the top two stay cached in memory — so a real lookup often costs one or two reads, not four.

Height changes in one place only, so that is what to watch. We use a tiny node — at most 4 keys — so a split fits on screen. Inserting 10, 20, 30, 40, 50:

Carrying on to 60, 70, 80 splits the right leaf too, giving the root [30,60] from the examples section. Notice what did not happen: nothing rotated, and no leaf ended up deeper than another. A B-tree grows at the root, which is why every leaf stays level.

// btree.ts
const MAX = 4;                   // most keys in a node; split at MAX + 1

class BNode {
  keys: number[] = [];
  children: BNode[] = [];        // empty on a leaf
  get leaf(): boolean { return this.children.length === 0; }
}

type Split = { key: number; right: BNode };   // what a split hands upward

class BTree {
  private root = new BNode();

  private slot(n: BNode, key: number): number {   // where key belongs here
    let i = 0;
    while (i < n.keys.length && key > n.keys[i]) i++;
    return i;
  }

  has(key: number): boolean {
    let n: BNode | undefined = this.root;
    while (n) {
      const i = this.slot(n, key);              // scan inside the page
      if (n.keys[i] === key) return true;
      n = n.leaf ? undefined : n.children[i];   // one level down
    }
    return false;
  }

  insert(key: number): void {
    const split = this.insertInto(this.root, key);
    if (split) {                 // the root split: the only way the tree gets taller
      const root = new BNode();
      root.keys = [split.key];
      root.children = [this.root, split.right];
      this.root = root;
    }
  }

  private insertInto(n: BNode, key: number): Split | null {
    const i = this.slot(n, key);
    if (n.keys[i] === key) return null;                  // already there

    if (n.leaf) {
      n.keys.splice(i, 0, key);
    } else {
      const split = this.insertInto(n.children[i], key);      // go down first
      if (!split) return null;
      n.keys.splice(i, 0, split.key);                         // absorb on the way up
      n.children.splice(i + 1, 0, split.right);
    }
    return n.keys.length > MAX ? this.splitNode(n) : null;
  }

  private splitNode(n: BNode): Split {
    const mid = n.keys.length >> 1;
    const key = n.keys[mid];                   // this one moves up
    const right = new BNode();
    right.keys = n.keys.splice(mid + 1);       // everything after the middle
    n.keys.pop();                              // drop the middle from the left
    if (!n.leaf) right.children = n.children.splice(mid + 1);
    return { key, right };
  }
}
  • Insert goes down, then fixes up. A split hands a key and a new node up to its parent, which absorbs them — and may split itself. The height changes only when that reaches the root.
  • MAX is 4 here so splits are visible. A real tree sets it from the page size, near 255.

The code on this page was run on every row above, then on 200 random trees of 2,000 keys. All leaves stayed at one depth, no node went over MAX or under half full, and no lookup was wrong.

The technique is matching the node to the block. When reading costs per block, not per byte, make your structure’s unit one block, so a read buys the most it can.

Signals that point to it

  • The data lives on disk or over a network, where a fetch costs far more than a comparison.
  • You need sorted order — ranges, prefixes, “next 20 rows” — so a hash table won’t do.
  • The obvious structure is O(log n), but each step is a separate fetch.

How to talk through it

  1. Ask where it lives, and say a disk read costs about a thousand comparisons. Then give the binary tree: 30 reads for a billion keys, 120 KB read to return 8 bytes.
  2. The idea in one sentence: “One node fills one page, so each read picks between 256 branches, not 2.”
  3. Do the maths: 256⁴ = 4.29 billion, so four levels, top two cached.
  4. Draw one split and say the rule: the middle key moves up, and the tree grows only at the root.

Follow-ups to expect

  • B-tree vs B+ tree? B+ keeps keys only in leaves and chains them, so a range scan is one walk down then sideways. Nearly all databases use B+.
  • Delete? The mirror of insert: a node below half full borrows from a sibling, or merges with it and pulls a key down from the parent.
  • Why not a hash index? O(1) lookups, but no order: no ranges, no sorting, no prefixes.
  • Bulk-loading sorted data? Build bottom-up, or you get the half-full tree above.

Mistakes people make

  • Saying “it’s O(log n), same as a BST” and stopping. True for comparisons, wrong for what costs money.
  • Thinking it grows at the leaves. It grows at the root, which is why it stays balanced.
  • Claiming keys live only in leaves — that is a B+ tree, not a B-tree.
