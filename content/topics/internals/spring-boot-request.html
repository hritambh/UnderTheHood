Spring Boot is the Spring Framework plus two conveniences: auto-configuration (it guesses your setup from what is on the classpath) and an embedded server (Tomcat ships inside your JAR, so you run java -jar app.jar).

This topic looks inside one part: what happens between the TCP socket and your controller method. Everything here is Spring Boot 4.1 on Java 17 or newer, with embedded Tomcat 11.

// OrderController.java
@RestController
class OrderController {
  private final OrderService service;
  OrderController(OrderService service) { this.service = service; }

  @GetMapping("/orders/{id}")
  Order get(@PathVariable long id) { return service.find(id); }
}

In Express you write app.get(path, fn) and the function is the route. Here the route is an annotation on a method of an object you never created. Spring created it at startup and holds it forever. Nearly every Spring surprise comes from that one difference.

One-line version: Spring builds every object once at startup and keeps them in a container. A request is one thread walking through those objects and back out.

“Walk me through what happens when a request hits your app” is the question every Spring interview opens with. It is this whole topic, and the follow-ups come from the same picture:

  • “Why is my injected field null?” Because something made that object with new. Spring only wires objects it built.
  • “Why did the app fall over at a few hundred users when the CPU was idle?” Because it ran out of threads, not CPU. See performance.
  • “Why didn’t my rollback happen?” Because the method was called from inside the same class and skipped the proxy.
  • “Why is startup slow but the first request fast?” Because all the wiring happens before any traffic arrives.

Coming from Node, the useful move is to stop reading Spring as magic and start reading it as “a map of pre-built objects, plus a thread”.

Follow one GET /orders/42.

  1. Tomcat accepts the connection and hands it to a free worker thread, named something like http-nio-8080-exec-7. That thread belongs to this request until the response is written.
  2. The filter chain runs. Spring Security, if you have it, is one filter. Same job and same ordering traps as Express middleware.
  3. The DispatcherServlet takes over. It is the single servlet mapped to /.
  4. It looks up GET /orders/{id} in a table of routes built at startup, and finds OrderController.get. Nothing is scanned now.
  5. Argument resolvers turn the 42 into a long. A JSON body would become an object here, via Jackson.
  6. Your method runs — on the one shared OrderController instance that every other thread is also using.
  7. It calls service.find(42). That object is not your class: it is a proxy wrapping it. @Transactional makes the proxy borrow a connection from Hikari, open a transaction, call your method, then commit and hand the connection back.
  8. The returned Order goes back to the DispatcherServlet, which writes it as JSON. The thread writes the bytes and returns to the pool.

The difference you can feel is step 7. The thread does not go anywhere while the database thinks.

Nothing above is built per request. It all exists before the first client connects:

The line that matters: a bean is a singleton. One OrderService object serves every request. So a field on it is shared by up to 200 threads at the same instant. In Node a module-level variable is shared too, but one thread means two requests never touch it in the same moment. In Spring they do. Keep request state in method parameters and local variables, never in fields.

You can rely on:

  • Every singleton bean is fully built before the first request. A missing dependency fails the startup, not a request at 3 a.m.
  • Constructor injection hands you a complete object, so the field can be final and never null.
  • @Transactional on a public method called from outside the class commits when the method returns, and rolls back on a RuntimeException.
  • One thread per request, so ThreadLocal works. That is how the current user and the logging context follow the request without being passed around.

People wrongly rely on:

  • “@Transactional always applies.” Calling another method on this goes straight to the object and skips the proxy. No proxy, no transaction.
  • “Any exception rolls back.” By default only unchecked exceptions do. A checked one commits unless you set rollbackFor.
  • “Injection works on an object I made with new.” Spring wires what Spring built. Everything else gets null fields.
  • “The thread-local context follows my @Async call.” That runs on a different thread, which has its own empty one.

From the steps above, with made-up numbers to show the shape, not benchmarks:

  • Steps 3 to 5 are nearly free. Routing is a map read, because the wiring was done at startup.
  • Step 7 is the whole cost, and mostly as waiting, not work.
  • The ceiling is threads, not CPU. Say a request takes 100 ms, 80 ms of it waiting on the database. 200 threads ÷ 0.1 s = about 2,000 requests/s. Let the request take 200 ms and the ceiling halves, with the CPU still idle.
  • The pool below is smaller. 200 threads share 10 Hikari connections, so 190 can be queued behind the database. That is usually the real limit — see Connection Pooling.
  • Node has the opposite shape. Waiting is free, so one process holds thousands of waiting requests — but 50 ms of your own CPU work stalls all of them.

Virtual threads (spring.threads.virtual.enabled=true, Java 21 or newer) give Spring Node’s shape without changing your code: the thread parks during the wait instead of being held, so the 200-thread limit stops mattering. The database pool still does.

Same request, but the database has stopped answering.

  1. At step 7 the proxy asks Hikari for a connection. None is free, so it waits — 30 seconds by default.
  2. It gives up and throws. The proxy sees an unchecked exception, rolls the transaction back, and returns the connection.
  3. The exception travels back up through your service and controller, on the same thread.
  4. Spring turns it into a response: your @ControllerAdvice handler if you wrote one, otherwise a default JSON body with the status and path. The client gets a 500.
  5. The thread goes back to the pool. The app is still running.

Nothing is half-written. The transaction rolled back, so the database is as it was. The case you cannot see is a failure just after the commit: the row is there, and the client is told it failed.

The worse version is the pile-up. If every request waits 30 seconds, all 200 threads fill. New connections sit in Tomcat’s accept queue, 100 of them by default, and after that the operating system refuses them. Clients see “connection refused” and the load balancer drops the instance, routes that never touch that database included. Short timeouts matter more here than the thread count.

Run the JAR with --debug to see what auto-configuration decided:

java -jar target/app.jar --debug

Read the condition report it prints. Positive matches shows what was switched on and which condition passed; negative matches shows what was skipped and what was missing. That report is the answer to “where did my Tomcat come from”.

Add spring-boot-starter-actuator, expose the endpoints, and look at the container itself:

# application.properties
management.endpoints.web.exposure.include=beans,conditions,health
curl -s localhost:8080/actuator/beans | jq '.contexts[].beans | length'
curl -s localhost:8080/actuator/conditions | head

Then watch the threads. With the app running, take a thread dump:

jcmd $(jcmd -l | grep app.jar | cut -d' ' -f1) Thread.print | grep http-nio

You will see a handful of idle http-nio-8080-exec-N threads. Fire fifty slow requests at it and dump again — the count climbs toward 200 and stops. That is the whole thread model, on screen.

  • “A new controller object is made for each request.” One object, shared by every thread. That is why a field on it is a bug waiting to happen.
  • “All those annotations mean slow reflection on every request.” The scanning and wiring happen once at startup. A request is a map lookup and a method call.
  • “Spring Boot needs a Tomcat installed on the server.” Tomcat is a library inside your JAR. There is nothing to install.
  • “More threads means more throughput.” Threads cost memory, and they all queue for the same ten database connections. Past that point, raising the number just moves the queue.
  • “Virtual threads make blocking code free.” They make waiting cheap. Every other limit — the connection pool, the database, your own CPU work — is exactly where it was.
  • “spring-boot-starter-web is the one to use.” In Spring Boot 4 it is deprecated in favour of spring-boot-starter-webmvc. Same Tomcat underneath.
  • Spring Boot is Spring plus auto-configuration plus an embedded Tomcat, so you run a plain JAR.
  • At startup it builds one instance of every bean and keeps them in the ApplicationContext.
  • A request is one Tomcat worker thread walking through those pre-built objects and back out.
  • The DispatcherServlet finds the controller method in a route table built at startup, so routing itself is cheap.
  • Your @Service is reached through a proxy, which is where @Transactional and security actually happen.
  • Calling a @Transactional method on this skips the proxy, so no transaction starts.
  • Beans are shared by every thread at once, so request state belongs in locals, never in fields.
  • The thread is held for the whole request, waiting included, so 200 threads cap how many can be in flight.
  • Virtual threads remove that cap; the connection pool below it, 10 by default, does not move.
  • When the database stalls, threads pile up, the accept queue fills, and the whole instance stops answering.
