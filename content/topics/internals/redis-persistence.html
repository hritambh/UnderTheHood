Redis is a key-value store that keeps the whole dataset in memory. That is where the speed comes from, and it is also the problem: memory is gone when the process dies.

So Redis writes to disk in two ways, and this topic is about those two. Everything here is Redis 7, open-source.

  • RDB: a snapshot. The whole dataset copied into one file, every so often.
  • AOF (append-only file): a log. Every write command appended as it happens, and replayed on startup.

You can run either, both, or neither. Both is the usual production answer, and neither is a real choice when Redis is only a cache.

One-line version: RDB is a photograph taken now and then, AOF is a diary written as you go. The gap between the last photo or diary entry and the crash is what you lose.

Knowing this changes three decisions you will actually face:

  • “Is my data safe in Redis?” The honest answer is a number of seconds, and it depends on settings you choose. You can’t give that answer without this.
  • Memory alarms during saves. Redis can briefly use much more memory than the dataset size, and the reason is in the walkthrough below.
  • Slow startup. A Redis that takes minutes to come back after a restart is replaying a log, and the size of that log is something you control.

It also answers the interview question behind “why not use Redis as your main database?” — which is really a question about durability, not speed.

Five parts matter here:

  • The command loop: one thread, running commands one at a time. No command overlaps another.
  • The dataset: your keys and values, in memory.
  • The AOF buffer: a small in-memory buffer where write commands land before they reach the file.
  • The AOF files: the log on disk, in a directory Redis 7 calls appendonlydir.
  • The RDB child: a forked child process that writes the snapshot, so the main thread keeps serving.

Note what is not in the picture: no write-ahead log the way a relational database has one. Redis answers the client first and writes to disk after.

Follow one command: SET user:42 "Asha", with AOF on and the default appendfsync everysec.

  1. The command arrives and waits its turn. The loop is single-threaded, so it runs alone.
  2. Redis updates the dataset in memory. The new value is live now — any client reading user:42 sees Asha.
  3. Redis appends the command to the AOF buffer, still in memory.
  4. Redis replies +OK to the client. Note the order: the client is told it worked while the write exists only in memory.
  5. At the end of the event loop iteration, the buffer is written to the AOF file with write(). That hands the bytes to the operating system, which may still hold them in its own cache.
  6. About once a second, a background thread calls fsync(), which tells the disk to make it permanent.

RDB works differently. When a save point fires, Redis forks. The child gets a frozen view of memory and writes the whole snapshot to dump.rdb; the parent keeps serving clients. The operating system only copies a memory page when the parent changes it, which is why a write-heavy moment during a save makes memory grow.

The AOF is a log of commands, so it grows forever if nothing trims it. AOF rewrite fixes that: Redis writes a new base file holding the current state, then keeps appending from there. A million INCR calls on one key collapse into one entry.

With aof-use-rdb-preamble on, that base file is written in RDB format — a snapshot with a command log after it, which is why startup from AOF is faster than replaying a million commands.

You can rely on:

  • Anything fsynced is on disk. With appendfsync always, that means every confirmed write, at the cost of a flush per write.
  • A partly-written AOF from a crash is detected at startup, and Redis can truncate the broken tail (aof-load-truncated is on by default).
  • An RDB file is a consistent point in time, because the child works from a frozen copy. It is never half-updated.

People wrongly rely on:

  • “+OK means saved.” It means in memory. With everysec, up to a second of confirmed writes can disappear.
  • “Replicas make it durable.” Replication is asynchronous: the primary doesn’t wait. A primary that dies can lose writes the replicas never saw.
  • “AOF means no data loss.” Only with always. The default is everysec.
  • “Redis is transactional.” MULTI/EXEC runs commands together without interleaving, but there is no rollback, and durability still depends on these settings.

From the steps above, with example numbers for the shape of it, not benchmarks:

  • The write itself is cheap. Steps 1–4 are memory work. The reply does not wait for the disk.
  • appendfsync always is the expensive setting. Every write waits for a disk flush, so throughput falls to what your disk can sync, which on a network disk can be a few thousand a second instead of tens of thousands.
  • Fork is a pause. The fork itself blocks the one thread while the OS copies page tables — longer with a bigger dataset. Afterwards, every page the parent writes to gets copied.
  • Memory can nearly double during a save on a write-heavy instance, because of those copies. This is the classic cause of an out-of-memory kill during a nightly snapshot.
  • A big AOF makes restarts slow, since startup replays it. That is what rewrite is for.

The power goes right after step 4 of the walkthrough: the client holds +OK for user:42, and the bytes are in the AOF buffer.

  1. The buffer is memory. It is gone, and so is that write.
  2. On restart, Redis loads from the AOF directory if AOF is on, otherwise from dump.rdb.
  3. If the crash landed mid-write(), the last entry is incomplete. Redis truncates that tail and logs a warning.
  4. The dataset comes back as of the last durable point. user:42 is missing or holds its old value.
  5. The client was never told. It believes the write happened.

How much you lose: nearly nothing with always, up to about a second with everysec, whatever the OS had cached with no, and up to the whole gap since the last snapshot with RDB alone. A disk that fills up is worse — writes to the AOF start failing, and with stop-writes-on-bgsave-error on, Redis refuses writes rather than pretending.

On a default install, with redis-cli:

redis-cli CONFIG GET appendonly appendfsync save
redis-cli SET user:42 "Asha"
redis-cli LASTSAVE        # unix time of the last successful snapshot
redis-cli BGSAVE          # take one now; LASTSAVE should move
redis-cli INFO persistence

In the INFO persistence output, look for aof_enabled, rdb_last_bgsave_status and aof_last_write_status (both should be ok), rdb_changes_since_last_save (how much is not in a snapshot yet), and aof_rewrite_in_progress.

redis-cli CONFIG SET appendonly yes    # creates appendonlydir
redis-cli BGREWRITEAOF                 # collapse the log
ls -l $(redis-cli CONFIG GET dir | tail -1)

To see a loss for yourself on a scratch instance: SET a key, then kill the process hard (kill -9) instead of using SHUTDOWN, and restart. With everysec and bad timing, the key is not there. SHUTDOWN saves first, which is why a clean restart never shows this.

  • “Redis is memory-only, so it can’t be a database.” It persists, and with always it is durable. The real limits are dataset size against RAM, and the recovery window you accept.
  • “AOF is slower than RDB.” Writing AOF entries is cheap. The cost is the fsync policy you choose, not the format.
  • “Snapshots are free because a child does the work.” The fork pauses the main thread, and copy-on-write can nearly double memory.
  • “Turning on AOF means I can stop taking snapshots.” Snapshots restore faster and are easier to copy elsewhere as a backup. Most setups keep both.
  • “Single-threaded means slow.” One thread avoids locks, and the usual limit is the network, not the CPU. It does mean one slow command, like KEYS on a big dataset, blocks everyone.
  • Redis holds the dataset in memory and persists in two ways: RDB snapshots and the AOF command log.
  • A write updates memory and replies +OK before anything reaches the disk.
  • AOF entries go to a buffer, then to the OS at the end of the loop, then to disk on fsync.
  • appendfsync everysec is the default and risks about a second of confirmed writes. always is durable and costs a flush per write.
  • RDB forks a child that writes a consistent snapshot while the parent serves traffic.
  • Fork pauses the thread briefly, and copy-on-write can nearly double memory during a save.
  • The AOF grows until a rewrite collapses it into a fresh base file.
  • Replication is asynchronous, so replicas are not a durability guarantee.
  • After a crash Redis loads the last durable point and truncates a broken AOF tail; anything newer is gone.
