Many programs talk to PostgreSQL at once, each inside a transaction: a group of statements that all happen or all don't. So one is changing a row while another reads it. What should the reader see?

The simple answer is a lock: the reader waits for the writer. Safe, and slow — one long report would freeze every write to the table. PostgreSQL does something else, called MVCC, multi-version concurrency control. An update never changes a row where it sits: it writes a new copy, leaves the old one in place, and shows each transaction the copy that was current when it looked. Nobody waits.

Everything here is PostgreSQL 14, and every command was run on it. The design is the same in later versions; output and defaults can differ.

One-line version: an update writes a new version of the row instead of changing the old one, and every transaction reads the versions that were committed when it took its look.

Most PostgreSQL surprises in production come back to this one design. Once you know it, these make sense:

  • The table keeps growing but the row count is flat. Old versions pile up faster than they are cleaned.
  • A report shows numbers a few seconds old, or two queries in a transaction disagree.
  • One forgotten open transaction slows the database down hours later.
  • SELECT count(*) is slow on a big table, even with an index.
  • An update-heavy table slows down with every index added.

It also tells you which settings matter — autovacuum, the isolation level, the idle-transaction timeout — and answers the usual interview questions about blocking and vacuum.

  • Transaction ID. A number given to each transaction that changes data, going up by one, so a higher number started later.
  • Row versions on a table page. Tables are stored in 8 KB pages, and one row can sit on a page several times, once per version. Each carries three hidden fields you can select like columns: xmin (creator), xmax (replacer, zero if none) and ctid (its page and slot, which points at the newer version once replaced).
  • Snapshot. A note saying “these transactions were finished when I looked”, which decides what you can see.
  • Commit log. How every transaction ended: committed, rolled back, or still running.
  • WAL (write-ahead log). Every change, written before it is trusted. It makes a commit survive a crash.
  • Vacuum. The cleaner, removing versions nobody can see. Autovacuum runs it for you.

The index matters because it points at row versions and knows nothing about who can see them.

Asha's row holds 500, created by transaction 100 long ago. A writer updates it while a reader reports on the same row.

-- the writer, which becomes transaction 101
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  1. The reader takes a snapshot: everything below 101 is finished, 101 and up hasn't happened. Read-only transactions get no ID.
  2. The writer gets ID 101 and finds the row through the index: page 0, slot 1, xmin 100 committed and xmax 0, so it is current.
  3. It stamps slot 1 with xmax = 101, which doubles as the row lock: another writer sees it and waits.
  4. It writes a new version into slot 3 (balance 400, xmin = 101), points slot 1's ctid at it, and logs the change. Slot 1 still holds the 500.
  5. No index entry is added, because balance is in no index and the version fits on the page: a HOT update. Change an indexed column, or fill the page, and every index gets one.
  6. The reader reads, while 101 still runs. Slot 1 was created before my snapshot and replaced by a transaction unfinished in it, so that replacement hasn't happened for me. It returns 500 and never waits.
  7. The writer commits: a WAL record, then a mark in the commit log. No row is touched, so commit costs the same for one row or a million. A new transaction now reads 400. Slot 1 is a dead row, but vacuum can only take it once no snapshot needs it — and our reader's does.

What you can rely on

  • A plain SELECT never waits for a writer, or makes one wait.
  • You never see uncommitted changes, at any level. PostgreSQL accepts READ UNCOMMITTED but runs it as Read Committed.
  • Two writers never both change the same version. The second waits at step 3, re-reads the newest version and applies its change to that, so two balance = balance - 10 statements take off 20.

What people wrongly rely on

  • “Two queries in one transaction see the same data.” Not by default: Read Committed takes a snapshot per statement, so the reader above would see 400 next time. Repeatable Read keeps one snapshot and keeps seeing 500.
  • “MVCC stops lost updates.” Only when the change is one statement. Read the balance, do the sum in your code, write it back, and two transactions both read 500 and both write 400. Do the sum inside the UPDATE, or lock with SELECT ... FOR UPDATE.
  • “Repeatable Read never fails.” Update a row changed since your snapshot and you get could not serialize access due to concurrent update; your code must retry.
  • “Deleted rows are gone.” A DELETE only sets xmax. The space returns after vacuum, for reuse inside that table.

Cheap: reading while others write; commit, which is one WAL write and one mark; and rollback, which is just a mark, because nothing was overwritten.

Costly

  • Every update writes the whole row again, even for one small column. A 200-byte row with 5 indexes (made-up numbers) costs a new 200-byte version plus 5 index entries when an indexed column changes.
  • Updates grow the table. On a laptop, 100,000 rows took 3,544 kB; updating each once took it to 7,080 kB. That extra space is bloat.
  • Vacuum frees space but rarely shrinks the file. That table stayed 7,080 kB after vacuuming, and the next full update reused the freed half. Only VACUUM FULL took it back to 3,544 kB, and it locks the table to do it.
  • Counting rows. No count is stored, because each transaction may see a different number, so count(*) checks visibility row by row.
  • A long-open transaction keeps dead versions alive across every table in the database.

Crash the same UPDATE: the server dies before the commit.

  1. At the crash the page holds both versions, old with xmax = 101 and new with xmin = 101, possibly already on disk.
  2. On restart it replays the WAL, which can even put back the uncommitted new version.
  3. 101 has no commit record, so the commit log reports aborted.
  4. Readers apply the normal rules. The old version was replaced by a transaction that never committed, so the replacement never happened: it is live, balance 500. The new version's creator never committed, so nobody will ever see it.
  5. Nothing is undone. Both versions stay until a later vacuum.

Uncommitted work is lost, which is correct. A transaction whose commit record reached disk is not: with default settings PostgreSQL only answers “committed” after that. One gap is left for your code — if the crash falls between the record landing and the answer reaching your app, the change is saved and your app doesn't know. It must check before retrying.

One more, and why it exists

A transaction ID is 32-bit, so there are about 4 billion and the counter goes round in a circle. PostgreSQL treats roughly 2 billion as the past and the rest as the future, so a very old row would one day look like it came from the future and vanish. To stop that, vacuum freezes old rows as visible to everyone always. Past autovacuum_freeze_max_age (200 million) autovacuum runs for this reason even if turned off, and if it still falls behind PostgreSQL refuses writes until the table is vacuumed. That is transaction ID wraparound, and why vacuum is never optional.

1. Watch an update create a new version

CREATE TABLE accounts (id INT PRIMARY KEY, owner TEXT, balance INT);
INSERT INTO accounts VALUES (1, 'Asha', 500), (2, 'Ravi', 300);
SELECT xmin, xmax, ctid, * FROM accounts;
 xmin | xmax | ctid  | id | owner | balance
 2945 |    0 | (0,1) |  1 | Asha  |     500
 2945 |    0 | (0,2) |  2 | Ravi  |     300

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SELECT xmin, xmax, ctid, * FROM accounts;
 2946 |    0 | (0,3) |  1 | Asha  |     400   <- new slot, new xmin
 2945 |    0 | (0,2) |  2 | Ravi  |     300   <- untouched

2. Find the old version still on the page

CREATE EXTENSION IF NOT EXISTS pageinspect;   -- needs superuser
SELECT lp, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('accounts', 0));
 lp | t_xmin | t_xmax | t_ctid
  1 |   2945 |   2946 | (0,3)   <- old version, stamped and pointing on
  3 |   2946 |      0 | (0,3)   <- the new one

3. Two sessions, two answers

-- A: one snapshot for the whole transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;    -- 400

-- B: change it, commit, then try to clean up
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SELECT balance FROM accounts WHERE id = 1;    -- 300
VACUUM (VERBOSE) accounts;
DETAIL:  1 dead row versions cannot be removed yet

-- A: same query, same transaction, then finish
SELECT balance FROM accounts WHERE id = 1;    -- 400
COMMIT;

-- B: now it can
VACUUM (VERBOSE) accounts;
DETAIL:  0 dead row versions cannot be removed yet

Look for: A and B give different answers at the same moment, neither waits, and vacuum names the version A still needs. Output shortened to fit.

To find who is holding vacuum back, look for idle in transaction sessions with a non-null backend_xmin in pg_stat_activity; for dead rows per table, n_dead_tup in pg_stat_user_tables.

  • “An update changes the row in place.” It writes a new version and marks the old one replaced, as demo 1 shows.
  • “A big rollback is slow.” Nothing is undone; the transaction is marked rolled back and its versions become invisible. The cost lands later, on vacuum.
  • “Vacuum gives disk space back.” It frees space inside the table for reuse; only a full rewrite shrinks the file.
  • “Every database does it this way.” MySQL's InnoDB has MVCC too, but changes the row in place and keeps old versions in a separate undo log. They don't bloat the table, and a long rollback has real work to do.
  • MVCC means an update writes a new version and leaves the old one in place, so readers and writers never wait for each other.
  • Each version carries xmin (creator), xmax (replacer) and ctid (its slot, or the newer one's).
  • A snapshot records which transactions had finished. A version is visible if its creator committed by then and its replacer had not.
  • Read Committed takes a new snapshot per statement; Repeatable Read keeps one per transaction.
  • A commit only writes the WAL and marks the commit log, so commit and rollback are both cheap. After a crash, a transaction with no commit record counts as rolled back and nothing is undone.
  • Replaced versions become dead rows. Vacuum frees the space for reuse but usually doesn't shrink the file.
  • Vacuum can't remove a version any open snapshot might need, so one forgotten transaction causes bloat across the database.
  • Transaction IDs are 32-bit and wrap around, so vacuum must freeze old rows. That is why vacuum is never optional.
