PostgreSQL is a relational database. Many programs talk to it at once, each inside a transaction: a group of statements that all happen or all don’t.

That creates a problem. One transaction is changing a row while another is reading it. What should the reader see? The simple answer is a lock: the reader waits until the writer is done. That is safe, and slow. One long report would freeze every write to the table.

PostgreSQL does something else, called MVCC: multi-version concurrency control. An update never changes a row where it sits. It writes a new copy of the row and leaves the old one in place. Each transaction is then shown the copy that was current when it looked. Nobody waits.

This topic looks inside that one mechanism: how the copies are stored, how PostgreSQL decides who sees which, and who cleans up the old ones.

Everything here describes PostgreSQL 14, and every command was run on it. The core design (row versions, xmin and xmax, snapshots, vacuum) is the same in later versions. Exact output text and default values can differ, so check yours.

One-line version: an update writes a new version of the row instead of changing the old one, and every transaction reads the versions that were committed when it took its look.

Most PostgreSQL surprises in production come back to this one design. Once you know it, these make sense:

  • The table keeps growing but the row count is flat. Old versions are piling up faster than they are cleaned.
  • A report shows numbers that are a few seconds old, or two queries in one transaction disagree with each other.
  • One forgotten open transaction slows the whole database down hours later.
  • SELECT count(*) is slow on a big table, even with an index.
  • An update-heavy table gets slower with every index you add.

It also tells you which settings matter. Autovacuum, the isolation level and the idle-transaction timeout all control parts of this mechanism.

And it answers a set of common interview questions: how do readers and writers avoid blocking each other, what is vacuum for, and what is the difference between Read Committed and Repeatable Read.

Six parts work together. Details come in the next section.

  • Transaction ID. A number PostgreSQL gives to each transaction that changes data. They go up by one: 100, 101, 102. A higher number started later.
  • Row versions, on a table page. A table is stored in 8 KB blocks called pages. One row can be on a page several times, once for each version. Every version is stamped with the transaction that created it and the one that replaced it.
  • Snapshot. A small note a transaction takes that says “these transactions were finished when I looked”. It decides which versions that transaction can see.
  • Commit log. A compact record of how every transaction ended: committed, rolled back, or still running.
  • WAL (write-ahead log). A file that records every change before the change is trusted. It is what makes a commit survive a crash.
  • Vacuum. The cleaner. It removes old versions that no one can see any more. Autovacuum is the background process that runs it for you.

The index in the diagram is an ordinary index. It matters here because it points at row versions, and it knows nothing about who can see them.

We’ll follow one statement. The table has a row for Asha with a balance of 500. Transaction 100 created that row and committed long ago.

-- the writer, which will become transaction 101
UPDATE accounts SET balance = balance - 100 WHERE id = 1;

At the same time, a reader is running a report that reads the same row. The transaction numbers below are made up to keep the story simple.

Before the update

Every row version carries three hidden fields. You can select them like normal columns.

  • xmin: the ID of the transaction that created this version.
  • xmax: the ID of the transaction that deleted or replaced it. Zero means nobody has.
  • ctid: where this version sits, as (page, slot). When a version is replaced, its ctid points to the newer one.

Asha’s row is one version in slot 1 of page 0: xmin = 100, xmax = 0, balance 500.

The steps

  1. The reader takes a snapshot. It notes: everything below 101 is finished, and 101 and above have not happened as far as I’m concerned. The reader only reads, so it never gets a transaction ID of its own.
  2. The writer starts and gets ID 101. PostgreSQL hands out the ID when the transaction first changes something.
  3. The writer finds the row. The index on id says the row is in page 0, slot 1. The writer reads that version and checks it is current: xmin 100 is committed and xmax is 0.
  4. The writer stamps the old version. It sets xmax = 101 on the version in slot 1. This also works as the row lock. Any other writer that wants this row sees an xmax from a running transaction and waits for 101 to finish.
  5. The writer adds a new version. It writes a full copy of the row into a free slot on the same page, slot 3, with balance 400, xmin = 101 and xmax = 0. The old version’s ctid now points to slot 3. The old version is not touched in any other way. The balance of 500 is still there.
  6. The change goes into the WAL. A record describing the change is added to the WAL. The page itself is changed in memory and written to the table file some time later.
  7. The index is left alone, if possible. balance is not in any index, and the new version fits on the same page. So PostgreSQL adds no index entry. The index still points to slot 1, and slot 1 leads to slot 3. This shortcut is called a HOT update. If an indexed column had changed, or the page were full, every index on the table would get a new entry.
  8. The reader reads the row, while 101 is still running. It follows the index to slot 1. Created by 100: finished before my snapshot, good. Replaced by 101: not finished in my snapshot, so for me the replacement hasn’t happened. This version is mine. The reader returns 500. It looks at slot 3 too: created by 101, not visible, skip. The reader never waited.
  9. The writer commits. PostgreSQL writes a commit record to the WAL and forces it to disk. Then it marks 101 as committed in the commit log. No row is touched. That is why a commit takes about the same time whether the transaction changed one row or a million.
  10. A new transaction reads the row. Slot 1: replaced by 101, and the commit log says 101 committed, so this version is dead to me. Slot 3: created by 101, committed, not replaced. It returns 400.
  11. The old version waits for vacuum. Slot 1 is now a dead row, but only once no running snapshot can still see it. Our reader’s snapshot can. When the reader finishes, vacuum is free to remove slot 1 and reuse the space.

What does the reader see next?

That depends on its isolation level, the setting that says how often a transaction takes a new snapshot.

  • Read Committed, the default: a new snapshot for every statement. The reader’s next query sees 400.
  • Repeatable Read: one snapshot for the whole transaction. The reader keeps seeing 500 until it ends.

What you can rely on

  • A plain SELECT never waits for a writer, and never makes a writer wait. Step 8 shows why: the reader just picks another version.
  • You never see uncommitted changes. A version whose xmin has not committed is skipped, at every isolation level. PostgreSQL accepts READ UNCOMMITTED but runs it as Read Committed.
  • One statement sees one moment in time. It never sees half of another transaction’s changes.
  • Two writers never both change the same version. The second one waits at step 4. In Read Committed it then re-reads the newest version and applies its change to that. So two balance = balance - 10 statements take off 20 in total.
  • A rolled-back transaction leaves nothing visible. Its versions stay on the page for a while, but nobody can see them.

What people wrongly rely on

  • “Two queries in one transaction see the same data.” Not at the default level. Read Committed takes a new snapshot per statement. Use Repeatable Read if a report needs one fixed view.
  • “MVCC stops lost updates.” Only when the change is one statement. If your code reads the balance, does the sum itself, then writes the result, two transactions can both read 500 and both write 400. Do the sum in the UPDATE, or lock the row with SELECT ... FOR UPDATE.
  • “Repeatable Read never fails.” If a row you try to update was changed after your snapshot, PostgreSQL stops you with could not serialize access due to concurrent update. Your code has to retry the transaction.
  • “Nothing ever blocks.” Writers block writers on the same row. And commands that change the table’s structure, like most forms of ALTER TABLE, take a lock that blocks readers too.
  • “Deleted rows are gone.” A DELETE only sets xmax. The space comes back after vacuum, and only for reuse inside the same table.

Cheap

  • Reading while others write. No waiting, from step 8.
  • Commit. One WAL write and one mark in the commit log, from step 9.
  • Rollback. The transaction is marked as rolled back in the commit log, and that is all. Nothing is undone, because nothing was overwritten.

Costly

  • Every update writes the whole row again, even when one small column changed (step 5). Say a row is 200 bytes and the table has 5 indexes (made-up numbers). Changing one indexed column writes a new 200-byte version plus 5 new index entries.
  • Updates make the table bigger. In one run on a laptop, a table of 100,000 small rows took 3,544 kB. Updating every row once took it to 7,080 kB: each row was there twice. Extra space held by dead versions is called bloat.
  • Vacuum frees space but rarely shrinks the file. After a vacuum, that table was still 7,080 kB. The next full update reused the freed half, and the size stayed the same. Only VACUUM FULL took it back to 3,544 kB, and that command locks the table while it rewrites it.
  • Counting rows. There is no stored row count, because each transaction may see a different number. count(*) has to check rows for visibility.
  • A long-open transaction. Its snapshot keeps dead versions alive (step 11), in every table in the database. Queries on busy tables then wade through more and more dead versions.
  • The first read after a big load. Readers save hint bits as they go, so a SELECT can cause disk writes.

Let’s crash the same UPDATE. The server dies after step 7 and before the commit in step 9. We ran this on a test server, and here is what happens.

  1. At the moment of the crash, the page holds both versions: the old one with xmax = 101, and the new one with xmin = 101. Some or all of this may already be on disk.
  2. The server starts again. The log says database system was not properly shut down; automatic recovery in progress.
  3. It replays the WAL from the last safe point, so the table files match everything that was logged. This can even put back the uncommitted new version.
  4. Transaction 101 has no commit record. So the commit log never says “committed”. Asking for its status returns aborted.
  5. Readers apply the normal rules. Old version: replaced by 101, which did not commit, so the replacement never happened. It is live, and the balance is 500. New version: created by 101, which did not commit. Nobody will ever see it.
  6. Nothing is undone. Both versions are still on the page. The useless one is removed by a later vacuum.

What can be lost: work that was not committed. That is the correct result.

What can’t be lost: a transaction whose commit record reached the disk. With default settings, PostgreSQL only answers “committed” after that.

One gap is left for your code. If the crash comes after the commit record is on disk but before the answer reaches your app, the change is saved and your app doesn’t know. It has to check before trying again.

Why the last setting exists

A transaction ID is a 32-bit number, so there are about 4 billion of them, and the counter goes round in a circle. PostgreSQL treats about 2 billion as “the past” and the rest as “the future”. A very old row would one day look like it came from the future, and vanish.

To stop that, vacuum freezes old rows. It marks them as “visible to everyone, always”, so their xmin no longer matters. When a table’s oldest IDs pass the age in this setting, autovacuum runs on it for this reason, even if autovacuum is turned off. If freezing still can’t keep up, PostgreSQL in the end refuses new writes until the table is vacuumed. This is called transaction ID wraparound. Vacuum is not optional.

You need a PostgreSQL you can play with. Your transaction IDs will be different numbers from the ones here.

1. Watch an update create a new version

-- see the hidden fields before and after an update
CREATE TABLE accounts (
  id       INT  PRIMARY KEY,
  owner    TEXT NOT NULL,
  balance  INT  NOT NULL
);
INSERT INTO accounts VALUES (1, 'Asha', 500), (2, 'Ravi', 300);

SELECT xmin, xmax, ctid, * FROM accounts;
 xmin | xmax | ctid  | id | owner | balance
------+------+-------+----+-------+---------
 2945 |    0 | (0,1) |  1 | Asha  |     500
 2945 |    0 | (0,2) |  2 | Ravi  |     300

UPDATE accounts SET balance = balance - 100 WHERE id = 1;

SELECT xmin, xmax, ctid, * FROM accounts;
 xmin | xmax | ctid  | id | owner | balance
------+------+-------+----+-------+---------
 2945 |    0 | (0,2) |  2 | Ravi  |     300
 2946 |    0 | (0,3) |  1 | Asha  |     400

What to look for: Asha’s row moved from slot 1 to slot 3 and got a new xmin. Ravi’s row didn’t change.

2. Find the old version still on the page

This uses pageinspect, one of PostgreSQL’s own add-on extensions. It needs a superuser, and on some systems the separate “contrib” package. The other parts work on a default install.

-- list every row version stored in page 0
CREATE EXTENSION IF NOT EXISTS pageinspect;

SELECT lp, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('accounts', 0));
 lp | t_xmin | t_xmax | t_ctid
----+--------+--------+--------
  1 |   2945 |   2946 | (0,3)
  2 |   2945 |      0 | (0,2)
  3 |   2946 |      0 | (0,3)

What to look for: slot 1 is still there. Its t_xmax is the updating transaction, and its t_ctid points to slot 3. That is steps 4 and 5.

3. Two sessions, two answers

Open two terminals, A and B.

-- A: take one snapshot for the whole transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;    -- 400

-- B: change the row and commit
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SELECT balance FROM accounts WHERE id = 1;    -- 300

-- A: same query, same transaction
SELECT balance FROM accounts WHERE id = 1;    -- 400

-- B: try to clean up while A is still open
VACUUM (VERBOSE) accounts;
INFO:  table "accounts": found 1 removable, 3 nonremovable
       row versions in 1 out of 1 pages
DETAIL:  1 dead row versions cannot be removed yet,
         oldest xmin: 2947

-- A: finish
COMMIT;
SELECT balance FROM accounts WHERE id = 1;    -- 300

-- B: try again
VACUUM (VERBOSE) accounts;
DETAIL:  0 dead row versions cannot be removed yet,
         oldest xmin: 2948

The vacuum output is shortened and wrapped to fit.

What to look for: A and B get different answers at the same moment, and neither waits. Then 1 dead row versions cannot be removed yet: that is the version A still needs. Once A commits, vacuum can take it.

4. Find who is holding vacuum back

-- sessions holding a snapshot, oldest first
SELECT pid, state, backend_xmin, now() - xact_start AS open_for
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY xact_start;

What to look for: a row with state idle in transaction and a large open_for. That session opened a transaction and went quiet. Run it while terminal A from part 3 is open and you’ll see A in the list.

To watch dead rows build up on a table, read n_dead_tup from pg_stat_user_tables. It is an estimate, and it updates with a short delay.

  • “An update changes the row in place.” It writes a new version and marks the old one as replaced. Part 1 of “See it yourself” shows the row moving to a new slot.
  • “A SELECT only reads.” The first reader to check a new row saves a hint bit on it. We watched a plain SELECT change a row’s flags on the page.
  • “A big rollback is slow, because the work has to be undone.” Nothing is undone. The transaction is marked as rolled back, and its versions become invisible. The cost comes later, as extra work for vacuum.
  • “Vacuum gives disk space back.” It frees space inside the table for reuse. The file usually stays the same size. Only a full rewrite, like VACUUM FULL, shrinks it.
  • “A long read-only query is harmless.” Its snapshot stops vacuum from removing dead versions across the database for as long as it runs.
  • “An index entry means the row exists.” Indexes point at dead versions too. PostgreSQL checks the table to be sure, unless the visibility map says the whole page is safe.
  • “MVCC means no locks.” It means readers need no locks. Writers still lock the rows they change.
  • “Every database does it this way.” MySQL’s InnoDB also has MVCC, but it changes the row in place and keeps the old versions in a separate undo log. Old versions there don’t bloat the table, and a long rollback has real work to do.
  • MVCC means an update writes a new version of a row and leaves the old one where it is. Readers and writers don’t wait for each other.
  • Each version carries xmin (who created it), xmax (who replaced it) and ctid (where it is, or where the newer version is).
  • A snapshot records which transactions were finished. A version is visible if its creator had committed by then and its replacer had not.
  • Read Committed takes a new snapshot for every statement. Repeatable Read keeps one for the whole transaction.
  • A commit only writes to the WAL and marks the transaction in the commit log. No rows are touched, so commit and rollback are both cheap.
  • After a crash, a transaction with no commit record counts as rolled back. Its versions are ignored, and nothing has to be undone.
  • Replaced versions become dead rows. Vacuum removes them and frees the space for reuse, but usually doesn’t shrink the file.
  • Vacuum can’t remove a version that any open snapshot might still need. One long or forgotten transaction causes bloat across the database.
  • If no indexed column changes and the page has room, a HOT update skips the indexes. Otherwise every index gets a new entry.
  • Transaction IDs are 32-bit and wrap around, so vacuum must freeze old rows. That is why vacuum is never optional.
