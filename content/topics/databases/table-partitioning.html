Partitioning means cutting one big table into several smaller tables, by a rule you choose. January’s orders go in one piece, February’s in the next, and so on. Each piece is called a partition. The column the rule looks at is the partition key.

Your app doesn’t see the pieces. It still reads and writes one table called orders. The database sends each row to the right partition, and reads only the partitions a query can need.

Everything stays in one database on one machine. That is the difference from sharding, where the pieces live on different machines. The topic “Database Sharding” covers that. Partitioning is the smaller, simpler step, and most tables that need one of the two only need this one.

The examples use PostgreSQL 14 and its built-in feature, called declarative partitioning. MySQL has partitioning too, with one extra limit worth knowing: a partitioned InnoDB table can’t have foreign keys.

One-line version: one table for your app, many smaller tables on disk, split by a column like the date. Queries skip the pieces they don’t need, and old pieces are dropped whole.

A table with a few million rows needs none of this. The trouble starts when one table grows to hundreds of millions of rows and keeps growing. Three things go wrong.

  • Deleting old data hurts. Say you keep one year of events and delete the oldest month every month. That DELETE touches tens of millions of rows, one at a time. It writes a lot, runs for a long time, and leaves the table file the same size. PostgreSQL marks the rows dead and reuses the space for new rows. It rarely hands it back to the disk.
  • Indexes outgrow memory. An index on a 600-million-row table can be bigger than the server’s memory. Then even a simple lookup has to read from disk.
  • Every maintenance job is huge. Rebuilding an index or cleaning up dead rows runs over the whole table, even though only last week’s rows changed.

Here is the first one on a small scale. A test table on a laptop held 3.1 million rows, one month’s worth being 268,000. Deleting that month and cleaning up left the table at 316 MB, exactly what it was before. The same data in monthly partitions: dropping the month took 9 milliseconds and gave 33 MB back at once.

With partitions, old data is a whole table that you drop. The index for this month is small. And maintenance runs on one piece at a time.

You can paste all of this into psql on an empty database. The first line makes dates print the same for everyone.

-- Create a table split by month
SET timezone = 'UTC';

CREATE TABLE orders (
  id           BIGINT GENERATED ALWAYS AS IDENTITY,
  customer_id  INT           NOT NULL,
  total        NUMERIC(10,2) NOT NULL,
  created_at   TIMESTAMPTZ   NOT NULL,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE orders_2026_03 PARTITION OF orders
  FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

INSERT INTO orders (customer_id, total, created_at) VALUES
  (42, 250.00, '2026-01-05 10:00'),
  (17,  80.50, '2026-01-20 18:30'),
  (42, 120.00, '2026-02-10 09:15'),
  (99, 999.99, '2026-02-28 23:59'),
  (17,  45.00, '2026-03-01 00:00'),
  (63, 310.25, '2026-03-14 12:00');

Two things to notice. FROM is included and TO is not, so a row at exactly midnight on 1 March belongs to March. And the primary key has created_at in it. That is a rule, and we’ll come back to it.

We inserted into orders. Where did each row really go? The hidden column tableoid tells us.

Only orders_2026_02 is in the plan. January and March were never opened. (The long filter line is wrapped here to fit.)

DROP TABLE orders_2026_01;

     4

The table you named, orders, is called the parent. It holds no rows at all. It only holds the rules: the partition key and the list of partitions with their ranges. Every partition is a normal table with its own files and its own indexes.

When a row is inserted

  1. The insert arrives at the parent, orders.
  2. PostgreSQL reads the partition key from the new row: created_at = 2026-02-10.
  3. It keeps the ranges sorted, so it finds the matching one quickly: orders_2026_02.
  4. The row is written into that table, and that table’s indexes are updated. No other partition is touched.
  5. If no range matches, the insert fails with the error from the example.

When a query runs

  1. The planner looks in the WHERE clause for conditions on the partition key.
  2. It compares them with each partition’s range and throws out every partition that can’t hold a matching row. This is partition pruning.
  3. It plans the query for the partitions that are left. Each one is read like any table, with its own index or a full scan.
  4. If the value is only known when the query runs, like now() or a parameter, the pruning happens at the start of the run. The plan then shows a line like Subplans Removed: 1.
  5. If there is no condition on the partition key, nothing can be pruned. Every partition is read and the results are joined end to end. That is the Append in the second plan.

One more thing follows from “each partition has its own indexes”. There is no single index across all partitions. So PostgreSQL can only promise a value is unique if the partition key is part of it. That is why the primary key had to be (id, created_at). Try id alone and you get:

-- What PostgreSQL says to PRIMARY KEY (id) on this table
ERROR:  unique constraint on partitioned table must include all
        partitioning columns

PostgreSQL has three ways to split a table.

Range

How it works: each partition takes a stretch of values, from one bound up to the next. This is what the orders example uses.

When to use it: data that arrives in time order and gets old: orders, events, logs, sensor readings.

Good: date queries hit one or two partitions, and old data is dropped whole. Bad: someone has to create the next partition before its first row arrives. And the newest partition takes nearly all the writes.

List

How it works: each partition is given a list of exact values.

-- Split by country
CREATE TABLE customers (
  id       BIGINT NOT NULL,
  country  TEXT   NOT NULL,
  name     TEXT   NOT NULL,
  PRIMARY KEY (id, country)
) PARTITION BY LIST (country);

CREATE TABLE customers_in PARTITION OF customers
  FOR VALUES IN ('IN');
CREATE TABLE customers_us_ca PARTITION OF customers
  FOR VALUES IN ('US', 'CA');
CREATE TABLE customers_other PARTITION OF customers DEFAULT;

The last one is a default partition. It takes every row that fits nowhere else. A customer from France lands in customers_other.

When to use it: a small, fixed set of values that queries nearly always filter on: country, region, tenant.

Good: one group can be moved, archived or dropped alone. Bad: sizes are uneven. If 80% of customers are in one country, that partition is nearly as big as the old table.

Hash

How it works: PostgreSQL runs the key through a hash function, divides by the number of partitions, and uses the remainder to pick one.

-- Split into four even pieces by user
CREATE TABLE sessions (
  user_id     BIGINT      NOT NULL,
  token       TEXT        NOT NULL,
  expires_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (user_id, token)
) PARTITION BY HASH (user_id);

CREATE TABLE sessions_0 PARTITION OF sessions
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- ... and the same for REMAINDER 1, 2 and 3

With 10,000 users inserted, the four partitions got 2,489, 2,527, 2,530 and 2,454 rows.

When to use it: there is no natural range or list, and you just want smaller pieces that all queries reach by one ID.

Good: even sizes, and nothing to create every month. Bad: you can’t drop “old” data, because old and new rows are mixed in every piece. A range of IDs reads all partitions. And changing the number of pieces means moving rows.

Assumptions (made up for this example, not measurements):

  • An events table gets 50 million rows a month. A row takes about 200 bytes.
  • We keep 12 months and remove the oldest one every month.
  • One index entry takes about 25 bytes.
  • The database can delete about 50,000 rows a second.

How big is it?

  • One month: 50,000,000 × 200 bytes = 10 GB.
  • Twelve months: 10 GB × 12 = 120 GB, in 50,000,000 × 12 = 600 million rows.

Removing the oldest month

  • As one table: DELETE has to remove 50 million rows. 50,000,000 ÷ 50,000 = 1,000 seconds, so about 17 minutes of heavy writing. After that the clean-up job has 50 million dead rows to clear. The file is still 120 GB.
  • With monthly partitions: drop one table. It takes milliseconds, and 10 GB of disk is free straight away.

The index on created_at

  • As one table: 600,000,000 × 25 bytes = 15 GB. On a server with 8 GB of memory, it can’t all stay in memory.
  • With monthly partitions: the current month’s index is 50,000,000 × 25 bytes = 1.25 GB. New rows and recent queries only use that one, and it fits in memory easily.

How many partitions?

  • By month: 12, plus one made ahead for next month.
  • By day: 365. Still fine.
  • By hour: 365 × 24 = 8,760. Too many. Every query has to think about all of them before it starts.

A real check of that last point, on a laptop: with 2,000 empty partitions, a query that named the partition key took under 3 ms to plan. A query that didn’t took about 150 ms to plan, before reading a single row.

These carry on from the example, where February and March are left. Run them in order.

Create the next partition before it is needed

-- Make April, then the insert that failed earlier works
CREATE TABLE orders_2026_04 PARTITION OF orders
  FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

INSERT INTO orders (customer_id, total, created_at)
VALUES (42, 60.00, '2026-04-02 08:00');

In real work a scheduled job does this a few partitions ahead. Many teams use the pg_partman extension for it.

See the partitions and their sizes

-- List partitions with a row estimate and size on disk
ANALYZE orders;

SELECT c.relname AS partition,
       c.reltuples::bigint AS rows,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_inherits i
JOIN pg_class c ON c.oid = i.inhrelid
WHERE i.inhparent = 'orders'::regclass
ORDER BY c.relname;

   partition    | rows | size
----------------+------+-------
 orders_2026_02 |    2 | 24 kB
 orders_2026_03 |    2 | 24 kB
 orders_2026_04 |    1 | 24 kB

rows is the estimate from the last ANALYZE, not a live count. In psql, \d+ orders also lists every partition with its range.

Add a table that already has data

-- Build May on the side, then attach it
CREATE TABLE orders_2026_05
  (LIKE orders INCLUDING DEFAULTS INCLUDING CONSTRAINTS);

ALTER TABLE orders_2026_05 ADD CONSTRAINT orders_2026_05_range
  CHECK (created_at >= '2026-05-01' AND created_at < '2026-06-01');

ALTER TABLE orders ATTACH PARTITION orders_2026_05
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

ALTER TABLE orders_2026_05 DROP CONSTRAINT orders_2026_05_range;

Before attaching, PostgreSQL must be sure every row fits the range. The CHECK already proves it, so the scan is skipped. Attaching also takes a lighter lock on orders than CREATE TABLE ... PARTITION OF does, so reads and writes carry on.

Remove old data

-- Take February out without blocking, then drop it
ALTER TABLE orders DETACH PARTITION orders_2026_02 CONCURRENTLY;
DROP TABLE orders_2026_02;

A plain DROP TABLE on a partition locks the parent for a moment, and has to wait for running queries first. Detaching with CONCURRENTLY avoids that. It can’t run inside a transaction, and it is refused if the table has a default partition. After detaching, orders_2026_02 is a normal table. You can keep it as an archive in place of dropping it.

Add an index without blocking writes

-- An empty index on the parent, then one partition at a time
CREATE INDEX orders_customer_idx ON ONLY orders (customer_id);

CREATE INDEX CONCURRENTLY orders_2026_03_customer_idx
  ON orders_2026_03 (customer_id);
ALTER INDEX orders_customer_idx
  ATTACH PARTITION orders_2026_03_customer_idx;
-- ... repeat both statements for every other partition

A plain CREATE INDEX on the parent builds the index on every partition, and blocks writes while it does. In PostgreSQL 14 you can’t add CONCURRENTLY to that. So you build each piece without blocking and attach it. When the last one is attached, the parent’s index becomes valid. Partitions created later get the index by themselves.

           'YYYY-MM-DD'::text))

How to read it:

  • Count the partitions in the plan. We have three: March, April, May. Two are listed.
  • Subplans Removed: 1 is the third. The date came from a function, so it was only known when the query ran, and March was pruned then.
  • Append with every partition under it means no pruning happened. Look at the WHERE clause.

The usual cause is a function wrapped around the key. WHERE date_trunc('month', created_at) = '2026-04-01' reads all three partitions. Write it as a plain range on created_at.

  • Fast with the key vs slower without it. A query that names the partition key reads one piece. A query that doesn’t reads all of them. In a laptop test with 12 partitions, a lookup by user ID read 48 pages across 12 indexes. The same lookup on one plain table read 4.
  • Easy clean-up vs a job you must not forget. Dropping a month is instant. In return, new partitions have to exist on time, or inserts fail.
  • Small indexes vs limited unique rules. Each partition’s index is small. But a unique rule must include the partition key, so “this email is unique in the whole table” can’t be enforced when you partition by date.
  • Not a general speed-up. In the same laptop test, counting one month’s rows took about the same time with and without partitions, because the plain table had a good index. Partitioning pays off in clean-up and in keeping the busy index small, more than in single queries.
  • More pieces vs planning time. Smaller partitions are nicer to manage. Thousands of them slow down the planning of every query.
  • Partitioning vs sharding. Partitioning keeps one database, with joins and transactions working as before. It adds no machines. If the problem is total write load or disk space on one server, this doesn’t fix it.
  • Hard to undo. The key and the split are chosen when the table is created. Changing either means building a new table and moving the rows.

Signals that it fits

  • The table is bigger than the server’s memory, or clearly heading there.
  • You delete or archive old data on a schedule.
  • Nearly every query filters on the same column, usually a date or a tenant.
  • Recent data is busy and old data is rarely read.
  • Clean-up and index rebuilds on the whole table take too long.

When you don’t need it

  • The table and its indexes fit in memory. A plain table with the right index is simpler and just as fast.
  • Queries reach the table in many different ways, with no column in common. Most of them would read every partition.
  • You need a unique rule on a column that isn’t the partition key.
  • A query is slow because an index is missing. Add the index first.
  • One machine can’t hold the data or take the writes. That is a job for sharding.
  • Partitioning to fix a slow query. If the query needed an index, it still does. Read the plan with EXPLAIN before changing the table.
  • Leaving the partition key out of queries. Then every partition is read, and the table is slower than before. Add the key to the WHERE clause wherever you can.
  • Wrapping the key in a function. date_trunc('month', created_at) = ... stops pruning. Use created_at >= ... AND created_at < ....
  • Forgetting the next partition. At midnight on the first of the month, every insert starts failing. Create partitions ahead with a scheduled job, and alert when fewer than two future ones exist.
  • Using a default partition to hide that. Rows pile up in it quietly. Later, creating the real partition fails, because rows that belong to it are sitting in the default. You have to move them out first.
  • Too many partitions. Daily partitions kept for ten years is 3,650 tables. Pick a size that leaves you with tens or a few hundred.
  • Cleaning up with DELETE anyway. That throws away the main benefit. Detach and drop the partition.
  • Expecting more capacity. All partitions share one server’s CPU, memory and disk. Partitioning organises the data. It doesn’t add room.

Common questions

  • What is partitioning, and how is it different from sharding? Both split one table into pieces by a key. With partitioning, the pieces are tables in the same database. With sharding, they are on different machines. Partitioning makes one big table easier to manage. Sharding adds capacity.
  • What is partition pruning? The database compares the query’s conditions with each partition’s range and skips the ones that can’t match. It only works when the query filters on the partition key.
  • How do you pick the partition key? Take the column that most queries filter on, and that decides when data gets old. For time-based data that is nearly always the timestamp.
  • Why must the primary key include the partition key? Each partition has its own index, and there is none across all of them. PostgreSQL can only check a value is unique inside one partition, so the key must decide the partition.

Follow-ups to expect

  • What if an update changes the partition key? PostgreSQL moves the row to the right partition. It is a delete plus an insert underneath.
  • How do you partition a table that is already huge? You can’t convert it in place. Create a new partitioned table, copy the rows over in batches, then swap the names. Or attach the old table as one big partition and let new data go into new ones.
  • How many partitions is too many? Hundreds are fine. Thousands start to cost planning time on every query.
  • What happens to a query with no partition key? It reads every partition and joins the results.
  • Range, list or hash? Range for time, list for a few fixed groups, hash when you only want even pieces.

How it fits a bigger design

In a design interview, partitioning is the answer to “this table grows forever”. Say what the table is partitioned by and how old data leaves: “events are partitioned by month, and we drop partitions older than a year.” It comes before sharding. Reach for sharding only when one machine can’t hold the data or take the writes, and even then each shard often keeps its own tables partitioned by time.

  • Partitioning splits one table into smaller tables inside the same database. The app still uses one table name.
  • The parent table holds no rows, only the rules. Each partition is a normal table with its own indexes.
  • An insert is sent to the partition whose range matches the row’s partition key. If none matches, the insert fails.
  • Partition pruning skips partitions that can’t match the query. It needs a plain condition on the partition key.
  • A query without the partition key reads every partition, and can be slower than on a plain table.
  • Range suits time-based data, list suits a few fixed groups, and hash gives even pieces with no way to drop old data.
  • Removing old data is a detach and a drop, which is instant and frees the disk. A big DELETE is slow and frees nothing.
  • A primary key or unique rule must include the partition key, because no index covers all partitions.
  • New partitions must exist before their rows arrive, and thousands of partitions slow down query planning.
  • Partitioning does not add capacity. When one machine is not enough, that is sharding.
