Partitioning means cutting one big table into several smaller tables by a rule you choose: January's orders in one piece, February's in the next. Each piece is a partition, and the column the rule looks at is the partition key.

Your app never sees the pieces. It reads and writes one table called orders; the database routes each row to the right partition and reads only the ones a query can need.

Everything stays in one database on one machine — the difference from sharding, where pieces live on different machines. Partitioning is the smaller step, and most tables that need one of the two need only this one. Examples use PostgreSQL 14; MySQL has partitioning too, with one extra limit: a partitioned InnoDB table can't have foreign keys.

One-line version: one table for your app, many smaller tables on disk, split by a column like the date. Queries skip the pieces they don't need, and old pieces are dropped whole.

A few million rows need none of this. Trouble starts at hundreds of millions and still growing, and it shows up in three places.

  • Deleting old data hurts. Removing a month means a DELETE over tens of millions of rows, one at a time. It writes heavily, runs long, and leaves the file the same size: PostgreSQL marks the rows dead and reuses the space rather than handing it back.
  • Indexes outgrow memory. An index on 600 million rows can exceed the server's RAM, so even a simple lookup reads from disk.
  • Every maintenance job is huge. Rebuilding an index or clearing dead rows runs over the whole table, though only last week changed.

Measured small: a laptop table of 3.1 million rows, one month being 268,000. Deleting that month and cleaning up left the table at 316 MB — exactly what it was. In monthly partitions, dropping the month took 9 milliseconds and gave 33 MB back at once.

Paste this into psql on an empty database.

SET timezone = 'UTC';

CREATE TABLE orders (
  id           BIGINT GENERATED ALWAYS AS IDENTITY,
  customer_id  INT NOT NULL, total NUMERIC(10,2) NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, created_at)          -- must include the partition key
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE orders_2026_03 PARTITION OF orders
  FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

INSERT INTO orders (customer_id, total, created_at) VALUES
  (42, 250.00, '2026-01-05 10:00'), (42, 120.00, '2026-02-10 09:15'),
  (99, 999.99, '2026-02-28 23:59'), (63, 310.25, '2026-03-14 12:00');

FROM is included and TO is not, so midnight on 1 March belongs to March. We inserted into orders — the hidden tableoid column shows where each row really went.

-- and removing a whole month is one statement
DROP TABLE orders_2026_01;

The table you named, orders, is the parent. It holds no rows — only the rules: the partition key and each partition's range. Every partition is a normal table with its own files and its own indexes.

On insert, PostgreSQL reads the key from the new row, finds the matching range (they are kept sorted, so this is quick), and writes into that table and its indexes. No other partition is touched, and with no matching range the insert fails.

On a query, the planner compares the WHERE conditions with each range and throws out every partition that can't hold a matching row: partition pruning. When the value is only known at run time, like now() or a parameter, that happens as the query starts and the plan says Subplans Removed: 1. With no condition on the key nothing is pruned, every partition is read and the results joined end to end — the Append above.

One rule follows from “each partition has its own indexes”: none spans all of them, so uniqueness can only be promised if the partition key is part of the key. That is why the primary key was (id, created_at). Try id alone and you get unique constraint on partitioned table must include all partitioning columns.

Three ways to split. Range gives each partition a stretch of values, as the example does. List gives each a set of exact values. Hash runs the key through a hash function and uses the remainder.

-- list: by country, with a catch-all
CREATE TABLE customers (id BIGINT, country TEXT NOT NULL,
  PRIMARY KEY (id, country)) PARTITION BY LIST (country);
CREATE TABLE customers_in    PARTITION OF customers FOR VALUES IN ('IN');
CREATE TABLE customers_us_ca PARTITION OF customers FOR VALUES IN ('US','CA');
CREATE TABLE customers_other PARTITION OF customers DEFAULT;

-- hash: four even pieces by user
CREATE TABLE sessions (user_id BIGINT, token TEXT,
  PRIMARY KEY (user_id, token)) PARTITION BY HASH (user_id);
CREATE TABLE sessions_0 PARTITION OF sessions
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);   -- and 1, 2, 3

With 10,000 users those four hash partitions got 2,489, 2,527, 2,530 and 2,454 rows. A default partition takes everything that fits nowhere else: a French customer lands in customers_other.

Assumptions, made up: an events table takes 50 million rows a month at 200 bytes each, kept 12 months, with 25-byte index entries and a delete rate of 50,000 rows a second.

The index tells the same story. On one table, 600,000,000 × 25 bytes = 15 GB, too big for an 8 GB server. In monthly partitions the current month's is 50,000,000 × 25 = 1.25 GB, and new rows and recent queries only touch that one.

How many? By month, 12 plus one ahead. By day, 365 — fine. By hour, 8,760 — too many, because every query weighs all of them first. On a laptop with 2,000 empty partitions, a query naming the key took under 3 ms to plan; one that didn't took about 150 ms, before reading a single row.

Create the next partition before it is needed

CREATE TABLE orders_2026_04 PARTITION OF orders
  FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

A scheduled job does this a few partitions ahead; many teams use pg_partman. In psql, \d+ orders lists every partition with its range.

Remove old data without blocking

ALTER TABLE orders DETACH PARTITION orders_2026_02 CONCURRENTLY;
DROP TABLE orders_2026_02;

A plain DROP TABLE on a partition locks the parent for a moment and waits for running queries. CONCURRENTLY avoids that; it can't run in a transaction and is refused when a default partition exists. After detaching it is an ordinary table — keep it as an archive if you like.

Add an index without blocking writes

CREATE INDEX orders_customer_idx ON ONLY orders (customer_id);   -- empty
CREATE INDEX CONCURRENTLY orders_2026_03_customer_idx
  ON orders_2026_03 (customer_id);
ALTER INDEX orders_customer_idx
  ATTACH PARTITION orders_2026_03_customer_idx;   -- repeat per partition

A plain CREATE INDEX on the parent builds on every partition and blocks writes throughout, and PostgreSQL 14 won't take CONCURRENTLY there. So build each piece separately and attach it; when the last is attached the parent's index is valid, and later partitions get it automatically.

Check that pruning happens

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF, SUMMARY OFF)
SELECT * FROM orders
WHERE created_at >= to_timestamp('2026-04-10', 'YYYY-MM-DD');

 Append (actual rows=0 loops=1)
   Subplans Removed: 1          <- March, pruned at run time
   ->  Seq Scan on orders_2026_04 orders_1
   ->  Seq Scan on orders_2026_05 orders_2

Count the partitions in the plan against the ones you have. Subplans Removed is run-time pruning, here because the date came from a function. An Append with every partition under it means no pruning at all — usually a function wrapped around the key, like date_trunc('month', created_at). Write a plain range instead.

  • Fast with the key vs slower without it. In a laptop test with 12 partitions, a lookup by user ID read 48 pages across 12 indexes. The same lookup on one plain table read 4.
  • Easy clean-up vs a job you must not forget. Dropping a month is instant; in return, new partitions must exist on time or inserts fail.
  • Small indexes vs limited unique rules. Each index is small, but a unique rule must include the partition key, so “this email is unique across the table” can't be enforced when you partition by date.
  • Not a general speed-up. Counting one month's rows took about the same time either way, because the plain table had a good index. The payoff is clean-up and a small busy index, not single queries.
  • Hard to undo. The key and the split are fixed at creation; changing either means a new table and moving every row.

Signals that it fits

  • The table is bigger than the server's memory, or clearly heading there.
  • Nearly every query filters on the same column, usually a date or a tenant.
  • Recent data is busy, old data rarely read.

When you don't need it

  • The table and its indexes fit in memory — a plain table with the right index is simpler and just as fast.
  • Queries reach the table many ways with no column in common, so most read every partition.
  • You need a unique rule on a column that isn't the partition key.
  • One machine can't hold the data or take the writes. That is sharding.
  • Partitioning to fix a slow query. If it needed an index, it still does.
  • Leaving the key out of queries. Every partition is read, and the table is slower than before.
  • Wrapping the key in a function. date_trunc('month', created_at) = ... stops pruning. Use a plain range.
  • Forgetting the next partition. At midnight on the first, every insert starts failing. Create them ahead with a job, and alert when fewer than two future ones exist.
  • Using a default partition to hide that. Rows pile up quietly, and later the real partition can't be created because its rows sit in the default. You must move them out first.
  • Too many partitions. Daily for ten years is 3,650 tables. Aim for tens or a few hundred.

Common questions

  • Partitioning vs sharding? Both split a table by a key. Partitions are tables in the same database; shards are on different machines. Partitioning makes a big table manageable, sharding adds capacity.
  • What is partition pruning? The planner compares the query's conditions with each range and skips what can't match. It needs a filter on the partition key.
  • How do you pick the key? The column most queries filter on, which also decides when data gets old. For time-based data, the timestamp.
  • Why must the primary key include the partition key? No index spans all partitions, so uniqueness can only be checked inside one.

Follow-ups to expect

  • An update changes the key? PostgreSQL moves the row: a delete plus an insert underneath.
  • Partitioning a table that is already huge? Not in place. Build a new partitioned table, copy rows in batches, swap the names — or attach the old table as one big partition and send new data elsewhere.

How it fits a bigger design

Partitioning answers “this table grows forever”. Say what it is split by and how old data leaves: “events are partitioned by month, and we drop partitions older than a year.” It comes before sharding — and when you do shard, each shard often still partitions by time.

  • Partitioning splits one table into smaller tables in the same database. The app still uses one table name.
  • The parent holds no rows, only the rules. Each partition is a normal table with its own indexes.
  • An insert goes to the partition whose range matches the key. If none matches, it fails.
  • Partition pruning skips partitions that can't match, and needs a plain condition on the partition key.
  • A query without the key reads every partition, and can be slower than on a plain table.
  • Range suits time-based data, list a few fixed groups, hash even pieces with no way to drop old data.
  • Removing old data is a detach and a drop: instant, and it frees disk. A DELETE is slow and frees nothing.
  • A unique rule must include the partition key, because no index covers all partitions.
  • New partitions must exist before their rows arrive, and thousands slow query planning.
  • Partitioning adds no capacity. When one machine is not enough, that is sharding.
