A normal index stores a whole value and points at the row holding it. Fine when you search for the whole value: customer_id = 4242, email = 'sam@example.com'. Useless for “articles mentioning refund”, where the word is buried in a paragraph.

An inverted index turns the mapping around. A table maps a row to its words; the index maps each word to the rows containing it. That list is a posting list, and “inverted” means this flip.

Examples use PostgreSQL 16, where this is two parts: the tsvector type, holding a document's processed words, and a GIN index over it. GIN stands for Generalized Inverted Index — the structure Elasticsearch and Lucene are built on too.

One-line version: store word → rows instead of row → words, and text search becomes a few lookups and a list merge.

Without one, text search means LIKE '%refund%', and three things go wrong at once.

  • It reads every row. A leading % means no sorted index can help, so every document is scanned on every search.
  • It matches the wrong things. It catches refunded, which you wanted, and non-refundable, which you may not. Searching run misses running.
  • It can't rank. Matching rows come back in no useful order. A document with the word in its title and five times in the body looks the same as one with it in a footnote.

The inverted index fixes all three. Words are cut to a common root before storage, so running and ran both become run. Each word's list is already built, so a search is a lookup. And the index keeps where each word appeared, which is what ranking uses.

Three articles.

CREATE TABLE articles (
  id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title TEXT NOT NULL,
  body  TEXT NOT NULL
);

INSERT INTO articles (title, body) VALUES
  ('Refund policy',  'We are refunding orders within 30 days.'),
  ('Shipping delay', 'Orders are running late this week.'),
  ('Payment errors', 'A failed payment is not a refund.');

First, what a document becomes. to_tsvector splits the text, drops the words too common to store, and cuts the rest back to a root:

SELECT to_tsvector('english', 'We are refunding orders within 30 days.');

 '30':6  'day':7  'order':4  'refund':3  'within':5

we and are are gone: they are stop words, too common to be worth a list. refunding became refund and days became day — that is stemming, cutting a word to a root so different endings meet. The number is the word's position.

Now search. @@ is the match operator, and the query goes through the same steps:

SELECT id, title FROM articles
WHERE to_tsvector('english', title || ' ' || body)
      @@ plainto_tsquery('english', 'refunded order');

 id |     title
 ---+---------------
  1 | Refund policy

Row 1 matched although it holds neither word as typed: refunding and orders stemmed to refund and order, and so did the query. Row 2 has order but not refund, and plainto_tsquery joins words with AND, so it is out.

Building the index is running that pipeline over every row, then collecting the results word by word.

  1. On write, the row's text is split, cleaned and stemmed into a tsvector.
  2. Each word is added to its posting list with the row's address. The words themselves sit in a B-tree, so finding one word's list is a normal tree walk.
  3. On search, the query is processed the same way, giving a small set of words.
  4. Each word's posting list is read. AND intersects them, OR unions them, starting from the shortest list because that bounds the work.
  5. What survives is a set of row addresses. The database fetches those rows and ranks them.

GIN doesn't write a posting list on every insert — that would be slow, because one row touches as many lists as it has distinct words. New entries go to a small pending list first and are folded in later, which is why a search right after a bulk load can be slower than normal.

GIN

The default for text search. One entry per word, pointing at every row that has it. Fast to search, slower to write, and the right answer unless you have a reason.

GiST

Stores a fixed-size signature per document instead of its words. Smaller and quicker to update, but signatures collide, so it returns false matches the database must recheck against the real rows. Worth it when the table is small or changes constantly.

Trigram (pg_trgm)

Indexes every three-letter run instead of words: refund becomes ref, efu, fun… That makes it the one option that serves LIKE '%fund%' and typo-tolerant matching. It has no idea what a word means, and the index is large.

Set it up properly

-- keep the processed text in a column: computed once
ALTER TABLE articles ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('english', title || ' ' || body)
  ) STORED;

CREATE INDEX articles_tsv_idx ON articles USING gin (tsv);

The database keeps a generated column up to date, and reading it is free. Indexing to_tsvector(...) directly also works, but every query must then repeat that exact expression or the index is skipped.

Check it is used, and rank

EXPLAIN ANALYZE
SELECT title, ts_rank(tsv, q) AS rank
FROM articles, plainto_tsquery('english', 'refund order') q
WHERE tsv @@ q ORDER BY rank DESC LIMIT 10;

 Bitmap Heap Scan on articles
   Recheck Cond: (tsv @@ q)
   ->  Bitmap Index Scan on articles_tsv_idx
         Index Cond: (tsv @@ q)

Read it inside out. Bitmap Index Scan means the posting lists were read into a set of row addresses; Bitmap Heap Scan then fetches those rows in page order. A Seq Scan means the index was skipped — usually a mismatched expression, or a configuration other than 'english'.

Query shapes and size

SELECT websearch_to_tsquery('english', '"order status" -refund');
 -- 'order' <-> 'status' & !'refund'   (phrase, and a word excluded)

SELECT pg_size_pretty(pg_relation_size('articles_tsv_idx'));

websearch_to_tsquery takes what a user actually types, quotes and minus signs included, and never errors on odd input. to_tsquery wants proper operators and throws on bad syntax, so never hand it raw user text.

  • Read speed vs write cost. One insert touches one B-tree entry, but 150 posting lists. Text-heavy tables with constant writes feel this.
  • Size vs precision. GIN stores every word and is large. GiST stores a signature, stays small, and pays with false matches it must recheck.
  • Stemming vs exactness. Stemming makes running find run, and also makes universe and university both stem to univers. You cannot have one without the other.
  • In your database vs a search engine. Postgres keeps search next to your rows, in the same transaction, with no sync to go wrong. Elasticsearch gives better ranking and scale, and a second system to keep in step.

Reach for it when

  • Users type words to find rows: articles, product descriptions, tickets, logs.
  • You need word matching rather than value matching, and want refunded to find refund.
  • The data is already in Postgres and the search is a feature, not the product.

You don't need one when

  • The column is a short exact value. Codes, emails, slugs and tags want a plain B-tree.
  • The table is small. A few thousand rows scan fast enough, and the index would just slow writes.
  • You search by meaning, not words. “How do I stop paying you” shares no word with “Cancel your subscription”; that needs vector search.
  • Search is the product. If ranking, facets and typo handling are what you sell, a real search engine earns its keep.
  • Indexing an expression, then querying a different one. An index on to_tsvector('english', body) does nothing for a query on title || body. The plan quietly goes back to a full scan.
  • Using the simple configuration by accident. It skips stemming, so refunded no longer finds refund and nobody can tell why results got worse.
  • Passing user text to to_tsquery. A stray & or quote throws a syntax error at the user. Use plainto_tsquery instead.
  • Sorting by rank over a huge match set. ts_rank runs on every matching row before LIMIT helps. A query matching 500,000 rows ranks all of them.
  • Expecting substring matches. A word index can't find '%fund%' inside refund. Trigrams are for that.

Common questions

  • What makes it “inverted”? The normal direction is row → words. The index stores word → rows, so one lookup gives every document with that word.
  • How is an AND of two words answered? Read both posting lists and keep the addresses in both, starting from the shorter list, since the answer can't be bigger than it.
  • Why is writing slower? One row adds an entry for every distinct word it holds. GIN softens that by batching new entries into a pending list.
  • GIN or GiST? GIN for read-heavy text search. GiST when the table is small or written to constantly, and false matches can be rechecked.

How it fits a bigger design

In most systems this is the whole of search, and often enough. When it isn't, the next step is a search service fed by a queue of document changes — and you now own the lag between a write landing and the search seeing it. Bigger systems run keyword and vector search side by side and merge the lists.

  • An inverted index stores word → rows instead of row → words. Each word's list of rows is a posting list.
  • LIKE '%word%' reads the whole table, matches the wrong things and can't rank. The index fixes all three.
  • Text is split, stripped of stop words and stemmed before storage, and the query goes through the same steps so both sides match.
  • In PostgreSQL that is a tsvector column with a GIN index, searched with @@. AND intersects posting lists, OR unions them, starting from the shortest.
  • Reading is cheap and writing is not: one row adds an entry per distinct word, batched through GIN's pending list.
  • GIN is the default. GiST is smaller and rechecks false matches. Trigram indexes handle substrings and typos.
  • Index an expression and every query must repeat it exactly, or the index is skipped. Use plainto_tsquery or websearch_to_tsquery for user input; to_tsquery throws on bad syntax.
  • It matches words, not meaning. A question phrased differently from the answer needs vector search.
