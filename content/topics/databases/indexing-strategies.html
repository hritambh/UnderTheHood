An index is a separate, sorted copy of one or more columns of a table. Each entry points back to the full row. It works like the index at the back of a book: you look up a word, get a page number, and go straight there.

Without an index, the database answers “find this customer’s orders” by reading every row in the table. That is a sequential scan. With the right index, it reads a handful of pages.

An indexing strategy is how you decide which indexes to create. Which columns? In what order? Covering which queries? It matters because indexes are not free. Each one takes disk space and slows down every write to the table.

All examples here use PostgreSQL. They were run on version 14, and work the same on newer versions.

One-line version: an index trades slower writes and more disk for faster reads. A good strategy means a few indexes shaped around your real queries, not one index per column.

Get it wrong in one direction, and reads are slow. A page that lists a customer’s orders is instant with 10,000 rows in the table. At 100 million rows, the same query takes half a minute, because it reads the whole table each time. Nothing in the code changed. The table just grew.

Get it wrong in the other direction, and writes are slow. A team adds an index for every slow query they ever saw. Two years later the table has 15 indexes. Each insert now writes to 16 places, the indexes take more disk than the data, and nobody knows which ones are still used.

And an index on the wrong columns, or with the columns in the wrong order, costs the same as a good one and is never picked.

Let’s build a table with a million orders. Each of 50,000 customers gets 20 of them.

-- Create an orders table and fill it with 1,000,000 rows
CREATE TABLE orders (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  INT           NOT NULL,
  status       TEXT          NOT NULL,
  total        NUMERIC(10,2) NOT NULL,
  created_at   TIMESTAMPTZ   NOT NULL
);

INSERT INTO orders (customer_id, status, total, created_at)
SELECT (g * 7) % 50000 + 1,
       CASE WHEN g % 100 = 0 THEN 'pending'
            WHEN g % 100 < 4 THEN 'cancelled'
            ELSE 'delivered' END,
       (g % 5000) / 10.0 + 5,
       TIMESTAMPTZ '2026-01-01 00:00+00' + g * INTERVAL '20 seconds'
FROM generate_series(1, 1000000) AS g;

ANALYZE orders;   -- refresh the statistics the planner uses

The query we care about: the five newest orders for one customer.

-- The five newest orders of customer 4242
SELECT id, total, created_at
FROM orders
WHERE customer_id = 4242
ORDER BY created_at DESC
LIMIT 5;

   id   | total  |       created_at
--------+--------+------------------------
 993463 | 351.30 | 2026-08-18 23:14:20+00

Now put EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF) in front of that query. It runs the query and prints what the database did. The plans below are trimmed a little to fit, and the times are from one laptop. Yours will differ.

Step 1: no index

-- Plan with no index on customer_id
 Limit (actual rows=5 loops=1)
   ->  Gather Merge (actual rows=5 loops=1)
         Workers Planned: 2
         Workers Launched: 2
         ->  Sort (actual rows=4 loops=3)
               Sort Key: created_at DESC
               ->  Parallel Seq Scan on orders (actual rows=7 loops=3)
                     Filter: (customer_id = 4242)
                     Rows Removed by Filter: 333327
 Execution Time: 11.705 ms

Seq Scan means it read the whole table. Three processes shared the work, and each threw away about 333,000 rows. So it read a million rows to find 20.

Step 2: an index on the filter column

-- Index the column in the WHERE clause
CREATE INDEX orders_cust_idx ON orders (customer_id);

 Limit (actual rows=5 loops=1)
   ->  Sort (actual rows=5 loops=1)
         Sort Key: created_at DESC
         Sort Method: top-N heapsort  Memory: 25kB
         ->  Bitmap Heap Scan on orders (actual rows=20 loops=1)
               Recheck Cond: (customer_id = 4242)
               Heap Blocks: exact=20
               ->  Bitmap Index Scan on orders_cust_idx (actual rows=20 ...)
                     Index Cond: (customer_id = 4242)
 Execution Time: 0.047 ms

Now it uses the index to find the 20 rows, fetches them from 20 table pages, and sorts them. About 250 times faster. But there is still a Sort step, and it fetched 20 rows to return 5.

Step 3: an index that matches the whole query

-- Index the filter column, then the sort column
CREATE INDEX orders_cust_created_idx
  ON orders (customer_id, created_at DESC);

 Limit (actual rows=5 loops=1)
   ->  Index Scan using orders_cust_created_idx on orders (actual rows=5 ...)
         Index Cond: (customer_id = 4242)
 Execution Time: 0.016 ms

No sort, and only 5 rows read. Inside this index, one customer’s orders sit next to each other, already newest first. The database walks to the first one and reads five entries.

That is the whole idea of an indexing strategy. The second index was fine. The third one was shaped like the query.

PostgreSQL’s default index is a B-tree: a tree of pages, where each page is 8 KB. The top page points to pages below it, which point to pages below them. The bottom pages, called leaf pages, hold the sorted values and the address of each row in the table.

The ranges in the picture are made up, to show the idea. Here is what happens for WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 5 with the index from step 3:

  1. The planner picks a plan. It looks at the indexes on the table and at its statistics, and estimates the cost of each way to run the query. Here the index is far cheaper than reading the table.
  2. Read the root page. It holds a few hundred values with pointers. The database finds the range that 4242 falls in and follows that pointer.
  3. Read one branch page, and do the same again.
  4. Read one leaf page. It finds the first entry for customer 4242. The entries for that customer are side by side, sorted by created_at, newest first.
  5. Follow five entries to the table. Each entry holds the address of a row: which table page, and which slot in it. The database reads those pages to get id and total.
  6. Stop. The LIMIT is met. No sorting was needed, because the index was already in the right order.

Our index has three levels for a million rows. A B-tree grows very slowly: a tree one level deeper holds a few hundred times more rows.

Two more things follow from this picture:

  • Leaf pages are linked (the grey arrows). So a range like “between March 1 and March 2” is one walk down the tree, then a walk sideways.
  • Every write touches the tree. An insert into orders must also add an entry to the right leaf page of every index on the table.

MySQL differs here. In MySQL (InnoDB), the table itself is stored inside the primary key index, and foreign key columns get an index automatically. Neither is true in PostgreSQL.

These build on the orders table from the example. Each one is a different way to shape an index around a query.

Single-column index

CREATE INDEX orders_cust_idx ON orders (customer_id);

  • How it works: one column, sorted. It handles =, <, >, BETWEEN, IN and ORDER BY on that column.
  • Use it when: queries filter on that one column, and the filter matches a small share of the rows.
  • Good: small, simple, and useful to many queries.
  • Bad: it does nothing for the other columns in the query. Step 2 still had to sort.

Composite index (several columns)

CREATE INDEX orders_cust_created_idx ON orders (customer_id, created_at DESC);

  • How it works: sorted by the first column, then by the second inside each value of the first. Like a phone book: surname, then first name.
  • Use it when: a query filters on one column and filters or sorts on another.
  • The order rule: put columns compared with = first, then the one used for a range or a sort.
  • Good: one index answers the filter and the sort. It also serves queries on customer_id alone, so the single-column index above is no longer needed.
  • Bad: it is no help for the second column alone. A phone book can’t find everyone called Asha. Counting one day’s orders by created_at still gave us Parallel Seq Scan on orders.

Covering index

-- Carry the total column inside the index
CREATE INDEX orders_cust_cover_idx ON orders (customer_id) INCLUDE (total);
VACUUM orders;

EXPLAIN (ANALYZE, COSTS OFF, TIMING OFF)
SELECT sum(total) FROM orders WHERE customer_id = 4242;

 Aggregate (actual rows=1 loops=1)
   ->  Index Only Scan using orders_cust_cover_idx on orders (actual rows=20 ...)
         Index Cond: (customer_id = 4242)
         Heap Fetches: 0
  • How it works: INCLUDE stores extra columns in the leaf pages. If the index holds every column the query needs, the database never visits the table. The plan says Index Only Scan.
  • Use it when: a very frequent query reads one or two small columns.
  • Good: it skips the table visits, which are usually the slowest part.
  • Bad: a bigger index. And it only skips the table on pages that VACUUM has marked as fully visible. Heap Fetches: 0 shows it worked. On a table with many recent writes, that number climbs.

Partial index

-- Index only the rows that are still pending
CREATE INDEX orders_pending_idx ON orders (created_at)
  WHERE status = 'pending';

-- For comparison: the same idea over every row
CREATE INDEX orders_status_idx ON orders (status, created_at);
  • How it works: only rows that match the WHERE go into the index. A query must use the same condition to be able to use it.
  • Use it when: queries always ask for a small, fixed slice. Pending orders, unread messages, rows not yet deleted.
  • Good: tiny. In our table 1% of rows are pending. The partial index is 240 kB. The full one is 39 MB. Writes to delivered orders never touch it.
  • Bad: useless for any other slice. WHERE status = 'cancelled' can’t use it.

Expression index

-- Find a customer by email, ignoring upper and lower case
CREATE TABLE customers (id INT PRIMARY KEY, email TEXT NOT NULL);
INSERT INTO customers
SELECT g, 'User' || g || '@Example.com'
FROM generate_series(1, 50000) AS g;

CREATE INDEX customers_email_idx ON customers (email);
ANALYZE customers;

EXPLAIN (COSTS OFF)
SELECT id FROM customers WHERE lower(email) = 'user4242@example.com';

 Seq Scan on customers
   Filter: (lower(email) = 'user4242@example.com'::text)

CREATE INDEX customers_email_lower_idx ON customers (lower(email));
ANALYZE customers;
-- the same EXPLAIN now gives:

 Index Scan using customers_email_lower_idx on customers
   Index Cond: (lower(email) = 'user4242@example.com'::text)
  • How it works: the index stores the result of an expression, not the raw column.
  • Use it when: queries always wrap the column in the same function.
  • Good: it makes those queries indexable at all. A plain index on email was ignored above.
  • Bad: the query must use the very same expression. Each write has to run the function.

Other kinds of index

Everything above is a B-tree. PostgreSQL has other kinds for data a B-tree handles badly.

  • GIN: for a column where one value holds many things, like a JSON document, an array, or text you search by word. Fast to search, slower to update.
  • BRIN: for huge tables where the column follows the order rows were inserted, like a timestamp on a log table. It only stores the lowest and highest value for each block of pages. So it is tiny, and much less exact. It is for big ranges, not single rows.
  • Hash: only handles =. A B-tree does that well too, so hash indexes are rare.
-- The same column, indexed two ways
CREATE INDEX orders_created_idx  ON orders (created_at);
CREATE INDEX orders_created_brin ON orders USING brin (created_at);

On our table the B-tree is 21 MB and the BRIN index is 24 kB.

Our example has a million rows and everything fits in memory, so even the full scan took only 12 ms. Let’s work out the same query at 100 million rows.

Assumptions (made up for the sums, not benchmarks):

  • 100 million orders, with rows the same size as ours. Our table is 65 MB for a million rows, so about 65 bytes a row.
  • Nothing is in memory yet. The disk reads 200 MB a second in a straight line, and one page at a random spot takes 0.1 ms.
  • An index page holds about 250 entries.

Reading without an index

  • Table size: 100,000,000 × 65 bytes = 6.5 GB, which is about 800,000 pages of 8 KB.
  • Full scan: 6,500 MB ÷ 200 MB a second = about 32 seconds. For every request.

Reading with the composite index

  • Tree depth: 250 × 250 × 250 = 15.6 million entries in three levels. That is not enough. A fourth level gives 3.9 billion. So 4 levels.
  • Pages read: 4 index pages + 5 table pages = 9 pages, against 800,000.
  • Time: 9 × 0.1 ms = about 1 ms.

The table grew 100 times. The scan got 100 times slower. The index lookup got one page longer.

What the indexes cost

  • Disk. After everything in this topic, our table is 65 MB and its eight indexes are 149 MB. That is 2.3 times the data. At 100 million rows: 6.5 GB of table and about 15 GB of indexes.
  • Writes. One insert now changes 9 places: the table and each of the 8 indexes. (The partial index is only touched for pending orders.)

The shape is what matters: reads go from seconds to milliseconds, and you pay for it on every write.

Create and remove an index without blocking writes

-- Build an index while the app keeps writing to the table
CREATE INDEX CONCURRENTLY orders_total_idx ON orders (total);

-- Remove one the same way
DROP INDEX CONCURRENTLY orders_total_idx;

-- Rebuild a bloated index
REINDEX INDEX CONCURRENTLY orders_cust_idx;

-- A CONCURRENTLY build that fails leaves a broken index behind. Find it:
SELECT indexrelid::regclass AS index FROM pg_index WHERE NOT indisvalid;

A plain CREATE INDEX blocks every insert, update and delete on the table until it finishes. On a big table that is minutes of downtime. CONCURRENTLY takes longer but lets writes through. It can’t run inside a transaction. If the last query returns a row, drop that index and build it again.

See how a query really runs

-- Run the query and show the plan, with page counts
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total, created_at FROM orders
WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 5;

 Limit  (cost=0.42..21.51 rows=5 width=22)
        (actual time=0.005..0.008 rows=5 loops=1)
   Buffers: shared hit=8
   ->  Index Scan using orders_cust_created_idx on orders
         (cost=0.42..84.77 rows=20 width=22)
         (actual time=0.004..0.007 rows=5 loops=1)
         Index Cond: (customer_id = 4242)
         Buffers: shared hit=8
 Planning Time: 0.425 ms
 Execution Time: 0.010 ms

(Long lines are wrapped here to fit.) How to read it:

  • Read from the inside out. The most indented step runs first and feeds the one above it.
  • The step name tells you how rows were found. Seq Scan: the whole table. Index Scan: the index, then the table. Index Only Scan: the index alone. Bitmap Heap Scan: the index collects row addresses first, then the table pages are read in order.
  • cost=0.42..84.77 is the planner’s guess, in its own units. It is not milliseconds.
  • rows=20 in the cost part is the guess. rows=5 in the actual part is what happened. Here it stopped early because of the LIMIT. If the two are far apart for no such reason, the statistics are old. Run ANALYZE.
  • Buffers: shared hit=8 means 8 pages, all found in memory: 3 index levels and 5 table pages. read would mean pages fetched from disk.

Warning signs: a Seq Scan with a large Rows Removed by Filter, a Sort that an index could have avoided, and a high Heap Fetches on an index-only scan.

Find indexes nobody uses

-- Size and use of every index on a table
SELECT indexrelname AS index,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan AS scans
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

          index          |  size   | scans
-------------------------+---------+-------
 orders_status_idx       | 39 MB   |     0
 orders_cust_cover_idx   | 30 MB   |     2
 orders_cust_created_idx | 30 MB   |     1
 orders_pkey             | 21 MB   |     0
 orders_created_idx      | 21 MB   |     0
 orders_cust_idx         | 7600 kB |     1
 orders_pending_idx      | 240 kB  |     1
 orders_created_brin     | 24 kB   |     0

scans counts how many times each index was used since the statistics were last reset, so your counts will differ. The biggest index here, orders_status_idx, has never been used. In production, an index that stays at 0 for weeks is one to drop. Two cautions: a primary key or unique index does its job even at 0 scans, and a read copy of the database keeps its own counts.

Find tables that are being scanned

-- Tables where the most rows are read by full scans
SELECT relname, seq_scan, seq_tup_read, idx_scan
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC
LIMIT 5;

  relname  | seq_scan | seq_tup_read | idx_scan
-----------+----------+--------------+----------
 orders    |       29 |     12000000 |        6
 customers |        3 |       100000 |        1

seq_tup_read is the number of rows read by full scans. A big table at the top of this list, with few index scans, is probably missing an index. Then find the slow query and EXPLAIN it.

  • Faster reads vs slower writes. Each index speeds up some queries and adds work to every insert. In PostgreSQL, an update that changes any indexed column adds a new entry to every index on the table, not only the one for that column.
  • One wide index vs several narrow ones. A composite index serves one query shape very well. Separate single-column indexes serve more shapes, each less well.
  • Covering vs small. Extra columns in the index save table visits. They also make the index bigger, so less of it stays in memory.
  • Partial vs general. A partial index is tiny and cheap to keep. It only helps the one slice it was built for.
  • Exact vs rough. A B-tree finds one row. A BRIN index is a thousand times smaller and only narrows things down to a block of pages.

Add an index when

  • A query that runs often filters or joins on a column, and matches a small share of the table.
  • A query sorts by a column and only takes the first few rows.
  • A column is a foreign key. PostgreSQL does not index these for you, and joins and deletes on the parent table need it.
  • A value must be unique. A unique index is how the database enforces that.
  • EXPLAIN shows a Seq Scan throwing away most of a big table.

You don’t need one when

  • The table is small. A few thousand rows fit in a handful of pages. Reading them all is as fast as using an index, and PostgreSQL will ignore your index anyway.
  • The query matches most of the table. Counting delivered orders, 96% of our rows, still used a Seq Scan even with an index on status. Reading nearly everything through an index is slower than just reading everything.
  • The column has only a few different values and you ask for the common ones. An index on a true/false column rarely helps. A partial index on the rare value might.
  • The table is written far more than it is read, like a log you only load in bulk later.
  • Another index already starts with the same columns. An index on (customer_id, created_at) makes one on (customer_id) redundant.
  • One index per column. Five single-column indexes are not the same as one index shaped for the query. You pay five write costs and still sort. Start from the query, not from the column list.
  • Wrong column order in a composite index. (created_at, customer_id) is nearly useless for “orders of this customer”. Columns compared with = go first.
  • Wrapping the column in a function. WHERE created_at::date = '2026-03-01' can’t use an index on created_at. Our test fell back to a Seq Scan. Write it as a range, created_at >= '2026-03-01' AND created_at < '2026-03-02', and the index is used.
  • Searching with a wildcard at the front. LIKE '%4242@Example.com' gave a Seq Scan too. A sorted list can’t help when you don’t know how the value starts. Text search needs a different kind of index.
  • Building an index without CONCURRENTLY in production. Writes to the table stop until it is done.
  • Never removing indexes. Queries change, and old indexes stay and slow down writes. Check pg_stat_user_indexes a few times a year.
  • Forgetting foreign key columns. Deleting a customer then scans the whole orders table to look for their orders.
  • Trusting a test on a tiny table. With 100 rows the planner picks a Seq Scan whatever you build. Test with a realistic amount of data.

Common questions

  • What is an index, and what does it cost? A sorted copy of some columns with pointers to the rows. It makes matching reads fast. It costs disk space and extra work on every write.
  • How do you choose the column order in a composite index? Equality columns first, then the column used for a range or a sort. The index works for any query that uses its first columns, but not for one that skips them.
  • Why would the database ignore an index? The query matches too many rows, the table is small, the column is wrapped in a function, the types don’t match, or the statistics are out of date.
  • What is a covering index? One that holds every column the query needs, so the table is never read. In PostgreSQL the plan shows Index Only Scan.
  • How do you find a missing index? Find the slow query, run EXPLAIN (ANALYZE, BUFFERS), and look for a scan that throws away most of what it reads.

How it fits a bigger design

In a system design, indexes come right after the data model. For each main query, say which index serves it. “The inbox reads the newest 20 by user, so the index is on user and time, newest first.” Cursor pagination, covered in the Pagination topic, only works well with an index on the cursor columns. And when a table gets too big for one machine, sharding splits it up, but each shard still needs the same indexes.

  • An index is a sorted copy of some columns that points back to the rows. Without one, the database reads the whole table.
  • The default index is a B-tree. A lookup reads one page per level, and a million rows needed only three levels.
  • Shape the index like the query. An index on the filter column and then the sort column removed both the scan and the sort.
  • In a composite index, equality columns go first. The index can’t help a query that skips its first column.
  • A covering index holds every column the query needs, so the table isn’t read. A partial index only holds the rows you ask for, so it stays tiny.
  • An expression index is needed when the query wraps the column in a function. Other kinds, like GIN and BRIN, fit JSON, text search and huge insert-ordered tables.
  • Every index costs disk and slows writes. Our eight indexes took 2.3 times the space of the table.
  • Use EXPLAIN (ANALYZE, BUFFERS) to see what a query does, and pg_stat_user_indexes to find indexes nobody uses.
  • Build indexes in production with CONCURRENTLY, so writes are not blocked.
  • Skip the index on small tables, and for queries that match most of the rows.
