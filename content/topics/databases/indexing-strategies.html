An index is a separate, sorted copy of one or more columns, where each entry points back to the full row. Like the index at the back of a book: look up a word, get a page number, go straight there.

Without one, “find this customer's orders” means reading every row in the table — a sequential scan. With the right index, it reads a handful of pages.

An indexing strategy is how you decide which to create: which columns, in what order, covering which queries. It matters because indexes aren't free. Each one takes disk and slows every write to the table. All examples are PostgreSQL 14.

One-line version: an index trades slower writes and more disk for faster reads. A good strategy means a few indexes shaped around your real queries, not one index per column.

Get it wrong in one direction and reads are slow. A page listing a customer's orders is instant at 10,000 rows. At 100 million the same query takes half a minute, because it reads the whole table every time. Nothing in the code changed; the table just grew.

Get it wrong the other way and writes are slow. A team adds an index for every slow query they ever saw; two years later the table has 15, each insert writes to 16 places, the indexes take more disk than the data, and nobody knows which are still used.

The strategy sits between those: enough for the queries that matter, and no more.

One million orders, the same query three ways. Plans are trimmed to fit; times are from one laptop.

CREATE TABLE orders (
  id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  INT NOT NULL, status TEXT NOT NULL,
  total NUMERIC(10,2) NOT NULL, created_at TIMESTAMPTZ NOT NULL
);
-- 1,000,000 rows: customer_id cycles 1..50000, 1% 'pending'
ANALYZE orders;   -- refresh the planner's statistics

SELECT id, total, created_at FROM orders
WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 5;

Step 1: no index

 Limit
   ->  Gather Merge  (Workers Launched: 2)
         ->  Sort  (Sort Key: created_at DESC)
               ->  Parallel Seq Scan on orders
                     Filter: (customer_id = 4242)
                     Rows Removed by Filter: 333327
 Execution Time: 11.705 ms

Seq Scan means it read the whole table: three processes each threw away about 333,000 rows, a million read to find 20.

Step 2: an index on the filter column

CREATE INDEX orders_cust_idx ON orders (customer_id);

 Limit
   ->  Sort  (Sort Key: created_at DESC)
         ->  Bitmap Heap Scan on orders  (actual rows=20)
               ->  Bitmap Index Scan on orders_cust_idx
 Execution Time: 0.047 ms

It finds the 20 rows through the index, fetches them from 20 table pages and sorts. About 250 times faster — but there is still a Sort, and it read 20 rows to return 5.

Step 3: an index shaped like the query

CREATE INDEX orders_cust_created_idx ON orders (customer_id, created_at DESC);

 Limit
   ->  Index Scan using orders_cust_created_idx on orders  (actual rows=5)
         Index Cond: (customer_id = 4242)
 Execution Time: 0.016 ms

No sort, five rows read. Inside this index one customer's orders sit together, already newest first, so the database walks to the first and reads five entries. The step-2 index was fine; the step-3 one was shaped like the query. That is the whole idea.

PostgreSQL's default index is a B-tree: a tree of 8 KB pages. The top page points at pages below, down to the leaf pages, which hold the sorted values and the address of each row.

Ranges in the picture are made up. For our step-3 query the database reads the root, follows the pointer for 4242, reads one branch page and does the same, then reads one leaf page where that customer's entries sit side by side, newest first. It follows five of them to the table and stops: the LIMIT is met, and no sort was needed.

A million rows needed three levels, and a B-tree grows very slowly — one more level holds a few hundred times more rows. Two things follow: leaf pages are linked (the grey arrows), so a date range is one walk down then sideways; and every write touches the tree, because an insert adds an entry to every index on the table.

MySQL differs. In InnoDB the table itself lives inside the primary key index, and foreign key columns are indexed automatically. Neither is true in PostgreSQL.

Seven shapes. The first two cover most real work.

The composite order rule

A composite index is sorted by its first column, then by the second inside each value of the first — a phone book: surname, then first name. So equality columns go first, then the range or sort column.

The other five, in one line each

-- covering: carries total, so the table is never read (Index Only Scan)
CREATE INDEX orders_cust_cover_idx ON orders (customer_id) INCLUDE (total);

-- partial: only the 1% pending rows. 240 kB, against 39 MB
CREATE INDEX orders_pending_idx ON orders (created_at) WHERE status = 'pending';

-- expression: a plain index on email can't serve lower(email) = '...'
CREATE INDEX customers_email_lower_idx ON customers (lower(email));

-- BRIN: min and max per block only. 24 kB, against 21 MB for the B-tree
CREATE INDEX orders_created_brin ON orders USING brin (created_at);

A covering index skips the table visits, usually the slowest part, but only on pages a recent VACUUM marked fully visible — watch Heap Fetches. A partial one is tiny and writes to other rows never touch it, but status = 'cancelled' can't use it.

Our million rows fit in memory, so even the full scan took 12 ms. The same query at 100 million rows, with made-up assumptions: 65 bytes a row, nothing cached, 200 MB/s in a straight line, 0.1 ms for a random page, 250 entries per index page.

WorkingResult
Table size100,000,000 × 65 bytes6.5 GB, about 800,000 pages

The table grew 100 times. The scan got 100 times slower; the lookup got one page longer.

What that costs. Our table is 65 MB and its eight indexes are 149 MB — 2.3 times the data, so at 100 million rows, 6.5 GB of table and about 15 GB of indexes. One insert now changes nine places.

Build and drop without blocking writes

CREATE INDEX CONCURRENTLY orders_total_idx ON orders (total);
DROP INDEX CONCURRENTLY orders_total_idx;
REINDEX INDEX CONCURRENTLY orders_cust_idx;   -- rebuild a bloated one

-- a failed CONCURRENTLY build leaves a broken index. Find it, then rebuild:
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;

A plain CREATE INDEX blocks every write until it finishes — minutes of downtime on a big table. CONCURRENTLY is slower, lets writes through, and can't run inside a transaction.

Read a plan

EXPLAIN (ANALYZE, BUFFERS) runs the query and shows what it did. Read it inside out: the most indented step runs first and feeds the one above.

  • The step name says how rows were found: Seq Scan the whole table, Index Scan the index then the table, Index Only Scan the index alone.
  • cost= is the planner's guess in its own units, not milliseconds. rows= is a guess in the cost part and the truth in the actual part — far apart for no reason like a LIMIT means stale statistics.
  • Buffers: shared hit=8 is 8 pages found in memory: 3 index levels plus 5 table pages. read means fetched from disk.

Warning signs: a Seq Scan with a large Rows Removed by Filter, a Sort an index could have avoided, a high Heap Fetches.

Find indexes nobody uses

SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)), idx_scan
FROM pg_stat_user_indexes WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

 orders_status_idx       | 39 MB  | 0    <- biggest, never used
 orders_cust_created_idx | 30 MB  | 1
 orders_created_brin     | 24 kB  | 0

An index at 0 scans for weeks is one to drop — but a primary key does its job at 0, and a read replica keeps its own counts. For the other direction, order pg_stat_user_tables by seq_tup_read: a big table at the top with few index scans is probably missing one.

  • Faster reads vs slower writes. In PostgreSQL an update that changes any indexed column adds an entry to every index on the table, not just that column's.
  • One wide index vs several narrow ones. A composite serves one query shape very well; separate single-column indexes serve more shapes, each less well.
  • Covering vs small. Extra columns save table visits and make the index bigger, so less of it stays in memory.

Add an index when

  • A frequent query filters or joins on a column and matches a small share of the table.
  • A query sorts by a column and takes only the first few rows.
  • A column is a foreign key — PostgreSQL does not index these for you, and joins and parent deletes need it.
  • EXPLAIN shows a Seq Scan throwing away most of a big table.

You don't need one when

  • The table is small. A few thousand rows fit in a handful of pages, and the planner will ignore your index anyway.
  • The query matches most of the table. Counting delivered orders, 96% of our rows, still chose a Seq Scan with an index on status.
  • The column has few distinct values and you ask for the common ones. A partial index on the rare value may still help.
  • Another index already starts with the same columns — (customer_id, created_at) makes (customer_id) redundant.
  • One index per column. Five single-column indexes are not one shaped for the query: you pay five write costs and still sort.
  • Wrong column order. (created_at, customer_id) is nearly useless for “this customer's orders”, as the diagram above shows.
  • Wrapping the column in a function. WHERE created_at::date = '2026-03-01' fell back to a Seq Scan; write it as a range instead.
  • A wildcard at the front. LIKE '%4242@Example.com' also gave a Seq Scan: a sorted list can't help when you don't know how the value starts.
  • Building without CONCURRENTLY in production, which stops writes until it finishes.
  • Never removing indexes. Queries change, old indexes stay and slow writes. Check pg_stat_user_indexes a few times a year.

Common questions

  • How do you choose column order in a composite index? Equality columns first, then the range or sort column. It serves any query using its first columns, never one that skips them.
  • Why would the database ignore an index? Too many matching rows, a small table, a column wrapped in a function, mismatched types, or stale statistics.
  • What is a covering index? One holding every column the query needs, so the table is never read. The plan says Index Only Scan.
  • How do you find a missing index? EXPLAIN (ANALYZE, BUFFERS) the slow query and look for a scan throwing away most of what it reads.

How it fits a bigger design

Indexes come right after the data model: for each main query, name the index that serves it. “The inbox reads the newest 20 by user, so the index is user then time, newest first.” Cursor pagination needs an index on the cursor columns, and a sharded table still needs the same indexes on every shard.

  • An index is a sorted copy of some columns pointing back at the rows. Without one the database reads the whole table.
  • The default is a B-tree: one page per level, and a million rows needed three levels.
  • Shape the index like the query: filter column then sort column removed both the scan and the sort.
  • In a composite index, equality columns go first. It can't help a query that skips its first column.
  • A covering index holds every column the query needs, so the table isn't read. A partial index holds only the rows you ask for, so it stays tiny.
  • An expression index is needed when the query wraps the column in a function. GIN fits JSON and text search; BRIN fits huge insert-ordered tables.
  • Every index costs disk and slows writes: our eight took 2.3 times the table.
  • Use EXPLAIN (ANALYZE, BUFFERS) to see what a query does, and pg_stat_user_indexes to find indexes nobody uses.
  • Build in production with CONCURRENTLY. Skip the index on small tables and queries matching most rows.
