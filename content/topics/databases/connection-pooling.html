Before your app can run a query, it needs a connection to the database: an open line that both sides have set up and agreed on. Setting one up takes far longer than a simple query does. And the database can only hold a limited number of them at once.

A connection pool is a small set of connections that are opened once and then kept. When a request needs the database, it borrows a connection, runs its queries, and gives it back. The next request uses the same one. Nobody pays the setup cost again.

The pool also acts as a cap. If it holds 10 connections, your app can never run more than 10 queries at the same moment. The eleventh request waits its turn. That is the point: it protects the database from being flooded.

The examples here use PostgreSQL, and were run on version 14. MySQL differs in one way that matters: it runs a thread per connection, not a whole process, so each connection is lighter. Pooling still helps there.

One-line version: open a few connections once, lend them out, take them back. It is faster for every request, and it stops your app from asking the database for more than it can give.

Without a pool, two things go wrong. One is slow. The other is an outage.

Every request pays the setup cost. A query that takes a fraction of a millisecond sits behind several milliseconds of connecting. Most of the time spent on the database is spent saying hello.

The database runs out of connections. PostgreSQL allows 100 connections by default. Here is how a normal day turns into an incident:

  1. The app opens a new connection for each request. Traffic is low, so only a few are open at once. Everything works.
  2. A sale starts. Now 300 requests are in flight together, and the app asks for 300 connections.
  3. PostgreSQL refuses everything past its limit with FATAL: sorry, too many clients already.
  4. Those requests fail. Users retry, which adds more requests.

The database was not slow and the queries were fine. The app asked for more connections than existed. With a pool, extra requests wait inside your app for a few milliseconds, and the database never sees more than the pool allows.

Run this in psql on a scratch database. Here it is called pool_demo. The results shown are from one run on a laptop with PostgreSQL 14.

-- A small table, and a login for our pretend app
CREATE TABLE accounts (
  id       INT PRIMARY KEY,
  owner    TEXT NOT NULL,
  balance  NUMERIC(12,2) NOT NULL
);

INSERT INTO accounts VALUES
  (1, 'Asha',  500.00),
  (2, 'Ravi',  120.50),
  (3, 'Meera', 980.00);

CREATE ROLE shop_app LOGIN CONNECTION LIMIT 3;
GRANT SELECT, UPDATE ON accounts TO shop_app;

SHOW max_connections;
--  max_connections
-- -----------------
--  100

The role shop_app may hold only 3 connections. That gives us a tiny limit we can hit safely, without filling up the whole server.

Each connection is a real process

Four rows: the three idle windows, and the one running this query (demo is the login I used). Now look at the machine itself, from a shell:

# List the server processes that belong to shop_app
$ ps -ax -o pid,command | grep 'postgres: shop_app'

The pid numbers match. Each connection is a whole operating-system process on the server. It stays alive while the connection is open, even when idle.

What running out looks like

Open a fourth window as shop_app. The connection fails, and the error that psql prints ends with this:

# A fourth connection for a role that is allowed three
$ psql -U shop_app pool_demo
... FATAL:  too many connections for role "shop_app"

It is refused at the door. When the whole server is full, the message is sorry, too many clients already, and it hits every app on that server.

What reusing a connection saves

PostgreSQL ships with a load tool called pgbench. We run one tiny query for 3 seconds, twice. The second run, with -C, opens a new connection for every query.

# one-query.sql holds: SELECT balance FROM accounts WHERE id = 1;

# One connection, kept open
$ pgbench -n -f one-query.sql -c 1 -T 3 pool_demo
latency average = 0.076 ms
tps = 13123.392807 (without initial connection time)

# A new connection for every query
$ pgbench -n -f one-query.sql -c 1 -T 3 -C pool_demo
latency average = 2.818 ms
average connection time = 2.333 ms
tps = 354.868692 (including reconnection times)

Only the lines that matter are shown. tps is queries finished per second, and latency average is the time for one.

  • With the connection kept open, one query took 0.076 ms.
  • With a new connection each time, it took 2.818 ms, and 2.333 ms of that was connecting. That is 2.333 ÷ 2.818 ≈ 83% of the time.
  • 13,123 ÷ 355 ≈ 37 times fewer queries per second, for the same query.

This is one run on one laptop, so your numbers will differ. It is also the kindest case: same machine, no encryption, no password. Over a network with both, connecting costs much more.

Here is what PostgreSQL does each time a client connects.

  1. The client opens a network connection to the postmaster. That is the main PostgreSQL process, the one listening on the port.
  2. The postmaster starts a brand-new process just for this client. It is called a backend. This is the process we saw in ps.
  3. If encryption is on, the backend and the client do a TLS handshake: several messages back and forth to agree on keys.
  4. The backend checks who the client is, usually with a password.
  5. The backend gets ready for work. It attaches to the database and sets up its own memory. As queries run, it fills its own caches with facts about tables and indexes.
  6. Now it can run queries. It stays alive, holding its memory, until the client disconnects. Then the process exits, and its warm caches are thrown away.

Steps 1 to 5 are the cost we measured. A pool does them once per connection, then skips them for every later request:

  1. At start-up, or on first use, the pool opens a few connections and keeps them.
  2. A request asks the pool for a connection. If one is free, it gets it at once.
  3. If none is free and the pool is below its maximum, the pool opens one more.
  4. If the pool is at its maximum, the request waits in a queue until a connection comes back or a timeout passes.
  5. The request runs its queries and gives the connection back. The backend process on the server never noticed that its user changed.

The diagram shows the two places a pool can live. Each app instance has its own small pool. When there are many instances, a separate program called a pooler sits in front of the database and shares a few real connections between them. PgBouncer is the common one for PostgreSQL.

Why not just raise the limit to 5,000? Each backend takes memory. And the server has a fixed number of CPU cores. Once more queries are running than the cores can serve, they take turns, and every one of them gets slower.

A pool inside the app

How it works: a library in your app holds the connections. In Node.js it is Pool from the pg package. In Java, HikariCP is a common one. Each running copy of your app has its own pool.

When to use it: always. This is the starting point for any server app.

Good: nothing extra to run. Requests wait inside your app, where you can time and log them.

Bad: the pools don’t know about each other. Ten instances with a pool of 20 can ask for 200 connections. Every new instance adds more.

An external pooler in session mode

How it works: apps connect to PgBouncer, not to PostgreSQL. A client gets one real connection for as long as it stays connected.

When to use it: for clients that connect and disconnect all the time, like scripts or old apps with no pool of their own.

Good: everything behaves as if you were talking to PostgreSQL directly.

Bad: a client that stays connected keeps its real connection, busy or not. So long-lived apps hold just as many as before.

An external pooler in transaction mode

How it works: a client gets a real connection only while a transaction is open. At COMMIT or ROLLBACK it goes straight back, and that client’s next transaction may land on a different one.

When to use it: when many app instances, or short-lived serverless functions, would together hold more connections than the database allows.

Good: a thousand client connections can share twenty real ones, because most clients are idle between transactions.

Bad: anything that lives on the connection past the end of a transaction breaks. That includes:

  • SET for a session setting. Use SET LOCAL inside a transaction.
  • LISTEN, which waits for notifications on one connection.
  • Advisory locks held for the session, and temporary tables that outlive a transaction.
  • Prepared statements made with SQL PREPARE. The kind that drivers create through the wire protocol works in PgBouncer 1.21 and later, when it is switched on.

An external pooler in statement mode

How it works: the real connection goes back after every single statement.

When to use it: rarely. Only when every query stands alone.

Good: the most sharing of all.

Bad: transactions with more than one statement are not allowed at all.

The usual large setup is the first and third together: a small pool in each app instance, pointed at a pooler in transaction mode.

Assumptions (made up for this example, not measurements):

  • One PostgreSQL server with 8 CPU cores and max_connections = 100.
  • 12 app instances. Each has a pool with a maximum of 20.
  • 1,000 requests a second in total. Each request runs 3 queries of 5 ms each.
  • Each backend process uses about 10 MB of memory of its own.

How many connections does the work need?

  • Query time per second: 1,000 requests × 3 queries × 5 ms = 15,000 ms.
  • One connection can do 1,000 ms of work per second. So 15,000 ÷ 1,000 = 15 connections busy on average.

How many can the pools ask for?

  • 12 instances × 20 = 240.
  • PostgreSQL keeps 3 of its 100 for superusers, so apps get 97.
  • 240 is far more than 97. On a quiet day nobody notices, because a pool only opens what it needs. On a busy day the pools grow, and instances start to get “too many clients”.

The right size

  • Keep 7 back for migrations, monitoring and a person with psql: 97 − 7 = 90 for the app.
  • 90 ÷ 12 instances = 7.5, so a pool of 7 each. In total 12 × 7 = 84.
  • Each instance needs 15 ÷ 12 = 1.25 connections on average. So 7 leaves room for bursts.
  • Memory for backends: 240 × 10 MB = 2.4 GB before, 84 × 10 MB = 840 MB after.

Would a bigger limit help? Not here. A common starting rule is twice the cores plus one, so 8 × 2 + 1 = 17 queries at once is about what this server does well. Our work needs 15. More connections would not finish more queries. They would take turns on the same cores.

When the instances multiply

Say the team moves to 40 small instances for the same traffic.

  • 40 × 7 = 280. That is over 90 again.
  • Shrinking to fit gives 90 ÷ 40 = 2 each. Then two slow queries block a whole instance.
  • With PgBouncer in transaction mode: 280 client connections in, 20 real ones out.
  • Is 20 enough? A transaction is 15 ms, so one real connection serves 1,000 ÷ 15 ≈ 66 requests a second. 20 × 66 = 1,320 requests a second, above our 1,000.

One slow call inside the borrow

A handler borrows a connection, then calls a payment API that takes 300 ms, then runs its queries.

  • It now holds the connection for 300 + 15 = 315 ms, not 15 ms.
  • A pool of 7 serves 7 ÷ 0.315 ≈ 22 requests a second. Before, it was 7 ÷ 0.015 ≈ 466.
  • Each instance gets 1,000 ÷ 12 ≈ 83 requests a second. So requests queue up and time out, while the database sits nearly idle.

See what the connections are doing

Keep the three shop_app windows from the example open. In one of them, start a transaction and don’t finish it:

-- In one shop_app window: a transaction left open
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

Then, in your own window:

-- Count connections by what they are doing
SELECT state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND datname = 'pool_demo'
GROUP BY state
ORDER BY count(*) DESC;

--         state        | count
-- ---------------------+-------
--  idle                |     2
--  active              |     1
--  idle in transaction |     1

How to read it:

  • idle: open and waiting for work. Normal for pooled connections.
  • active: running a query right now. If this stays close to your pool total, the pool is too small or the queries are too slow.
  • idle in transaction: a BEGIN was sent and never finished. The connection does nothing, but it can’t be lent to anyone else, and it still holds its locks. If these stay around, the app has a bug.

Find the stuck one, and end it

-- Transactions left open, oldest first
SELECT pid,
       date_trunc('second', now() - xact_start) AS open_for,
       left(query, 40) AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

--   pid  | open_for |                last_query
-- -------+----------+------------------------------------------
--  43506 | 00:00:40 | UPDATE accounts SET balance = balance -

-- Close that connection. Its open transaction is rolled back.
SELECT pg_terminate_backend(43506);

open_for is how long the transaction has been open. last_query is the last thing it ran, which tells you which code to look at. While it sat there, any other update to that row had to wait. After the terminate, Asha’s balance is 500.00 again, because the update was never committed.

Let the database clean up after the app

-- End any transaction that sits idle for more than 30 seconds
ALTER ROLE shop_app SET idle_in_transaction_session_timeout = '30s';

-- Stop any single query that runs for more than 5 seconds
ALTER ROLE shop_app SET statement_timeout = '5s';

New connections for that role pick these up. A connection that breaks the first rule is closed with FATAL: terminating connection due to idle-in-transaction timeout. A query that breaks the second gets ERROR: canceling statement due to statement timeout, and the connection stays usable.

The pool in app code

// db.provider.ts
import { Pool } from 'pg';

export const pool = new Pool({
  host: process.env.DB_HOST,
  database: 'shop',
  max: 7,                          // never more than 7 connections
  idleTimeoutMillis: 30_000,       // close one left unused for 30 s
  connectionTimeoutMillis: 2_000,  // wait at most 2 s for a free one
});
// transfers.service.ts
async transfer(from: number, to: number, amount: number) {
  const client = await this.pool.connect();    // borrow
  try {
    await client.query('BEGIN');
    await client.query(
      'UPDATE accounts SET balance = balance - $1 WHERE id = $2',
      [amount, from],
    );
    await client.query(
      'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
      [amount, to],
    );
    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();                           // always give it back
  }
}

The release() is in finally, so the connection goes back even when a query throws. For a single query, pool.query(...) borrows and returns by itself. To watch the pool, log pool.waitingCount. Above zero for long means requests are queuing.

PgBouncer

; pgbouncer.ini (login settings left out)
[databases]
shop = host=10.0.0.5 port=5432 dbname=shop

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
  • max_client_conn: how many app connections PgBouncer accepts.
  • default_pool_size: how many real connections it opens, for each pair of database and user.

The app then connects to port 6432 and changes nothing else. To check on it, run SHOW POOLS; in its admin console. Read cl_waiting (clients waiting for a real connection), sv_active and sv_idle (real connections in use and free), and maxwait (seconds the oldest waiting client has waited). If cl_waiting and maxwait stay above zero, the real pool is too small or transactions are too long.

  • Small pool vs big pool. A small pool keeps the database fast and makes requests wait in your app. A big pool lets every request in at once, and then they all slow each other down inside the database.
  • Waiting vs failing fast. A long wait for a free connection hides short bursts. It also lets requests pile up until everything times out together. A short wait fails some requests early and keeps the rest healthy.
  • App pool vs external pooler. The app pool is free and simple, but each instance only knows about itself. A pooler gives one shared cap for all instances. It is also one more program to run, one more network hop, and one more thing that can fail.
  • Transaction mode vs session mode. Transaction mode shares connections far better. It takes away session features, and bugs from that show up as odd behaviour, not clear errors.

Use a pool inside the app when

  • The app is a long-running server that handles many requests. That is nearly every backend.
  • You see connection setup in your traces, or “too many clients” in your logs.

Add an external pooler when

  • Instances × pool size is getting close to max_connections.
  • The number of instances goes up and down by itself with traffic.
  • The code runs as short-lived serverless functions, where each copy would open its own connection.
  • Many different apps share one database server.

You don’t need it when

  • It is a one-off script or a nightly job. One connection, opened once and closed at the end, is fine.
  • You have a few instances and the sum fits easily. Three instances with a pool of 10 against a limit of 100 need no PgBouncer. Don’t add a moving part to fix a problem you don’t have.
  • The real problem is slow queries. A pool shares connections. It does not make a 2-second query faster.
  • Forgetting to multiply by instances. A pool of 20 looks small until there are 12 copies of the app. Fix: work out instances × pool size, and keep it under the limit with some to spare.
  • Making the pool bigger when things are slow. If the database is already busy, more connections add more queries fighting for the same cores. Fix: find the slow queries first. Grow the pool only when the database has room and requests are still waiting.
  • Not giving the connection back. One code path that throws before release() loses a connection for good. After a few hours the pool is empty and every request times out. Fix: release in finally, every time.
  • Holding a connection while doing something else. Calling another service in the middle of a transaction keeps a connection busy for nothing, as the numbers showed. Fix: do the slow work first, then borrow.
  • Creating a pool per request. That is the same as having no pool. Fix: one pool for the whole app, made at start-up.
  • No timeout on waiting. If requests wait for ever, a full pool looks like a frozen app. Fix: set a wait limit of a second or two, and return a clear error.
  • Leaving transactions open. A BEGIN with no COMMIT holds a connection and its locks. Fix: set idle_in_transaction_session_timeout, and treat every hit as a bug.
  • Using session features through transaction mode. A SET on one query quietly applies to some other client’s connection later. Fix: use SET LOCAL inside the transaction, or keep a direct connection for the code that needs session features.

Common questions

  • What is a connection pool, and why use one? A set of open database connections that requests borrow and return. Opening a connection costs far more than a small query, and the database has a hard limit on connections. A pool removes the setup cost and caps how many the app can use.
  • How do you size it? From two sides. From the database: the connection limit, minus some kept back, divided by the number of instances. From the work: requests per second × the time each holds a connection gives the number busy on average. If the first is smaller than the second, add a pooler or cut the hold time.
  • What happens when the pool is empty? The request waits in a queue. If a connection comes back in time, it carries on. If the wait limit passes first, it gets an error.
  • Session pooling or transaction pooling? Session mode holds a real connection for as long as the client is connected. Transaction mode holds it for one transaction, so many more clients can share. The price is losing features that live on the connection.

Follow-ups to expect

  • Why can a bigger pool make things slower? More queries running than there are cores, all taking turns.
  • How would you find a connection leak? Watch the waiting count in the pool, and look for old idle in transaction rows in pg_stat_activity.
  • What about serverless functions? Each copy opens its own connection, so put a pooler in transaction mode in front.

How it fits a bigger design

In a design diagram, the pool is the arrow between your service and the database. Each time you add app instances, check instances × pool size against the database limit. With sharding, each instance keeps a pool per shard, so the sum multiplies again. The same idea shows up outside databases: the proxies in the “Load Balancer” topic keep connections to the backends open and reuse them.

  • A connection pool keeps a few database connections open and lends them to requests, so no request pays the setup cost.
  • In PostgreSQL every connection is its own server process, and the server allows 100 by default. Ask for more and the connection is refused.
  • The pool is also a cap. When it is empty, requests wait in the app, up to a time limit, and the database is not flooded.
  • Size it from the database side: the limit, minus some kept back, divided by the number of instances. Small pools usually finish more work than big ones.
  • When many instances add up to more than the limit, put PgBouncer in front. In transaction mode, a real connection is held only for one transaction.
  • Transaction mode breaks things that live on the connection: session SET, LISTEN, session locks.
  • Always give the connection back in finally, and never hold one while doing slow work that isn’t a query.
  • idle in transaction in pg_stat_activity means a transaction was left open. Set a timeout so the database ends those itself.
