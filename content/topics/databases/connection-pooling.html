Before your app can run a query it needs a connection: an open line both sides have set up and agreed on. Setting one up takes far longer than a simple query, and the database can only hold so many at once.

A connection pool is a small set of connections opened once and kept. A request borrows one, runs its queries, gives it back. Nobody pays the setup cost again.

The pool is also a cap:

  • Ten connections means your app never runs more than ten queries at once. The eleventh request waits.
  • That is the point. The database never sees more load than it agreed to.
  • Examples use PostgreSQL 14. MySQL uses a thread per connection, so each is lighter, but pooling still helps.

One-line version: open a few connections once, lend them out, take them back. Faster for every request, and your app can’t ask the database for more than it can give.

Without a pool two things go wrong. One is slow, the other is an outage.

Every request pays the setup cost. A query taking a fraction of a millisecond sits behind several milliseconds of connecting — most of the database time is spent saying hello.

The database runs out of connections. PostgreSQL allows 100 by default, and a normal day turns into an incident like this:

  1. The app opens a connection per request. Traffic is low, few are open, everything works.
  2. A sale starts. 300 requests are in flight, so the app asks for 300 connections.
  3. PostgreSQL refuses everything past the limit: FATAL: sorry, too many clients already.
  4. Those requests fail, users retry, and the retries add more requests.

The database wasn’t slow and the queries were fine. The app asked for connections that didn’t exist. With a pool, the extra requests wait a few milliseconds inside your app instead.

Run this in psql on a scratch database called pool_demo.

CREATE TABLE accounts (id INT PRIMARY KEY, balance NUMERIC(12,2) NOT NULL);
INSERT INTO accounts VALUES (1, 500.00), (2, 120.50);

CREATE ROLE shop_app LOGIN CONNECTION LIMIT 3;   -- a limit we can hit safely
GRANT SELECT, UPDATE ON accounts TO shop_app;
SHOW max_connections;   --  100

Open three psql -U shop_app pool_demo windows and leave them idle, then look at the server:

SELECT pid, usename, state FROM pg_stat_activity
WHERE backend_type = 'client backend' AND datname = 'pool_demo';
--   pid  | usename  | state
--  43505 | shop_app | idle      <- also a process: postgres: shop_app pool_demo
--  43506 | shop_app | idle
--  43507 | shop_app | idle

The pids match: each connection is a whole operating-system process on the server, alive and holding memory even while idle. A fourth window is refused at the door with FATAL: too many connections for role "shop_app".

Now measure what reuse saves, with pgbench running one tiny query for 3 seconds. The -C run opens a new connection per query.

$ pgbench -n -f one-query.sql -c 1 -T 3 pool_demo      # kept open
latency average = 0.076 ms     tps = 13123

$ pgbench -n -f one-query.sql -c 1 -T 3 -C pool_demo   # new each time
latency average = 2.818 ms  (2.333 ms of it connecting)   tps = 355

37 times fewer queries per second for the same query. One laptop run, and the kindest case: no network, no encryption.

What PostgreSQL does on every connect:

  1. The client opens a network connection to the postmaster, the process listening on the port.
  2. The postmaster forks a new process for this client alone: a backend.
  3. With encryption on, client and backend do a TLS handshake — several round trips.
  4. The backend checks who the client is, usually with a password.
  5. It attaches to the database and fills its own caches as queries run. On disconnect the process exits and those warm caches are thrown away.

A pool pays 1–4 once and skips them after. A request gets a free connection at once; if none is free the pool opens one more, up to its maximum; at the maximum the request queues until one returns or a timeout passes. The backend never notices its user changed.

The diagram shows both places a pool can live: inside each app instance, and in a separate pooler in front that shares real connections between them — PgBouncer, for PostgreSQL.

Why not set the limit to 5,000? Each backend takes memory, and cores are fixed. Once more queries run than the cores can serve, they take turns and all get slower.

The app pool is the starting point for every server app: nothing extra to run, requests wait where you can log them. Its weakness is that pools don’t know about each other — ten instances with a pool of 20 can ask for 200.

Session mode behaves exactly like PostgreSQL, but a client that stays connected keeps its real connection busy or not — so long-lived apps hold as many as before.

Transaction mode is where the sharing happens: a real connection is held only between BEGIN and COMMIT, so a thousand mostly-idle clients share twenty real ones. The price is that anything living on the connection past a transaction breaks — session SET (use SET LOCAL), LISTEN, session locks, temp tables, SQL PREPARE.

The usual large setup is both: a small pool per instance, pointed at a pooler in transaction mode.

Assumptions, made up: 8 cores, max_connections = 100, 12 app instances with a pool of 20 each, 1,000 requests/s running 3 queries of 5 ms, 10 MB per backend.

  • Work needed: 1,000 × 3 × 5 ms = 15,000 ms of query time a second. One connection gives 1,000 ms a second, so 15 busy on average.
  • What the pools can ask for: 12 × 20 = 240, against 97 available. Quiet days hide it; busy days bring “too many clients”.
  • Right size: keep 7 back for migrations and a human with psql → 90 ÷ 12 = a pool of 7 each. Backend memory drops from 2.4 GB to 840 MB.

Raising the limit wouldn’t help. A common rule is twice the cores plus one — 17 concurrent queries is about what this server does well, and the work needs 15. More would just take turns on the same cores.

At 40 instances, 40 × 7 = 280 breaks the limit again, and shrinking to 2 each means two slow queries block an instance. PgBouncer in transaction mode takes those 280 clients onto 20 real connections: a 15 ms transaction means each serves 66 requests/s, so 20 × 66 = 1,320/s, above our 1,000.

One slow call inside the borrow ruins it. Hold the connection through a 300 ms payment call and a pool of 7 serves 7 ÷ 0.315 ≈ 22 requests/s instead of 466 — while the database sits idle.

In one shop_app window, start a transaction and don’t finish it (BEGIN; UPDATE accounts SET balance = balance - 50 WHERE id = 1;). Then look at the states:

SELECT state, count(*) FROM pg_stat_activity
WHERE backend_type = 'client backend' AND datname = 'pool_demo'
GROUP BY state;
--         state        | count
--  idle                |     2
--  active              |     1
--  idle in transaction |     1
  • idle: open, waiting for work. Normal for a pooled connection.
  • active: running a query. Staying near the pool total means it is too small, or the queries are too slow.
  • idle in transaction: a BEGIN that was never finished. It does nothing, can’t be lent out, and still holds its locks. These are bugs.
-- find the stuck one (open_for = how long, last_query = which code), end it
SELECT pid, now() - xact_start AS open_for, left(query, 40) AS last_query
FROM pg_stat_activity WHERE state = 'idle in transaction';
SELECT pg_terminate_backend(43506);   -- its transaction is rolled back

-- let the database clean up after the app
ALTER ROLE shop_app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE shop_app SET statement_timeout = '5s';
// db.provider.ts
export const pool = new Pool({ max: 7,
  idleTimeoutMillis: 30_000,       // close one unused for 30 s
  connectionTimeoutMillis: 2_000 });  // wait at most 2 s for a free one

const client = await this.pool.connect();       // borrow
try { /* BEGIN, updates, COMMIT */ }
finally { client.release(); }                   // always give it back

Release in finally, so a throwing query still returns the connection, and log pool.waitingCount — above zero for long means requests are queuing. On PgBouncer, SHOW POOLS; tells you the same thing: cl_waiting and maxwait above zero mean the real pool is too small.

  • Small pool vs big pool. Small keeps the database fast and makes requests wait in your app. Big lets everyone in at once, and then they all slow each other down inside the database.
  • Waiting vs failing fast. A long wait hides short bursts, and lets requests pile up until everything times out together. A short wait sheds some early and keeps the rest healthy.
  • App pool vs pooler. The app pool is free and simple but only knows itself. A pooler gives one shared cap, at the cost of another program, another hop and another thing that fails.
  • Transaction mode vs session mode. Transaction mode shares far better and takes away session features — and those bugs show up as odd behaviour, not clear errors.
  • A pool in the app: always, for any long-running server. Certainly once you see connect time in your traces or “too many clients” in the logs.
  • Add a pooler when instances × pool size approaches max_connections, when instance count scales by itself, when the code runs as serverless functions, or when many apps share one server.

You don’t need it for a one-off script — one connection is fine. Three instances with a pool of 10 against a limit of 100 don’t need PgBouncer either. And if the real problem is slow queries, pooling won’t help: it shares connections, it doesn’t make a 2-second query faster.

  • Forgetting to multiply by instances. A pool of 20 looks small until there are 12 copies. Work out instances × pool size and keep it under the limit with room to spare.
  • Growing the pool when things are slow. On a busy database that just adds queries fighting for the same cores.
  • Not giving the connection back. One path that throws before release() loses a connection for good. Release in finally.
  • Holding a connection during slow non-database work. One 300 ms API call cuts throughput twentyfold. Do the slow work first, then borrow.
  • Creating a pool per request. That is having no pool. One pool, made at start-up.
  • No wait timeout. Requests waiting forever make a full pool look like a frozen app.
  • Leaving transactions open. BEGIN with no COMMIT holds a connection and its locks. Set idle_in_transaction_session_timeout and treat every hit as a bug.
  • Session features through transaction mode. A SET quietly applies to some other client’s connection later. Use SET LOCAL.

Common questions

  • What is a pool? Open connections that requests borrow and return. Connecting costs far more than a small query, and the database has a hard limit.
  • How do you size it? Database side: limit minus reserve, divided by instances. Work side: requests/s × hold time. If the first is smaller, add a pooler or cut the hold time.
  • When it’s empty? The request queues, then gets a connection or times out.
  • Session or transaction pooling? Session holds a connection for the whole client connection; transaction holds it per transaction, so many more clients share — at the price of connection-level features.

Follow-ups to expect

  • Why can a bigger pool be slower? (More queries than cores, all taking turns.)
  • How would you find a connection leak? (Pool waiting count, and old idle in transaction rows.)
  • What about serverless? (Each copy opens its own connection, so put a pooler in transaction mode in front.)

How it fits a bigger design

In a diagram, the pool is the arrow between your service and the database. Every time you add instances, check instances × pool size against the limit — and with sharding each instance keeps a pool per shard, so it multiplies again.

  • A pool keeps a few connections open and lends them out, so no request pays the setup cost.
  • In PostgreSQL each connection is its own server process, and the default limit is 100.
  • The pool is also a cap: when empty, requests wait in the app instead of flooding the database.
  • Size from the database side: limit, minus a reserve, divided by instances. Small pools usually finish more work than big ones.
  • Connecting cost about 2.3 ms against a 0.076 ms query in the measured example — 83% setup.
  • When instances add up past the limit, put PgBouncer in front in transaction mode.
  • Transaction mode breaks session SET, LISTEN and session locks.
  • Always release in finally, and never hold a connection during slow non-database work.
  • idle in transaction means a transaction was left open; set a timeout so the database ends it.
