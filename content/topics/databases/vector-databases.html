An embedding is a list of numbers standing for a piece of text, an image or a sound. A model produces it, and things that mean similar things get similar numbers. “Cancel my subscription” and “end my plan” land close together, with no word in common.

A vector database stores those lists and answers one question fast: which stored vectors are nearest to this one? That is similarity search, and it is the whole job.

You get it as its own product (Pinecone, Milvus, Qdrant, Weaviate) or as an add-on to a database you already run. Examples use PostgreSQL 16 with pgvector, so you can run every line.

One-line version: a vector database finds the rows closest in meaning, not the rows that match a word. It gets fast by returning probably the nearest rows instead of certainly the nearest ones.

Normal indexes answer “where is this value?”. A B-tree finds customer_id = 4242; a text index finds the word refund. Neither answers “what is close to this?”, because closeness isn't a value you can sort by in advance.

Say a help centre gets “how do I stop paying you”. The right article is “Cancel your subscription”. Word search finds nothing — not one word matches. Embeddings put both in nearly the same place, so it comes first.

The catch is cost. Nothing is sorted, so the honest answer means comparing the query with every stored vector — fine at 10,000 rows, hopeless at 10 million. Everything below exists to avoid that.

Four help articles. Real embeddings have hundreds of numbers; we use two so you can see them on a page.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE docs (
  id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title     TEXT NOT NULL,
  embedding vector(2) NOT NULL
);

INSERT INTO docs (title, embedding) VALUES
  ('Cancel your subscription', '[0.9, 0.1]'),
  ('Ending a plan early',      '[0.7, 0.4]'),
  ('Change your billing card', '[0.5, 0.6]'),
  ('Reset your password',      '[0.1, 0.9]');

The model turns that question into [0.85, 0.2]. <=> is cosine distance: 0 is the same direction, 1 is unrelated.

SELECT title, round((embedding <=> '[0.85,0.2]')::numeric, 4) AS distance
FROM docs
ORDER BY embedding <=> '[0.85,0.2]'
LIMIT 3;

          title           | distance
 -------------------------+----------
  Cancel your subscription |   0.0072
  Ending a plan early      |   0.0412
  Change your billing card |   0.2009

“Reset your password” sits at 0.6649 and never makes the top three. Put the four rows and the question on a grid and the ordering is just distance:

With no index, PostgreSQL reads every row, works out the distance and keeps the best three. A million rows means a million distance sums, on every query.

An index avoids that by giving up on being exact. This is approximate nearest neighbour search, ANN for short: rows that are almost always the nearest, in a fraction of the time. pgvector's default is HNSW, a layered graph where every vector links to the ones near it.

  1. Start at the single entry node in the top layer.
  2. Hop to whichever neighbour is nearer the query. Repeat until no neighbour is nearer.
  3. Drop one layer and do the same, now with more nodes and shorter hops.
  4. In layer 0, keep a shortlist of the best ef_search candidates found so far, then return the top LIMIT of them.

The top layers are a rough map that reaches the right neighbourhood in a few jumps; layer 0 does the careful part. Nothing guarantees the true nearest row was in the neighbourhood you landed in. That is the approximation.

Three ways to answer the query. You choose by how much wrongness you can take.

Exact (no index)

Compare the query with every row. Always right, and the only option that is. Fine up to a few tens of thousands of rows.

IVFFlat

Group the vectors into lists clusters once, each with a centre point. A query checks the centres, then searches only the nearest probes clusters.

Cheap to build and small on disk. The weak spot: a query on the edge between clusters misses neighbours that fell inside a cluster you didn't probe.

HNSW

The layered graph above. Better recall at the same speed, and it takes new rows as they arrive. It costs more to build and wants the whole graph in memory.

Exact search is a disk-speed problem that gets worse with every row. Both index types turn it into a small number of comparisons. The HNSW index itself will be bigger than the vectors, so plan for graph and data to sit in memory — once the hops become disk reads, the speed is gone.

Build an index

-- cosine distance, the usual choice for text embeddings
CREATE INDEX docs_embed_hnsw ON docs
  USING hnsw (embedding vector_cosine_ops);

-- IVFFlat: build only once the table has real data
CREATE INDEX docs_embed_ivf ON docs
  USING ivfflat (embedding vector_cosine_ops) WITH (lists = 1000);

The operator class has to match the operator you query with: vector_cosine_ops for <=>, vector_l2_ops for <->. Get it wrong and the index is simply never used.

Check that it is used

EXPLAIN ANALYZE
SELECT title FROM docs ORDER BY embedding <=> '[0.85,0.2]' LIMIT 3;

 Limit
   ->  Index Scan using docs_embed_hnsw on docs
         Order By: (embedding <=> '[0.85,0.2]'::vector)

Read the step name. Index Scan with an Order By: line means the index did the work. If you see Seq Scan and a Sort instead, it is reading everything: usually the wrong operator, or a LIMIT you forgot.

Trade recall for speed

SET hnsw.ef_search = 100;   -- default 40; bigger = better recall, slower
SET ivfflat.probes = 10;    -- default 1; bigger = better recall, slower

SELECT pg_size_pretty(pg_relation_size('docs_embed_hnsw'));

Both are session settings, so you can raise them for one query. To measure recall, run the query again with the index off (SET enable_indexscan = off;) and count how many of the exact top 10 the indexed query returned.

  • Recall vs speed. The only knob that matters. Raising ef_search or probes finds more of the true neighbours and costs time in direct proportion.
  • Build time vs query time. HNSW is slow to build and fast to query. IVFFlat is the other way round.
  • Memory vs disk. ANN indexes assume they are in memory. Once the graph spills to disk, random reads cancel most of the gain.
  • Meaning vs exactness. Embeddings find things no keyword matches, but can't promise a row containing a word, a price or a date. Keyword search still wins there.
  • One database vs a specialist one. pgvector keeps vectors next to your rows, so one query does filter plus search. A dedicated vector database handles billions and sharding, at the cost of keeping two stores in step.

Reach for it when

  • Users search in their own words and the right answer shares no words with the question.
  • You are feeding a language model: find the 5 most relevant chunks, put them in the prompt.
  • You want “more like this” — related articles, duplicate detection, image or song lookup.
  • The thing you search has no useful keywords at all, like a photo or an audio clip.

You don't need one when

  • Keyword search already works. Product codes, names and tags want an inverted index, not meaning.
  • The set is small. Under about 10,000 rows, exact search in a plain table is quick, always right and has no knobs.
  • The answer must be exactly right. Anything legal, financial or rules-based should not be answered by “probably the nearest”.
  • You can't re-embed. Every vector depends on one model. No plan for re-running it is no plan at all.
  • Mixing models. Vectors from two models are not comparable, even at the same size. Changing the model means re-embedding every row.
  • The wrong operator class. An index built with vector_l2_ops does nothing for a <=> query. The plan silently falls back to a full scan.
  • Building IVFFlat on an empty table. The clusters are worked out from the rows present at build time. Build it on an empty table and every later row lands badly; rebuild after a big load.
  • Filtering hard, then wondering where the results went. WHERE lang = 'de' on top of an ANN search throws away rows the index already picked: you ask for 10 and get 2. Raise ef_search, or filter first and search exactly.
  • Never measuring recall. Approximate search never errors. It quietly returns slightly worse answers, and nobody notices for months.

Common questions

  • Why can't a B-tree do this? It sorts by value in one dimension. “Near” in 768 dimensions is not a position in a sorted list, so there is nothing to walk down.
  • What does “approximate” cost you? Recall. The index can miss a true neighbour it never visited. ef_search and probes buy it back.
  • HNSW or IVFFlat? HNSW for rows arriving all the time. IVFFlat when the index must build fast or stay small, and data is loaded in batches.
  • How do you combine it with filters? Small filtered set: filter first, then search exactly. Large one: raise ef_search, then filter what comes back.

How it fits a bigger design

Vector search is usually one half of a search service: keyword search handles exact words, vector search handles meaning, and the lists are merged before ranking. Writes need a second path — when a document changes, something has to re-embed it. That is a queue and a worker, not a database feature.

  • An embedding is a list of numbers standing for text, an image or a sound; similar meanings give similar numbers. A vector database answers one question: which stored vectors are nearest to this one.
  • Nothing is sorted, so an exact answer means comparing the query with every row — about 1.5 seconds for a million 768-number vectors. ANN indexes trade that exactness for speed.
  • HNSW is a layered graph. You enter at the top, hop towards the query, and drop layers until the careful search in layer 0.
  • IVFFlat groups vectors into clusters and searches only the nearest few. Cheap to build, weaker at cluster edges.
  • ef_search and probes are the recall knobs: higher finds more true neighbours and takes longer.
  • The index operator class must match the query operator, or the index is never used. Vectors are tied to one model, so changing the model means re-embedding everything.
  • Keyword search and vector search solve different problems; real systems usually run both and merge the results.
